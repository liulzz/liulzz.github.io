长期记忆与上下文压缩
让上下文保持有界

长时间运行的任务会遇到一个硬约束：上下文窗口是有限的。 本章讲解 AgentScope Java 的四个正交策略，它们共同保证智能体可以持续工作数小时而不失控。

一个具体的约束

假设一个任务需要执行 200 轮推理，每轮的工具结果平均 3000 字符。上下文将达到 60 万字符，而主流模型的上下文窗口通常是 128K token 量级。因此直接的结果是：任务进行到一半就会超出窗口，然后失败。

一个直观的错误做法是「定期删除早期消息」。但这样做会丢失关键信息：智能体可能忘记任务目标，或者重复已经做过的工作。AgentScope Java 提供了四个策略解决这个问题，它们的分工是：有的负责让上下文变浅，有的负责让它变窄。

场景

本章场景

为知识助手增加长期记忆能力，并让它的上下文在长时间会话中保持有界：

  • 它能记住「张三是支付模块负责人」这类长期有用的事实
  • 会话超过 30 条消息时，自动压缩早期历史，保留任务目标与关键结论
  • 工具返回超大结果时落盘，上下文里只留指针

9.1先讲理论：四个正交策略

「正交」的意思是这四个策略解决不同维度的问题，互不干扰，可以独立启用或关闭。四项默认全部关闭，需要你按场景显式开启。

策略解决的问题触发时机对应中间件
对话摘要上下文太深每次模型推理前CompactionMiddleware
大结果落盘上下文太宽工具执行后ToolResultEvictionMiddleware
溢出兜底模型真的返回超长错误call() 抛错时HarnessAgent.recoverFromOverflow
参数截断工具参数过大摘要前的轻量预处理CompactionConfig.TruncateArgsConfig

用两个维度来理解这个分工：

上下文体积的两个方向 深度（有多少轮对话） ═══════════════════ ↑ │ 策略 1：对话摘要 ← CompactionConfig │ 把早期轮次替换为结构化摘要 │ └────────────────────────────→ 宽度（单条内容多长） 策略 2：大结果落盘 ← ToolResultEvictionConfig 把超大内容移到磁盘 横切两个方向的兜底： 策略 3：溢出恢复 ← 真实超长时触发 策略 4：参数截断 ← 摘要前先瘦身

策略一：对话摘要

当消息数量达到阈值时，框架把较早的消息替换为一段结构化摘要，并保留最近若干条原始消息。

启用对话摘要java
HarnessAgent agent = HarnessAgent.builder()
        .name("kb-assistant")
        .model(model)
        .workspace(workspace)
        .compaction(CompactionConfig.builder()
                .triggerMessages(30)     // 达到 30 条消息时触发
                .keepMessages(10)        // 压缩后保留最近 10 条原文
                .build())
        .build();

完整的配置项与缺省值：

字段缺省值说明
triggerMessages50按消息条数触发，0 表示关闭
triggerTokens0按估算 token 触发；0 表示动态（模型上下文窗口减保留量）
keepMessages20保留尾部消息数
keepTokens-1-1 表示动态；0 表示使用 keepMessages；大于 0 表示固定 token 预算（覆盖 keepMessages）
flushBeforeCompacttrue压缩前先提取事实到当日日志
offloadBeforeCompacttrue压缩前先把原始消息追加到永不压缩的日志
summaryPromptDEFAULT_SUMMARY_PROMPT摘要提示词，必须包含 {messages} 占位符
modelnull专用压缩模型，缺省使用 Agent 主模型

缺省摘要提示词的结构包含四个部分，这个结构本身值得注意：

默认摘要结构text
SESSION INTENT   这次会话的意图是什么
SUMMARY          发生了什么
ARTIFACTS        产生了哪些产物（文件、记录、结论）
NEXT STEPS       后续要做什么
为什么摘要结构要这样设计

「会话意图」与「后续步骤」是压缩中最容易丢失也最重要的信息。如果只写「摘要」，模型产出的往往是流水账；而明确要求保留意图与下一步，压缩后的智能体才能真正继续工作，而不是从头再来。这也是官方把它作为缺省结构的原因。

策略二：大结果落盘

工具可能返回极长的内容，例如一次读取了整个代码仓库、一次查询返回了上万行日志。这类内容占据大量 token，但模型通常只需要其中一小部分。

启用大结果落盘java
HarnessAgent.builder()
        .toolResultEviction(ToolResultEvictionConfig.defaults())
        .build();

缺省行为：

  • 超过 80K 字符的工具结果被写入磁盘
  • 上下文中只保留约 2K 头部 + 2K 尾部预览，以及一行指向完整内容的 read_file 指令
  • read_file 读取的内容默认不被排除，因为模型读取文件通常是刻意行为
工具是否默认排除落盘原因
read_file排除模型主动读取文件，通常是刻意行为，落盘会造成额外往返
write_file / edit_file排除同上
list_files排除同上
memory_*排除记忆内容需要精确，不应被截断
session_search排除同上
grep_files / glob_files不排除搜索结果在长仓库中可能极长
Shell execute不排除官方明确说明 shell 输出故意不排除，因为构建输出与测试输出经常极长

策略三与四

策略三（溢出兜底）是一张安全网：当模型真的返回 context_length_exceeded 错误、call() 抛错时，框架自动执行一次恢复。它不依赖任何阈值判断，因此是最后一道防线。

策略四（参数截断）是一次轻量预处理：在生成摘要之前，先把过长的工具调用参数截断，减少送入摘要模型的内容量。

启用参数截断java
CompactionConfig.builder()
        .triggerMessages(80)
        .truncateArgs(CompactionConfig.TruncateArgsConfig.builder()
                .maxArgLength(2000)
                .truncationText("... [已截断] ...")
                .build())
        .build();

压缩不会触碰什么

这一点非常重要：压缩只作用于对话历史，以下内容不会被压缩。

不被压缩的内容存储位置原因
Plan Mode 上下文AgentState.getPlanModeContext()计划状态是当前执行依据，丢失会破坏模式
子智能体后台任务workspace/agents/<parentId>/tasks/<sessionId>.jsontask_id、状态、结果都是长期数据
任务清单AgentState.getTasksContext()todo_write 的内容代表进度
权限规则AgentState.getPermissionContext()安全策略不能因为压缩而失效

9.2两层长期记忆

上下文压缩解决的是「单次会话内」的问题，而长期记忆解决的是「跨会话」的问题：智能体需要记住三天前、上周、上个月学到的关于用户与团队的事实。

AgentScope 的记忆分两层，都以文件形式保存在工作区：

记忆文件text
workspace/
├── MEMORY.md                  ← 整理后的长期记忆，每轮注入系统提示词
└── memory/
    └── 2026-07-10.md          ← 按日期追加的事实日志（不做去重）
层文件写入方式读取方式
当日事实日志memory/YYYY-MM-DD.md压缩前由 MemoryFlushMiddleware 从对话前缀提取新事实并追加不直接注入；供后台合并任务使用
整理后的记忆MEMORY.md后台任务合并、去重并全量重写每轮注入系统提示词，受 maxContextTokens 限制

写入与读取流程

提取

压缩之前，MemoryFlushMiddleware 从对话前缀中提取新出现的事实。

追加

事实被追加写入 memory/YYYY-MM-DD.md。这个文件只追加，不去重。

合并

受节流的后台任务定期把 memory/ 下的日志合并并去重。

重写

后台任务重写整个 MEMORY.md，把 token 数控制在上限内。

注入

每轮推理，MEMORY.md 被注入系统提示词。

读取有两条路径：框架自身通过两层读取机制加载 MEMORY.md；此外 Agent 还可以调用 memory_search 与 memory_get 查询较早的记忆条目，因为较早的事实可能已被合并掉，不再出现在 MEMORY.md 中。

记忆查询工具text
memory_search query="..."                  最多返回 30 条命中
memory_get path="..." startLine=10 endLine=40  读取指定记忆文件的片段

注入预算

MEMORY.md 在注入前会做 token 估算，超出预算时按字符数截断。截断后会追加一条提示，引导模型使用 memory_search 查找旧条目。需要显式设置预算时使用 maxContextTokens：

配置记忆预算java
HarnessAgent agent = HarnessAgent.builder()
        .name("kb-assistant")
        .model(model)
        .workspace(workspace)
        // MEMORY.md 的注入预算（注意：不是整个系统提示词的预算）
        .maxContextTokens(8000)
        .build();

9.3MemoryConfig 完整配置

记忆行为通过 .memory(MemoryConfig) 配置。需要说明的是，记忆处理涉及三次独立的 LLM 调用，你可以为其中任意一次指定更轻量的模型以降低成本。

完整记忆配置java
HarnessAgent.builder()
        .model("openai:o3")                   // 主推理模型
        .memory(MemoryConfig.builder()
                // 为记忆操作单独指定更轻量的模型
                .model("openai:gpt-4.1-mini")
                .build())
        .compaction(CompactionConfig.builder()
                .model("openai:gpt-4.1-mini")  // 压缩也用轻量模型
                .build())
        .build();
字段缺省值说明
modelnull提取与合并使用的模型，接受 Model 实例或 "provider:model" 字符串
flushPromptnull提取提示词，缺省用 MemoryFlushManager.DEFAULT_FLUSH_PROMPT
consolidationPromptnull合并提示词模板，必须包含两个 %d
consolidationMaxTokens4_000MEMORY.md 的 token 上限
consolidationMinGap30 分钟后台维护的最小间隔
dailyFileRetentionDays90当日日志归档到 memory/archive/ 的天数
sessionRetentionDays180清理 *.log.jsonl 的天数
flushTriggeralways()ALWAYS / NEVER / throttled(Duration)

控制提取时机

提取频率java
// 默认：每次压缩前提取
.memory(MemoryConfig.builder()
        .flushTrigger(MemoryConfig.FlushTrigger.always())
        .build())

// 限制为每 10 分钟最多一次，减少 LLM 调用
.memory(MemoryConfig.builder()
        .flushTrigger(MemoryConfig.FlushTrigger.throttled(Duration.ofMinutes(10)))
        .build())

// 完全关闭自动提取
.memory(MemoryConfig.builder()
        .flushTrigger(MemoryConfig.FlushTrigger.never())
        .build());

这个参数直接影响成本。always() 意味着每次压缩都额外发起一次 LLM 调用，在高频会话中开销可观。多数场景下 throttled(...) 是更合理的选择。

定制提取与合并提示词

两个提示词都可以追加或替换，用于贴合具体业务：

定制提示词java
.memory(MemoryConfig.builder()
        .flushPrompt(MemoryFlushManager.DEFAULT_FLUSH_PROMPT + """

                """

                附加的项目规则：
                - 绝不记录客户个人信息（姓名、邮箱、电话）
                - 项目内部术语一律使用英文
                """

                """)
        .build())
定制合并提示词java
.memory(MemoryConfig.builder()
        .consolidationPrompt(jt(24,
                        "你正在把每日记忆账本合并为 MEMORY.md。",
                        "控制在 %d 个 token（约 %d 个字符）之内。",
                        "以 markdown 格式输出完整文件内容。",
                        "...",
                        "这里写你自己的规则 ..."))
        .build())
合并提示词必须恰好包含两个 %d

第一个是 max-tokens，第二个是 max-chars。如果数量不对，构建器会在构造期直接拒绝，而不是等到运行时才失败。这是刻意的设计——避免因占位符错误而产生错误的 token 预算。

保留期与维护

保留策略java
.memory(MemoryConfig.builder()
        .consolidationMinGap(Duration.ofHours(2))  // 首次可运行，之后至少间隔 2 小时
        .dailyFileRetentionDays(30)                // 30 天后归档当日日志
        .sessionRetentionDays(60)                  // 60 天后清理会话日志
        .consolidationMaxTokens(8_000)             // 提高 MEMORY.md 上限
        .build());

9.4会话日志查询工具

压缩会减少上下文中的消息数量，但完整对话仍然保留在永不压缩的日志里。框架提供三个工具用于查询历史：

会话查询工具text
session_list   agentId="..."                    列出该 Agent 的会话
session_history agentId="..." sessionId="..." lastN=20
                读取指定会话的最后 N 条记录
session_search query="..." agentId="..."       在会话日志中检索

数据来源是 workspace/agents/<agentId>/sessions/<sessionId>.log.jsonl，这个文件只追加、永不压缩。

9.5动手：配置完整的上下文治理

ContextGovernance.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.memory.compaction.CompactionConfig;
import io.agentscope.core.memory.compaction.ToolResultEvictionConfig;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.memory.MemoryConfig;

import java.nio.file.Paths;
import java.time.Duration;

public class ContextGovernance {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get(".agentscope/workspace"))

                // 策略一：对话摘要
                .compaction(CompactionConfig.builder()
                        // 按条数与 token 双阈值触发，取先到者
                        .triggerMessages(30)
                        .triggerTokens(60_000)
                        // 压缩后保留最近 10 条原文
                        .keepMessages(10)
                        // 摘要前的参数截断，减少送入摘要模型的内容
                        .truncateArgs(CompactionConfig.TruncateArgsConfig.builder()
                                .maxArgLength(2000)
                                .truncationText("... [已截断] ...")
                                .build())
                        .build())

                // 策略二：大结果落盘
                .toolResultEviction(ToolResultEvictionConfig.defaults())

                // 长期记忆
                .memory(MemoryConfig.builder()
                        // 限制提取频率，每 10 分钟最多一次
                        .flushTrigger(MemoryConfig.FlushTrigger.throttled(
                                Duration.ofMinutes(10)))
                        .consolidationMaxTokens(4_000)
                        .dailyFileRetentionDays(60)
                        .sessionRetentionDays(90)
                        .build())

                // MEMORY.md 的注入预算
                .maxContextTokens(8000)

                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan").sessionId("governance-001").build();

        // 一次正常调用
        Msg reply = agent.call(new UserMessage(
                "支付服务的读超时是多少？"), ctx).block();
        System.out.println(reply.getTextContent());

        // 查看上下文状态
        var state = agent.getAgentState("zhangsan", "governance-001");
        System.out.println("当前上下文消息数： " + state.getContext().size());
    }
}

InspectCompaction.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;
import java.nio.file.Paths;

public class InspectCompaction {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get(".agentscope/workspace"))
                .compaction(CompactionConfig.builder()
                        // 为了便于观察，把阈值设得很低
                        .triggerMessages(8)
                        .keepMessages(3)
                        .build())
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan").sessionId("compact-test").build();

        // 连续 10 轮，必然触发压缩
        for (int i = 1; i <= 10; i++) {
            final int n = i;
            agent.streamEvents(new UserMessage("第 " + n + " 个问题：介绍一下模块 " + n))
                    .doOnNext((AgentEvent e) -> {
                        if (e.getType() == io.agentscope.core.event.AgentEventType.AGENT_END) {
                            var state = agent.getAgentState("zhangsan", "compact-test");
                            System.out.println("第 " + n + " 轮后，"
                                    + "上下文消息数 = " + state.getContext().size());
                        }
                    })
                    .blockLast();
        }

        System.out.println("\n上下文被控制在 8 条以内，压缩生效。");
        System.out.println("但完整对话仍在 .log.jsonl 中：");
        System.out.println("  workspace/agents/kb-assistant/sessions/compact-test.log.jsonl");
    }
}

运行后你会观察到上下文消息数在达到阈值后不再增长，但会话日志文件持续增长。这就是压缩与持久化日志的分工。

观察记忆文件的变化

InspectMemory.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.memory.MemoryConfig;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.Paths;
import java.time.Duration;

public class InspectMemory {

    public static void main(String[] args) throws Exception {
        Path ws = Paths.get(".agentscope/workspace");

        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(ws)
                .compaction(CompactionConfig.builder()
                        .triggerMessages(6)
                        .keepMessages(3)
                        .build())
                // 用较短间隔，便于在测试中观察
                .memory(MemoryConfig.builder()
                        .flushTrigger(MemoryConfig.FlushTrigger.throttled(
                                Duration.ofSeconds(5)))
                        .consolidationMinGap(Duration.ofSeconds(5))
                        .build())
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan").sessionId("memory-test").build();

        // 第一轮：明确给出长期事实
        agent.call(new UserMessage(
                "记住这些长期信息：我叫张三，是支付模块负责人，"
                + "我的代码风格偏好使用中文注释，评审时喜欢先看测试。"), ctx).block();

        System.out.println("=== 压缩触发前的工作区文件 ===");
        listMemoryFiles(ws);

        // 继续几轮，触发压缩与记忆提取
        for (int i = 0; i < 6; i++) {
            agent.call(new UserMessage("支付模块的接口有哪些？"), ctx).block();
        }

        System.out.println("\n=== 压缩与记忆提取后的工作区文件 ===");
        listMemoryFiles(ws);

        // 验证记忆生效：新会话中询问
        RuntimeContext fresh = RuntimeContext.builder()
                .userId("zhangsan").sessionId("memory-verify").build();
        var reply = agent.call(new UserMessage("你还记得我叫什么吗？"), fresh).block();
        System.out.println("\n新会话中的回答： " + reply.getTextContent());
    }

    private static void listMemoryFiles(Path ws) throws Exception {
        Path memoryDir = ws.resolve("memory");
        if (Files.exists(memoryDir)) {
            try (var s = Files.list(memoryDir)) {
                s.forEach(p -> System.out.println("  memory/" + p.getFileName()));
            }
        }
        Path memMd = ws.resolve("MEMORY.md");
        if (Files.exists(memMd)) {
            System.out.println("  MEMORY.md 内容：");
            System.out.println("  " + Files.readString(memMd).indent(4));
        } else {
            System.out.println("  MEMORY.md 尚未生成（后台合并任务有节流延迟）");
        }
    }
}

这个示例的关键点是：即使这是一个全新的 sessionId，模型依然能回答「你还记得我叫什么」，因为长期记忆是按 userId 隔离并注入提示词的，与具体会话无关。

9.6成本控制

记忆与压缩功能都会额外调用 LLM，因此会显著影响成本。以下是可以立即采取的措施。

措施做法效果
限制提取频率flushTrigger(throttled(Duration.ofMinutes(10)))把每次压缩都触发改为按节流触发
指定轻量模型memory(...).model(...) 与 compaction(...).model(...)记忆与摘要用小模型，主推理用大模型
调高触发阈值增大 triggerMessages压缩次数减少，但单次压缩成本上升
控制记忆上限consolidationMaxTokens降低 MEMORY.md 大小，减少每轮注入成本
设置注入预算maxContextTokens限制 MEMORY.md 注入量
清理历史dailyFileRetentionDays、sessionRetentionDays减少磁盘占用
节流不是立即生效

记忆提取与后台合并任务都是节流执行的，因此在配置之后不会立刻看到文件变化。在测试环境中可以设置较短间隔，但在生产环境中应当设置合理的间隔，否则后台任务会成为持续的负载来源。

9.7本章小结

  • 四个正交策略分别解决不同维度：摘要管深度，落盘管宽度，溢出恢复兜底，参数截断预处理。默认全部关闭。
  • 压缩只作用于对话历史，不触碰计划模式上下文、后台任务、任务清单与权限规则。
  • 默认摘要结构包含会话意图、摘要、产物、后续步骤四部分，这种结构能有效避免压缩后丢失任务目标。
  • 长期记忆分两层：memory/YYYY-MM-DD.md 只追加，MEMORY.md 全量重写并每轮注入。
  • 记忆涉及三次独立 LLM 调用（提取、合并、摘要），可以分别为它们指定更轻量的模型。
  • 合并提示词必须恰好包含两个 %d，数量不对会在构建期被拒绝。
  • 成本控制的首选手段是限制提取频率与指定轻量模型。
练习
  1. 按 InspectCompaction 的思路，把压缩阈值调到很低，观察上下文消息数与 GenerateReason 的变化。
  2. 检查压缩后 .log.jsonl 文件是否仍然保留了完整对话，验证「上下文有界、记录完整」这一分工。
  3. 运行 InspectMemory，观察 memory/ 目录与 MEMORY.md 的生成过程，并验证新会话中记忆是否生效。
  4. 自定义 flushPrompt，加入一条规则：绝不记录客户个人信息。测试该规则是否生效。
  5. 尝试把 consolidationPrompt 中的 %d 删掉一个，观察构建期报出的错误信息，解释这个设计的作用。
  6. 为记忆与压缩配置轻量模型，并对比配置前后的 token 消耗。
  7. 设计一个方案：让知识助手在压缩后仍然记住「用户偏好中文回答」这条信息。说明你会用哪个机制、配置在哪里。
