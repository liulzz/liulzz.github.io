会话与状态管理
让智能体在服务中保持连续

前三章的智能体都是「一次调用、一个结果」。本章把它改造成一个多用户 Web 服务： 区分租户、隔离会话、把业务对象注入工具方法，并让状态可以跨进程恢复。 核心是三个对象的分工：RuntimeContext、AgentState、AgentStateStore。

从脚本到服务

到目前为止，知识助手都是命令行程序：启动一次、提问几次、退出。一旦把它放进 Web 服务，问题立刻出现。第一个问题是身份：HTTP 请求没有「我是谁」，工具却需要知道当前用户是谁、属于哪个租户。第二个问题是隔离：张三是张三的会话，李四是李四的会话，两者不能互相看到对方的对话。第三个问题是连续性：用户在两次访问之间离开又回来，助手应该还记得之前谈过什么。

AgentScope Java 用三个对象回答这三个问题。RuntimeContext 回答「这次调用是谁」，AgentState 回答「之前谈了什么」，AgentStateStore 回答「状态放在哪里、怎么在进程重启后取回」。本章讲清三者的分工边界，以及多用户并发时的行为。

场景

本章场景

把团队知识助手改造为多用户 Web 服务：

  • 每个 HTTP 请求携带 RuntimeContext，标明 userId 与 sessionId

  • 状态写入可替换的存储，本地开发用 JSON 文件，生产用 Redis

5.1先讲理论：三层状态模型

「状态」这个词在框架里指三件不同的事。把它们混在一起是大多数使用困惑的来源，因此先建立这张表。

层对象生命周期是否跨进程典型内容
易失运行时状态AgentState一次调用开始时装载，调用结束后保存是（由存储实现保证）对话上下文、压缩摘要、权限规则、工具状态、当前回复位置、任务上下文、Plan Mode 上下文
单次调用元数据RuntimeContext调用期间绑定，调用结束后解绑否userId、sessionId、请求标识、任意注入的业务对象
持久化存储AgentStateStore与应用同生命周期是按 (userId, sessionId) 寻址的 AgentState 读写接口

三者的关系可以用一张图表示：

一次调用的完整过程 HTTP 请求 │ ▼ RuntimeContext(userId=alice, sessionId=s-001, 附加属性) │ ← 框架在调用期间绑定这一次调用，下游读到同一引用 ▼ ┌──────────────────────────────────────────┐ │ 按 (userId, sessionId) 取状态 │ │ ▼ │ │ AgentState ──► ReAct 推理循环 ◄── @Tool 方法 │ │ │ │ │ │ │ └── 读 RuntimeContext 的属性 │ │ ▼ │ └────────┼─────────────────────────────────────────┘ │ 保存 ▼ AgentStateStore（内存 / JSON 文件 / Redis / OSS / MySQL） RuntimeContext 的自由属性不写入 AgentState，也不被存储。 但是 userId 与 sessionId 决定「取哪个状态槽」。

RuntimeContext：每次调用的元数据袋

RuntimeContext 的定位是「一次调用的元数据袋」。它由调用方构建，作为参数传给 call 或 stream。框架在调用期间把它绑定到当前执行上下文，因此下游的工具、中间件、钩子读到的都是同一个引用，不需要逐层传递。调用结束后框架解绑，下一次调用可以绑定另一个。

构建与读取 RuntimeContextjava
import io.agentscope.core.agent.RuntimeContext;

RuntimeContext ctx = RuntimeContext.builder()
        .userId("alice")
        .sessionId("session-001")
        // 字符串属性：任意键值对，用于进程内协调
        .put("request_id", "req-abc-123")
        // 类型化属性：按类型登记，供工具参数自动注入
        .put(UserContext.class, new UserContext("alice", "en"))
        .build();

String sid = ctx.getSessionId();
String uid = ctx.getUserId();

因此，工具方法里想拿到 userId，不需要把它作为工具参数传进来，也不需要自己维护一个 ThreadLocal。这一点比「参数层层传递」或「静态变量」都可靠，因为框架保证了同一次调用内的同一性。

为什么 Agent 实例必须无状态

第一章论证过无状态设计对推理循环的价值。本章从另一个角度说明这个约束：它是水平扩展的前提。一个 Agent 实例如果把「当前对话」保存在字段里，那么同时服务两个用户时必然互相覆盖，而要避免覆盖就必须为每个用户各建一个实例，实例数量就会随用户数增长。

因此框架的设计是：Agent 实例不持有任何会话数据，状态全部放在 AgentState 中，由 AgentStateStore 按 (userId, sessionId) 存取。每次调用开始时按上下文选定状态槽，调用结束后写回。这带来两个直接结果：

  • 一个单例 Agent 可以同时服务任意数量的用户与会话，实例数量与负载无关。
  • 同一个 Agent 实例可以被放在负载均衡后的任意副本上，因为副本之间不共享内存，状态在存储里。
缺省会话的处理

调用时未传入 RuntimeContext，框架会替换为 RuntimeContext.empty()：session 字段为 null，属性表为空。此时 Agent 回退到构建器上设置的 defaultSessionId。这适合单元测试与命令行演示，但在服务端场景下一定要显式传入，否则所有请求会落到同一个状态槽。

RuntimeContext 的两层属性槽

RuntimeContext 有两组互不干扰的属性槽。它们看起来相似，但是用途完全不同，官方文档明确要求不要混用。

字符串属性槽类型化属性槽
写入方法put(String key, Object value)put(Class<T> type, T value)
put(String key, Class<T> type, T value)
读取方法get(String key)get(Class<T> type)
get(String key, Class<T> type)
键的形式任意字符串Class 对象，可选附加字符串键
典型用途进程内协调：中间件与中间件之间传递信号，例如标记「本轮已授权，跳过审批」把业务对象注入工具方法参数：租户配置、审计器、数据库连接
是否进入模型可见的工具 Schema否否
是否写入 AgentState否否

两者都不会出现在模型看到的工具 Schema 里，也不会被持久化。区别在于框架是否用它来满足方法参数：类型化属性可以驱动工具注入，字符串属性不会。

类型化属性驱动工具注入

这是类型化属性槽最重要的用途。在 @Tool 方法上声明一个类型参数，框架在调用该工具时会自动从 RuntimeContext 中取出匹配类型的值传进去。工具方法自身因此不需要写任何查找逻辑，也不需要知道 RuntimeContext 的存在。

这项能力带来两个直接收益。第一，工具签名保持干净，模型看到的参数列表里没有租户配置这类与业务语义无关的对象。第二，工具与租户逻辑解耦：同一个工具类可以服务多个租户，租户差异全部由 RuntimeContext 承载。

RuntimeContext 与 AgentState 的边界

这是本章最需要记住的一条规则：RuntimeContext 的自由属性永远不会进入 AgentState，因此也不会被 AgentStateStore 写回。但是 userId 与 sessionId 会驱动持久化寻址——每次调用激活对应的 (userId, sessionId) 状态槽。

内容放在哪里重启进程后是否还在
对话上下文、压缩摘要AgentState在
权限规则、工具状态AgentState在
任务上下文、Plan Mode 上下文AgentState在
userId / sessionIdRuntimeContext不在（由调用方每次重新传入）
请求标识、中间件信号RuntimeContext 字符串属性不在
租户配置、审计器实例RuntimeContext 类型化属性不在

因此可以这样理解：RuntimeContext 回答「这次是谁」，AgentState 回答「之前发生了什么」。前者由每次请求重新构造，后者由存储恢复。需要跨请求长期存在的业务数据（例如用户偏好、租户配额），既不应该只放在 RuntimeContext 里，也不应该写入对话上下文，而应当由业务自己的数据库管理。

streamEvents 没有 RuntimeContext 重载

需要上下文的事件流请使用 stream(msgs, options, ctx)。streamEvents 没有接受 RuntimeContext 的重载，如果确实需要上下文，可以在构建器上配置全局的 toolExecutionContext，但这种做法会让所有调用共用一个上下文，在多用户服务中通常不合适。服务端代码应当优先使用 stream 的三参数形式。

另外，旧的 ToolExecutionContext（位于 io.agentscope.core.tool）已标记为 @Deprecated。迁移时使用 RuntimeContext.asToolExecutionContext() 做桥接兼容。

并发语义

框架对并发的处理规则只有两条，而且都是自动的，不需要你写锁。

场景行为原因
相同 (userId, sessionId) 的并发调用自动串行化：第二个请求等待第一个完成同一会话状态不能被两个调用同时读写，否则消息顺序不可控
不同 session 的并发调用并行执行状态槽互不重叠，无需协调
同一个 Agent 实例服务多个用户并行执行Agent 实例不持有会话数据，槽位按调用选定

串行化的粒度是「状态槽」，而不是「Agent 实例」。因此十个用户各自提问会同时进行，而同一个用户在同一会话里连发两条消息，第二条会等待第一条完成。这个设计保证了对话消息顺序与用户看到的一致。

串行化不等于可以省掉超时设置

如果某个会话的第一条请求卡在模型调用上，同会话的后续请求会一直等待。因此服务端仍然需要为 call 设置超时，并在超时后返回明确的错误，而不是无限期挂起。

5.2动手：会话状态存储

本节用三种存储实现同一个知识助手，对比它们的代码差异与适用场景。三种实现只差一行配置，其余代码完全相同——这正是存储抽象的价值。

示例一：三种 AgentStateStore

StateStoreDemo.javajava
import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.state.InMemoryAgentStateStore;
import io.agentscope.core.state.JsonFileAgentStateStore;

import java.nio.file.Path;
import java.nio.file.Paths;

public class StateStoreDemo {

    public static void main(String[] args) {
        // 实现一：内存存储。只在当前进程有效，进程退出即丢失。
        // 适用于单元测试与单进程演示。
        var memoryStore = new InMemoryAgentStateStore();

        // 实现二：JSON 文件存储。每个 (userId, sessionId) 对应一个 JSON 文件。
        // 适用于单机开发与调试，重启进程后会话仍在。
        Path sessionDir = Paths.get(
                System.getProperty("user.home"), ".agentscope/sessions");
        var fileStore = new JsonFileAgentStateStore(sessionDir);

        // 两者的构造与使用方式完全一致，因此切换存储不需要改动其他代码
        ReActAgent memAgent = buildAgent(memoryStore);
        ReActAgent fileAgent = buildAgent(fileStore);

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("alice")
                .sessionId("demo-001")
                .build();

        // 同一个 sessionId 连续两轮，第二轮会恢复第一轮的上下文
        memAgent.call(new UserMessage("我叫 Alice，负责支付模块。"), ctx).block();
        Msg reply = memAgent.call(new UserMessage("我负责什么？"), ctx).block();
        System.out.println("内存存储： " + reply.getTextContent());

        // 换一个 sessionId，状态相互隔离
        RuntimeContext other = RuntimeContext.builder()
                .userId("alice")
                .sessionId("demo-002")
                .build();
        Msg fresh = memAgent.call(new UserMessage("我负责什么？"), other).block();
        System.out.println("新会话（应为不知道）： " + fresh.getTextContent());
    }

    private static ReActAgent buildAgent(
            io.agentscope.core.state.AgentStateStore store) {
        return ReActAgent.builder()
                .name("kb-assistant")
                .sysPrompt("你是一个团队知识助手，回答保持简洁。")
                .model("dashscope:qwen-plus")
                // 显式设置状态存储。
                // 注意：ReActAgent 未设置时为 null，不会持久化；
                // 只有 HarnessAgent 才缺省使用 JsonFileAgentStateStore。
                .stateStore(store)
                .build();
    }
}

这个示例验证了两件事。第一，相同 sessionId 的第二次调用能够恢复第一次的内容，因此模型能回答「我负责什么」。第二，sessionId 换成 demo-002 之后，模型无法回答同一个问题，因为它面对的是一个空状态槽。会话隔离由 sessionId 单独决定，与 userId 无关。

生产环境：Redis 与关系库

多副本部署时，本地文件与内存都不再适用：副本 A 写入的状态，副本 B 读不到。AgentScope 为此提供了 Redis、OSS 与 MySQL 三种扩展实现。下面是 Redis 的配置方式：

RedisStore.javajava
import io.agentscope.core.ReActAgent;
import io.agentscope.ext.redis.RedisAgentStateStore;
import redis.clients.jedis.JedisPooled;

public class RedisStore {

    public static void main(String[] args) {
        JedisPooled client = new JedisPooled("127.0.0.1", 6379);

        RedisAgentStateStore store = RedisAgentStateStore.builder()
                .jedisClient(client)
                // 自定义键前缀，多个应用共用一个 Redis 时用于区分
                .keyPrefix("myapp:session:")
                .build();

        ReActAgent agent = ReActAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .stateStore(store)
                .build();

        System.out.println("Agent 已就绪，任意副本均可处理同一会话。");
    }
}

集群模式需要换成 lettuceClusterClient(RedisClusterClient.create(...))，或者在已经持有 Redisson 实例时使用 redissonClient(redisson)。三个方法的具体签名以所用版本的 Javadoc 为准。

选型对照如下：

实现所在模块适用场景限制
InMemoryAgentStateStoreagentscope-core单元测试、单进程演示进程退出即丢失，不适合生产
JsonFileAgentStateStoreagentscope-core单机开发、调试、离线复现问题多副本之间不共享，需要本地磁盘
RedisAgentStateStoreagentscope-extensions-redis多副本生产默认选择需要可用的 Redis 服务
OssAgentStateStoreagentscope-extensions-oss需要对象存储、快照归档访问延迟高于 Redis
MysqlAgentStateStoreagentscope-extensions-mysql状态需要进关系库：审计、报表、与其他表 join写入延迟较高，需注意表结构
如何判断该用 MySQL 而不是 Redis

判断标准只有一条：是否需要用 SQL 查询状态。「统计过去七天每个租户的会话数」「把某个用户的会话与工单表关联」这类需求要求状态在关系库里；如果只是按 (userId, sessionId) 存取，Redis 更合适。

示例二：类型化属性驱动工具注入

这一节实现本章场景中最关键的部分：把租户配置注入工具方法，让工具代码里完全不出现查找逻辑。

TenantTools.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.tool.Tool;
import io.agentscope.core.tool.ToolParam;
import io.agentscope.core.tool.Toolkit;

import java.util.List;
import java.util.Map;

/** 租户配置。普通 POJO，不实现任何框架接口。 */
public class TenantConfig {
    private final String tenantId;
    private final String locale;
    private final int maxSearchResults;

    public TenantConfig(String tenantId, String locale, int maxSearchResults) {
        this.tenantId = tenantId;
        this.locale = locale;
        this.maxSearchResults = maxSearchResults;
    }

    public String getTenantId() { return tenantId; }
    public String getLocale() { return locale; }
    public int getMaxSearchResults() { return maxSearchResults; }
}

/** 审计器。同样是普通 POJO。 */
public class AuditRecorder {
    private final List<String> records = new java.util.ArrayList<>();

    public void record(String action) {
        records.add(action);
        System.out.println("[audit] " + action);
    }

    public int count() { return records.size(); }
}

/** 工具集合。TenantConfig 与 AuditRecorder 由框架自动传入。 */
public class TenantTools {

    /**
     * 按租户配置执行知识检索。
     *
     * 注意方法签名：tenant 参数的类型是 TenantConfig。
     * 模型看不到这个参数，也不会尝试填写它，
     * 框架在调用时从 RuntimeContext 的类型化属性中取出实例传入。
     */
    @Tool(
            name = "search_knowledge",
            description = "在团队知识库中检索文档，返回最相关的若干条。")
    public String searchKnowledge(
            @ToolParam(name = "query", description = "检索关键词") String query,
            TenantConfig tenant,
            AuditRecorder audit) {

        audit.record("search_knowledge tenant=" + tenant.getTenantId()
                + " query=" + query);

        // 租户差异完全由注入的配置决定，工具自身没有任何 if-else 分支
        int limit = tenant.getMaxSearchResults();
        String locale = tenant.getLocale();

        return "tenant=" + tenant.getTenantId()
                + ", locale=" + locale
                + ", limit=" + limit
                + ", 命中 3 条文档（示例数据）";
    }
}

组装与调用：

TenantInjectionDemo.javajava
import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.tool.Toolkit;

public class TenantInjectionDemo {

    public static void main(String[] args) {
        Toolkit toolkit = new Toolkit();
        toolkit.registerTool(new TenantTools());

        ReActAgent agent = ReActAgent.builder()
                .name("kb-assistant")
                .sysPrompt(jt(16,
                        "你是一个团队知识助手。",

                        "回答保持简洁，不确定的内容要明确说明。"))

        // 为 alice 构造上下文：类型化属性在这里登记业务对象

                .put(AuditRecorder.class, audit)
                .build();

        Msg reply = agent.call(new UserMessage(
                "支付服务的读超时是多少？"), aliceCtx).block();
        System.out.println(reply.getTextContent());

        // 换成另一个租户，同一个 Agent 实例、同一份工具代码
        RuntimeContext bobCtx = RuntimeContext.builder()
                .userId("bob")
                .sessionId("session-001")
                .put(TenantConfig.class, new TenantConfig("t-risk", "en-US", 3))
                .put(AuditRecorder.class, audit)
                .build();

        Msg other = agent.call(new UserMessage(
                "风控规则有哪些？"), bobCtx).block();
        System.out.println(other.getTextContent());

        // 两次调用共用的审计器，计数为 2
        System.out.println("审计记录条数： " + audit.count());
    }
}
验证注入是否生效

把 searchKnowledge 中打印出的 tenant.getTenantId() 与提问的用户对照。如果框架没有注入成功，方法会收到 null，抛出 NullPointerException，因此这段代码同时也是一个断言。此外，audit.count() 在两次调用后等于 2，说明同一个工具实例在不同会话中被复用，而注入的对象可以每次不同。

需要强调的是：TenantConfig 与 AuditRecorder 都不会出现在模型看到的工具 Schema 中。模型只需要填写 query，它既不需要知道租户 ID，也不允许自行指定租户。因此租户隔离由服务端构造的上下文保证，而不是靠提示词约束。

示例三：单例 Agent 的 HTTP 集成

把前面的配置组织成 Web 服务。核心只有一句话：应用启动时创建一个 Agent，每个请求传入不同的 RuntimeContext。

AssistantController.javajava
import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.state.RedisAgentStateStore;
import org.springframework.web.bind.annotation.*;

import java.util.List;
import java.util.Map;

@RestController
@RequestMapping("/api/assistant")
public class AssistantController {

    // 单例 Agent。它不持有任何会话数据，因此可以被所有请求共享。
    private final ReActAgent agent;

    public AssistantController() {
        var store = RedisAgentStateStore.builder()
                .jedisClient(new redis.clients.jedis.JedisPooled(
                        "127.0.0.1", 6379))
                .keyPrefix("kb-assistant:session:")
                .build();

        this.agent = ReActAgent.builder()
                .name("kb-assistant")
                .sysPrompt("你是团队知识助手，回答保持简洁。")
                .model("dashscope:qwen-plus")
                .stateStore(store)
                .build();
    }

    /**
     * 提问接口。
     *
     * userId 与 sessionId 由请求头传入，服务端不信任客户端构造的
     * 其他属性。租户配置应当在这里按 userId 从配置中心或数据库查出，
     * 而不是从请求体直接反序列化得到。
     */
    @PostMapping("/chat")
    public Map<String, Object> chat(
            @RequestHeader("X-User-Id") String userId,
            @RequestHeader(value = "X-Session-Id", required = false) String sessionId,
            @RequestBody ChatRequest body) {

        String sid = (sessionId == null || sessionId.isBlank())
                ? "session-" + java.util.UUID.randomUUID()
                : sessionId;

        TenantConfig tenant = TenantConfigRepository.findByUser(userId);

        RuntimeContext ctx = RuntimeContext.builder()
                .userId(userId)
                .sessionId(sid)
                .put("request_id", java.util.UUID.randomUUID().toString())
                .put(TenantConfig.class, tenant)
                .build();

        Msg reply = agent.call(new UserMessage(body.question()), ctx).block();

        return Map.of(
                "sessionId", sid,
                "answer", reply.getTextContent());
    }

    /** 查看当前会话的上下文消息数，便于联调。 */
    @GetMapping("/state")
    public Map<String, Object> state(
            @RequestHeader("X-User-Id") String userId,
            @RequestHeader("X-Session-Id") String sessionId) {

        var state = agent.getAgentState(userId, sessionId);
        return Map.of(
                "userId", state == null ? userId : userId,
                "messageCount", state.getContext().size());
    }

    public record ChatRequest(String question) {}
}

这个控制器里有三个值得注意的细节。第一，Agent 字段是 final 且只在构造时创建一次，这是「无状态」设计的直接体现。第二，X-Session-Id 缺省时生成新 ID，因此客户端第一次访问与后续访问的行为是统一的。第三，TenantConfig 是服务端按 userId 查出来的，而不是从请求体反序列化的，这一点对多租户服务的安全性至关重要。

响应式栈的差异

上面的写法会阻塞 Web 线程。如果使用 WebFlux，应当返回 Mono，并把 Agent 调用放在响应式链路上：

ReactiveController.javajava
import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.UserMessage;
import org.springframework.web.bind.annotation.*;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

@RestController
@RequestMapping("/api/assistant")
public class ReactiveController {

    private final ReActAgent agent;

    public ReactiveController(ReActAgent agent) {
        // Agent 由配置类创建并注入，这里不重复构建
        this.agent = agent;
    }

    @PostMapping("/chat")
    public Mono<String> chat(@RequestHeader("X-User-Id") String userId,
                             @RequestHeader("X-Session-Id") String sessionId,
                             @RequestBody ChatRequest body) {
        RuntimeContext ctx = RuntimeContext.builder()
                .userId(userId)
                .sessionId(sessionId)
                .build();

        return agent.call(new UserMessage(body.question()), ctx)
                .map(msg -> msg.getTextContent());
    }

    /**
     * 流式接口。
     *
     * 注意：streamEvents 没有 RuntimeContext 重载，
     * 因此需要上下文时使用 stream(msgs, options, ctx)。
     */
    @GetMapping("/stream")
    public Flux<String> stream(@RequestHeader("X-User-Id") String userId,
                               @RequestHeader("X-Session-Id") String sessionId,
                               @RequestParam String q) {
        RuntimeContext ctx = RuntimeContext.builder()
                .userId(userId)
                .sessionId(sessionId)
                .build();

        // 三参数形式，带上下文的事件流
        return agent.stream(java.util.List.of(new UserMessage(q)), null, ctx)
                .map(event -> String.valueOf(event));
    }

    public record ChatRequest(String question) {}
}

示例四：会话状态巡检工具

线上排查问题时经常需要知道：某个会话现在有多少条消息、状态文件有多大、什么时候创建的。把这些信息做成一个工具，比临时写日志更方便。

SessionInspector.javajava
import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.AgentState;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.tool.Tool;
import io.agentscope.core.tool.ToolParam;

public class SessionInspector {

    private final ReActAgent agent;

    public SessionInspector(ReActAgent agent) {
        this.agent = agent;
    }

    /**
     * 巡检当前会话的状态。
     *
     * RuntimeContext 用字符串属性槽即可：这里只需要读取一个字符串，
     * 不需要把对象注入方法参数，因此没有必要占用类型化属性槽。
     */
    @Tool(
            name = "inspect_session_state",
            description = "查看当前会话的状态摘要：消息数量、状态体积、会话标识。")
    public String inspect(
            @ToolParam(name = "label", description = "巡检标签，用于区分同一会话的多次巡检")
            String label,
            RuntimeContext ctx) {

        String sid = ctx.getSessionId();
        String uid = ctx.getUserId();

        // 按 (userId, sessionId) 取得该会话的状态
        AgentState state = agent.getAgentState(uid, sid);
        if (state == null) {
            return "会话 " + sid + " 尚无状态，可能是首次调用。";
        }

        int messageCount = state.getContext().size();

        // 序列化后可以观察状态体积，用于判断是否需要清理
        String json = state.toJson();
        int bytes = json.getBytes(java.nio.charset.StandardCharsets.UTF_8).length;

        // 状态中除对话上下文外还包含压缩摘要、权限规则、工具状态等
        return String.format(
                "[%s] userId=%s, sessionId=%s%n"
                        + "  对话消息数：%d 条%n"
                        + "  状态体积：%d 字节（约 %.1f KB）%n"
                        + "  当前请求标识：%s",
                label, uid, sid, messageCount, bytes, bytes / 1024.0,
                String.valueOf(ctx.get("request_id")));
    }

    public static void main(String[] args) {
        ReActAgent agent = ReActAgent.builder()
                .name("kb-assistant")
                .sysPrompt("你是一个团队知识助手。")
                .model("dashscope:qwen-plus")
                .build();

        SessionInspector inspector = new SessionInspector(agent);
        agent.registerTool(inspector);

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("alice")
                .sessionId("inspect-001")
                .put("request_id", "req-abc-123")
                .build();

        agent.call(new UserMessage("我叫 Alice，负责支付模块。"), ctx).block();
        agent.call(new UserMessage("支付服务有哪些接口？"), ctx).block();

        Msg reply = agent.call(new UserMessage(
                "调用 inspect_session_state 巡检当前会话，label 填 final。"), ctx).block();
        System.out.println(reply.getTextContent());

        // 也可以在服务代码中直接读取状态，不经过模型
        AgentState state = agent.getAgentState("alice", "inspect-001");
        System.out.println("直接读取消息数： " + state.getContext().size());
    }
}

这个工具同时演示了两种读取上下文的方式。第一种是把 RuntimeContext 作为方法参数，直接读取 sessionId、userId 与字符串属性。第二种是通过 agent.getAgentState(userId, sessionId) 在服务代码中直接读取状态，完全不经过模型。第二种方式在巡检与监控接口中更常用，因为它不消耗模型调用。

另外还有一个重载 agent.getAgentState(runtimeContext)，它在已经有上下文对象时更方便，避免重复传两个字符串。

5.4本章小结

  • 状态分三层：AgentState 是易失运行时状态，RuntimeContext 是单次调用元数据，AgentStateStore 负责跨进程恢复。三者的生命周期与持久化特性各不相同。
  • Agent 实例对会话而言无状态，这是水平扩展的前提：单例可以服务任意用户，任何副本都能处理同一会话。
  • RuntimeContext 在调用期间绑定，下游工具、中间件与钩子读到同一引用，因此不需要层层传参。
  • 两层属性槽互相隔离：字符串属性用于进程内协调，类型化属性用于驱动工具参数注入，两者都不进入模型可见的 Schema，也都不写入 AgentState。
  • RuntimeContext 的自由属性永不持久化，但 userId 与 sessionId 驱动持久化寻址。需要长期存在的业务数据应当由业务自己的数据库管理。
  • 并发语义只有两条：相同 (userId, sessionId) 的调用自动串行化，不同会话并行执行。因此仍然需要为 call 设置超时。
  • 存储选型：内存用于测试，JSON 文件用于单机开发，Redis 是多副本生产默认，MySQL 用于需要 SQL 查询的状态，OSS 用于归档与跨地域。
  • 多租户服务的关键是把租户对象由服务端按 userId 查出后注入上下文，而不是从请求体反序列化；隔离由上下文保证，不依赖提示词。
练习
  1. 按示例一的思路，分别用 InMemoryAgentStateStore 与 JsonFileAgentStateStore 构建 Agent，提问三轮后退出进程再重新提问，对比两者的差异。
  2. 设计题：为一个多租户知识助手设计隔离方案。要求明确回答四个问题：（1）userId 与 sessionId 分别从哪一层取值，如何防止客户端伪造；（2）租户配置、审计器、数据库连接分别放在哪一层；（3）同一租户下的不同用户能否共享会话历史，如何实现；（4）选哪种 AgentStateStore，理由是什么。要求方案中能指出哪些数据由框架持久化、哪些不持久化。
  3. 追问：为什么 RuntimeContext 上的自由属性不会被 AgentStateStore 写回？请从「职责分离」与「状态体积」两个角度解释设计理由，并说明如果你需要一个跨请求长期存在的业务字段（例如用户偏好），应该放在哪里、怎么在工具中取得。
  4. 实现示例四的巡检工具，并在其中输出状态 JSON 的前 200 个字符，观察 AgentState 的实际结构。
  5. 用两个不同 sessionId 与两个不同 userId 组合共发起四次调用，验证隔离边界究竟由 userId 还是 sessionId 决定。
  6. 把示例二中的 TenantConfig 换成用字符串属性槽传递（例如 put("tenant_id", "t-payments")），对比两种方式的差异：工具签名、模型可见的参数、以及能否在框架不感知的情况下改造工具。
  7. 为同一会话设置一个较短的超时时间，模拟模型卡住的场景，观察同会话的后续请求如何表现。

下一章讨论模型层。会话与状态解决了「上下文从哪里来、到哪里去」，而模型层决定了「每一轮推理由谁完成、花费多少成本」。
