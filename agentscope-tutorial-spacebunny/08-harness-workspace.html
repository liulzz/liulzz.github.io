这一章为什么重要

到目前为止，知识助手每次启动都是空白的：它不知道自己是谁、不记得上次说了什么、不具备任何可复用的技能。这些问题在演示场景下不明显，但一旦投入真实使用，缺陷会立刻显现。

AgentScope Java 2.0 用两个概念解决这个问题：Harness 提供工程化能力，Workspace 提供可持久化的文件空间。本章讲清这两个概念的设计意图与配合方式。

场景

本章场景

把知识助手改造为具备长期身份的系统：

  • 它的人格与行为规则写进 AGENTS.md，可以纳入 Git 版本管理
  • 它的团队知识写进 knowledge/，只有索引进入提示词，详情按需读取
  • 它记住的长期事实沉淀到 MEMORY.md
  • 重启进程之后，它仍然是同一个助手

8.1先讲理论：双层架构

AgentScope Java 2.0 的第一个核心设计是双层 Agent 架构。底层是 ReActAgent，负责推理与行动；上层是 HarnessAgent，通过中间件与 Toolkit 两个通道注入工程化能力。

关键在于：能力挂载在推理循环之外，而不是嵌入其中。无论工作区注入、上下文压缩还是子智能体委派，都发生在 ReAct 循环的特定节点上，推理算法本身保持不变。因此开发阶段可以使用最轻量的内核，生产阶段启用全部工程化能力，业务代码无需重写。

两者的关系

官方文档明确说明：HarnessAgent 是 ReActAgent 的一个薄封装，两者构建器字段基本一致。从 ReActAgent 切换到 HarnessAgent，通常只需要改类名，再加上工作区配置。

从内核切换到 Harnessjava
// 开发阶段：最轻量的内核
ReActAgent dev = ReActAgent.builder()
        .name("kb-assistant")
        .sysPrompt("你是一个团队知识助手。")
        .model("dashscope:qwen-plus")
        .build();

// 生产阶段：同一套逻辑，增加工作区与工程化能力
HarnessAgent prod = HarnessAgent.builder()
        .name("kb-assistant")
        .sysPrompt("你是一个团队知识助手。")
        .model("dashscope:qwen-plus")
        .workspace(Paths.get(".agentscope/workspace"))
        .compaction(CompactionConfig.builder()
                .triggerMessages(30)
                .keepMessages(10)
                .build())
        .build();
什么时候必须用 HarnessAgent

如果你需要以下任意一项，就必须使用 HarnessAgent，因为这些能力由 Harness 提供：工作区文件定义、长期记忆、上下文压缩、子智能体委派、技能管理、Plan Mode、沙箱隔离、Channel 通道。如果只需要推理加工具，ReActAgent 已经足够。

Harness 提供了哪些能力

能力解决的问题构建方法
工作区驱动的人格人格、知识、子智能体声明、技能、MCP 白名单都以文件形式保存.workspace(path)
状态持久化相同 (userId, sessionId) 跨请求、跨进程、跨副本恢复默认开启，可用 .stateStore(...) 覆盖
两层长期记忆长对话中的事实沉淀到 MEMORY.md默认开启，用 .memory(...) 自定义

三个共享对象

Harness 的各项能力互不依赖，它们通过三个共享对象协作。理解这一点，你就理解了 Harness 的全部设计。

三项能力如何协作 RuntimeContext ──→ 当前这次调用是谁在说话（sessionId、userId、附加属性） 不持久化 Workspace ──→ 读写哪些文件。物理落点是配置选择： 本地磁盘 / 远程 KV / 沙箱容器 AgentStateStore ──→ 运行时状态如何跨调用恢复 三项能力互不知晓对方的存在。 你配置 workspace 路径，它们各自去正确的位置读写。

执行顺序

Harness 在构建时按固定顺序装配内置中间件，而你通过 .middleware(...) 添加的中间件运行在所有内置中间件之前。这一点在你需要在外层做日志或审计时很重要。

8.2动手：第一个 HarnessAgent

本章场景的实现分三步：创建工作区目录、写人格文件、构建 Agent。

创建工作区

工作区是一个普通目录，用 .workspace(...) 指定路径即可，目录不存在时框架会创建。

写入 AGENTS.md

这是唯一通常需要手工创建的文件。不创建时 Agent 仍可运行，只是没有人格注入。

构建并运行

构建完成后，调用方式与 ReActAgent 完全一致。

编写 AGENTS.md

workspace/AGENTS.mdmarkdown
# 团队知识助手

你是团队的内部知识助手，服务于研发、产品与运营同学。

## 角色

- 你只回答与本团队业务、技术、流程相关的问题。
- 回答前先检索 `knowledge/` 目录下的文档，不要凭记忆作答。
- 引用内容时必须标明来源文件路径。

## 行为规则

- 回答保持简洁，能一句话说清就不要用三句。
- 不确定的内容必须明确说明「文档中没有记载」，不要推测。
- 涉及生产环境操作时，先说明影响范围，再询问是否继续。
- 拒绝回答与团队业务无关的通用闲聊。

## 边界

- 不执行任何写入生产系统的操作。
- 不输出任何密钥、令牌、密码等敏感信息。

构建并运行

HarnessFirst.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.memory.compaction.CompactionConfig;

import java.nio.file.Paths;

public class HarnessFirst {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .sysPrompt("你是团队知识助手，行为规则见 AGENTS.md。")
                .model("dashscope:qwen-plus")
                // 指定工作区路径，目录不存在时框架自动创建
                .workspace(Paths.get(".agentscope/workspace"))
                // 上下文压缩：超过 30 条消息触发，保留最近 10 条
                .compaction(CompactionConfig.builder()
                        .triggerMessages(30)
                        .keepMessages(10)
                        .build())
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan")
                .sessionId("demo-001")
                .build();

        // 第一轮：告诉它一些会长期有用的事实
        agent.call(new UserMessage(
                "我叫张三是支付模块的负责人，习惯用中文回答。"), ctx).block();

        // 第二轮：相同 sessionId，上下文自动恢复
        Msg reply = agent.call(new UserMessage(
                "我叫什么？负责什么？"), ctx).block();

        System.out.println(reply.getTextContent());
    }
}

运行后你会得到两棵目录树：

.agentscope/workspace/ 工作区（智能体内容） ├── AGENTS.md 你手写的：人格与行为规则 └── agents/kb-assistant/ └── sessions/ 永不压缩的原始对话日志 ~/.agentscope/state/kb-assistant/ 状态存储（在工作区之外） └── zhangsan/demo-001/ └── agent_state.json 自动保存与加载
为什么 AgentState 不在工作区里

官方文档给出的理由是：状态是恢复工作区本身的前提（例如沙箱被清空后需要状态来恢复），因此它不能与工作区数据相互纠缠。默认路径是 ~/.agentscope/state/<agentId>/，可通过系统属性 agentscope.state.home 修改，也可通过 .stateStore(...) 换成 Redis 或 MySQL 实现。

验证工作区生效

import io.agentscope.core.message.Msg;

import io.agentscope.harness.agent.HarnessAgent;
import java.nio.file.Files;

public class VerifyWorkspace {

    public static void main(String[] args) throws Exception {

8.3Workspace 目录布局

Workspace 使用统一的逻辑目录布局。这个布局的含义是：无论文件物理上位于本地磁盘、远程 KV 还是沙箱容器，逻辑相对路径保持不变。

.agentscope/workspace/text
├── AGENTS.md                     ← 静态：人格 + 行为规则
├── MEMORY.md                     ← 长期：整理后的长期记忆（每轮注入）
├── tools.json                    ← 静态：MCP 服务 + 工具白名单/黑名单（可选）
├── memory/                       ← 长期：按日期追加的事实日志
│   └── 2026-07-10.md
├── knowledge/                    ← 静态：知识入口与参考文件
│   ├── KNOWLEDGE.md              ←   完整注入提示词
│   └── api-reference.md          ←   只注入文件路径列表
├── skills/                       ← 静态：每个技能一个子目录
│   └── <skill-name>/SKILL.md
├── subagents/                    ← 静态：子智能体声明（文件名即 agent_id）
│   └── <agent-id>.md
├── plans/                        ← 运行时：Plan Mode 写出的计划
│   └── PLAN.md
└── agents/<agentId>/             ← 运行时：框架写入
    ├── sessions/
    │   ├── sessions.json         ← 会话索引
    │   └── <sessionId>.log.jsonl ← 永不压缩的完整对话记录
    └── tasks/
        └── <sessionId>.json      ← 子智能体后台任务记录

三类内容，三种生命周期

工作区里的文件并非同一种东西。它们由不同的写入者产生，也被不同的读取方使用。理解这一点有助于排查问题。

类型写入者读取者典型文件
静态资产工程师或用户框架每轮注入，或调用时按需读取AGENTS.md、knowledge/、skills/、subagents/、tools.json
运行时文件框架或 Agent框架在下一次调用时恢复agents/<agentId>/sessions/、tasks/、plans/
长期记忆Agent 加后台任务框架注入提示词，Agent 通过工具查询MEMORY.md、memory/YYYY-MM-DD.md

每轮如何组装系统提示词

在每次推理之前，WorkspaceContextMiddleware 会把相关内容追加到构建器设置的 sysPrompt 之后，形成最终的系统消息。注入内容与预算规则如下。

注入区块来源预算与行为
## Session Context内置模板含当天日期、操作系统、工作区绝对路径、临时目录、当前 sessionId。无预算限制
## Domain Knowledge 等内置模板指导模型使用记忆与知识；禁用相应能力时会被省略
## Workspace内置模板，按文件系统模式分支告诉模型当前是在本地、沙箱还是远程存储中运行
<agents_context>完整 AGENTS.md完整注入，无限制
<memory_context>MEMORY.md受 maxContextTokens 限制，缺省 8000；超出按字符截断
<domain_knowledge_context>完整 knowledge/KNOWLEDGE.md + knowledge/ 下所有文件路径列表KNOWLEDGE.md 完整注入；其他文件只注入文件名目录，不注入正文
<x_md>通过 .additionalContextFile("X.md") 添加完整注入，无限制
改文件立即生效，无需重启

系统提示词在每个推理步骤重新组装，因此修改 AGENTS.md 或 MEMORY.md 后，下一次调用就会读取新内容，不需要重启进程，也不需要重新构建 Agent。这对于调试提示词非常方便。

知识目录的索引与详情分离

knowledge/ 采用「索引在提示词、详情在磁盘」的模式。只有 knowledge/KNOWLEDGE.md 的完整内容进入提示词，目录下其他任意深度的文件只贡献一份路径列表。模型需要具体内容时，通过 read_file、grep_files、glob_files 按需读取。

workspace/knowledge/KNOWLEDGE.mdmarkdown
# 团队知识索引

本文件是知识库入口，会完整进入系统提示词。
下方只列出各文档的路径与用途，模型按需读取具体文件。

## 支付模块

- `knowledge/payment/service.md` —— 支付服务接口文档，含超时与重试配置
- `knowledge/payment/refund.md` —— 退款流程与状态机

## 风控模块

- `knowledge/risk/rules.md` —— 风控规则清单与阈值
- `knowledge/risk/model.md` —— 风险评分模型说明

## 内部流程

- `knowledge/process/onboarding.md` —— 新同事入职流程
- `knowledge/process/release.md` —— 发布流程与回滚预案
knowledge/payment/service.mdmarkdown
# 支付服务接口文档

## 超时配置

| 环境 | 读超时 | 写超时 |
|---|---|---|
| 测试 | 1 秒 | 2 秒 |
| 生产 | 3 秒 | 5 秒 |

## 重试策略

支付网关调用失败后最多重试 2 次，间隔 200 毫秒。
写操作不自动重试，需要人工确认。

这样组织的好处是：无论知识库有几百还是几万份文档，进入提示词的只有一份索引，token 消耗保持可控。

8.4工作区路径解析与配置

路径解析顺序

未显式调用 .workspace(...) 时，build() 按以下优先级解析：

优先级来源示例
1workspace(Path) / workspace(String)显式配置，覆盖其他来源
2agentscope.workspace 系统属性-Dagentscope.workspace=/data/workspace
3AGENTSCOPE_WORKSPACE 环境变量export AGENTSCOPE_WORKSPACE=/data/workspace
4缺省值${user.dir}/.agentscope/workspace

空白值（例如单个空格）会被视为未设置，继续尝试下一优先级。容器部署时通常用环境变量指定：

Dockerfiledocker
ENV AGENTSCOPE_WORKSPACE=/data/agent-workspace
docker-compose.yml / k8syaml
env:
  - name: AGENTSCOPE_WORKSPACE
    value: /data/agent-workspace

其他工作区配置

HarnessConfig.javajava
HarnessAgent agent = HarnessAgent.builder()
        .name("kb-assistant")
        .model("dashscope:qwen-plus")
        .workspace(Paths.get(".agentscope/workspace"))
        // 追加任意工作区相对路径，内容完整注入提示词
        .additionalContextFile("SOUL.md")
        .additionalContextFile("PREFERENCES.md")
        // MEMORY.md 的注入预算（不是整个提示词的预算）
        .maxContextTokens(8000)
        .build();

常用关闭项

关闭某些能力时可以使用下列方法，它们同时会移除提示词中相应的指引行：
方法禁用内容
disableWorkspaceContext()系统提示词注入，包括 AGENTS.md、MEMORY.md、knowledge/
disableMemoryHooks()记忆提取与后台维护；同时移除提示词中自动提取记忆的 Persistence 行
disableMemoryTools()memory_search、memory_get、memory_save、session_search 工具及相应指引
disableSubagents()整个子智能体子系统
disableDynamicSkills()每轮技能重新合并，改为构建时一次性合并
disableToolsConfig()禁止读取 tools.json
disableSessionPersistence()AgentState 自动持久化

disableMemoryHooks() 与 disableMemoryTools() 同时使用时，会完全跳过 <memory_context>（MEMORY.md）的注入。

8.5tools.json：声明式工具配置

tools.json 位于工作区根目录，在构建时读取一次。它用于声明 MCP 服务与工具白名单，避免把这些配置硬编码在 Java 代码里。

workspace/tools.jsonjson
{
  // 白名单：非空时，只有列出的工具会保留
  "allow": ["read_file", "grep_files", "glob_files", "list_files"],
  // 黑名单：列出的工具始终被移除，优先级高于 allow
  "deny": ["write_file", "edit_file"],
  // MCP 服务，以名称为 key
  "mcpServers": {
    "amap": {
      "transport": "streamableHttp",
      "url": "https://mcp.amap.com/mcp?key=${AMAP_API_KEY}"
    },
    "local-py": {
      "transport": "stdio",
      "command": "python",
      "args": ["mcp_servers/my_server.py"],
      "env": {"PYTHONUNBUFFERED": "1"}
    }
  }
}

几个容易遇到的细节：

  • allow 与 deny 在所有工具注册完成后才应用，因此它们也会过滤 Harness 内置工具，例如 read_file、memory_search、agent_spawn。
  • 使用 allow 时，需要显式列出希望保留的内置工具，否则它们也会被过滤掉。
  • ${ENV_VAR} 支持环境变量替换。变量缺失时会发出警告并替换为空字符串。
  • MCP 服务在构建时注册到 Toolkit，Agent 会看到这些服务暴露的工具。

8.6多租户与用户覆盖

Workspace 支持多租户隔离，机制分为「运行时数据」与「静态资产」两条路径。它们的隔离方式不同，这一点很容易混淆。

内容类别是否按 userId 分区隔离方式示例
运行时数据
（session、task、memory）		是路径前缀、KV 命名空间或沙箱状态槽agents/<agentId>/sessions/
静态资产
（AGENTS.md、skills、subagents、tools.json）		否，默认共享需要通过 per-user 覆盖目录实现skills/code-reviewer/SKILL.md

用户覆盖目录

如果需要按用户区分静态资产，可以增加 per-user 覆盖目录。框架先查找用户级目录，找不到再回退到共享目录。

多用户覆盖布局text
workspace/
├── skills/code-reviewer/SKILL.md      ← 共享，所有人可见
├── subagents/researcher.md            ← 共享
└── alice/                             ← 只有 userId=alice 可见
    ├── AGENTS.md                      ← alice 的人格与行为
    ├── knowledge/                     ← alice 的领域知识
    ├── skills/
    │   └── code-reviewer/SKILL.md     ← 覆盖同名共享技能
    └── subagents/
        └── researcher.md              ← 覆盖同名共享声明

解析顺序为：先查找 alice/skills/code-reviewer/，若不存在再查找共享的 skills/code-reviewer/。冲突规则是：低层中的独有技能仍然可见，只有同名技能被高层覆盖。子智能体声明遵循相同的覆盖逻辑。

因此同一个 Agent 实例可以实现两层多租户

定义层多租户：不同用户拥有不同的人格、知识与技能。演进数据多租户：不同用户的记忆、会话、任务相互隔离。这一点在设计共享型 Agent 时非常有用。

IsolationScope

IsolationScope 决定工作区与文件系统的分区维度。这个概念在第十三章讲沙箱时会再次出现。

IsolationScope共享范围典型用途
SESSION每个 sessionId 完全隔离单次会话隔离、临时沙箱
USER（缺省）同一 userId 的所有 session用户的多会话共享长期记忆与技能；缺少 userId 时回退到 SESSION
AGENT该 Agent 的所有用户与 session共享知识库型 Agent
GLOBAL整个 store instance 共用一个位置所有 Agent 与用户竞争同一位置，应谨慎使用

配置多租户工作区

MultiTenantHarness.javajava
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.IsolationScope;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;

public class MultiTenantHarness {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get("/opt/agent/workspace"))
                .build();

        // 张三的记忆与李四的完全隔离
        agent.call(new UserMessage("我负责支付模块。"),
                RuntimeContext.builder()
                        .userId("zhangsan").sessionId("s-1").build()).block();

        agent.call(new UserMessage("我负责风控模块。"),
                RuntimeContext.builder()
                        .userId("lisi").sessionId("s-1").build()).block();

        Msg reply = agent.call(new UserMessage("我负责什么？"),
                RuntimeContext.builder()
                        .userId("zhangsan").sessionId("s-1").build()).block();

        // 输出「支付模块」，说明两个用户的记忆相互隔离
        System.out.println(reply.getTextContent());
    }
}

8.7工作区写入的正确方式

这一节看起来像细节，但在实际项目中经常成为故障来源，因此单独说明。

不要用 java.nio.Files 写入工作区

在工作区中读写文件必须通过 harnessAgent.getWorkspaceManager()。使用 java.nio.Files 会写到宿主本地磁盘，在沙箱或共享存储模式下就会写到错误的位置。框架的全部工作区读写都经过配置的 AbstractFilesystem，只有它知道当前的物理落点。

唯一例外是构建期的初始化脚本：此时还没有运行时上下文，写入目标明确是本地模板，使用 java.nio.Files 是正确的。

框架对接受工作区相对路径的 API 会做路径穿越校验，例如拒绝 ../../etc/passwd 这样的输入。

8.8本章小结

  • HarnessAgent 是 ReActAgent 的薄封装，构建器字段基本一致，切换时通常只需改类名并增加工作区配置。
  • 能力挂载在推理循环之外，因此可以按需启用，推理内核保持不变。
  • Harness 的各项能力互不依赖，它们共享 RuntimeContext、Workspace、AgentStateStore 三个对象。
  • 自定义中间件运行在所有 Harness 内置中间件之前。
  • Workspace 用统一的逻辑目录布局，物理落点可以是本地磁盘、远程 KV 或沙箱容器。
  • 系统提示词每轮重新组装，修改 AGENTS.md 后立即生效，无需重启。
  • knowledge/ 采用「索引在提示词、详情在磁盘」的模式，这是控制 token 消耗的关键设计。
  • 运行时数据按 userId 隔离，静态资产默认共享，需要按用户区分时使用 per-user 覆盖目录。
  • 写入工作区必须用 getWorkspaceManager()，不能用 java.nio.Files。
练习
  1. 按本章示例创建一个工作区，写入一份属于你自己的 AGENTS.md，验证它是否在系统提示词中生效（可以临时在提示词里加入一句可观察的指令）。
  2. 删除 AGENTS.md，重启进程，再次提问。观察人格是否消失，并解释为什么 Agent 仍能运行。
  3. 修改 AGENTS.md 中的一条规则，不重启进程直接再次提问，验证「每轮重新组装」这一机制。
  4. 创建 knowledge/ 目录并放入三份文档，其中只有 KNOWLEDGE.md 是索引。验证其他文档只以路径形式出现。
  5. 配置 additionalContextFile("PREFERENCES.md")，验证该文件内容被完整注入提示词。
  6. 实现一个多用户场景：让 alice 与 bob 拥有不同的 AGENTS.md，并验证彼此不可见。
  7. 对照本章的目录树，列出你当前的工作区里每个文件的来源（框架写入、Agent 写入、还是你手工创建）。
