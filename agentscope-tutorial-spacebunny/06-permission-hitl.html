权限系统与人工确认
把不可预知的模型关进可控的策略里

前五章的智能体已经能检索文档、调用模型、管理会话。但只要它开始写文件、删数据、 执行命令，一个新的问题就出现了：模型下一次会调用什么，你无法事先知道。 本章介绍 AgentScope Java 的权限系统如何在运行时判定每一次工具调用， 以及当判定结果为「需要确认」时，如何用HITL 把决定权交还给人。

为什么需要权限系统

前几章我们反复强调一件事：工具决定了智能体的能力边界，而决定调用哪个工具的控制权在模型手里。这在只读场景里没什么问题，但是一旦工具具备写入或删除能力，风险就出现了。

具体来说，风险有三层：

  • 意图不可预知：同一句「清理一下旧文档」，模型可能选择 delete_doc，也可能选择 move_to_archive。你无法在代码里穷举它所有的选择。
  • 参数不可预知：即使工具名确定，模型传入的路径也可能是 docs/prod/ 而不是 docs/tmp/。
  • 后果不可撤销：删除文件、推送代码这类操作没有回滚按钮。因此事后的审计不如事前的判定重要。

权限系统的设计目标因此很明确：在工具执行之前介入，用规则和模式替代对模型意图的预测。你无法控制模型做什么，但是你可以决定哪些事情允许发生。

场景

本章场景

把上一章的团队知识助手升级为知识库管理助手。它需要能够：

  • 新增、修改文档（create_doc、update_doc）
  • 删除文档（delete_doc）—— 删除前必须获得人工确认
  • 任何针对 docs/prod/ 的删除 —— 一律拒绝，不提供确认选项
  • 在 CI 定时任务中无人值守地同步文档 ——此时不能阻塞等待人工确认

本章结束时，这个助手具备三档行为：普通写入自动进行，删除暂停等待确认， 生产文档直接拒绝。而在 CI 场景下，同一套规则会以另一种方式运行： 把所有「需要确认」直接降级为「拒绝」，从而不会阻塞。

6.1三态决策

权限判定的输出是一个决策值。AgentScope Java 中最终决策只有三种：

决策含义后续行为
ALLOW允许执行工具立即执行，模型继续推理
DENY拒绝执行工具不执行，模型收到拒绝原因
ASK需要人工确认Agent 暂停，触发 HITL 流程
PASSTHROUGH 不是第四种最终决策

PermissionDecision 有四个静态工厂方法：allow(message)、deny(message)、ask(message)、passthrough(message)。前三个是最终决策，会直接决定工具是否执行。而 passthrough 表示工具自己不表态，把评估责任交回引擎，由引擎继续检查规则与模式。因此 PASSTHROUGH 只是判定过程中的一个中间结果，而不是第四种最终决策。

工厂方法返回的决策类型语义
allow(message)最终决策 ALLOW工具已确认安全，直接放行
deny(message)最终决策 DENY工具拒绝执行，message 作为原因
ask(message)最终决策 ASK暂停并请求人工确认，message 说明原因
passthrough(message)委派结果引擎继续评估规则与全局模式

把决策设计成三态而不是布尔值，是因为「我暂时不知道，交给人」这个状态必须存在。如果只有允许与拒绝两种取值，那么所有不确定的操作都只能二选一：要么全部放行从而失去防护，要么全部拒绝从而无法使用。ASK 让「先问一句」成为一等公民。

6.2三个决策组件

一次工具调用的权限判定会依次经过三个组件。它们不是并列的三套规则，而是一条有优先级的判定链。

组件位置作用
Built-in Checks工具内部ToolBase#checkPermissions(toolInput, context)，基于本次实际输入判定
RulesPermissionContextState静态规则，或用户接受 ASK 后由框架生成的 suggested rules
ModePermissionContextState全局默认策略，在没有任何规则命中时生效
工具调用即将执行 ① 工具自身的 checkPermissions(toolInput, context) │ ├─ ALLOW ──────────────→ 放行，流程结束 ├─ DENY ───────────────→ 拒绝，流程结束 ├─ ASK ────────────────→ 暂停，进入人工确认流程 └─ PASSTHROUGH ────────→ 继续 ↓ ② 规则匹配（PermissionRule 列表） │ ├─ 命中 DENY 规则 ─────→ 拒绝，流程结束 ├─ 命中 ALLOW 规则 ────→ 放行，流程结束 ├─ 命中 ASK 规则 ──────→ 暂停，进入人工确认流程 └─ 无规则命中 ─────────→ 继续 ↓ ③ 全局模式（PermissionMode） │ ├─ DEFAULT ────────→ ASK（默认最保守） ├─ ACCEPT_EDITS ─→ 工作目录内的文件操作放行，其余 ASK ├─ EXPLORE ──────→ 读取放行，所有写入与命令拒绝 ├─ BYPASS ───────→ 放行一切（DENY 与 ASK 规则除外） └─ DONT_ASK ─────→ ASK 降级为 DENY 无论走哪条分支，最终结果为 ASK 时Agent 都会暂停

这个顺序解释了几个容易困惑的现象。比如你在 BYPASS 模式下仍然会看到「需要确认」的提示——那说明命中了一条 ASK 规则，因为规则检查在模式之前。又比如工具返回 PASSTHROUGH 之后行为完全没有变化——因为它本来就表示「不表态，继续评估」。

把业务规则写进 Built-in Checks

前两章已经介绍过 checkPermissions。这里再强调一次它的特殊地位：这项检查不受模式与规则影响，也就是说它既不能被 BYPASS 跳过，也不能被一条 ALLOW 规则覆盖。因此凡是「必须禁止」的业务约束，都应该写在这里，而不是写进规则列表。

ProductionGuardTool.javajava
import io.agentscope.core.message.TextBlock;
import io.agentscope.core.message.ToolResultBlock;
import io.agentscope.core.permission.PermissionDecision;
import io.agentscope.core.tool.ToolBase;
import io.agentscope.core.tool.ToolCallParam;
import io.agentscope.core.tool.ToolExecutionContext;
import reactor.core.publisher.Mono;

import java.util.List;
import java.util.Map;

/**
 * 删除文档工具。生产环境的删除在代码层面直接拒绝，
 * 不依赖任何规则或模式，因此无法被 BYPASS 绕过。
 */
public class ProductionGuardTool extends ToolBase {

    public ProductionGuardTool() {
        super(ToolBase.builder()
                .name("delete_doc")
                .description("删除指定文档。此操作不可撤销。")
                .inputSchema(Map.of(
                        "type", "object",
                        "properties", Map.of(
                                "path", Map.of(
                                        "type", "string",
                                        "description", "文档相对路径，例如 docs/tmp/a.md")),
                        "required", List.of("path")))
                .readOnly(false)
                .concurrencySafe(false));
    }

    @Override
    public Mono<PermissionDecision> checkPermissions(
            Map<String, Object> toolInput,
            ToolExecutionContext context) {

        Object target = toolInput.get("path");
        if (target instanceof String s && s.startsWith("prod/")) {
            return Mono.just(PermissionDecision.deny(
                    "禁止删除生产环境文档：" + s));
        }
        return Mono.just(PermissionDecision.passthrough("交由规则与模式评估"));
    }

    @Override
    public Mono<ToolResultBlock> callAsync(ToolCallParam param) {
        String path = (String) param.getInput().get("path");
        return Mono.just(ToolResultBlock.builder()
                .id(param.getId())
                .name(getName())
                .output(List.of(TextBlock.builder()
                        .text("已删除文档：" + path)
                        .build()))
                .build());
    }
}
checkPermissions 的第二个参数

该参数的类型在不同版本中存在差异：部分版本写作 io.agentscope.core.permission.PermissionContextState，本章代码按官方示例写作 ToolExecutionContext。请以你所安装版本的 API 参考为准，两种写法的用法都是「读取本次执行的上下文」。

Suggested Rules：从一次确认变成长期规则

被拒绝或者被拒绝确认的操作，如果每次都重新问一遍，体验会很差。AgentScope 的做法是：当一次 ASK 被用户接受后，框架可以根据这次调用的输入生成 suggested rules，你确认后把它们加入 PermissionContextState，于是同类操作在后续会话中不再询问。

SuggestedRules.javajava
import io.agentscope.core.event.ConfirmResult;
import io.agentscope.core.message.ToolUseBlock;

/**
 * 用户点了「允许，并且以后不要再问」之后，
 * 把框架生成的建议规则一并保存。
 */
public class SuggestedRules {

    public static ConfirmResult build(ToolUseBlock toolCall, boolean accepted) {
        return new ConfirmResult(
                /* confirmed = */ accepted,
                /* toolCall  = */ toolCall,
                // rules 为 null 时表示不生成建议规则
                /* rules     = */ toolCall.getSuggestedRules());
    }
}

第二、三个参数分别是「是否确认」与「本次调用的工具块」，第三个参数携带建议规则。因此规则既可以来自配置文件，也可以来自用户的一次点击，这是权限系统与 HITL 之间最重要的连接点。

6.3PermissionMode：五档全局策略

模式是判定链的最后一环，也是最粗粒度的一层。它回答的问题是：当没有任何规则命中时，默认怎么办。

模式行为用例
DEFAULT所有操作都需要显式规则或用户确认最安全的默认，推荐作为起点
ACCEPT_EDITS自动允许工作目录内的文件操作用户在场时主动开发
EXPLORE只读：允许读取，拒绝所有写入和命令代码探索、方案规划
BYPASS允许一切，但 DENY 与 ASK 规则仍然生效完全受信任的沙箱环境
DONT_ASK将 ASK 降级为 DENY无人值守任务、定时作业、CI

模式通过 ReActAgent 构造器的 permissionContext(...) 设置：

ModeSetup.javajava
import io.agentscope.core.ReActAgent;
import io.agentscope.core.permission.PermissionContextState;
import io.agentscope.core.permission.PermissionMode;

public class ModeSetup {

    public static ReActAgent build(String modelName) {
        PermissionContextState permCtx = PermissionContextState.builder()
                .mode(PermissionMode.DEFAULT)
                .build();

        return ReActAgent.builder()
                .name("my_agent")
                .sysPrompt(""""
                        你是一个知识库管理助手。
                        新增与修改文档可以直接执行。
                        删除任何文档前必须获得人工确认。
                        生产环境的文档禁止删除。
                        """")
                .model(modelName)
                .permissionContext(permCtx)
                .build();
    }
}

ACCEPT_EDITS 需要额外声明工作目录，否则框架无法判断某个路径是否在允许范围内。

AcceptEditsSetup.javajava
import io.agentscope.core.permission.AdditionalWorkingDirectory;
import io.agentscope.core.permission.PermissionContextState;
import io.agentscope.core.permission.PermissionMode;

PermissionContextState permCtx = PermissionContextState.builder()
        .mode(PermissionMode.ACCEPT_EDITS)
        // 第二个参数为来源标识，与 PermissionRule#source 同义
        .addWorkingDirectory("/my/project",
                new AdditionalWorkingDirectory("/my/project", "userSettings"))
        .build();
模式不是互斥的开关

模式只在一轮判定中生效一次，它不等于「关闭权限系统」。把模式设为 BYPASS 之后，DENY 规则依然会拒绝，危险路径检查依然会触发 ASK，工具内部的 checkPermissions 依然会拒绝。因此模式是「默认怎么办」，而不是「一律怎么办」。

6.4PermissionRule 的语义

PermissionRule 是一个 record，包含四个字段。其中最容易被误解的是第二个字段。

字段类型是否必填说明
toolNameString必填规则适用的工具名
ruleContentString可为 null不是全局表达式，由工具自身的 matchRule() 解释；null 表示匹配该工具的所有调用
behaviorPermissionBehavior必填ALLOW / DENY / ASK / PASSTHROUGH
sourceString必填规则来源，例如 "userSettings" / "projectSettings" / "session" / "suggested"
ruleContent 由工具自己解释

这是本章最容易被写错的一点。ruleContent 不是一个由框架统一求值的表达式语言。框架把规则内容和本次工具输入一起交给工具的 matchRule(ruleContent, toolInput) 方法，由工具自己决定是否匹配。因此不同工具的 ruleContent 语法可以完全不同：文件类工具可能写成路径前缀，数据库工具可能写成表名。如果你想跨工具统一过滤条件，需要自己在工具里实现 matchRule()。

ruleContent 为 null 时的语义是「匹配该工具的所有调用」，这在配置里非常常用：「不管参数是什么，delete_doc 都要问我」。

三种行为各有一条对应的配置方法，参数是「规则名 + 规则对象」：

RuleSetup.javajava
import io.agentscope.core.permission.PermissionBehavior;
import io.agentscope.core.permission.PermissionContextState;
import io.agentscope.core.permission.PermissionMode;
import io.agentscope.core.permission.PermissionRule;

PermissionContextState permCtx = PermissionContextState.builder()
        .mode(PermissionMode.DEFAULT)
        // 该工具的任意调用都放行
        .addAllowRule("safe_read", new PermissionRule(
                "safe_read", null, PermissionBehavior.ALLOW, "userSettings"))
        // 该工具的任意调用都需要人工确认
        .addAskRule("dangerous_delete", new PermissionRule(
                "dangerous_delete", null, PermissionBehavior.ASK, "userSettings"))
        // 该工具的任意调用都拒绝
        .addDenyRule("drop_table", new PermissionRule(
                "drop_table", null, PermissionBehavior.DENY, "userSettings"))
        .build();

也可以直接使用 PermissionBehavior.PASSTHROUGH 构造规则，效果与工具返回 passthrough() 一致：不在这一层做决定，继续走模式判定。

一个 ruleContent 非 null 的例子：

RuleWithContent.javajava
import io.agentscope.core.permission.PermissionBehavior;
import io.agentscope.core.permission.PermissionRule;

// 仅对 staging 环境放行，ruleContent 的含义由 deploy 工具的
// matchRule() 解释：它会取出 input 里的 environment 字段做比较
PermissionRule stagingOnly = new PermissionRule(
        "deploy",
        "staging",
        PermissionBehavior.ALLOW,
        "projectSettings");

两条不可绕过的红线

权限判定链上有两处无论模式如何都会生效的检查。这两点决定了安全策略的可靠下界。

DENY 规则不能被 BYPASS 绕过

把模式设为 BYPASS 之后，命中 DENY 规则的调用依然会被拒绝。因此真正的禁止项应该写成 DENY 规则，而不是依赖工具内部的检查或者指望模式配置。

危险路径检查不能被 BYPASS 绕过

框架内置的敏感文件路径检查独立于模式与规则。即使在 BYPASS 模式下，命中敏感路径的调用依然会触发 ASK。

ASK 规则在 BYPASS 下同样生效

BYPASS 只绕过「没有规则命中时的默认行为」，它不会覆盖已经写下的规则。所以如果你在 BYPASS 模式下仍然看到确认提示，说明确实有一条 ASK 规则或一项危险路径检查命中了，这属于预期行为。

6.5危险路径保护

框架维护了一份敏感路径清单，存放在常量类 ToolDangerousPathConstants 中（具体包路径请以你所安装版本的 API 参考为准）。一旦工具调用的输入涉及这些路径，会直接触发 ASK。自定义工具可以通过 @Tool 的 dangerousFiles 与 dangerousDirectories 属性追加自己的条目。

类别默认覆盖的路径
Shell 配置.bashrc .zshrc .bash_profile .profile
Git 配置.gitconfig .gitmodules
SSH.ssh/config .ssh/authorized_keys id_rsa id_ed25519
凭据文件.env .env.local .npmrc .pypirc .aws/credentials
敏感目录.git/ .ssh/ .aws/ .kube/

这份清单的设计出发点很朴素：这些文件一旦被改写，攻击者就能在之后的所有会话中获得持久权限，因此必须在改动发生的当场就让人知道。注意 .env 与 .git/ 都在其中，这意味着「让智能体写一个环境变量文件」这类看起来无害的操作同样会触发确认。

DangerousPathTool.javajava
import io.agentscope.core.tool.Tool;
import io.agentscope.core.tool.ToolParam;

public class DangerousPathTool {

    @Tool(
            name = "write_file",
            description = "写入工作目录内的文件。",
            readOnly = false,
            // 追加本工具特有的敏感路径，与框架内置清单合并生效
            dangerousFiles = {"/my/project/secrets/service.key"},
            dangerousDirectories = {"/my/project/deploy/"})
    public String writeFile(
            @ToolParam(name = "path", description = "文件路径")
            String path,
            @ToolParam(name = "content", description = "文件内容")
            String content) {
        return "已写入 " + path;
    }
}

6.6动手：完整策略配置

先把本章场景的策略写出来。目标有三个：普通读取与写入自动进行，删除需要确认，生产目录的删除一律拒绝。注意最后一条我们用两条机制各实现一次：工具内部检查一次（见 6.2 节），再叠加一条 DENY 规则作为第二道保障。

PermissionSetup.javajava
package com.example.kb;

import io.agentscope.core.ReActAgent;
import io.agentscope.core.permission.AdditionalWorkingDirectory;
import io.agentscope.core.permission.PermissionBehavior;
import io.agentscope.core.permission.PermissionContextState;
import io.agentscope.core.permission.PermissionMode;
import io.agentscope.core.permission.PermissionRule;
import io.agentscope.core.tool.Toolkit;

/**
 * 知识库管理助手的权限配置。
 * 目标：新增与修改自动放行，删除需要人工确认，生产文档禁止删除。
 */
public class PermissionSetup {

    /** 规则来源标识：来自用户级设置。 */
    private static final String USER = "userSettings";

    public static PermissionContextState buildContext() {
        return PermissionContextState.builder()
                // 未命中任何规则时的默认策略
                .mode(PermissionMode.DEFAULT)

                // ---- 放行：只读类工具，ruleContent 为 null 表示匹配全部调用 ----
                .addAllowRule("search_docs", new PermissionRule(
                        "search_docs", null, PermissionBehavior.ALLOW, USER))
                .addAllowRule("read_doc", new PermissionRule(
                        "read_doc", null, PermissionBehavior.ALLOW, USER))

                // ---- 放行：写入类工具 ----
                .addAllowRule("create_doc", new PermissionRule(
                        "create_doc", null, PermissionBehavior.ALLOW, USER))
                .addAllowRule("update_doc", new PermissionRule(
                        "update_doc", null, PermissionBehavior.ALLOW, USER))

                // ---- 询问：删除类操作一律需要人工确认 ----
                .addAskRule("delete_doc", new PermissionRule(
                        "delete_doc", null, PermissionBehavior.ASK, USER))

                // ---- 拒绝：不可撤销且影响面过大的操作 ----
                .addDenyRule("drop_table", new PermissionRule(
                        "drop_table", null, PermissionBehavior.DENY, USER))
                .addDenyRule("delete_doc", new PermissionRule(
                        "delete_doc", "prod/", PermissionBehavior.DENY, USER))

                // ---- 工作目录：ACCEPT_EDITS 模式需要，DEFAULT 模式下同样建议声明 ----
                .addWorkingDirectory("/my/project",
                        new AdditionalWorkingDirectory("/my/project", USER))
                .build();
    }

    public static ReActAgent buildAgent(String modelName) {
        Toolkit toolkit = KnowledgeTools.create();

        return ReActAgent.builder()
                .name("kb-manager")
                .sysPrompt("""
                        你是一个知识库管理助手。
                        新增与修改文档可以直接执行。
                        删除文档前必须获得用户确认。
                        docs/prod/ 下的文档禁止删除，也不要尝试用其他方式绕过。
                        """)
                .model(modelName)
                .toolkit(toolkit)
                .permissionContext(buildContext())
                .build();
    }

    // 占位类，实际使用时替换为本项目的工具实现
    static class KnowledgeTools {
        static Toolkit create() {
            return new Toolkit();
        }
    }
}

这份配置里有三处值得说明：

  • delete_doc 上同时存在 ASK 与 DENY 两条规则。规则按 DENY 优先的顺序评估，因此生产路径的删除在规则层就已被拒绝，不会走到 ASK 那一层，也就不会弹确认框。
  • 第二条 delete_doc 规则的 ruleContent 是 "prod/"。它的含义由 delete_doc 工具自己的 matchRule() 决定——前提是该工具实现了这个方法；如果没有实现，那么非 null 的 ruleContent 需要你在工具侧补充匹配逻辑。
  • 工具内部的 checkPermissions 已经在 6.2 节拒绝了 prod/ 前缀。这里再加一条 DENY 规则，是为了让「禁止」这件事在配置层面可见、可审计。
为什么 DENY 要写在多处

因为这三处机制的执行时机不同：工具检查在代码里，DENY 规则在配置里，危险路径清单在框架里。同一条安全约束在多处出现并不冗余，因为任意一处失效时其余各处仍然生效。代价是维护成本，因此建议把「禁止项」单独列成一份清单来管理。

6.7动手：Blocking API 的 HITL

HITL 的完整流程一共有八步。前四步由框架完成，后四步由你的应用完成。

Agent 暂停工具执行

判定结果为 ASK 时，Agent 在执行工具之前挂起，返回一个 Mono 序列但不完成。

返回 Msg，GenerateReason 为 PERMISSION_ASKING

调用方通过 result.getGenerateReason() 判断发生了暂停，而不是靠猜测消息内容。

Msg 中包含状态为ASKING 的 ToolUseBlock

每个待执行工具对应一个 ToolUseBlock，其 getState() 为 ToolCallState.ASKING。

调用方提取待执行工具

从 result.getContent() 中筛选出这些块，得到工具名与完整输入。

展示给用户

命令行、Web 页面或 IM 消息均可。本章用一个简单的控制台提示函数代替。

用户确认或拒绝

得到一个布尔值。生产系统中这一步通常还需要记录确认人与时间戳。

构造 ConfirmResult

每个待执行工具对应一个 ConfirmResult。

通过恢复消息的 metadata 传回

键为 Msg.METADATA_CONFIRM_RESULTS，值为 List<ConfirmResult>，随一条普通用户消息一起交回 Agent。

BlockingHitlDemo.javajava
package com.example.kb;

import io.agentscope.core.ReActAgent;
import io.agentscope.core.event.ConfirmResult;
import io.agentscope.core.message.GenerateReason;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.MsgRole;
import io.agentscope.core.message.ToolCallState;
import io.agentscope.core.message.ToolUseBlock;
import io.agentscope.core.message.UserMessage;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Scanner;

public class BlockingHitlDemo {

    public static void main(String[] args) {
        ReActAgent agent = PermissionSetup.buildAgent("dashscope:qwen-plus");

        // call 有Msg 与 List<Msg> 两种入参形式
        Msg result = agent.call(new UserMessage("删除 /tmp/important.txt")).block();

        if (result != null && result.getGenerateReason() == GenerateReason.PERMISSION_ASKING) {

            // 取出状态为 ASKING 的工具调用
            List<ToolUseBlock> askingTools = result.getContent().stream()
                    .filter(b -> b instanceof ToolUseBlock)
                    .map(ToolUseBlock.class::cast)
                    .filter(t -> t.getState() == ToolCallState.ASKING)
                    .toList();

            askingTools.forEach(t -> System.out.println(
                    "待执行工具：" + t.getName() + " 参数：" + t.getInput()));

            boolean approved = askUser();

            // 一个待执行工具对应一个确认结果
            List<ConfirmResult> confirmResults = new ArrayList<>();
            for (ToolUseBlock t : askingTools) {
                confirmResults.add(new ConfirmResult(approved, t));
            }

            // 确认结果放在恢复消息的 metadata 里
            Map<String, Object> meta = new HashMap<>();
            meta.put(Msg.METADATA_CONFIRM_RESULTS, confirmResults);

            Msg resumeMsg = Msg.builder()
                    .name("user")
                    .role(MsgRole.USER)
                    .textContent(approved ? "approved" : "denied")
                    .metadata(meta)
                    .build();

            Msg finalResult = agent.call(List.of(resumeMsg)).block();
            System.out.println(finalResult.getTextContent());
        } else {
            // 没有发生暂停，直接输出
            System.out.println(result.getTextContent());
        }
    }

    /** 真实项目中替换为前端的确认对话框 */
    private static boolean askUser() {
        Scanner scanner = new Scanner(System.in);
        System.out.print("是否允许执行上述操作？(y/N) ");
        String line = scanner.nextLine().trim();
        return "y".equalsIgnoreCase(line) || "yes".equalsIgnoreCase(line);
    }
}
输出示例text
用户：删除 /tmp/important.txt
待执行工具：delete_doc 参数：{path=/tmp/important.txt}
是否允许执行上述操作？(y/N) y
已删除文档：/tmp/important.txt
恢复消息的文本内容要明确表态

textContent 会被模型看到，因此应当写成 "approved" 或 "denied" 这样明确的字样，不要留空。如果留空，模型在下一轮推理时只能看到工具结果而看不到人的态度，后续推理的质量会明显下降。

把确认结果放在 metadata 而不是拼接进文本，是为了让结构化数据与自然语言分离：框架读取 metadata 拿到精确的确认状态，模型读取文本理解人的意图。两者职责不同，因此不要合并。

6.8动手：Streaming API 的 HITL

事件驱动的方式更适合交互式界面。关键差别在于：框架直接发出 RequireUserConfirmEvent，你从事件的 getToolCalls() 里取待确认工具即可，不需要像Blocking 那样从 Msg 的内容块里筛选。此外事件还带一个 replyId，用于把确认结果与本次询问关联起来。

StreamingHitlDemo.javajava
package com.example.kb;

import io.agentscope.core.ReActAgent;
import io.agentscope.core.event.AgentEventType;
import io.agentscope.core.event.ConfirmResult;
import io.agentscope.core.event.RequireUserConfirmEvent;
import io.agentscope.core.event.TextBlockDeltaEvent;
import io.agentscope.core.event.UserConfirmResultEvent;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.MsgRole;
import io.agentscope.core.message.ToolUseBlock;
import io.agentscope.core.message.UserMessage;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Scanner;
import java.util.concurrent.atomic.AtomicReference;

public class StreamingHitlDemo {

    public static void main(String[] args) {
        ReActAgent agent = PermissionSetup.buildAgent("dashscope:qwen-plus");

        // replyId 把确认请求与确认结果关联起来
        AtomicReference<String> pendingReplyId = new AtomicReference<>();
        List<ToolUseBlock> pendingTools = new ArrayList<>();

        agent.streamEvents(List.of(new UserMessage("清理过期文档")))
                .doOnNext(event -> {
                    if (event instanceof RequireUserConfirmEvent ask) {
                        // 事件驱动：直接取待确认工具，无需解析 Msg
                        ask.getToolCalls().forEach(pendingTools::add);
                        pendingReplyId.set(ask.getReplyId());
                        ask.getToolCalls().forEach(t -> System.out.println(
                                "\n待确认：" + t.getName() + " 参数：" + t.getInput()));
                    } else if (event.getType() == AgentEventType.TEXT_BLOCK_DELTA) {
                        System.out.print(((TextBlockDeltaEvent) event).getDelta());
                    }
                })
                .blockLast();

        if (pendingTools.isEmpty()) {
            return;   //本次没有触发确认，事件流已结束
        }

        boolean approved = askUser();

        List<ConfirmResult> confirmResults = new ArrayList<>();
        for (ToolUseBlock t : pendingTools) {
            confirmResults.add(new ConfirmResult(approved, t));
        }

        Map<String, Object> meta = new HashMap<>();
        meta.put(Msg.METADATA_CONFIRM_RESULTS, confirmResults);

        Msg resumeMsg = Msg.builder()
                .name("user")
                .role(MsgRole.USER)
                .textContent(approved ? "approved" : "denied")
                .metadata(meta)
                .build();

        agent.streamEvents(List.of(resumeMsg))
                .doOnNext(event -> {
                    if (event instanceof UserConfirmResultEvent ack) {
                        // 恢复调用会先发出确认结果事件，其 replyId 与之前一致
                        System.out.println("\n确认已提交 replyId="
                                + ack.getReplyId() + " 待处理数=" + pendingTools.size());
                    } else if (event.getType() == AgentEventType.TEXT_BLOCK_DELTA) {
                        System.out.print(((TextBlockDeltaEvent) event).getDelta());
                    }
                })
                .blockLast();
    }

    private static boolean askUser() {
        Scanner scanner = new Scanner(System.in);
        System.out.print("是否允许执行上述操作？(y/N) ");
        String line = scanner.nextLine().trim();
        return "y".equalsIgnoreCase(line) || "yes".equalsIgnoreCase(line);
    }
}

事件顺序值得留意：

事件顺序text
TextBlockDeltaEvent   delta="我先"
TextBlockDeltaEvent   delta="查看有哪些文档可以清理"
RequireUserConfirmEvent  replyId=r-7  toolCalls=[delete_doc]
  ← 此处事件流结束，Agent 处于暂停状态
（用户确认，随后调用恢复流程）
UserConfirmResultEvent   replyId=r-7
ToolCallStartEvent       delete_doc
ToolResultEndEvent       SUCCESS
TextBlockDeltaEvent   delta="已清理 2 份过期文档。"

可以看到 UserConfirmResultEvent 的 replyId 与之前的 RequireUserConfirmEvent 完全一致。在并发场景下，可能有多轮确认交错出现，因此必须用 replyId 而不是时间顺序来配对。

恢复调用也可以用 call()

确认结果通过消息 metadata 传递，因此恢复阶段用 agent.call(...) 或 agent.streamEvents(...) 都可以。区别只在于：用 call() 时拿不到 UserConfirmResultEvent，如果你的界面需要显示「确认已提交」这类状态，那么请用 streamEvents()。

6.9动手：外部执行工具

有些操作根本不应该由智能体所在进程执行：需要走审批流程的发布操作、需要 DBA 到机房执行的操作、或者需要用户在浏览器里点击确认的操作。这类工具通过 externalTool(true) 声明，Agent 发出 RequireExternalExecutionEvent 之后暂停，由你的系统实际执行，再将结果返回给框架。

声明外部执行工具

构造时设置 externalTool(true)，此时不需要实现 callAsync()。

Agent 发出 RequireExternalExecutionEvent 并暂停

事件中包含待执行的工具调用。

外部系统实际执行

你的应用把工具调用转成实际动作：调审批接口、转成工单，或者干脆等一个人来动手。

把结果包装为 ToolResultBlock

每个工具调用对应一个结果块，其中 id 与 name 必须与原调用一致。

恢复 Agent

结果列表通过恢复消息的 metadata 传回。

Agent 发出 ExternalExecutionResultEvent 后继续推理

该事件的 getReplyId() 与之前的 RequireExternalExecutionEvent 一致。

ExternalToolDemo.javajava
package com.example.kb;

import io.agentscope.core.ReActAgent;
import io.agentscope.core.event.RequireExternalExecutionEvent;
import io.agentscope.core.event.ExternalExecutionResultEvent;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.MsgRole;
import io.agentscope.core.message.TextBlock;
import io.agentscope.core.message.ToolResultBlock;
import io.agentscope.core.message.ToolResultState;
import io.agentscope.core.message.ToolUseBlock;
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.permission.AdditionalWorkingDirectory;
import io.agentscope.core.permission.PermissionContextState;
import io.agentscope.core.permission.PermissionMode;
import io.agentscope.core.tool.ToolBase;
import io.agentscope.core.tool.ToolCallParam;
import io.agentscope.core.tool.Toolkit;
import reactor.core.publisher.Mono;

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class ExternalToolDemo {

    /** 外部执行工具：只声明参数，不实现 callAsync */
    public static class PublishDocTool extends ToolBase {

        public PublishDocTool() {
            super(ToolBase.builder()
                    .name("publish_doc")
                    .description("把文档发布到对外官网，需要走发布审批流程。")
                    .inputSchema(Map.of(
                            "type", "object",
                            "properties", Map.of(
                                    "path", Map.of("type", "string",
                                            "description", "文档路径"),
                                    "site", Map.of("type", "string",
                                            "description", "目标站点")),
                            "required", List.of("path", "site")))
                    .readOnly(false)
                    .concurrencySafe(false)
                    // 执行权交给外部系统
                    .externalTool(true));
        }
    }

    public static void main(String[] args) {
        Toolkit toolkit = new Toolkit();
        toolkit.registerTool(new PublishDocTool());

        PermissionContextState permCtx = PermissionContextState.builder()
                .mode(PermissionMode.ACCEPT_EDITS)
                .addWorkingDirectory("/my/project",
                        new AdditionalWorkingDirectory("/my/project", "userSettings"))
                .build();

        ReActAgent agent = ReActAgent.builder()
                .name("kb-publisher")
                .sysPrompt("""
                        你是一个文档发布助手。
                        发布文档必须走发布系统，不要自己写文件。
                        """)
                .model("dashscope:qwen-plus")
                .toolkit(toolkit)
                .permissionContext(permCtx)
                .build();

        List<ToolUseBlock> externalCalls = new ArrayList<>();

        agent.streamEvents(List.of(new UserMessage("把 API 文档发布到官网")))
                .doOnNext(event -> {
                    if (event instanceof RequireExternalExecutionEvent ext) {
                        ext.getToolCalls().forEach(externalCalls::add);
                    }
                })
                .blockLast();

        if (externalCalls.isEmpty()) {
            return;
        }

        // ---- 外部系统实际执行，逐个汇总输出 ----
        List<ToolResultBlock> executionResults = new ArrayList<>();
        for (ToolUseBlock tc : externalCalls) {
            String output = callExternalPublisher(tc);
            executionResults.add(ToolResultBlock.builder()
                    .id(tc.getId())
                    .name(tc.getName())
                    .output(List.of(TextBlock.builder().text(output).build()))
                    .state(ToolResultState.SUCCESS)
                    .build());
        }

        Map<String, Object> meta = new HashMap<>();
        // 说明：外部执行结果在 metadata 中的键名请以当前版本的 API 参考为准
        meta.put("tool_execution_results", executionResults);

        Msg resumeMsg = Msg.builder()
                .name("user")
                .role(MsgRole.USER)
                .textContent("外部执行已完成")
                .metadata(meta)
                .build();

        agent.streamEvents(List.of(resumeMsg))
                .doOnNext(event -> {
                    if (event instanceof ExternalExecutionResultEvent done) {
                        System.out.println("外部执行结果已接收 replyId="
                                + done.getReplyId());
                    }
                })
                .blockLast();
    }

    /** 真实的发布系统调用：这里返回一个占位结果 */
    private static String callExternalPublisher(ToolUseBlock tc) {
        return "已提交发布工单，内容：" + tc.getInput();
    }
}

与 HITL 的差别值得强调：HITL 是人做决策，智能体执行；外部执行是人做决策，外部系统执行。因此外部执行工具不需要实现 callAsync()，而 HITL 的工具必须实现。

6.10动手：无人值守与提前停止

DONT_ASK：把询问变成拒绝

CI 与定时任务里没有人可以做确认，因此等待确认等于任务无法完成。PermissionMode.DONT_ASK 把所有 ASK 自动降级为 DENY，于是判定不再需要等待，模型会立刻看到「被拒绝」并调整方案。因此 DONT_ASK 不会让任务卡住，但是它也不会让原本会被允许的操作通过——这一点常被误解。

UnattendedDemo.javajava
package com.example.kb;

import io.agentscope.core.ReActAgent;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.permission.PermissionBehavior;
import io.agentscope.core.permission.PermissionContextState;
import io.agentscope.core.permission.PermissionMode;
import io.agentscope.core.permission.PermissionRule;
import io.agentscope.core.tool.Toolkit;

import java.util.List;

public class UnattendedDemo {

    public static void main(String[] args) {
        PermissionContextState permCtx = PermissionContextState.builder()
                .mode(PermissionMode.DONT_ASK)
                // 无人值守场景必须显式放行，否则一切操作都会被拒绝
                .addAllowRule("search_docs", new PermissionRule(
                        "search_docs", null, PermissionBehavior.ALLOW, "projectSettings"))
                .addAllowRule("create_doc", new PermissionRule(
                        "create_doc", null, PermissionBehavior.ALLOW, "projectSettings"))
                .addAllowRule("delete_doc", new PermissionRule(
                        "delete_doc", null, PermissionBehavior.DENY, "projectSettings"))
                .build();

        ReActAgent agent = ReActAgent.builder()
                .name("ci-doc-bot")
                .sysPrompt("""
                        你是一个 CI 文档同步助手。
                        被拒绝的操作不要重试，改用其他方式完成任务。
                        """)
                .model("dashscope:qwen-plus")
                .toolkit(KnowledgeTools.create())
                .permissionContext(permCtx)
                .build();

        // 全程不会暂停，模型直接拿到拒绝结果并自行调整
        Msg report = agent.call(
                List.of(new UserMessage("同步 docs/ 目录到知识库，删除已失效的文档")))
                .block();
        System.out.println(report.getTextContent());
    }

    // 占位类，实际使用时替换为本项目的工具实现
    static class KnowledgeTools {
        static Toolkit create() {
            return new Toolkit();
        }
    }
}
DONT_ASK 下必须补充 ALLOW 规则

因为 ASK 会被降级为 DENY，所以那些你希望 Agent 正常执行的操作必须显式写成 ALLOW 规则。一个常见的错误是只设置了模式而没有添加规则，结果所有工具调用都被拒绝。因此 DONT_ASK 的正确用法是「显式列出允许清单」，而不是「先放开再说」。

全部工具被拒绝时让 Agent 停止

默认行为偏向向后兼容：当一轮推理中所有工具调用都被拒绝时，Agent 不会停止，而是继续进入下一次推理迭代，模型只看到 Permission denied by user 这样的工具结果。这样设计是为了兼容那些依赖后续推理来调整策略的场景，但是对无人值守任务来说，继续推理通常没有意义，而且会消耗 token。

如果需要立即停止，可以在 onActing 扩展点监听 AllToolsDeniedEvent，紧随其后发出一个 RequestStopEvent。此时 getGenerateReason() 会返回 ALL_TOOLS_DENIED。

StopOnAllDeniedMiddleware.javajava
package com.example.kb;

import io.agentscope.core.event.AllToolsDeniedEvent;
import io.agentscope.core.event.RequestStopEvent;
import io.agentscope.core.message.GenerateReason;
import io.agentscope.core.middleware.AgentMiddleware;
import io.agentscope.core.middleware.MiddlewareContext;
import reactor.core.publisher.Flux;

import java.util.function.Function;

/**
 * 全部工具被拒绝时立即停止 Agent。
 * 适用于无人值守任务，避免无意义的持续推理。
 */
public class StopOnAllDeniedMiddleware implements AgentMiddleware {

    /**
     * 说明：方法签名以第 07 章介绍的 AgentMiddleware 接口为准，
     * 这里按 next.apply(input) 的函数式形态书写。
     */
    @Override
    public Flux<Object> onActing(MiddlewareContext context,
                                 Function<Object, Flux<Object>> next) {
        return next.apply(context.getInput()).flatMap(event -> {
            if (event instanceof AllToolsDeniedEvent) {
                // 先转发原事件，再发出停止请求，顺序不能颠倒
                return Flux.just(event,
                        new RequestStopEvent("All tools denied by user",
                                GenerateReason.ALL_TOOLS_DENIED));
            }
            return Flux.just(event);
        });
    }
}

顺序是这段代码的关键：

  • 先 Flux.just(event, ...) 把 AllToolsDeniedEvent 转发出去，这样上层仍能知道发生过什么。
  • 紧接着发出 RequestStopEvent，Agent 随即停止。
  • 如果顺序颠倒，停止请求会在 AllToolsDeniedEvent 之前被消费，上层将收不到拒绝事件。

受信任沙箱中阻止危险命令BYPASS为不可撤销命令添加 DENY 规则（drop_table、force_push）；其余操作全部放行以换取效率
完整策略分层ACCEPT_EDITS工具内检查业务红线 + DENY 规则兜底禁止项 + ASK 规则保留需要人确认的操作 + 声明工作目录

import io.agentscope.core.permission.PermissionBehavior;
import io.agentscope.core.permission.PermissionContextState;
import io.agentscope.core.permission.PermissionMode;
import io.agentscope.core.permission.PermissionRule;

// ===== 配方二：无人值守自动化 =====
// DONT_ASK 下所有 ASK 变DENY，因此必须显式放行必需工具
PermissionContextState unattended = PermissionContextState.builder()
        .mode(PermissionMode.DONT_ASK)
        // ruleContent "staging" 由 deploy 工具自己解释：只允许 staging 环境
        .addAllowRule("deploy", new PermissionRule(
                "deploy", "staging", PermissionBehavior.ALLOW, "project"))
        // 不限定规则内容，表示 git_commit 的任意调用都放行
        .addAllowRule("git_commit", new PermissionRule(
                "git_commit", null, PermissionBehavior.ALLOW, "project"))
        .build();

// ===== 配方三：受信任沙箱中阻止危险命令 =====
PermissionContextState sandbox = PermissionContextState.builder()
        .mode(PermissionMode.BYPASS)
        // BYPASS 不覆盖 DENY 规则，这两条始终生效
        .addDenyRule("drop_table", new PermissionRule(
                "drop_table", null, PermissionBehavior.DENY, "project"))
        .addDenyRule("force_push", new PermissionRule(
                "force_push", null, PermissionBehavior.DENY, "project"))
        .build();

// ===== 配方四：完整策略分层 =====
// 危险文件删除由 delete_doc 的 checkPermissions 拒绝；
// 其余删除由ASK 规则请求确认；
// 数据库与强推由 DENY 规则兜底；
// 工作目录内的编辑由 ACCEPT_EDITS 放行。
PermissionContextState layered = PermissionContextState.builder()
        .mode(PermissionMode.ACCEPT_EDITS)
        .addWorkingDirectory("/my/project",
                new AdditionalWorkingDirectory("/my/project", "projectSettings"))
        .addAskRule("delete_doc", new PermissionRule(
                "delete_doc", null, PermissionBehavior.ASK, "project"))
        .addDenyRule("drop_table", new PermissionRule(
                "drop_table", null, PermissionBehavior.DENY, "project"))
        .addDenyRule("force_push", new PermissionRule(
                "force_push", null, PermissionBehavior.DENY, "project"))
        .build();
配方三为什么用 BYPASS

在完全受信任的沙箱里，每次文件写入都弹确认框会严重影响效率。把模式设为 BYPASS 之后，只有显式写下的 DENY 规则与框架内置的危险路径检查会生效。因此使用 BYPASS 的前提是：你能接受「除禁止项之外的一切操作都不再询问」。如果不确定，就用 ACCEPT_EDITS。

6.12Blocking 与 Streaming 对比

call()（Blocking）streamEvents()
获取待处理工具从 Msg 中筛选 state == ASKING 的 ToolUseBlock直接从 RequireUserConfirmEvent.getToolCalls() 读取
暂停信号getGenerateReason() == PERMISSION_ASKING收到 RequireUserConfirmEvent 事件
恢复方式agent.call(List.of(resumeMsg))agent.streamEvents(List.of(resumeMsg))
确认回执无专门事件，从返回的 Msg 读取结果先发出 UserConfirmResultEvent，getReplyId() 与之前一致
并发安全单次调用内顺序处理，无并发问题可能出现多轮确认交错，必须用 replyId 配对
适用场景REST 接口、命令行工具、批处理任务WebSocket / SSE 推送、聊天界面、需要实时进度的场景

两套API 的确认消息构造方式完全相同，因为确认数据始终放在 Msg 的 metadata 里。因此从Blocking 迁移到 Streaming 时，需要改的只有「如何拿到待确认工具」这一处。

6.13权限设计清单

权限配置是最容易「看起来生效了、实际有漏洞」的部分。下面这份清单建议在每次上线前逐条确认。

上线前检查清单
  • 模式选择有依据：能说出为什么选 DEFAULT / ACCEPT_EDITS / EXPLORE / BYPASS / DONT_ASK，而不是随手挑一个。
  • 禁止项写成 DENY 规则：所有不可撤销的高危操作都有 DENY 规则或工具内检查，而不是只依赖模式。
  • 禁止项双写：关键禁止项同时存在于工具的 checkPermissions 与配置规则中。
  • 规则来源可追溯：每条规则的 source 填写正确，区分 userSettings / projectSettings / session / suggested。
  • 非 null 的 ruleContent 有实现：凡是设置了 ruleContent 的规则，其工具都实现了 matchRule()，否则该规则不会按预期匹配。
  • ASK 规则不会导致死锁：自动任务使用的配置中没有孤立无援的 ASK 规则，或者模式设为 DONT_ASK。
  • 恢复消息文本明确表态：textContent 写明 approved 或 denied，不留空。
  • 确认结果与replyId 配对：Streaming 场景下确认请求与确认结果按 replyId 关联，没有依赖事件到达顺序。
  • 拒绝后有明确出口：需要立即停止时配置了 StopOnAllDeniedMiddleware。
  • 确认动作可审计：确认人与确认时间被记录，满足合规要求。
  • 危险路径已评估：确认工具不会写到框架内置清单与自定义 dangerousFiles 覆盖的路径。
  • 有验证手段：有一组针对禁止项的用例，验证它们在各模式下都被拒绝。

清单中第 5 条与第 11 条最容易被忽略。前者是本章反复强调的 ruleContent 语义问题；后者是因为「在 DEFAULT 模式下验证通过」并不能说明在 BYPASS 模式下同样安全——因此验证用例应该在所有可能使用的模式下各执行一次。

6.14本章小结

  • 最终决策只有三态：ALLOW / DENY / ASK。PASSTHROUGH 是判定过程中的委派结果，不是第四种最终决策。
  • 判定链的顺序是：工具 checkPermissions → 规则 → PermissionMode。前一层给出最终决策时流程立即结束。
  • PermissionMode 是「无规则命中时的默认策略」，不是「一律怎么办」。因此 BYPASS 不会覆盖 DENY 规则。
  • ruleContent 由工具的 matchRule() 解释，不是全局表达式；为 null 时匹配该工具的全部调用。
  • 两条红线不可绕过：DENY 规则与框架内置的危险路径检查。因此真正的禁止项应该写成 DENY 规则。
  • HITL 八步流程中，前四步由框架完成，后四步由应用完成。确认数据通过 Msg.METADATA_CONFIRM_RESULTS 传递。
  • Blocking 需要从 Msg 中筛选 ASKING 块，Streaming 直接读事件；并发场景必须用 replyId 配对。
  • 全部工具被拒绝时默认继续推理，需要停止则在 onActing 中监听 AllToolsDeniedEvent 并发出 RequestStopEvent。
  • DONT_ASK 让任务不会阻塞，但必须配合显式 ALLOW 规则，否则所有调用都会被拒绝。
