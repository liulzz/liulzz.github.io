第 11 章

多智能体协作
把复杂任务分派给专职子智能体

前几章的助手始终是单体的：所有推理都在一个上下文里完成。本章引入子智能体编排： 知识助手可以把大文档分析、多语言翻译、代码审校分派给专职子智能体， 同步等待或后台执行，并按依赖关系组合结果。

预计耗时 40 分钟 产出 可并行编排的知识助手 关键 agent_spawn / workspaceMode

一个具体的瓶颈

假设张三给知识助手一个任务：「把这三份各 200 页的架构文档分别分析，把其中的接口变更点翻译成英文，顺便检查文档里引用的代码片段有没有过期 API，然后给我一份汇总报告。」

这个任务对单体智能体是不友好的。原因不在于任务本身太难，而在于三类工作互不相关又必须同时进行：文档分析需要大量原文，翻译只需要其中一小部分，代码审校需要精确的符号匹配。如果全部放进一个上下文，三份文档的原文会把窗口占满，而模型在面对 60 万字符时也已经无法稳定聚焦。

子智能体编排解决的正是这个问题。每个子智能体有自己的上下文，只把结论返回给父智能体，原文留在自己的会话里。因此本章的核心不是「多开几个 Agent」，而是决定什么时候分派、分派给谁、怎么等、怎么合并。

场景

本章场景

把知识助手升级为可编排的协调者：

  • 为三类专职任务各声明一个子智能体：文档分析、多语言翻译、代码审校
  • 子智能体的指令以文件形式保存，可以纳入 Git 版本管理
  • 短任务同步等待，长任务后台执行并在完成后自动回推
  • 无依赖的子任务并行执行，有依赖的按顺序合并
  • 父智能体的事件流按 source 区分父子，前端可以分别渲染

11.1先讲理论：子智能体编排

为什么需要子智能体

子智能体不是「更小的智能体」，它解决的是三个具体问题。理解了这一点，你就知道什么时候该用、什么时候不该用。

动机解决的问题单体做法的问题子智能体做法
上下文隔离子任务只需要一小部分输入，不需要父智能体的全部上下文把 200 页文档读进主上下文，窗口被占满，后续推理质量下降子智能体读自己的文件，只把结论作为 tool result 返回
并行执行多个无依赖子任务同时进行一个上下文里只能一次做一个任务，总耗时是各步之和同一 reasoning turn 发出多个 spawn，缺省并行执行，形成 fan-out / fan-in barrier
职责分离不同子任务用不同的系统提示词、模型与工具白名单一段提示词里混杂审校规则与翻译规则，模型难以兼顾每个子智能体有独立的 AGENTS 内容与 tools allowlist
成本可控简单子任务用轻量模型所有步骤都走同一个大模型为子智能体单独指定 model 与 steps
不要为了拆而拆

子智能体有额外成本：每次 spawn 都要构造新的 Agent 实例、独立维护会话历史、结果返回时还要消耗父智能体的 token。如果一个子任务只需一两步工具调用，那么直接由父智能体完成更划算。推荐的判断标准是子任务是否需要独立且大量的上下文，满足这一条时拆分才有收益。

三种声明来源

子智能体的定义有三个来源，它们在构建时合并成一个统一的声明集合。模型看到的 agent 列表由三部分组成，因此你可以同时使用文件定义固定角色、用 API 定义动态角色。

方式用途配置位置
内置 general-purpose通用兜底子 Agent，继承父 Agent 的能力，无需声明即可 spawn始终存在，无需配置
Workspace spec 文件项目专用、可版本控制的子 Agent，适合随代码一起评审workspace/subagents/<id>.md
程序化声明运行时决定，支持远程 Agent 与动态参数，适合按租户组装builder.subagent(SubagentDeclaration.builder()...)

内置的 general-purpose 是一个兜底角色。它的指令来自父 Agent，能力也继承父 Agent，因此当你需要一个「通用执行者」时可以直接指定它，无需先写一份 spec 文件。它使用的是 SHARED 工作区模式，因此产出对父 Agent 直接可见。

spec 文件格式

文件路径是 workspace/subagents/<id>.md。这里有一条必须记住的规则：文件名去掉 .md 就是 agent_id，不要在 front matter 里再设 name。AgentSpecLoader 在构建时非递归扫描 workspace/subagents/*.md，因此子目录里的声明文件不会被加载。

遵循这条规则带来一个直接好处：父 Agent 无需注册即可调用它，因为 agent_id 已经由文件路径确定了。

最小可用 spec 文件markdown
---
description: Code-review specialist. Use when the user wants to review a PR, hunt for code issues, or check code style.
---

You are a subagent focused on code review. Follow this flow:
1. First read_file / grep_files to gather context
2. Give specific suggestions by file and line
3. End with an overall 1–5 score

父 Agent 的调用方式就是它的 agent_id 加一句任务描述：

父 Agent 调用方式text
agent_spawn agent_id="reviewer" task="review every change in this PR"

You are a subagent focused on code review.
官方文档内部存在一处不一致

官方文档在介绍 expose_to_user 的 Markdown 示例里，出现过一个 name: researcher 字段。这与前文「文件名即 agent_id，不要设 name」的规则直接冲突。本教程的判断是：那是示例书写疏漏，不代表运行时行为。

建议做法：始终以文件名作为 agent_id，例如 researcher.md 对应 agent_id="researcher"；front matter 里不写 name。如果你的版本确实识别 name 字段，请用一次 agent_list 验证实际生效的 id，不要在文档尚未澄清时依赖该字段。

ISOLATED 与 SHARED

工作区模式决定子智能体在哪里读写文件。这个选择不是风格问题，它直接影响父 Agent 能否立即看到子 Agent 的产出。

ISOLATED（缺省）SHARED
工作区来源独立目录，未指定 path 时框架自动创建子目录直接使用父 Agent 的工作区
运行时状态分桶按 parent sessionId × userId 分桶与父 Agent 相同
会话隔离同一用户不同会话调用同一子 Agent，状态互不污染与父 Agent 共享
父 Agent 能否立即读产物不能，需要子 Agent 在返回值中给出结论或路径可以，父 Agent 下一步 read_file 即可
典型用法需要大量独立上下文、产出是一份结论的分析任务父 Agent 需要读取中间产物的流水线式任务；内置 general-purpose 使用此模式

因此判断依据很简单：如果子任务以「返回一段结论」结束，选 ISOLATED；如果子任务以「在工作区里产出文件供后续步骤使用」结束，选 SHARED。大多数分析类子智能体适合前者，而内置的 general-purpose 之所以用后者，正是因为它的定位是通用执行者，产出通常留在父上下文的工作区里更方便。

同步与后台

委派方式由 timeout_seconds 一个参数决定。这个参数的语义比看起来更微妙，因此单独说明。

timeout_seconds语义父 Agent 行为结果返回方式
> 0同步。缺省 30 秒，最大 600 秒父 Agent 在当前步骤阻塞等待，子 Agent 结果作为 tool result 返回直接随 tool result 返回
= 0后台。立即返回 task_id父 Agent 立即继续下一步，子 Agent 在后台运行完成后自动推送到父 Agent 的下一轮

同步模式有一个容易忽略的行为：如果等待时间到了子 Agent 还没结束，这次 in-flight run 会转为后台任务，返回 status: timeout_promoted 与 task_id，子 Agent 继续运行。也就是说同步等待超时并不等于失败，父 Agent 随后仍然可以用 task_output 取得结果。

强制同步：应用代码侧

LLM 自己决定 timeout_seconds，这在生产中不够可靠。框架提供一个应用侧开关，通过 RuntimeContext 的属性键覆盖 LLM 的选择。

强制同步执行java
import io.agentscope.core.agent.RuntimeContext;
// AgentSpawnTool 的包名请按版本核对，官方文档未给出完整全限定名
import io.agentscope.harness.agent.AgentSpawnTool;

RuntimeContext ctx = RuntimeContext.builder()
        .sessionId("s-1")
        // 打开强制同步
        .put(AgentSpawnTool.CTX_FORCE_SYNC, true)
        // 指定硬等待时间（秒）
        .put(AgentSpawnTool.CTX_FORCE_SYNC_TIMEOUT_SECONDS, 120)
        .build();

覆盖规则有三条，必须记住：

  • 设置了 CTX_FORCE_SYNC_TIMEOUT_SECONDS 时，它完全替换 LLM 给的 timeout_seconds；值小于等于 0 时回退到 30 秒，最大 600 秒。
  • 没有设置硬等待时间时，LLM 给的 timeout_seconds=0 会被改为缺省 30 秒同步等待，并且不会提交后台任务；LLM 给的正数 timeout 保持不变。
  • 同步等待超时返回 status: timeout，中断子 Agent，不会提升为带 task_id 的后台任务。这与上面「同步等待超时转为后台」是不同的路径，前者属于模型驱动的等待，后者属于应用强制的等待。

agent_send 同样遵循这个开关。

子智能体与后台任务工具

框架提供两组工具，它们操作的是两类不同的对象：一类是子智能体实例，另一类是后台任务。两类对象通过 task_id 关联。

Tool作用对象作用
agent_spawn子 Agent 实例创建子 Agent，可同步或后台执行
agent_send子 Agent 实例向已有子 Agent 发送后续消息
agent_list子 Agent 实例列出活跃子 Agent 实例
task_output后台任务按 task_id 获取结果，支持阻塞或非阻塞
wait_async_results后台任务等待后台结果；可指定 task_ids 或 wait_all=true
task_cancel后台任务取消正在运行的后台任务
task_list后台任务列出所有后台任务及其状态

agent_spawn 与 agent_send 在 timeout_seconds=0 时会返回该 task_id，这正是两类对象的连接点。

后台结果自动推送

后台任务完成后，框架会在父 Agent 下一次推理之前，把结果作为 system reminder 注入对话末尾。注入内容的形状大致如下：

自动推送的注入内容xml
<system-reminder>
Background tasks delivered:
- task_id=xxx, agent=research-analyst, status=COMPLETED
  result summary: ...
</system-reminder>

因此父 Agent 不需要轮询。这是一个实际影响提示词编写的事实：你不必要求自己「记得定期调用 task_output」，因为结果会主动到达。轮询只在需要精确控制合并时机时才有意义。

取得后台结果的三种方式

方式配置语义
自动推送缺省方式完成时注入下一轮，无需任何调用
task_outputtask_output(task_id, block=false)查询单个任务状态，不阻塞
wait_async_resultswait_async_results(task_ids="id1,id2")指定集合全部进入 terminal status 才返回，每个任务结果直接嵌入 tool return
wait_async_resultswait_async_results(wait_all=true)wait-all barrier；使用调用开始时未完成任务的一次快照，等待期间新建的任务不自动加入
不带参数的 wait_async_results 不是 barrier

wait_async_results() 不带任何参数时，只等待任意一个 inbox message 到达就返回，它不是 wait-all barrier。需要等待全部后台任务时，必须显式传 task_ids 或 wait_all=true。这个差别在多任务场景中很容易被忽略，因为调用本身不会报错，只是返回得比预期早。

递归安全与权限继承

子智能体不能无限增殖。框架为此设置了硬约束，同时保证委派不能绕过安全边界。

规则具体行为设计意图
递归限制子智能体被强制标记为 leaf，不能继续 spawn 子智能体；仍有 3 层硬上限避免委派深度失控与成本指数上升
userId 传播父 Agent 的 RuntimeContext.userId 转发给子 Agent保留多租户隔离链，子 Agent 的产物归属同一用户
权限继承父 Agent 的所有 DENY 规则自动传播；父 Agent 被禁止的工具，子 Agent 同样被禁止无法通过委托绕过安全边界
Plan Mode 继承父 Agent 处于 Plan Mode 时，spawn 的子 Agent 自动继承只读限制规划阶段不会因为委派而产生写操作
继承开关inheritParentPermissions(false) 关闭权限继承适用于需要最小权限子 Agent 的场景

事件转发与 source

推荐使用 streamEvents()，它返回 Flux<AgentEvent>。旧的 stream() 系列返回 Flux<Event>，自 2.0.0 起标记为 @Deprecated(forRemoval = true)。

父子事件通过 source 字段区分，规则很简单：父事件的 source 为 null，子事件不为 null，其值是以 / 分隔的路径，例如 "main/researcher"。

一次含子智能体调用的完整事件序列 caller └─ parent.streamEvents(msg, ctx) ├─ AGENT_START ← parent ├─ TEXT_BLOCK_DELTA … ├─ TOOL_CALL_START "agent_spawn" │ [child spawned] ├─ AGENT_START (source="main/researcher") ├─ TEXT_BLOCK_DELTA … (source="main/researcher") ├─ TOOL_CALL_START … (source="main/researcher") ├─ TOOL_RESULT_END … (source="main/researcher") ├─ AGENT_END (source="main/researcher") │ [agent_spawn returns; child result → parent TOOL_RESULT] ├─ TOOL_RESULT_END ← parent ├─ TEXT_BLOCK_DELTA … ← parent 第二轮 └─ AGENT_END

远程 Agent 通过 Protocol 产生的子事件还带有 metadata，包含 AgentEvent.METADATA_TASK_ID 与 AgentEvent.METADATA_PARENT_SESSION_ID。因此即使同一 turn 并发调用同一个远程 Agent，也能通过 task / session metadata 区分。

按 source 过滤事件java
Flux<AgentEvent> events = agent.streamEvents(new UserMessage("分析这三份文档"), ctx);

// 仅父事件
events.filter(e -> e.getSource() == null).subscribe(...);

// 仅子事件
events.filter(e -> e.getSource() != null).subscribe(...);

// 仅特定子 Agent
events.filter(e -> e.getSource() != null
                && e.getSource().contains("researcher")).subscribe(...);

// 远程子事件：用 metadata 区分同一 turn 的并发调用
events.filter(e -> e.getSource() != null
                && e.getMetadata() != null
                && e.getMetadata().get(AgentEvent.METADATA_TASK_ID) != null)
      .subscribe(...);

转发边界

「事件转发」并不总是实时。是否能看到子 Agent 的实时事件，取决于父调用的形态、子 Agent 是本地还是远程、以及是否配置了远程流式。这张表是本章最容易记错的部分，因此放在理论部分最后。

场景是否实时转发子结果的实际去向
streamEvents() + 同步本地子 Agent，timeout_seconds>0是子事件实时进入父流；最终结果作为父的 tool result
call() non-streaming否子结果作为 tool_result 字符串返回
timeout_seconds=0 后台任务否完成后通过反向通知推送到父 Agent 的下一轮
Remote subagent + 父 streamEvents() + remoteStreaming=true是远程事件按 remoteStreamDetail 的档位转发
Remote subagent + 父 call() 或 remoteStreaming=false否远程结果作为最终结果返回，不逐事件转发

远程事件转发有三档粒度，由 remoteStreamDetail 控制。FULL 是缺省值。

档位包含内容适用场景
STATUSrun lifecycle、tool call boundaries、tool results、confirmation requests只关心进度，不需要文本
FULL（缺省）STATUS + text deltas + thinking deltas大多数需要展示模型输出的场景
VERBOSE全部远程事件：block boundaries、tool argument deltas、tool output deltas、token usage、hints、agent results、custom events需要观察 token 消耗或调试远程 Agent 时
只有 VERBOSE 会转发远程工具输出与 token 用量

官方文档特别说明：只有 VERBOSE 会把远程 tool output 内容与 token usage 转发到父 Agent。它不是缺省值，因为对只渲染文本的客户端来说，它会产生大量额外事件。因此调试时先切到 VERBOSE，确认行为后不要一直开着。

错误处理

子智能体内部抛出异常时，框架捕获该异常并写成父 Agent 的 TOOL_RESULT，不会向父事件流触发 onError。因此一个子智能体失败不会中断父智能体，父 Agent 会看到一段描述失败原因的文本并自行决定下一步。父事件流自身的错误仍然使用标准 Reactor 方式处理，例如 onErrorResume。

示例三：后台委派与结果 barrier

需要长时间执行的子任务应当用后台方式。让父 Agent 在等待期间继续做别的工作，是这一节的核心价值。

BackgroundDelegation.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;

import java.nio.file.Paths;

public class BackgroundDelegation {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("orchestrator")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get(".agentscope/workspace"))
                // 后台任务状态落盘位置（缺省值）：
                // workspace/agents/<parentAgentId>/tasks/<sessionId>.json
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan").sessionId("bg-001").build();

        Msg reply = agent.call(new UserMessage(
                "把 docs/ 下的三份架构文档分别做结构化摘要，"
                + "完成后给我一份合并报告。"), ctx).block();

        System.out.println(reply.getTextContent());
        System.out.println("任务状态文件： "
                + ".agentscope/workspace/agents/orchestrator/tasks/bg-001.json");
    }
}

在这个场景下，模型会按下面的节奏工作，而父 Agent 并不是干等：

后台委派时序text
[父] agent_spawn analyzer task="summarize docs/a.md" timeout_seconds=0
       → 立即返回 task_id=t-001
[父] agent_spawn translator task="translate docs/a.md summary" timeout_seconds=0
       → 立即返回 task_id=t-002
[父] agent_spawn linter task="check code refs in docs/a.md" timeout_seconds=0
       → 立即返回 task_id=t-003
[父] 做自己的准备工作（例如先读索引、确认输出格式）

... 子 Agent 在后台运行 ...

[框架] 三个任务完成后，在父 Agent 下一次推理之前注入：
        <system-reminder>
        Background tasks delivered:
        - task_id=t-001, agent=analyzer, status=COMPLETED
          result summary: ...
        - task_id=t-002, agent=translator, status=COMPLETED
          result summary: ...
        - task_id=t-003, agent=linter, status=COMPLETED
          result summary: ...
        </system-reminder>

[父] 合并三份结果，输出报告

如果父 Agent 需要在同一步之内等待全部结果（例如它马上要汇总），就用 barrier。注意两种写法的区别：

两种 barrier 写法text
wait_async_results(task_ids="t-001,t-002,t-003")
    等待指定集合全部进入 terminal status 才返回，
    每个任务的结果直接嵌入 tool return。

wait_async_results(wait_all=true)
    使用调用开始时未完成任务的一次快照作为集合，
    等待期间新建的任务不会自动加入。

wait_async_results()
    只等待任意一个 inbox message 到达 —— 不是 wait-all barrier。
自动推送与 barrier 的选择

两者不冲突，但适用场景不同。父 Agent 在等待期间还有别的工作可做时，自动推送更合适，因为结果到达即可使用。父 Agent 必须拿到全部结果才能继续时，barrier 更合适，因为它保证了「返回时集合已全部完成」。另外 barrier 的一次快照语义很重要：它不会把等待期间新产生的后台任务纳入集合，因此如果你在同一轮里又派发了新任务，需要再调用一次。

后台任务的存储位置在缺省情况下是 workspace/agents/<parentAgentId>/tasks/<sessionId>.json。这个文件不会被上下文压缩影响，因此 task_id、状态与结果都是长期数据。

示例四：并行 fan-out 分析多份文档

ToolkitConfig.parallel 的缺省值是 true。因此同一 reasoning turn 发出的多个同步 agent_spawn 会并行执行，ReActAgent 与 HarnessAgent 均适用。父 Agent 会等待整批 tool results 返回后再进入下一次 reasoning，这形成了一个同步的 fan-out / fan-in barrier。

FanOutDocuments.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;

import java.nio.file.Paths;

public class FanOutDocuments {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get(".agentscope/workspace"))
                // 这里不加任何配置：parallel 缺省即并行。
                // 若要强制串行，见本节末尾的说明。
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan").sessionId("fanout-001").build();

        // 三份文档彼此无依赖，模型可以在同一个 turn 里发出三次 spawn，
        // 框架并行执行它们，等全部返回后再让父 Agent 继续。
        Msg reply = agent.call(new UserMessage(
                "分析 docs/arch-payment.md、docs/arch-risk.md、"
                + "docs/arch-order.md 三份文档。"
                + "每份文档独立分析，互不影响，"
                + "最后给我一份三者的对比结论。"), ctx).block();

        System.out.println(reply.getTextContent());
    }
}

并行结构对应的调度图示：

三个无依赖子任务（并行） parent reasoning #1 │ ├─ spawn(doc-a) ──┐ ├─ spawn(doc-b) ──┼── 并行执行 ──┐ └─ spawn(doc-c) ──┘ │ ▼ parent reasoning #2 ←────────── fan-in barrier （父 Agent 在此之前不做任何推理）

如果你需要串行，例如后一个子任务的参数依赖前一个的输出，就用自定义 Toolkit 关闭并行：

关闭并行java
import io.agentscope.core.tool.ToolkitConfig;
// ToolkitConfig 的包名请按版本核对

HarnessAgent agent = HarnessAgent.builder()
        .name("kb-assistant")
        .model("dashscope:qwen-plus")
        .toolkit(ToolkitConfig.builder()
                .parallel(false)   // 同一 turn 内的工具调用改为顺序执行
                .build())
        .build();

拆分是否合理，可以按下面的标准判断。需要注意的是，这三条不是「并行一定优于串行」的排序，而是「什么时候并行才安全」的边界。

依赖关系推荐方式原因
无依赖边并行：同一 turn 发出多个 spawn总耗时从各步之和降到最慢的一步
有依赖边等上游结果返回后再派发，或在父 Agent 内合并后再派发并行执行的下游会拿到不存在的输入
短任务 / 关键路径同步等待（timeout_seconds > 0）或显式 barrier父 Agent 立刻就需要这个结果
长任务后台执行（timeout_seconds = 0）父 Agent 可以在等待期间做别的工作

示例五：事件分流

前端通常希望父智能体与子智能体的输出分别渲染：父的推理过程显示在一个区域，每个子智能体显示在自己的折叠面板里。source 字段就是为这个需求设计的。

EventRouting.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;
import reactor.core.publisher.Flux;

import java.nio.file.Paths;

public class EventRouting {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("orchestrator")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get(".agentscope/workspace"))
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan").sessionId("event-001").build();

        Flux<AgentEvent> events =
                agent.streamEvents(new UserMessage("分析三份架构文档"), ctx);

        events.subscribe(event -> {
            String source = event.getSource();   // 父事件为 null

            if (source == null) {
                // 父智能体的推理与工具调用
                render("main", event);
            } else {
                // 子智能体事件，source 形如 "main/researcher"
                render(source, event);
            }
        }).blockLast();
    }

    private static void render(String channel, AgentEvent event) {
        String type = event.getType().name();
        if ("TEXT_BLOCK_DELTA".equals(type)) {
            System.out.println("[" + channel + "] " + event.getDelta());
        } else if ("AGENT_START".equals(type)) {
            System.out.println("[" + channel + "] === 开始 ===");
        } else if ("AGENT_END".equals(type)) {
            System.out.println("[" + channel + "] === 结束 ===");
        }
    }
}

如果你需要把子事件聚合而不是逐条转发，按 source 做过滤即可。三种常见过滤条件：

按需过滤java
// 仅父事件：用于「主对话区」渲染
events.filter(e -> e.getSource() == null);

// 仅子事件：用于「子任务区」渲染
events.filter(e -> e.getSource() != null);

// 仅特定子 Agent：source 路径包含 agent 片段
events.filter(e -> e.getSource() != null
                && e.getSource().contains("researcher"));
deprecated 的 stream() 不要在新代码里使用

streamEvents() 返回 Flux<AgentEvent>，是 2.0 的推荐接口。旧的 stream() 系列返回 Flux<Event>，自 2.0.0 起标记 @Deprecated(forRemoval = true)，会在后续版本中移除。另外提醒一句：只有 streamEvents() + 同步本地子 Agent 才实时转发子事件，换成 call() 就只能拿到最终结果字符串。

示例六：把子智能体暴露给用户

前面的例子中，子智能体的生命周期完全由父智能体掌握，用户无法直接与它对话。开启 expose_to_user 之后，子智能体会在 Gateway 中注册为用户可直接访问的入口。

声明要暴露的子智能体markdown
---
description: Research specialist. Use when the user wants a dedicated
  researcher that can be talked to directly over multiple turns.
expose_to_user: true
persist_session: true
---

You are a subagent focused on research. Keep a stable line of inquiry
across turns, and state sources explicitly.
ExposeSubagent.javajava
import io.agentscope.core.event.SubagentExposedEvent;
import io.agentscope.harness.agent.HarnessAgent;
// ChatUiChannel / SendOptions 的包名请按版本核对
import io.agentscope.harness.channel.ChatUiChannel;
import io.agentscope.harness.channel.SendOptions;

import reactor.core.publisher.Flux;

public class ExposeSubagent {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("orchestrator")
                .model("dashscope:qwen-plus")
                .build();

        // channel() 会自动创建内部 gateway 并连接 bridge。
        // 不绑定 Channel 时 expose_to_user=true 会被静默忽略：
        // 子 Agent 仍能正常运行，只是无法暴露。
        ChatUiChannel chat = agent.channel(ChatUiChannel.create());

        chat.sendStream(SendOptions.userId("user-1"),
                        "Spawn a researcher to investigate AI trends")
            .doOnNext(event -> {
                if (event instanceof SubagentExposedEvent se) {
                    // se.getSubagentId() 用于直接与子智能体对话
                    System.out.printf("id=%s agent=%s label=%s%n",
                            se.getSubagentId(),
                            se.getAgentId(),
                            se.getLabel());
                }
            })
            .blockLast();

        // 拿到 subagentId 之后，用户可以直接与该子智能体对话
        chat.sendToSubagent("sub-123", "Focus on LLM agents specifically")
            .block();
    }
}

expose_to_user=true 有两个效果，这一点在官方文档中是明确的：

  1. 在 Gateway 中注册为用户可直接访问的 entry point；
  2. 发出 SubagentExposedEvent，字段为 getSubagentId()、getAgentId()、getSessionId()、getLabel()。

曝光策略优先级

曝光决策可能来自四个地方。优先级自上而下，第一个给出明确意见的来源胜出；如果都没有意见，缺省为 false。

优先级来源类型
1当前调用的 RuntimeContext 覆盖（键 AgentSpawnTool.CTX_EXPOSE_TO_USER）值可为 Boolean 或字符串
2SubagentDeclaration 的 per-type policyBoolean 或字符串
3LLM 的 expose_to_user tool argumentBoolean 或字符串
4都没有意见时的缺省false

三态语义：

值语义
TRUE始终暴露
FALSE永不暴露，即使 LLM 传 true
null无意见，继续向下一级回退

这个三态设计的价值在于：应用可以用一个 Boolean 覆盖全部子智能体类型，声明可以按类型分别表态，而模型仍然保留最后一层决定权。因此想做全局封禁时，把 RuntimeContext 里的这个键设为 false 即可，不需要逐个修改声明。

跨重启与多副本

缺省的 exposure 是 in-process 的：subagentId 只在创建它的那个节点上有效，节点重启后即失效。如果你的服务是多副本部署，或者需要在进程重启后仍然解析同一个 subagentId，就要接入分布式存储。

后台任务在多副本下的语义

在多副本或共享存储模式下，后台任务的分布有明确约定，理解它们可以避免很多困惑：

  • 任意节点可读 task state；
  • 执行固定在创建它的节点，不会迁移；
  • 任意节点可读结果，并推送给父 Agent；
  • 可以从任意节点调用 task_cancel；
  • 执行节点轮询 cancel 标记并中止任务。

也就是说「可读」与「可执行」是分离的，这在设计取消逻辑时尤其重要。

后续交互与持久化

子 Agent 创建后返回一个运行时实例句柄 agent_key。你可以向同一个子 Agent 追加消息，这比每次重新 spawn 更省成本，因为会话历史被保留了。

两种后续交互方式text
方式一：使用 agent_key
agent_spawn agent_id="reviewer" task="review the PR"
    → 返回 agent_key = "agent:reviewer:abc-123"
agent_send agent_key="agent:reviewer:abc-123"
           message="also check the schema changes"

方式二：使用 spawn 时指定的 label
agent_spawn agent_id="reviewer" task="review the PR" label="pr-reviewer"
agent_send label="pr-reviewer"
           message="also check the schema changes"

agent_list          列出活跃子 Agent 实例

如果希望子 Agent 在多次 spawn 之间复用同一个实例，在声明里加上 persistSession(true)。框架按 (parentSessionId, agentId, label) 生成确定性 key，相同组合再次调用 agent_spawn 时复用现有实例，保留 conversation history 与运行状态。需要注意的是，这意味着同一个 label 的后续任务会继承上一次的全部上下文，因此复用与「每次干净开始」是两种不同的语义，按任务性质选择。

agent_generate：让模型自己写声明

该工具缺省关闭。启用之后，LLM 可以生成 spec 内容并写入 workspace/subagents/<name>.md。官方给出的提示很明确：生产环境应谨慎使用，通常先让 Agent 起草，再由人工审核后写入文件。原因是写入的声明会直接改变后续所有会话的委派行为，未经审核的声明等价于修改了系统提示词。

11.3委派设计指南

description 是唯一的委派信号

模型只能看到 description。它不知道子智能体的正文写了什么流程，也不知道它有哪些工具。因此 description 的质量直接决定委派是否发生。

写法description 内容模型能否正确委派
反例description: Code review不能。信息不足，模型无法判断当前请求是否属于该范围
正例description: Code-review specialist. Use when the user wants to review a PR, hunt for code issues, or check code style.能。给出了触发条件与典型措辞

可操作的写法是三段式：角色一句话 + Use when 触发条件 + 典型用户措辞。「Use when」这一段最关键，因为它描述的是用户会怎么说，而模型匹配的是措辞而不是抽象语义。因此在 description 里直接写出用户的原话，比写出职责定义更有效。

同步还是后台

这个问题只有一个判断点：父 Agent 在等待期间是否还有别的工作可做。不过在回答之前，先要排除一个前提：子任务的产出形态。如果子任务以「在工作区里产出文件供后续步骤使用」结束，那么无论同步还是后台都必须等它完成，此时选择标准就是耗时；如果产出只是一段结论，那么后台执行带来的延迟完全可以被后续工作覆盖。

情况选择理由
父 Agent 拿到结果就要立刻用同步，timeout_seconds 给 30~120减少一次额外往返
结果不紧急，但同一轮内必须齐全后台 + wait_async_results barrier并行等待，返回时集合已全部完成
结果可以晚几轮再用后台 + 自动推送父 Agent 完全不必轮询
子任务耗时超过数分钟后台同步最大 600 秒，超时会转为后台任务，反而多一次状态转换
不确定同步，缺省 30 秒同步超时会自动转后台，不会丢结果

最后一行值得强调：同步超时转为后台任务是一条安全的回退路径。因此「先用同步看看快不快」是一个可行的策略，慢任务会自动转后台，你不需要预先知道哪个任务慢。但是如果你用应用侧 CTX_FORCE_SYNC 强制同步，这个回退就不存在了：超时返回 status: timeout 并中断子 Agent。所以强制同步适合「我确定它很快」的场景。由此可见，是否开启 CTX_FORCE_SYNC，本质上是在「可预测性」与「不丢结果」之间做取舍，而不只是设置一个超时数字。

按依赖关系拆分

把一个复杂任务拆成子任务时，按下面的顺序判断每条边：

列出全部子任务

先把任务写成清单，包含每个子任务的输入来源与产出形态。产出是「一段结论」还是「工作区里的文件」决定了 ISOLATED 还是 SHARED。

标出依赖边

子任务 B 的输入是否包含子任务 A 的输出？如果包含，这条边就不能并行。

合并无依赖的相邻任务

如果两个子任务之间没有边，而且都很短，把它们合并成一个子智能体反而更划算，因为省掉一次构造与结果回传。

为每条依赖边确定等待点

同步等待、barrier，还是让父 Agent 合并后再派发。三者都可以，关键是要显式决定，因为遗漏等待点是最常见的调度错误来源。与此同时要注意，父 Agent 的合并动作本身也是一个节点，它同样需要等待自己派发的所有上游任务。

最后才决定并行还是后台

并行是执行策略，不是拆分策略。拆得对再选并行，拆错了并行只会放大错误，于是错误会以更快的速度同时出现在多个子任务上。

一个常见错误：把「按文档拆」当成唯一拆法

按文件拆分适用于「每份文件都过一遍」的分析型任务，这也是本章示例采用的方式。但是需要汇总统计的任务（例如「统计全部文档中 TODO 的总数」）不适合按文档拆，因为每个子智能体只能看到自己那份的计数，无法给出全局结论。这类任务要么合并成一个子智能体，要么让子智能体输出中间计数、由父 Agent 求和。判断标准是：子任务的产出能否独立回答问题的一部分，能就可以并行，不能就要重新拆。

11.4本章小结

  • 子智能体解决三个问题：上下文隔离、并行执行、职责分离。但是每次 spawn 都有额外成本，因此只有当子任务确实需要独立且大量上下文时拆分才有收益。
  • 三种声明来源在构建时合并：内置 general-purpose、workspace/subagents/<id>.md、builder.subagent(...)。文件名的 .md 后缀就是 agent_id，不要在 front matter 里再设 name。
  • AgentSpecLoader 在构建时非递归扫描 subagents/*.md，子目录中的声明不会被加载。
  • 官方文档在 expose_to_user 的示例里出现过 name 字段，与「文件名即 agent_id」规则冲突。建议以文件名作为 agent_id，并用 agent_list 验证实际生效的 id。
  • ISOLATED 独立工作区，运行时状态按 parent sessionId × userId 分桶；SHARED 直接使用父 Agent 工作区，父 Agent 可立即读取产出。
  • timeout_seconds > 0 为同步（缺省 30 秒，最大 600 秒），= 0 为后台并立即返回 task_id。同步等待超时会转为后台任务，而应用侧 CTX_FORCE_SYNC 强制同步超时则直接中断。
  • wait_async_results() 不带参数只等任意一个消息到达，不是 wait-all barrier。需要全部等待时必须传 task_ids 或 wait_all=true。
  • 后台任务完成后由框架自动推送为 system reminder，父 Agent 不需要轮询，提示词里也不必写「记得轮询」。
  • ToolkitConfig.parallel 缺省为 true，因此同一 turn 的多个同步 spawn 天然并行，形成 fan-out / fan-in barrier。需要串行时显式设为 false。
  • 父子事件通过 source 区分：父事件为 null，子事件为以 / 分隔的路径。实时转发只在 streamEvents() + 同步本地子 Agent 时成立。
  • 子智能体是 leaf，不能继续 spawn，硬上限 3 层；父 Agent 的 DENY 规则与被禁工具自动传播，委派无法绕过安全边界。
练习
  1. 按示例一创建 workspace/subagents/reviewer.md，然后分别用「帮我审一下这个 PR」和「今天天气如何」提问，观察模型是否委派，并解释差异来自哪个字段。在此基础上，把文件移到 subagents/team/reviewer.md 再测一次，验证 AgentSpecLoader 的扫描确实是非递归的；最后用 agent_list 确认生效的 agent_id 与文件名一致。
  2. 分别用同步（timeout_seconds=60）与后台（timeout_seconds=0）委派同一个耗时任务，对比父 Agent 在等待期间的行为差异，并验证后台结果是否以 system reminder 形式出现。然后把 ToolkitConfig 的 parallel 设为 false，再次执行示例四，观察事件顺序的变化。
  3. 把 CTX_EXPOSE_TO_USER 在 RuntimeContext 中设为 false，验证即使 LLM 传入 expose_to_user=true 也不会暴露；再改造示例六，让同一个 label 被 spawn 两次，验证 persistSession(true) 是否真的保留了会话历史。
  4. 构造一组对照实验：一个「无依赖」子任务方案与一个「有依赖」子任务方案（让下游任务的输入包含上游输出），对比两者的耗时与结果正确性，并观察并行执行有依赖时的具体错误表现。
  5. 设计题：为「分析 8 份季度财报并产出一份对比报告」设计一个子智能体编排方案。要求：①列出需要哪些子智能体，每个的 description 怎么写；②标注每个子智能体用 ISOLATED 还是 SHARED，并说明理由；③画出依赖关系，指出哪几处是并行 barrier；④说明哪些步骤用同步、哪些用后台，并给出 timeout_seconds 的具体取值；⑤说明最终报告由谁合并，以及报告存放在哪里。
