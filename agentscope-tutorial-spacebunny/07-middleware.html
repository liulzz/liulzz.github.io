中间件
五个扩展点，不改一行Agent 代码

上一章我们用 onActing 扩展点做了一个「全部工具被拒绝就停止」的中间件， 但没有解释它是什么、能放在哪里、能做什么。 本章把这件事讲透：AgentScope Java 2.0 提供五个生命周期扩展点， 分为 Onion 与 Transformer 两类， 你可以在不修改 Agent 与模型代码的前提下插入日志、追踪、输入改写与访问控制。

为什么需要中间件

先看一个具体的问题。上一章的知识助手需要「统计每次模型调用的耗时」，你会怎么实现？

直接在 ReActAgent 里加计时字段是最直观的做法，但是这样会有三个后果：业务代码与框架代码混在一起；同一个 Agent 想换一个统计方式就必须改源码；如果这个 Agent 是别人提供的，你根本改不了。

中间件正是为这类需求设计的。它是一段可以插在推理流程任意位置的独立代码，与Agent、模型、工具三者都解耦。需要统计耗时就装一个，需要接入链路追踪就再装一个，两者互不干扰，也不需要改动已有的类。

常见的插入目的有四类：

  • 观测：日志、指标、链路追踪、耗时统计。
  • 治理：限流、超时、重试、模型故障转移、提前停止。
  • 输入改写：动态系统提示词、上下文注入、脱敏。
  • 输出加工：过滤中间轮次的思考文本、聚合事件、裁剪提示词。
场景

本章场景

继续完善团队知识助手，为它增加一层可观测与治理能力。目标四项：

  • 耗时可见：记录每一次模型调用的耗时、消息条数与结束信号
  • 调用受控：模型调用之间保持最小间隔，避免触发服务端限流
  • 上下文动态化：系统提示词每次组装时都带上当前时间与当前用户租户， 而不再是一次性写死的字符串
  • 及时停止：全部工具被拒绝时立即结束本次推理， 不继续消耗 token

本章结束时，知识助手的主代码保持不变， 所有新增能力都由一组中间件提供。

7.1先讲理论：五个扩展点

AgentScope Java 在一次 reply 流程中提供五个可以插入逻辑的位置。它们不是并列的五个函数，而是有明确嵌套层次的五个阶段。

Hook类型作用范围
onAgentOnion包裹完整的 reply 流程，包括所有 ReAct 轮次、工具执行与最终输出
onReasoningOnion包裹单个 reasoning step：输入组装 → 模型调用 → 流式解码
onActingOnion包裹单次工具调用
onModelCallOnion包裹原始 ChatModel API 调用，最接近模型
onSystemPromptTransformer系统提示词组装时触发；多个中间件依次转换前一个的输出

嵌套关系

这五个扩展点的包含关系如下。理解这张图比记住签名更重要，因为它决定了 order 的含义与日志的插入位置。

一次 reply 内部的结构 onAgent/ └── ReAct loop（每轮）/ ├── onReasoning/ │ ├── onSystemPrompt（组装系统提示词） │ └── onModelCall（模型 API 调用） └── onActing（每次工具调用）

onSystemPrompt 位于 onReasoning 内部，因为系统提示词是在组装模型输入的过程中生成的，而不是在推理开始之前一次性确定。因此一个只关心提示词的中间件，无法脱离onReasoning 单独存在。

onActing 的追踪范围有限

onActing 只跟踪 Agent runtime 内部执行的工具。上一章提到的外部执行工具（externalTool(true)），以及通过其他外部执行机制运行的工具，都不会被 onActing 记录。因此如果你的可观测需求包含外部工具，需要在应用层单独埋点，不能依赖这个扩展点。

Onion 与 Transformer

五个扩展点分成两类。它们的差别不在于能否改写数据，而在于有没有「内层 handler」这个概念。

Onion（洋葱型）Transformer（转换型）
形态包装下一个 handler：在 next.apply(input) 前后插入逻辑从左到右组成一条 pipeline：没有「内层 handler」
签名末参Function<XxxInput, Flux<AgentEvent>> next无 next 参数
能看到什么既能看输入，也能看内层产生的中间事件流只看当前提示词字符串
属于此类的 hookonAgent、onReasoning、onActing、onModelCallonSystemPrompt

用一个具体的例子可以看清差别。Onion 型扩展点的执行过程是：

Onion 型执行过程text
进入 onXxx（外层中间件 A）
  调用 next.apply(input)
    进入 onXxx（内层中间件 B）
      调用 next.apply(input)
        进入实际逻辑（模型调用 / 工具执行）
        事件开始向外流出：B 先看到，A 后看到
      B 的后置逻辑
    A 看到 B 已经处理过的事件流
  A 的后置逻辑

而 Transformer 型的执行过程是一条直线：

Transformer 型执行过程text
originalPrompt
  → 中间件1.onSystemPrompt() → promptA
  → 中间件2.onSystemPrompt() → promptB
  → finalPrompt（真正发给模型的字符串）

因此 onSystemPrompt 的写法是「返回一个新字符串」，而不是「调用 next 再加工」。多个此类中间件按注册顺序从左到右依次转换，后一个看到的是前一个的输出。

执行顺序与 order

Onion 型的顺序由 order() 决定，缺省值为 1。规则有三条：

  • order 越高越靠外层。
  • 缺省值为 1。
  • order相同时，保持 Builder 中的注册顺序。

因此 order = 0 的中间件运行在缺省 order = 1 的中间件内部。这一点在需要「贴近模型」做事情时很有用。

顺序示例：middlewares = [mw1(order=2), mw2(order=1)]text
mw1_pre → mw2_pre → 内层逻辑 → mw2_post → mw1_post

流式事件的完整顺序：
  mw1_pre
  mw2_pre
  mw2_event        ← 内层中间件先看到流式事件
  mw1_event
  ...
  mw2_post
  mw1_post

注意事件流的那一段：内层中间件先看到事件，外层后看到。因此外层中间件观察到的事件序列里，已经包含了内层处理过的事件。这一点在统计事件数量时容易出错——如果你想统计「框架发出了多少原始事件」，应该放在最内层而不是最外层。

Transformer 型的顺序简单得多：onSystemPrompt 从左到右执行，与 order() 无关。

把两者合起来，一次完整的生命周期是这样的：

完整生命周期 onAgent 进入 └─ 第 1 轮 ReAct ├─ onReasoning 进入 │ ├─ onSystemPrompt（组装系统提示词） │ ├─ onModelCall（模型 API 调用，流式输出） │ └─ onReasoning 退出 └─ onActing（每次工具调用各一次） └─ 第 2 轮 ReAct（若模型再次要求调用工具） └─ ……结构相同…… onAgent 退出

各扩展点的输入类型

四个 Onion 型扩展点各自有一个 input 类型，它们都在 io.agentscope.core.middleware 包下。这些类型都是不可变的，因此替换某个字段必须构造一个新的 input，不能就地修改。

HookInput 类型字段
onAgentAgentInputmsgs: List<Msg>
onReasoningReasoningInputmessages: List<Msg>、tools: List<ToolSchema>、options: GenerateOptions
onActingActingInputtoolCalls: List<ToolUseBlock>
onModelCallModelCallInputmessages、tools、options、model: Model
onSystemPrompt无（直接是 String）当前 system prompt

需要改写传给下一层的内容时，用构造器创建一个新对象再传给 next：

InputRewrite.javajava
// 原始 input 的四个字段原样保留，只把 model 换成备用模型
ModelCallInput switched = new ModelCallInput(
        input.messages(),
        input.tools(),
        input.options(),
        fallbackModel);

return next.apply(switched);

MiddlewareBase 的完整形态

五个扩展点都声明在 io.agentscope.core.middleware.MiddlewareBase 上，实现这个接口时只需覆盖你关心的部分，未实现的扩展点会被框架跳过并直通。因此一个只做耗时统计的中间件只需要实现一个方法。

MiddlewareBase.javajava
package io.agentscope.core.middleware;

import io.agentscope.core.agent.Agent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEvent;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

import java.util.function.Function;

public interface MiddlewareBase {

    /** 缺省返回 1。数值越大越靠外层；onSystemPrompt 不受此值影响。 */
    default int order() {
        return 1;
    }

    default Flux<AgentEvent> onAgent(
            Agent agent, RuntimeContext ctx, AgentInput input,
            Function<AgentInput, Flux<AgentEvent>> next) {
        return next.apply(input);
    }

    default Flux<AgentEvent> onReasoning(
            Agent agent, RuntimeContext ctx, ReasoningInput input,
            Function<ReasoningInput, Flux<AgentEvent>> next) {
        return next.apply(input);
    }

    default Flux<AgentEvent> onActing(
            Agent agent, RuntimeContext ctx, ActingInput input,
            Function<ActingInput, Flux<AgentEvent>> next) {
        return next.apply(input);
    }

    default Flux<AgentEvent> onModelCall(
            Agent agent, RuntimeContext ctx, ModelCallInput input,
            Function<ModelCallInput, Flux<AgentEvent>> next) {
        return next.apply(input);
    }

    // Transformer 型：没有 next 参数，返回新的提示词
    default Mono<String> onSystemPrompt(
            Agent agent, RuntimeContext ctx, String currentPrompt) {
        return Mono.just(currentPrompt);
    }
}
官方文档中存在两组签名

官方文档的 Practical examples 章节里还出现过省略 RuntimeContext 的写法，例如 onModelCall(Agent, ModelCallInput, Function) 与 onSystemPrompt(Agent, String)。页面没有说明这是重载、向后兼容的签名，还是示例与API 参考的版本不一致。本章的代码统一使用带 RuntimeContext 的形式，因为它提供了会话标识与扩展属性，能力是超集。实现时请以你所安装版本的 API 参考为准；如果该版本只有无 RuntimeContext 的形式，删掉该参数即可，其余代码不变。

RuntimeContext 的共享规则

RuntimeContext 是本章最需要注意的数据结构。它的规则可以概括为三句：

  • 同一次 reply 中，所有扩展点与所有工具共享同一个 RuntimeContext 实例。
  • 内部 map 是线程安全的，因此可以从任意扩展点 put，也可以从工具方法中读取。
  • 它不持久化。跨请求的状态属于 AgentState 的职责，与RuntimeContext 无关。

因此可以实现「上下文传播」：在 onAgent 生成一个追踪标识，后续所有扩展点与工具都能读到它。

TraceContextMiddleware.javajava
package com.example.kb;

import io.agentscope.core.agent.Agent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.middleware.AgentInput;
import io.agentscope.core.middleware.MiddlewareBase;
import reactor.core.publisher.Flux;

import java.util.UUID;
import java.util.function.Function;

/**
 * 上下文传播：在流程入口生成一个追踪标识，
 * 之后任何扩展点与工具都可以通过 RuntimeContext 读取。
 */
public class TraceContextMiddleware extends MiddlewareBase {

    public static final String TRACE_ID = "trace_id";

    @Override
    public Flux<AgentEvent> onAgent(Agent agent, RuntimeContext ctx,
                                    AgentInput input,
                                    Function<AgentInput, Flux<AgentEvent>> next) {
        // 读取上游传来的属性
        String requestId = ctx.get("request_id");
        String userId = ctx.getUserId();
        String sessionId = ctx.getSessionId();

        // 写入本次调用的追踪标识
        ctx.put(TRACE_ID, UUID.randomUUID().toString());

        System.out.println("requestId=" + requestId
                + " userId=" + userId
                + " sessionId=" + sessionId
                + " traceId=" + ctx.get(TRACE_ID));

        return next.apply(input);
    }
}
不要在中间件的实例字段里保存单次请求的数据

中间件实例通常在多个 Agent 与多次调用之间复用。如果把 traceId、开始时间、或者当前轮次写进实例字段，那么并发请求之间会互相覆盖，日志与指标会串在一起。因此 per-request 的数据一律放在 RuntimeContext 中。在 Reactor 场景下，也可以使用 Reactor 的 contextWrite 在响应式链条中传递。

可以安全放在实例字段里的，只有与请求无关的配置：限流间隔、上报开关、备用模型实例等。

还有一个细节：如果构建器上同时配置了全局的 toolExecutionContext，派发工具时会先把它与 per-call 的上下文合并。发生 key 冲突时，per-call 的上下文优先，因此你在 onAgent 里写入的值会覆盖全局配置中的同名项。

7.2动手：编写中间件

本章场景的四项目标分别由四个中间件完成。本节按「观测 → 治理 → 上下文 → 停止」的顺序逐个实现。

示例一：全阶段观测

第一个中间件同时实现四个扩展点，在进入与退出时各记录一次时间。它的用途是把一次调用的完整结构打印出来，帮助你确认中间件的实际安装位置是否符合预期。

StageObservabilityMiddleware.javajava
package com.example.kb;

import io.agentscope.core.agent.Agent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.middleware.AgentInput;
import io.agentscope.core.middleware.MiddlewareBase;
import io.agentscope.core.middleware.ModelCallInput;
import io.agentscope.core.middleware.ReasoningInput;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

import java.util.function.Function;

/**
 * 全阶段观测中间件。
 * 同时覆盖四个 Onion 型扩展点与onSystemPrompt，
 * 在进入与退出时各记录一次时间，用于确认嵌套层次。
 */
public class StageObservabilityMiddleware extends MiddlewareBase {

    /** order越大越靠外层，这里取 10 让它包住所有缺省中间件。 */
    @Override
    public int order() {
        return 10;
    }

    @Override
    public Flux<AgentEvent> onAgent(Agent agent, RuntimeContext ctx,
                                    AgentInput input,
                                    Function<AgentInput, Flux<AgentEvent>> next) {
        long start = System.nanoTime();
        return next.apply(input)
                .doOnComplete(() -> log(ctx, "onAgent 结束",
                        (System.nanoTime() - start) / 1_000_000));
    }

    @Override
    public Flux<AgentEvent> onReasoning(Agent agent, RuntimeContext ctx,
                                        ReasoningInput input,
                                        Function<ReasoningInput, Flux<AgentEvent>> next) {
        long start = System.nanoTime();
        // ReasoningInput 里能看到本轮的 tools 数量，这是判断
        // 「模型是否被授予了工具」最直接的位置
        System.out.println("[onReasoning] 进入 messages=" + input.messages().size()
                + " tools=" + input.tools().size());
        return next.apply(input)
                .doOnComplete(() -> log(ctx, "onReasoning 结束",
                        (System.nanoTime() - start) / 1_000_000));
    }

    @Override
    public Flux<AgentEvent> onModelCall(Agent agent, RuntimeContext ctx,
                                        ModelCallInput input,
                                        Function<ModelCallInput, Flux<AgentEvent>> next) {
        long start = System.nanoTime();
        return next.apply(input)
                .doOnComplete(() -> log(ctx,
                        "onModelCall 结束 model=" + input.model()
                                + " messages=" + input.messages().size()
                                + " 耗时=" + (System.nanoTime() - start) / 1_000_000 + "ms"));
    }

    @Override
    public Mono<String> onSystemPrompt(Agent agent, RuntimeContext ctx,
                                       String currentPrompt) {
        // Transformer 型：返回新字符串，没有 next
        System.out.println("[onSystemPrompt] 长度=" + currentPrompt.length());
        return Mono.just(currentPrompt);
    }

    private void log(RuntimeContext ctx, String stage, long costMs) {
        System.out.printf("[%s] userId=%s sessionId=%s 耗时=%dms%n",
                stage, ctx.getUserId(), ctx.getSessionId(), costMs);
    }

    // 说明：Agent 接口读取名称的方法请以当前版本的 API 参考为准，
    // 常见形式为 name() 或 getName()。本例只用 RuntimeContext 中的标识，
    // 因此不依赖该方法。
}

装载方式如下，middlewares 接受列表：

LoadMiddleware.javajava
package com.example.kb;

import io.agentscope.core.ReActAgent;
import io.agentscope.core.tool.Toolkit;

import java.util.List;

public class LoadMiddleware {

    public static ReActAgent buildAgent(String modelName, Toolkit toolkit) {
        return ReActAgent.builder()
                .name("kb-assistant")
                .sysPrompt("你是一个团队知识助手。")
                .model(modelName)
                .toolkit(toolkit)
                .middlewares(List.of(

    }

未实现的扩展点会直通

StageObservabilityMiddleware 没有实现 onActing，因此工具调用不会产生任何额外日志。这是刻意安排的：把中间件写成「只覆盖我关心的阶段」是一种常用做法，因为每多覆盖一个扩展点，就多一层对内层事件的观察与加工，也多一分影响正确性的机会。

示例二：耗时统计与调用限流

本章场景的前两项目标由两个中间件完成，它们放在同一个文件里。

耗时统计的关键选择是 doFinally 而不是 doOnComplete：前者无论流是正常结束、报错还是被取消都会执行，因此统计结果不会因为异常而丢失。

LatencyAndRateLimit.javajava
package com.example.kb;

import io.agentscope.core.agent.Agent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.middleware.MiddlewareBase;
import io.agentscope.core.middleware.ModelCallInput;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

import java.time.Duration;
import java.util.concurrent.atomic.AtomicLong;
import java.util.function.Function;

/** 耗时统计：记录每次模型调用的毫秒数与结束信号。 */
class ModelLatencyMiddleware extends MiddlewareBase {

    private final AtomicLong total = new AtomicLong();
    private final AtomicLong count = new AtomicLong();

    @Override
    public Flux<AgentEvent> onModelCall(Agent agent, RuntimeContext ctx,
                                        ModelCallInput input,
                                        Function<ModelCallInput, Flux<AgentEvent>> next) {
        long start = System.nanoTime();
        return next.apply(input)
                .doFinally(signal -> {
                    long costMs = (System.nanoTime() - start) / 1_000_000;
                    long n = count.incrementAndGet();
                    long sum = total.addAndGet(costMs);
                    System.out.printf(
                            "[latency] cost=%dms signal=%s 累计 n=%d 平均=%dms%n",
                            costMs, signal, n, sum / n);
                });
    }

    /** 供业务侧读取聚合结果。 */
    public long averageCostMs() {
        long n = count.get();
        return n == 0 ? 0 : total.get() / n;
    }
}

/**
 * 调用限流：保证两次模型调用之间的最小间隔。
 *
 * 注意：这里用AtomicLong 记录上次调用的发起时刻，
 * 实现的是「按发起时间间隔」而非严格的排队限流。
 * 如果你需要严格的并发上限（例如同时只允许 1 个模型请求），
 * 请使用 flatMap(..., 1) 之类的背压手段，或在网关层做限制。
 */
class RateLimitMiddleware extends MiddlewareBase {

    private final long minIntervalMs;
    private final AtomicLong lastCallAt = new AtomicLong(0);

    RateLimitMiddleware(long minIntervalMs) {
        this.minIntervalMs = minIntervalMs;
    }

    @Override
    public Flux<AgentEvent> onModelCall(Agent agent, RuntimeContext ctx,
                                        ModelCallInput input,
                                        Function<ModelCallInput, Flux<AgentEvent>> next) {
        long now = System.currentTimeMillis();
        long elapsed = now - lastCallAt.getAndSet(now);
        long waitMs = Math.max(0, minIntervalMs - elapsed);

        if (waitMs == 0) {
            return next.apply(input);
        }
        // 延迟之后继续，顺序与内层事件的先后都被保留
        return Mono.delay(Duration.ofMillis(waitMs))
                .thenMany(next.apply(input));
    }
}

public class LatencyAndRateLimit {

    public static void main(String[] args) {
        ModelLatencyMiddleware latency = new ModelLatencyMiddleware();
        // 两次模型调用之间至少间隔 800 毫秒
        RateLimitMiddleware rateLimit = new RateLimitMiddleware(800);

        // order=2 让统计位于限流之外，因此统计到的是含等待的端到端时间；
        // 若想只统计模型本身耗时，把 order 设为 0
        ReActAgent agent = ReActAgent.builder()
                .name("kb-assistant")
                .sysPrompt("你是一个团队知识助手。")
                .model("dashscope:qwen-plus")
                .toolkit(KnowledgeTools.create())
                .middlewares(List.of(latency, rateLimit))
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan").sessionId("latency-001").build();

        agent.call(new UserMessage("退款流程是怎样的？"), ctx).block();

        System.out.println("平均耗时=" + latency.averageCostMs() + "ms");
    }

    static class KnowledgeTools {
        static Toolkit create() {
            return new Toolkit();
        }
    }
}
order 在这里的实际意义

把耗时统计设为 order = 2、限流设为 order = 1，那么统计中间件位于限流中间件之外，测到的是「含限流等待」的端到端耗时。如果把它设为 order = 0，它就会运行在限流中间件内部，测到的纯粹是模型 API 的耗时。两种口径都有意义，因此选择哪一种取决于你要回答什么问题。

示例三：动态系统提示词

前面几章的系统提示词都是构建时写死的字符串。但有些信息只有运行时才知道：当前时间、当前用户所属租户。把它们写死意味着要么定期重建 Agent，要么在提示词里留一个空字段让模型自己猜。两种做法都不好，因此这里用 onSystemPrompt 解决。

这个中间件实现 Supplier<String>，把「要注入什么」与「怎么注入」分开：get() 负责产出文本，onSystemPrompt 负责把它追加到当前提示词之后。

DynamicSystemPromptMiddleware.javajava
package com.example.kb;

import io.agentscope.core.agent.Agent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.middleware.MiddlewareBase;
import reactor.core.publisher.Mono;

import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.format.DateTimeFormatter;
import java.util.function.Supplier;

/**
 * 动态系统提示词。
 * 实现 Supplier<String> 把上下文文本的产出与注入方式分离：
 * get() 每次被调用都重新计算，因此时间等信息始终是当下的值。
 */
public class DynamicSystemPromptMiddleware extends MiddlewareBase
        implements Supplier<String> {

    private static final DateTimeFormatter FORMAT =
            DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");

    /** 与请求无关的租户标识，可以安全地放在实例字段里。 */
    private final String tenantId;

    public DynamicSystemPromptMiddleware(String tenantId) {
        this.tenantId = tenantId;
    }

    @Override
    public String get() {
        return "## Current Context\n"
                + "- 当前时间：" + LocalDateTime.now().format(FORMAT) + "\n"
                + "- 当前时区：" + ZoneId.systemDefault().getId() + "\n"
                + "- 当前租户：" + tenantId + "\n";
    }

    @Override
    public Mono<String> onSystemPrompt(Agent agent, RuntimeContext ctx,
                                       String currentPrompt) {
        // 单次请求内的信息直接来自 RuntimeContext，
        // 不需要经过 Supplier
        String injected = get()
                + "- 当前用户：" + ctx.getUserId() + "\n"
                + "- 会话标识：" + ctx.getSessionId();

        // 多行文本块用 + 连接，末尾留一个空行分隔
        return Mono.just(currentPrompt + "\n\n" + injected + "\n");
    }
}

第一行日志来自上一节的全阶段观测中间件，这说明两个中间件都装上了。另外注意 长度=612 这个数字：同一个 Agent 实例在不同时刻调用，这个长度会随时间变化，而 Agent 对象并没有重建。因此提示词是每次推理重新组装的。

不要在 onSystemPrompt 里做耗时操作

这个扩展点在每次推理时被调用，而且位于 onReasoning 内部。如果 get() 中包含远程查询或文件读取，它会直接加到每一轮推理的延迟上。本章的例子里只读取内存中的字段，因此开销可以忽略。如果确实需要动态内容，建议在 onAgent 中提前算好放进 RuntimeContext，onSystemPrompt 里只做读取。

下面是完整的初始化代码。这段代码有三处不可省略：导出地址、批处理器、关闭钩子。

TracingSetup.javajava
package com.example.kb;

import io.agentscope.core.ReActAgent;
import io.agentscope.core.tracing.OtelTracingMiddleware;
import io.opentelemetry.api.OpenTelemetry;
import io.opentelemetry.api.trace.Tracer;
import io.opentelemetry.context.propagation.ContextPropagators;
import io.opentelemetry.exporter.otlp.http.trace.OtlpHttpSpanExporter;
import io.opentelemetry.sdk.OpenTelemetrySdk;
import io.opentelemetry.sdk.trace.SdkTracerProvider;
import io.opentelemetry.sdk.trace.export.BatchSpanProcessor;
import io.opentelemetry.api.trace.propagation.W3CTraceContextPropagator;

public class TracingSetup {

    public static void main(String[] args) {
        // ---- 1. SDK 初始化：整个进程只能做一次 ----
        String endpoint = System.getenv().getOrDefault(
                "OTEL_EXPORTER_OTLP_ENDPOINT",
                "http://localhost:4318/v1/traces");

        // 可选：需要 Authorization header 的后端（例如 Langfuse）
        // 变量值形如 Basic <base64-credentials>
        String authorization = System.getenv("OTEL_EXPORTER_OTLP_AUTHORIZATION");

        var exporterBuilder = OtlpHttpSpanExporter.builder().setEndpoint(endpoint);
        if (authorization != null && !authorization.isBlank()) {
            exporterBuilder.addHeader("Authorization", authorization);
        }

        SdkTracerProvider tracerProvider = SdkTracerProvider.builder()
                .addSpanProcessor(
                        BatchSpanProcessor.builder(exporterBuilder.build()).build())
                .build();

        OpenTelemetry openTelemetry = OpenTelemetrySdk.builder()
                .setTracerProvider(tracerProvider)
                .setPropagators(ContextPropagators.create(
                        W3CTraceContextPropagator.getInstance()))
                .buildAndRegisterGlobal();

        // ---- 2. 关闭钩子：保证进程退出前把未发送的 span 刷出去 ----
        Runtime.getRuntime().addShutdownHook(new Thread(tracerProvider::close));

        // ---- 3. 装载中间件 ----
        ReActAgent agent = ReActAgent.builder()
                .name("kb-assistant")
                .sysPrompt("你是一个团队知识助手。")
                .model("dashscope:qwen-plus")
                .toolkit(KnowledgeTools.create())
                .middleware(new OtelTracingMiddleware())
                .build();

        Tracer tracer = openTelemetry.getTracer("com.example.kb");

        // 从这里开始，模型调用与工具执行会自动产生 span
        runOnce(agent);

        // 正常退出时主动关闭，也可以不依赖关闭钩子
        tracerProvider.close();
    }

    private static void runOnce(ReActAgent agent) {
        // 实际业务调用
    }

    static class KnowledgeTools {
        static io.agentscope.core.tool.Toolkit create() {
            return new io.agentscope.core.tool.Toolkit();
        }
    }
}

这个中间件会为三个扩展点生成嵌套的 span：

扩展点span 名称含义
onAgentinvoke_agent <name>一次完整的 reply，是最外层的 span
onModelCallchat <model>一次模型 API 调用，是 invoke_agent 的子 span
onActingexecute_tool <name>一次工具调用，与模型调用同级

span 的属性包含 agent 名称、session ID、模型名称、token 数量、工具名称与输入，因此后端可以直接按这些维度聚合。因为 span 是嵌套的，所以调用链在可视化后端里天然呈现为树形。

它的实现有一个重要特征：未配置 SDK 时开销接近零。此时三个扩展点都直接执行 next.apply(input)，不做任何埋点工作。此外它读取的是进程级的 GlobalOpenTelemetry，因此只要全局已经注册，中间件就能直接使用。

SDK 初始化的四条硬约束
  • 每个进程只注册一次：重复调用 buildAndRegisterGlobal() 会抛异常。
  • 必须在使用中间件之前注册：OtelTracingMiddleware 读取全局对象，注册顺序不对会拿不到 Tracer。
  • 不要调用已弃用的 TracerRegistry.register(...)：该 API 属于旧版本 SDK，请改用 buildAndRegisterGlobal()。
  • 必须关闭 SdkTracerProvider：BatchSpanProcessor 是批量上报的，不关闭就不会发出最后一批 span。本例同时用了关闭钩子与显式关闭，两者并不冲突。

如果你的应用是 Spring Boot，并且 OpenTelemetry 的自动配置已经注册了 GlobalOpenTelemetry，那么直接复用它即可，不要再注册一次。

需要指向某个具体的追踪后端时，用环境变量指定即可：

环境变量bash
export OTEL_EXPORTER_OTLP_ENDPOINT="https://cloud.example.com/api/public/otel/v1/traces"
# 后端要求 Authorization header 时（官方特别提到 Langfuse）
export OTEL_EXPORTER_OTLP_AUTHORIZATION="Basic <base64-credentials>"

示例五：模型故障转移

第五个中间件解决一个具体的稳定性问题：单个模型实例在高峰期可能返回 429 或 5xx。一个能在失败时切换到备用模型、又不影响正常路径的写法是onErrorResume。

它的价值在于调用方感知不到失败：Agent 依然是调用了一个模型，只是这次调用的是备用实例。因此业务代码不需要写任何重试逻辑。

ModelFailoverMiddleware.javajava
package com.example.kb;

import io.agentscope.core.agent.Agent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.middleware.MiddlewareBase;
import io.agentscope.core.middleware.ModelCallInput;
import io.agentscope.core.model.Model;
import reactor.core.publisher.Flux;

import java.util.function.Function;

/**
 * 模型故障转移：主模型调用失败时改用备用模型。
 *
 * 工作位置很关键——onModelCall 最接近模型，
 * 因此这里的重试不会把 ReAct 循环的状态带入重来一遍，
 * 也不会重新组装系统提示词。
 */
public class ModelFailoverMiddleware extends MiddlewareBase {

    private final Model fallback;
    private final int maxRetries;

    public ModelFailoverMiddleware(Model fallback, int maxRetries) {
        this.fallback = fallback;
        this.maxRetries = maxRetries;
    }

    @Override
    public Flux<AgentEvent> onModelCall(Agent agent, RuntimeContext ctx,
                                        ModelCallInput input,
                                        Function<ModelCallInput, Flux<AgentEvent>> next) {
        // ModelCallInput 的字段都是不可变的，
        // 换模型必须构造一个新的 input
        ModelCallInput switched = new ModelCallInput(
                input.messages(),
                input.tools(),
                input.options(),
                fallback);

        return next.apply(input)
                .onErrorResume(err -> {
                    System.err.println("[failover] 主模型失败，切换到备用模型："
                            + err.getMessage());
                    if (maxRetries <= 0) {
                        return Flux.error(err);
                    }
                    return next.apply(switched);
                });
    }
}

装载时可以放在靠近模型的位置：

FailoverSetup.javajava
// order=0：运行在最内层，紧贴模型，
// 因此故障转移不会触发任何外层中间件的「重试」计数
ReActAgent agent = ReActAgent.builder()
        .name("kb-assistant")
        .sysPrompt("你是一个团队知识助手。")
        .model("dashscope:qwen-max")      // 主模型
        .toolkit(toolkit)
        .middlewares(List.of(
                new ModelFailoverMiddleware(backupModel, 1)))
        .build();
关于这个写法的两点说明

其一，next.apply(switched) 复用了同一个 next，因此备用模型走的仍然是当前扩展点的下游链路。如果 maxRetries 大于 1，你需要在 onErrorResume 内部显式做次数控制，否则会形成自我递归。示例中因此直接返回 Flux.error(err)。生产环境更稳妥的做法是把备用模型包装成一个显式的降级响应，让模型自己决定如何继续，而不是无条件重试。

其二，故障转移改变的是模型，因此不同模型的工具调用能力、上下文长度可能不一致。切换前应当确认备用模型支持 input.tools() 中的全部工具。

示例六：只保留最终答案

最后一个例子来自内置中间件。ReAct 循环中，模型在调用工具之前通常会先说一句「我来查一下」。这些文本对用户没有价值，尤其是在把流式输出直接呈现给用户的界面上。FinalAnswerFilterMiddleware 解决的就是这个问题。

本中间件在 2.0.3 中引入

官方 2.0.3 的 Release Notes 把 FinalAnswerFilterMiddleware 列为新增项 （对应 PR #2926 与 issue #2872），因此如果你使用的版本低于 2.0.3， classpath 中不会有这个类。使用前请确认依赖版本。

它的工作方式是：按模型调用缓冲文本事件， 当本轮产生工具调用时抑制中间轮次的文本， 只输出最终面向用户的回答。 由于每轮文本必须缓冲到模型调用结束才能判断该轮是否会调用工具， 因此输出会略微延迟，这是设计的必然结果。

FinalAnswerFilterDemo.javajava
package com.example.kb;

import io.agentscope.core.ReActAgent;
import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.event.AgentEventType;
import io.agentscope.core.event.TextBlockDeltaEvent;
import io.agentscope.core.middleware.FinalAnswerFilterMiddleware;
import io.agentscope.core.message.UserMessage;

public class FinalAnswerFilterDemo {

    public static void main(String[] args) {
        ReActAgent agent = ReActAgent.builder()
                .name("kb-assistant")
                .sysPrompt("你是一个团队知识助手。")
                .model("dashscope:qwen-plus")
                .toolkit(KnowledgeTools.create())
                .middlewares(List.of(new FinalAnswerFilterMiddleware()))
                .build();

        agent.streamEvents(List.of(new UserMessage("退款流程是怎样的？")))
                .doOnNext(FinalAnswerFilterDemo::print)
                .blockLast();
    }

    private static void print(AgentEvent event) {
        // 只渲染最终一轮的文本：
        // 「我来查一下」这类中间轮次文本已被中间件抑制
        if (event.getType() == AgentEventType.TEXT_BLOCK_DELTA) {
            System.out.print(((TextBlockDeltaEvent) event).getDelta());
        }
    }

    static class KnowledgeTools {
        static io.agentscope.core.tool.Toolkit create() {
            return new io.agentscope.core.tool.Toolkit();
        }
    }
}

它的行为需要准确理解，因为它有一个容易误解的限制：

  • 只暴露最终 ReAct reasoning round 的文本。
  • 产生 tool call 的中间轮次，其文本被抑制。
  • tool event 与其他非文本 event 继续正常流出，因此进度条之类的界面元素不会消失。
  • 每一轮的文本会缓冲到模型调用结束。原因是在此之前无法确认这一轮会不会调用工具——只有拿到完整输出才能判断它是中间轮还是最终轮。

最后一条是这个中间件的代价：它牺牲了流式输出的实时性。如果你需要逐字输出效果，就不要装它。

7.3内置中间件速查

除本章示例之外，框架还提供三个内置中间件。它们的包路径与启用方式差别不小，因此单独列表。

类名包路径作用启用方式
OtelTracingMiddlewareio.agentscope.core.tracing为 onAgent、onModelCall、onActing 生成 OpenTelemetry span；未注册 SDK 时直通.middleware(new OtelTracingMiddleware())，需先注册 GlobalOpenTelemetry
TaskReminderMiddlewareio.agentscope.core.middleware配合内置 TodoTools 使用：每次 reasoning step 前读取 AgentState.tasksContext，渲染为 <system-reminder> 注入上下文，让长时间运行的任务持续与计划保持一致通过 enableTaskList(true) 启用相关能力，官方示例中未显式构造
FinalAnswerFilterMiddlewareio.agentscope.core.middleware只暴露最终 ReAct 轮次的文本，抑制中间轮次；tool event 与非文本事件不受影响.middlewares(List.of(new FinalAnswerFilterMiddleware()))

TaskReminderMiddleware 解决的是长时间任务中的典型问题：智能体制定了计划，但在几十轮之后忘记了进度。它在每个 reasoning step 之前把任务清单重新注入一次，因此模型始终知道「现在该做第几步」。这类能力需要在构建器上启用任务清单，而不是手工 new 出来。

7.4中间件设计清单

中间件是可复用、可并发、跨 Agent 共享的组件，这几个性质决定了它的写法与普通业务类不同。下面这份清单建议在每个中间件写完后逐条过一遍。

写中间件时的检查清单
  • 不缓存单次请求的状态：实例字段里只放与请求无关的配置（限流间隔、上报开关、备用模型）。per-request 数据放RuntimeContext，或使用 Reactor 的 contextWrite。
  • 明确 order 的意图：能说出「为什么这层要在这层外面或里面」。贴近模型的任务（限流、故障转移）用小值，全局观测与审计用大值。
  • 只覆盖需要的扩展点：未实现的扩展点会直通，这是特性而不是遗漏。
  • 确认 onActing 的覆盖范围：外部执行工具不会被 onActing 跟踪，这类工具的可观测需要在应用层另行实现。
  • 改写输入时构造新对象：四个 input 类型都是不可变的，用构造器生成新对象再传给 next。
  • 替换模型时确认能力一致：故障转移或限流切换模型前，确认备用模型支持全部 tools。
  • 考虑流式语义：内层中间件先看到事件。如果要统计原始事件数量，逻辑必须放在最内层。
  • 异常路径也要执行清理：清理逻辑用 doFinally 而不是 doOnComplete，否则异常和取消时会漏掉。
  • transformer 型注意执行位置：onSystemPrompt 在每次推理时被调用，其中不要做远程查询或文件读取；需要动态内容时先在 onAgent 中算好。
  • 知道 transformer 型没有 next：想「观察但不修改」时返回 Mono.just(currentPrompt)，不能试图调用下一个中间件。
  • 全局状态只注册一次：OpenTelemetry 这类进程级对象重复注册会抛异常，已有自动配置时直接复用。
  • 有验证手段：有一组用例能确认中间件确实被调用，而不只是「装了但没生效」。最直接的办法是在最外层打印一条日志。

清单里最容易被忽略的是第 1 条与第 7 条。前者是因为中间件实例长期复用，一个字段写错就会在并发场景下产生难以定位的串数据问题；后者则是因为「我统计到的事件数不对」这类现象，根因往往在于把统计逻辑写在了外层。由此可见，中间件的两个关键约束——实例复用与嵌套次序——都不是从代码语法上看出来的，而是从生命周期上看出来的。语法正确的中间件依然可能写错这两点，因此它们必须逐条确认，而不是凭直觉。

最后补充一个 Reactive 编程层面的注意点。中间件运行在 Reactor 链条上，因此不要在 onXxx 方法体里执行阻塞操作。如果确实需要访问阻塞资源（例如同步的 HTTP 客户端），请包装成 Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())，否则会占用事件循环线程，在并发稍高时表现为整体响应变慢而不是单个请求变慢。

7.5本章小结

  • 中间件让你在不修改 Agent 与模型代码的前提下插入逻辑，分为日志追踪、治理、输入改写与输出加工四类目的。
  • 五个扩展点有明确嵌套关系：onAgent ⊃ ReAct 循环 ⊃ onReasoning ⊃（onSystemPrompt 与 onModelCall），onActing 与推理同级。
  • Onion 型包装下一个 handler，可在 next.apply(input) 前后插入逻辑并观察事件流；Transformer 型从左到右组成 pipeline，没有 next。
  • Onion 型 order 越大越靠外层，缺省为 1，相同 order 保持注册顺序。内层中间件先看到流式事件。
  • 四个 Onion 型扩展点的 input 类型都是不可变的，改写字段必须构造新对象，例如 new ModelCallInput(msgs, tools, options, fallback)。
  • onActing 只跟踪 Agent runtime 内部执行的工具，外部执行工具不在其中。
  • 同一次 reply 中所有扩展点与工具共享同一个 RuntimeContext，但是绝不能在中间件实例字段里保存单次请求的状态。
  • 三个内置中间件：OtelTracingMiddleware（链路追踪，类名中没有单独的 TracingMiddleware）、TaskReminderMiddleware（任务提醒）、FinalAnswerFilterMiddleware（只输出最终答案，代价是失去逐字流式效果）。
  • 官方文档中存在带 RuntimeContext 与不带它的两组签名，页面未说明差异来源，因此应以你所安装版本的 API 参考为准。

把本章的内容收束成一句话：中间件的价值不在于「能写多少逻辑」，而在于它把逻辑放在了正确的位置上。限流要放在 onModelCall，提示词注入要放在 onSystemPrompt，全链路追踪要放在 onAgent。位置选对了，代码通常很短；位置选错了，代码写得再长也解决不了问题。于是下一章的问题自然出现：框架自己已经内置了一批中间件，它们与你自己写的中间件之间是什么关系？

练习
  1. 按示例一实现一个 StageObservabilityMiddleware，在四个 Onion 型扩展点与 onSystemPrompt 中都打印进入日志。运行一次包含工具调用的任务，根据打印顺序画出实际的嵌套结构，并说明它与7.1 节给出的图是否一致。
  2. 实现 ModelLatencyMiddleware，分别用 order = 0 与 order = 5 装载两次，对比输出的耗时数值。解释为什么两次结果不同，以及在什么场景下应该选哪一种。
  3. 把示例三的 DynamicSystemPromptMiddleware 改为不在 get() 中读取时间，而是在 onAgent 中计算一次并放入 RuntimeContext，然后由 onSystemPrompt 读取。说明这种改法解决了什么问题。
  4. 接入 OtelTracingMiddleware，分别用两个 order 值各运行一次任务，在后端对比span 的父子关系，并说明 trace 层级如何随 order 变化。
  5. 设计一个「自动重试」中间件：当 onModelCall 遇到异常时，最多重试两次，每次间隔递增。要求重试次数记录在 RuntimeContext 中，而不是中间件的实例字段里。然后用两个并发请求验证计数是否相互独立。
  6. 设计题：为一个对外提供服务的知识助手设计一整套中间件方案。需要满足：每次调用可按 sessionId 追踪；模型调用不超过每秒 5 次；主模型不可用时切换备用模型；所有工具被拒绝时立即停止；系统提示词中包含当前日期。请写出每个中间件的order 取值与理由，并说明哪些需求无法用中间件解决。
