模型层决定了智能体的可靠性

一个智能体应用在演示阶段表现良好，进入生产后通常会遇到三类问题：服务商接口超时、某个租户使用了不同的密钥、以及模型的自由文本输出无法被程序处理。这三个问题的答案全部位于模型层，因此本章单独讨论它。

AgentScope Java 把模型层拆成若干职责明确的接口，因此上面三类问题分别对应不同的机制：接入问题由 ModelRegistry 与 ModelProvider 负责，故障问题由 maxRetries 与 fallbackModel 负责，而输出问题由结构化输出机制负责。

场景

本章场景

继续完善团队知识助手，运营团队提出了三项要求：

  • 稳定性：主模型超时或报错时自动改用备用模型，并且切换行为要能被监控
  • 可写入：工单分类结果必须是固定结构的 Java 对象，不允许出现多余文字
  • 多租户：不同企业客户使用各自的 API Key 与接入地址

本章结束时，助手具备这三项能力，并且新增一个可切换的服务商通道。

4.1先讲理论：模型抽象的层次

AgentScope Java 没有为每个服务商单独设计一套智能体 API，而是把模型层拆成五个协作的部分。理解这五个部分的分工，后续遇到接入问题时才能判断问题出在哪一层。

层职责关键类型
ChatModelBase模型调用的抽象基类。负责把消息与工具 Schema 交给具体实现，并把响应转换为 Flux<ChatResponse>。子类只需实现 doStreamio.agentscope.core.model.ChatModelBase
Formatter消息格式转换器。在框架的 Msg 与服务商私有消息格式之间互转，各 provider 的差异大多集中在这里例如 io.agentscope.extensions.model.dashscope.formatter.DashScopeChatFormatter
Credential凭证与模型清单。持有 API Key，并可列出该账号下可用的模型io.agentscope.core.credential.CredentialBase
ModelRegistry模型注册表与解析器。按 model-id 解析出 Model 实例，并管理命名实例、自定义工厂与缓存策略io.agentscope.core.model.ModelRegistry
ModelProvider服务商扩展点。框架通过 Java SPI 自动发现其实现，新增服务商无需修改框架代码ModelProvider

这个分层带来一个直接结果：如果你在 Formatter 中处理了消息角色，那么换成任何一个服务商都不需要改智能体代码。因此当遇到「某个服务商行为与预期不一致」的问题时，第一排查位置应当是 Formatter，而不是智能体逻辑。

解析一个 model-id 时的查找路径 ModelRegistry.resolve("dashscope:qwen-plus") │ ├─ 1. 已注册的命名实例 register(name, model) │ 命中即直接返回 │ ├─ 2. 自定义工厂 registerFactory(regex, factory) │ 正则匹配 model-id，命中则调用工厂创建 │ └─ 3. Java SPI 自动发现的 ModelProvider 实现 supports(modelId, context) 为真时调用 create(...) 密钥来源：对应的环境变量，或 ModelCreationContext 中显式传入的值

缓存策略

解析结果是否缓存，直接影响多租户场景的正确性。因此 ModelRegistry 用 CachePolicy 枚举把这项策略显式化，共三档。

CachePolicy行为适用场景
DEFAULTresolve(String) 保持 legacy model-id 缓存行为；resolve(String, nonEmptyContext) 不缓存默认取值。带上下文解析时天然隔离租户，因此无需额外配置
DISABLED完全不使用缓存，每次解析都创建新的模型实例需要每次都重新读取凭证的场合，例如凭证会被热更新
ENABLED强制缓存与 option() / component() 同时使用时，用户必须提供 cacheId 作为缓存键
ENABLED 与自定义参数组合时的强制约束

当 CachePolicy.ENABLED 与 ModelCreationContext 的 option() 或 component() 同时生效时， 上下文中的参数不再参与缓存键的计算，因此框架要求你显式提供 cacheId。 缺少 cacheId 会导致不同租户共用同一个模型实例， 这在多租户场景下是严重的错误。

容错的两个层次

「模型出错之后怎么办」这个问题在 AgentScope Java 中有两个层次的答案，它们的适用边界不同，因此需要区分。

第一层：框架级容错

声明在 Agent builder 上，由框架负责执行，包括 maxRetries（同一模型的重试次数）与 fallbackModel（重试耗尽后切换到的备用模型）。此外还有 failoverListener 用于观测切换行为。这一层解决的是单次请求的偶发故障。

第二层：自定义中间件

通过中间件拦截模型调用，可以实现更复杂的策略：按租户区分备用模型、按错误类型选择不同备用模型、或者在连续失败后主动降低并发。中间件机制在第七章展开，本章只做预告。

两者的关系是：框架级容错覆盖了大多数常见场景，实现成本极低，因此应当先用它；只有当需求超出「重试次数 + 单一备用模型」这个组合时，才值得引入自定义中间件。

结构化输出的两条路径

结构化输出的目标是：让模型返回的结果可以直接映射为一个 Java 对象，而不是一段需要二次解析的文本。框架为此提供两条路径，选择哪一条由模型能力决定，而不是由你决定。

维度Native 路径Fallback 路径
触发条件supportsNativeStructuredOutput = true该标志为 false；或者 Native 请求被服务端拒绝（HTTP 400）时自动切换
实现方式使用 response_format 配合 json_schema注入一个合成工具 generate_response，并附加指令提示
额外开销零，服务端强制 schema占用一轮工具调用，prompt 变长
正确性来源由服务端的 schema 校验保证依赖模型按提示输出，约束强度较弱

因此选择依据可以归结为一句话：如果该服务商端点支持 json_schema，就走 Native；否则走 Fallback。你通常不需要关心具体是哪条路径，因为框架会自动选择，但延迟指标与成本估算需要按最坏情况考虑。

4.2动手：provider 全景与切换

接入模型有两种写法：字符串 model-id 与显式构造。前者适合快速验证与单一服务商场景，后者适合需要精细控制参数的场景。下面把两种写法并列，先看清差别。

ProviderOverview.javajava
import io.agentscope.core.ReActAgent;
import io.agentscope.core.model.GenerateOptions;
import io.agentscope.core.model.Model;
import io.agentscope.core.model.ModelRegistry;
import io.agentscope.extensions.model.dashscope.DashScopeChatModel;

/**
 * 模型接入的两种形式。
 *
 * 前置条件：环境变量 DASHSCOPE_API_KEY 已配置。
 */
public class ProviderOverview {

    public static void main(String[] args) {

        // 形式一：字符串 model-id。前缀决定 provider，冒号后是模型名。
        // 解析优先级：命名实例 → 自定义工厂 → SPI 自动发现的 ModelProvider
        Model byId = ModelRegistry.resolve("dashscope:qwen-plus");
        System.out.println(byId.getModelName());

        // 形式二：显式构造。可以控制 builder 上的每一项参数，
        // 不依赖环境变量，也不受注册表缓存策略影响。
        Model explicit = DashScopeChatModel.builder()
                .apiKey(System.getenv("DASHSCOPE_API_KEY"))
                .modelName("qwen-plus")
                .stream(true)
                // 开启思考模式会占用额外输出内容，
                // 因此结构化输出场景必须保持关闭。
                .enableThinking(false)
                .nativeStructuredOutput(false)
                .defaultOptions(GenerateOptions.builder()
                        .temperature(0.2)
                        .maxTokens(2048)
                        .build())
                .build();

        // model(...) 同时接受 model-id 字符串与 Model 实例
        ReActAgent agent = ReActAgent.builder()
                .name("kb-assistant")
                .sysPrompt(jt(24,
                        "你是一个团队知识助手。",
                        "回答前先检索文档，不要凭记忆作答。"))
                .model(explicit)
                .build();
    }
}

不经过智能体，直接使用模型

有些任务不需要推理循环，例如文本分类、实体抽取、标题生成。此时直接使用模型可以省去工具装配与事件流的消耗。model.stream(...) 返回 Flux<ChatResponse>，因此可以按流式方式消费。

DirectModelCall.javajava
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.model.ChatResponse;
import io.agentscope.core.model.GenerateOptions;
import io.agentscope.core.model.Model;
import io.agentscope.core.model.ModelRegistry;

import java.util.List;

public class DirectModelCall {

    public static void main(String[] args) {
        Model model = ModelRegistry.resolve("dashscope:qwen-plus");

        model.stream(
                        List.of(new UserMessage("从 1 数到 5。") ),
                        // 第二个参数是本次可用的工具 Schema 列表，直接使用模型时通常为空
                        List.of(),
                        GenerateOptions.builder()
                                .temperature(0.0)
                                .build())
                .doOnNext(chunk -&gt; System.out.println("Chunk: " + chunk.getContent()))
                .doOnComplete(() -&gt; System.out.println("Stream completed"))
                .blockLast();
    }
}

需要留意的是，返回类型中的 ChatResponse 所在包以你所安装版本的 API 参考为准，在 2.0.x 中它位于 io.agentscope.core.model 之下。

4.3动手：结构化输出

知识助手的一项日常任务是工单分类。分类结果需要直接写入工单表，因此必须是结构确定的 Java 对象，而不是一段包含解释文字的回复。

StructuredOutputDemo.javajava
import com.fasterxml.jackson.databind.JsonNode;
import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;

import java.util.List;
import java.util.Map;

/**
 * 结构化输出演示。
 *
 * 目标类型的形状由 Java 类型决定：
 * record 的组件会被转换为 JSON Schema 的 properties，
 * 因此字段名与类型就是契约，不要随意改动。
 */
public class StructuredOutputDemo {

    /** 最常见的写法：Java record 描述输出结构。 */
    public record WeatherResponse(String location,
                                  String temperature,
                                  String condition) {
    }

    /** 结构中可以包含集合。 */
    public record Ticket(String title, String priority, List&lt;String&gt; tags) {
    }

    public static void main(String[] args) {
        ReActAgent agent = ReActAgent.builder()
                .name("ticket-classifier")
                .sysPrompt(jt(24,
                        "你是一个工单分类助手。",
                        "根据用户描述判断优先级，",
                        "priority 只允许取 low / medium / high 之一。"))
                .model("dashscope:qwen-plus")
                .maxRetries(2)
                .build();

        // ---- 读取方式一：直接反序列化为目标类型 ----
        Msg result = agent.call(
                        List.of(new UserMessage("旧金山现在天气如何？")),
                        WeatherResponse.class)
                .block();

        WeatherResponse weather = result.getStructuredData(WeatherResponse.class);
        System.out.println(weather.location()
                + " / " + weather.temperature()
                + " / " + weather.condition());

        // ---- 读取方式二：从元数据中取出原始 Map ----
        // 适用于结构尚未确定、需要先查看字段的阶段
        Object raw = result.getMetadata().get("_structured_output");
        if (raw instanceof Map&lt;?, ?&gt; map) {
            System.out.println(map.get("location"));
        }

        // ---- 目标类型为 JsonNode 时使用原生 JSON Schema ----
        // 适合结构复杂或字段会频繁变动的场景
        Msg freeForm = agent.call(
                        List.of(new UserMessage("把这段需求整理为 JSON。")),
                        JsonNode.class)
                .block();
        JsonNode node = freeForm.getStructuredData(JsonNode.class);

        // ---- 带运行上下文的重载 ----
        Msg withContext = agent.call(
                        List.of(new UserMessage("列出三个未关闭的缺陷。")),
                        Ticket.class,
                        RuntimeContext.builder()
                                .userId("zhangsan")
                                .sessionId("s-004")
                                .build())
                .block();
    }
}

关于上面的代码，有三点需要说明。

  • getStructuredData(Class) 是首选读取方式，它返回目标类型的实例；getMetadata().get("_structured_output") 返回的是未经类型转换的原始结构，适合探索阶段使用。
  • JsonNode 走的是原生 JSON Schema 路径，因此不需要预先声明 Java 类型，代价是失去编译期检查。
  • 结构化输出与工具可以协同：智能体可以先调用检索工具获取事实，再按 schema 输出最终结果。这实际上是最常见的用法，因为多数结构化任务都需要外部信息。
启用思考模式会关闭结构化输出

DashScope 的 enableThinking(true) 与结构化输出不能同时使用， 框架会自动改为 Fallback 路径。如果既需要思考模式， 又需要确定的输出结构，建议改为两段式： 先用一个开启思考模式的智能体产出分析文本， 再用第二个智能体把文本整理为结构化结果。

还有两点框架行为值得知道：第一，当 Native 路径被服务端以 HTTP 400 拒绝时，框架会自动改用合成工具方案，因此偶发的 400 不会直接暴露为业务异常；第二，Fallback 路径的 generate_response 是一个合成工具，它在工具列表中对外可见，如果你的系统需要严格控制工具清单，需要把它计入。

4.4动手：容错配置

运营团队的第一个要求是主模型故障时自动降级，并且切换行为可以被监控。这两点分别由框架的降级配置与 failoverListener 提供。

FaultToleranceDemo.javajava
import io.agentscope.core.ReActAgent;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;

import java.time.Instant;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;

/**
 * 主模型超时自动降级，并把切换行为记录到指标系统。
 */
public class FaultToleranceDemo {

    /**
     * 演示用的指标收集器。
     * 生产环境请替换为 Micrometer、OpenTelemetry 或业务自有的上报通道，
     * 关键要求是：记录动作本身不能阻塞，也不能抛出异常。
     */
    static class Metrics {

        private final Map&lt;String, AtomicLong&gt; failoverCounters =
                new ConcurrentHashMap&lt;&gt;();

        /** 主模型失败时由框架调用，参数分别是主模型与原始异常。 */
        void recordFailover(String primaryModel, Throwable error) {
            failoverCounters
                    .computeIfAbsent(primaryModel, k -&gt; new AtomicLong())
                    .incrementAndGet();

            System.out.println("[failover] " + primaryModel
                    + " 失败原因=" + error.getClass().getSimpleName()
                    + " 时间=" + Instant.now());
        }

        long count(String modelName) {
            AtomicLong counter = failoverCounters.get(modelName);
            return (counter == null) ? 0L : counter.get();
        }
    }

    public static void main(String[] args) {
        Metrics metrics = new Metrics();

        ReActAgent agent = ReActAgent.builder()
                .name("kb-assistant")
                .sysPrompt(jt(24,
                        "你是一个团队知识助手。",
                        "回答前先检索文档，不要凭记忆作答。"))
                // 主模型标识
                .model("dashscope:qwen-plus")
                // 同一模型上的重试次数
                .maxRetries(3)
                // 重试仍然失败时改用的备用模型
                .fallbackModel("dashscope:qwen-max")
                // 切换发生时同步回调，携带原始异常
                .failoverListener((primary, error) -&gt;
                        metrics.recordFailover(primary.getModelName(), error))
                .build();

        Msg reply = agent.call(
                List.of(new UserMessage("支付服务的超时时间是多少？"))).block();

        System.out.println(reply.getTextContent());
        System.out.println("qwen-plus 触发降级次数："
                + metrics.count("qwen-plus"));
    }
}

关于 failoverListener 的三条约束

这个监听器承担了一个容易被忽略的职责，因此它的行为约定需要单独说明。

约束原因实践建议
它是进程内唯一的切换信号主模型调用的错误不会进入事件流，也不会经过中间件，因此外部没有其他途径感知切换发生了把降级计数作为核心监控指标，不要只在错误日志里体现
在切换处同步调用回调会阻塞在切换链路上只做计数与上报，不要在其中做数据库写入或远程调用
实现必须非阻塞且线程安全；抛出的异常会被记录并忽略异常不会向上传播，因此回调里的错误不会让请求失败，但也会被静默丢弃自己 try-catch 并就地记录日志，不要依赖框架的日志
2.0.1 对重试链路的修正

2.0.1 把 OpenAI 的 streaming 分支包进了 Flux.defer， 因此重试会真正重新发起 HTTP 请求，而不是复用已经消费过的流。 在此之前的版本中，流式场景下的重试实际上无法再次请求服务端。

最后提醒一个容易忽略的点：maxRetries 作用于模型调用，因此它与第三章的工具有关但不是同一件事。工具执行失败走的是工具自身的重试与权限流程，两者不要混淆计数。

4.5动手：多租户密钥

第二个要求涉及多租户。正确做法不是为每个租户创建一个智能体，也不是把密钥写进 RuntimeContext，而是用 ModelCreationContext 把创建参数显式传给 ModelRegistry.resolve。

MultiTenantModelDemo.javajava
import io.agentscope.core.model.GenerateOptions;
import io.agentscope.core.model.Model;
import io.agentscope.core.model.ModelCreationContext;
import io.agentscope.core.model.ModelRegistry;

import java.util.List;
import java.util.Map;

/**
 * 多租户模型创建。
 *
 * 所在包：io.agentscope.core.model
 * 关键点：带上下文的 resolve 不参与缓存，
 * 因此不同租户即使使用同一个 model-id，也会得到各自的模型实例。
 */
public class MultiTenantModelDemo {

    /** 租户信息由业务侧维护，与模型层解耦。 */
    record Tenant(String tenantId, String apiKey, String baseUrl) {
    }

    static final Map&lt;String, Tenant&gt; TENANTS = Map.of(
            "acme", new Tenant(
                    "acme",
                    System.getenv("ACME_OPENAI_KEY"),
                    "https://api.openai.com/v1"),
            "globex", new Tenant(
                    "globex",
                    System.getenv("GLOBEX_OPENAI_KEY"),
                    "https://openai.globex.example.com/v1"));

    public static void main(String[] args) {
        Tenant acme = TENANTS.get("acme");
        Tenant globex = TENANTS.get("globex");

        // 同一个 model-id，两个租户
        Model acmeModel = ModelRegistry.resolve(
                "openai:gpt-4.1-mini", contextFor(acme));

        Model globexModel = ModelRegistry.resolve(
                "openai:gpt-4.1-mini", contextFor(globex));

        // 两个实例相互独立，密钥不会串用
        System.out.println("实例是否相同：" + (acmeModel == globexModel));
    }

    /** 把租户配置转换为模型创建上下文。 */
    static ModelCreationContext contextFor(Tenant tenant) {
        return ModelCreationContext.builder()
                .apiKey(tenant.apiKey())
                .baseUrl(tenant.baseUrl())
                .stream(false)
                // 键值形式的自定义参数，最终由模型实现自行读取
                .option("contextWindowSize", 128000)
                // 也可以直接指定某个组件的完整配置对象
                .component(GenerateOptions.class, GenerateOptions.builder()
                        .parallelToolCalls(false)
                        .temperature(0.1)
                        .build())
                .build();
    }
}

ModelCreationContext 的主要入口：

入口类型说明
apiKey(String)String本次创建使用的密钥，优先级高于环境变量
baseUrl(String)String本次创建使用的接入地址
stream(boolean)boolean是否使用流式响应
option(String, Object)键值对传给模型实现的扩展参数
component(Class, T)类型 + 实例直接指定某个组件的配置，例如 GenerateOptions
cacheId(String)String缓存键。CachePolicy.ENABLED 下使用扩展参数时必须提供
不要用静态注册表区分租户

把租户模型注册成全局命名实例，等于让所有请求共享同一个密钥， 在多租户环境下等于把一个租户的凭证暴露给另一个租户。 因此多租户场景必须使用 resolve(modelId, context)， 或者至少为每个租户使用独立的命名实例名。

4.6动手：Spring Boot 配置

在 Spring Boot 项目中，模型通常不手工构造，而是交给 starter 由配置决定。各 provider 都有对应的 starter：agentscope-openai-spring-boot-starter、agentscope-dashscope-spring-boot-starter 等，命名规律为 agentscope-{provider}-spring-boot-starter。

application.yamlyaml
agentscope:
  model:
    # provider 决定使用哪一个模型实现
    provider: openai
  openai:
    # 对应 agentscope.<provider>.api-key
    api-key: ${OPENAI_API_KEY}
    # 对应 agentscope.<provider>.model-name
    model-name: gpt-4.1-mini
    # 对应 agentscope.<provider>.stream
    stream: true

配置键的规律是固定的四类：agentscope.model.provider 选定 provider，其余三项位于 agentscope.<provider> 之下。因此新增一个 provider 时，配置文件的结构完全一致。

当默认值需要调整时，各 starter 提供了对应的 Customizer 接口，例如 OpenAIChatModelBuilderCustomizer 与 DashScopeChatModelBuilderCustomizer。在 @Configuration 中以 @Bean 注册即可：

ModelCustomizerConfig.javajava
import io.agentscope.core.model.GenerateOptions;
import io.agentscope.extensions.model.openai.OpenAIChatModelBuilderCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.annotation.Order;

@Configuration
public class ModelCustomizerConfig {

    /**
     * 为所有 OpenAI 模型实例设置默认生成参数。
     *
     * Customizer 接口的方法签名以你所安装版本的 API 参考为准，
     * 语义是「接收 builder 并追加默认配置」。
     * 多个 Customizer 可以同时存在，@Order 决定应用顺序。
     */
    @Bean
    @Order(10)
    public OpenAIChatModelBuilderCustomizer defaultOptionsCustomizer() {
        return builder -&gt; builder.defaultOptions(
                GenerateOptions.builder()
                        .temperature(0.2)
                        .maxTokens(2046)
                        .build());
    }
}
配置项与显式构造的优先级

配置文件的值会先生成默认模型实例， 而显式构造的模型不受配置影响。混用两种方式时， 请明确当前智能体拿到的是哪一个实例， 否则会出现「改了配置但行为没变」的情况。

4.7动手：接入自定义服务商

如果团队使用的是内部部署的模型服务，官方 provider 中没有对应实现，可以通过 ModelProvider 扩展点接入，而不需要修改任何框架代码。

MyProviderChatModel.javajava
import io.agentscope.core.credential.CredentialBase;
import io.agentscope.core.model.ChatResponse;
import io.agentscope.core.model.ChatModelBase;
import io.agentscope.core.model.GenerateOptions;
import io.agentscope.core.model.Model;
import io.agentscope.core.model.ModelCreationContext;
import io.agentscope.core.model.ModelProvider;
import io.agentscope.core.model.ModelRegistry;
import io.agentscope.core.message.Msg;
import io.agentscope.core.tool.ToolSchema;
import reactor.core.publisher.Flux;

import java.util.List;

/**
 * 自定义服务商示例。
 *
 * 需要完成两件事：
 * 1. 实现模型，继承 ChatModelBase 并实现 doStream
 * 2. 实现 ModelProvider，声明支持哪些 model-id
 *
 * 注意：类必须标注 @Component，或通过 META-INF/services 注册，
 * 否则框架的 Java SPI 发现不会生效。
 */
public class MyProviderChatModel {

    /** 模型实现：把框架消息转换为内部协议，并把响应转换回 ChatResponse。 */
    static class MyChatModel extends ChatModelBase {

        private final String apiKey;
        private final String modelName;

        MyChatModel(String apiKey, String modelName) {
            this.apiKey = apiKey;
            this.modelName = modelName;
        }

        @Override
        protected Flux&lt;ChatResponse&gt; doStream(List&lt;Msg&gt; msgs,
                                              List&lt;ToolSchema&gt; tools,
                                              GenerateOptions options) {
            // 在这里实现真实的 HTTP 调用，
            // 并把每一段响应通过 Flux 依次发出。
            // 官方未公开具体工厂方法签名时，
            // 可先用 Flux.just 构造占位响应验证链路。
            return Flux.error(new UnsupportedOperationException(
                    "请在此实现对内部模型服务的调用"));
        }

        @Override
        public String getModelName() {
            return modelName;
        }
    }

    /** Provider 实现：告诉注册表如何判断与创建。 */
    static class MyProvider implements ModelProvider {

        @Override
        public boolean supports(String modelId, ModelCreationContext context) {
            return modelId != null &amp;&amp; modelId.startsWith("myprov:");
        }

        @Override
        public Model create(String modelId, ModelCreationContext context) {
            String apiKey = (context != null &amp;&amp; context.getApiKey() != null)
                    ? context.getApiKey()
                    : System.getenv("MYPROV_API_KEY");
            String name = modelId.substring("myprov:".length());
            return new MyChatModel(apiKey, name);
        }
    }

    /**
     * 也可以跳过 SPI，直接注册工厂函数。
     * 正则匹配 model-id，命中后调用工厂创建模型。
     */
    static void registerWithFactory() {
        ModelRegistry.registerFactory(
                "myprov:.*",
                modelId -&gt; new MyChatModel(
                        System.getenv("MYPROV_API_KEY"),
                        modelId.substring("myprov:".length())));
    }
}

与自定义 provider 相关的两个细节：第一，框架的 SPI 机制要求实现类可被无参实例化，因此把密钥等可变信息通过 ModelCreationContext 传入，而不是写在实现类里；第二，如果还需要继承凭证能力以支持 listModels()，则需要另外继承 CredentialBase 并实现 getChatModelClass()，该方法返回的类供框架在创建模型时使用。

CredentialDemo.javajava
import io.agentscope.core.credential.CredentialBase;
import io.agentscope.core.model.ModelCard;

import java.util.List;
import java.util.concurrent.atomic.AtomicReference;

/**
 * 凭证实现与模型清单查询。
 *
 * listModels() 返回 List&lt;ModelCard&gt;，
 * ModelCard 提供 modelName() 与 contextSize() 等信息，
 * 可用于构建「模型选择器」这类界面。
 *
 * 注意：CredentialBase 读取密钥的方法名以你所安装版本的
 * API 参考为准，此处写作 getApiKey()。
 */
class CredentialDemo extends CredentialBase {

    @Override
    public Class&lt;?&gt; getChatModelClass() {
        // 返回本凭证对应的模型实现类
        return MyProviderChatModel.MyChatModel.class;
    }

    @Override
    public String getApiKey() {
        String key = System.getenv("MYPROV_API_KEY");
        return (key == null) ? "" : key;
    }

    public void printModelCards() {
        // listModels() 是 Reactor 风格的异步调用，因此返回 Mono
        List&lt;ModelCard&gt; cards = listModels().block();
        if (cards != null) {
            for (ModelCard card : cards) {
                System.out.println(card.modelName()
                        + " 上下文长度=" + card.contextSize());
            }
        }
    }
}

ModelCard 是选择模型时的重要参考：它给出的 contextSize() 直接决定该模型能容纳多少工具 Schema 与历史消息，因此在治理模型成本时，应当把它作为选择依据之一。

4.9结构化输出支持矩阵

这张表决定每个 provider 会走 Native 还是 Fallback 路径，因此直接影响输出延迟与成本。

模型 / 通道supportsNativeStructuredOutput说明
OpenAI（GPT-4o 等）true使用 response_format + json_schema，零额外开销
OpenAI Official（Responses API）true由 Responses 端点保证 schema
OpenAI 通道 + DeepSeek / GLM formatterfalse走 Fallback 路径
DashScopefalse原生端点只支持 json_object，不支持 json_schema
Anthropicfalse默认走 Fallback 路径

在表格之外，还有两个行为会影响实际结果：Native 路径被服务端以 HTTP 400 拒绝时框架会自动改用 Fallback，因此「某天突然变慢」往往与这条规则有关；另外 DashScope 开启 enableThinking 后会被强制使用 Fallback。

选择建议

如果输出结构稳定且对延迟敏感，优先选择支持 Native 的 provider；如果必须使用某个不支持的 provider，那么 Fallback 带来的额外一轮工具调用应当在容量规划中体现出来，而不是等监控告警之后再调整。

4.10本章小结

  • 模型层分为 ChatModelBase、Formatter、Credential、ModelRegistry 与 ModelProvider 五层，排查问题时按层次定位。
  • ModelRegistry 的解析优先级为：命名实例 → 自定义工厂 → SPI 自动发现的 provider。
  • CachePolicy 有 DEFAULT / DISABLED / ENABLED 三档。DEFAULT 下带上下文的 resolve 不缓存，因此多租户场景天然隔离。
  • 容错分两层：框架级的 maxRetries 与 fallbackModel 覆盖常见故障，复杂策略交给中间件（第七章）。
  • failoverListener 是进程内唯一的切换信号，因此实现必须非阻塞、线程安全，且需要自行处理异常。
  • 结构化输出有 Native 与 Fallback 两条路径，由 supportsNativeStructuredOutput 决定，Native 失败时自动切换到 Fallback。
  • 多租户必须使用 ModelCreationContext 传密钥，不要用全局命名实例区分租户。
练习
  1. 用字符串 model-id 与显式构造两种方式分别创建 DashScope 模型，打印两者返回的模型名，并说明它们在凭证来源与缓存行为上的差别。
  2. 定义一个 MeetingRecord record（含标题、时间、参与人数、决议事项列表），让智能体按该结构输出，并分别用 getStructuredData 与 getMetadata().get("_structured_output") 读取结果。
  3. 为知识助手配置 maxRetries(2) 与备用模型，在 failoverListener 中打印主模型名与异常类型，然后人为制造一次超时，观察降级计数是否变化。
  4. 设计题：为一个「高并发 + 严格成本约束」的智能体服务设计降级策略。要求明确：主模型与备用模型的组合、重试次数、哪些错误可以重试而哪些不应重试、如何避免限流错误被重试放大、以及在什么条件下应该直接失败而不是降级。请说明为什么这个策略不能只靠 maxRetries 与 fallbackModel 两个配置项表达。
  5. 用 ModelCreationContext 为两个租户创建 OpenAI 模型实例，设置不同的 apiKey 与 baseUrl，验证两个实例相互独立；然后把 CachePolicy 改为 ENABLED 且不提供 cacheId，观察框架的报错信息。
  6. 为内部部署的模型服务实现一个 ModelProvider，要求支持 myprov: 前缀，并验证它既能通过 SPI 自动发现，也能通过 ModelRegistry.registerFactory 注册。
