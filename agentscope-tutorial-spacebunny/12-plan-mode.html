Plan Mode
先规划，后执行

前面各章讨论的智能体都有一个共同前提：模型说完就做。 但长任务往往需要人先看一眼方案。Plan Mode 把「意图」与「行动」解耦， 让智能体在只读状态下完成思考与计划，经过人工确认之后才进入执行阶段。

一个具体的风险

设想知识助手接到这样一个指令：「把 knowledge/payment/ 下的文档全部迁移到 knowledge/payment-v2/，并更新所有引用。」这个任务会修改几十个文件、影响多个模块的引用关系。如果模型在理解需求之后直接开始移动文件，那么中途任何一次判断失误都会作用在真实文件上。

问题的根源在于：模型的意图与模型的行动没有被分离。第 08 章的 AGENTS.md 里写「涉及生产环境操作时先询问」，这只是提示词层面的建议，它没有在机制上阻止模型写入文件。Plan Mode 补的就是这一层：它让「先想清楚」从一句请求变成一个受约束的执行阶段。

场景

本章场景

延续第八章的团队知识助手，为它加上规划能力：

  • 它接到批量文档迁移这类长任务时，先进入只读规划状态
  • 它把方案写进 plans/PLAN.md，此时不改动任何业务文件
  • 方案经人工确认后，它才调用 plan_exit 进入执行阶段
  • 执行阶段的任务清单与进度实时反映到界面上
  • 调用结束后能判断它停在哪一种状态，从而决定后续动作

12.1先讲理论：三个工具构成的状态机

Plan Mode 是针对长任务的只读规划状态。启用之后，框架向 Toolkit 注册三个工具，模型通过调用它们在规划状态与执行状态之间流转。整个机制只有三个动作，因此也容易理解。

工具作用参数
plan_enter进入 Plan Mode，随后模型进入只读规划状态无
plan_write写入当前 plan 文件，缺省路径为 plans/PLAN.mdcontent
plan_exit退出 Plan Mode 进入执行阶段，触发人工确认（HITL）rationale（可选）

三个工具的流转关系如下。注意 plan_write 不是必需的，但没有它就得不到可审阅的方案。

Plan Mode 状态流转 构建模式（build） 模型可读可写，工具全集可用 │ │ plan_enter ← 一次调用即完成状态切换 ▼ 规划状态（planning） 只允许只读工具 + plan_write + todo_write │ │ plan_write ← 反复调用，逐步完善方案 │ （允许 0 次或多次） │ │ plan_exit(rationale) ← 触发人工确认 ▼ 执行阶段 恢复正常权限校验，模型开始改动文件 若模型不调用 plan_exit，则停留在规划状态。
进入规划

模型自己判断当前任务需要先规划，调用 plan_enter。此后任何写操作都被拒绝。

写出方案

模型调用 plan_write 把方案写入 plans/PLAN.md。可以多次调用，后一次写入会覆盖前一次，因此模型通常在方案成形后才写一次。

请求确认

模型调用 plan_exit 并附带一段理由。此时系统进入人工确认环节，用户同意后才真正开始执行。

构建器选项

Plan Mode 默认关闭，需要显式启用。四个相关选项如下：

方法缺省值说明
enablePlanMode() / enablePlanMode(boolean)false启用 Plan Mode，同时注册三个规划工具
planFileDirectory(String)"plans"plan 文件根目录，取工作区相对路径
allowShellInPlanMode() / allowShellInPlanMode(boolean)false允许模型在规划阶段执行 shell 命令
enableTaskList()—规划阶段的任务清单以 reminder 形式呈现给模型
启用 Plan Modejava
HarnessAgent agent = HarnessAgent.builder()
        .name("planner")
        .model(model)
        .workspace(workspace)
        .enablePlanMode()               // 安装 Plan Mode 三件套工具
        .planFileDirectory("plans")     // 可选，缺省即为 "plans"
        .build();

规划阶段需要查看环境时（例如确认某个目录是否存在），默认连 shell 都不可用。如果你的任务确实需要在规划阶段执行只读命令，可以显式开启：

允许规划阶段执行 shelljava
HarnessAgent agent = HarnessAgent.builder()
        .name("planner")
        .model(model)
        .workspace(workspace)
        .enablePlanMode()
        .allowShellInPlanMode()   // 允许模型在 plan 阶段执行只读 shell
        .build();
allowShellInPlanMode 只适用于只读命令

这个开关不区分读写，它只是把 shell 工具放回可用列表。因此开启之后，安全性依赖你在 AGENTS.md 中写明的命令约定，以及操作系统层面的权限设置。如果迁移任务本身不需要查看环境信息，建议保持关闭。

只读约束的边界

Plan Mode 生效期间，工具列表被替换为一个白名单。被拒绝的调用会返回固定的提示文本，让模型知道原因并调整行为。

类别工具规划阶段
允许read_file、grep_files、glob_files、list_files可用，用于了解现状
允许memory_search、memory_get、session_list、session_history、session_search可用，用于查阅历史与长期事实
允许plan_enter、plan_write、plan_exit、todo_write可用，规划状态的控制手段
拒绝write_file、edit_file被拒绝，这正是 Plan Mode 的目的
拒绝Shell execute缺省被拒绝；调用 allowShellInPlanMode() 后可用

被拒绝时模型看到的文本是固定的，因此可以据此判断是模式限制还是其他原因：

拒绝提示原文text
[Tool denied — plan mode is active]
Only read-only tools and plan_enter / plan_write / plan_exit / todo_write are allowed.

plans 文件与 PlanModeContext 的分离

「当前是否处于规划状态」这项信息与「计划正文」存放在两个完全不同的地方。这一点在第 08 章讲工作区布局时已经出现过，此处需要明确区分。

计划正文规划状态
载体plans/PLAN.mdPlanModeContext
归属Workspace（工作区）AgentState（状态存储）
物理位置工作区下的 plans/ 目录，目录名由 planFileDirectory 决定缺省在工作区之外的 AgentStateStore，本地默认路径为 ~/.agentscope/state/<agentId>/
内容Markdown 格式的方案文本是否处于 planning phase、当前 plan 文件路径
谁写入模型通过 plan_write框架在 plan_enter / plan_exit 时更新
谁读取人直接审阅；模型用 read_file 读取框架在每轮推理前检查，据此决定工具白名单
为什么状态不与文件放在一起

原因与第 08 章相同：状态是恢复工作区本身的前提，它不能与工作区数据相互纠缠。此外，PlanModeContext 只需要保存一个布尔值与一个路径，把它放进 prompt 反而浪费 token。因此你看到两类数据落在两个位置，这是设计结果而不是缺陷。

Plan Mode 与上下文压缩的关系

第 09 章列出了压缩不会触碰的四类内容，其中第一项就是 Plan Mode 上下文。因此一次长时间的规划会话可以安全地进行压缩：规划状态不会因为消息被摘要而丢失。

内容存储位置压缩时是否受影响
PlanModeContextAgentState.getPlanModeContext()不受影响
任务清单AgentState.getTasksContext()不受影响
子智能体后台任务workspace/agents/<parentId>/tasks/不受影响
权限规则AgentState.getPermissionContext()不受影响

一个实践推论是：plans/PLAN.md 不受压缩影响，因此它可以作为长任务的稳定依据。即使上下文被压缩多次，模型仍然可以 read_file 重新读取完整方案，而不依赖可能被摘要过的对话历史。

12.2四种终态

一次调用结束后，智能体可能停在四种不同的状态上。它们的共同点是「模型没有继续执行」，但是原因完全不同，因此对应的处理逻辑也不同。这是本章最需要记住的一张表。

终态判定条件含义建议处理
从未进入规划整个过程中没有出现 plan_enter模型判断任务简单，直接在执行阶段工作正常，无需处理
已退出规划出现 plan_enter，之后出现 plan_exit方案已交付并获确认，执行阶段正在进行正常，等待执行结果
写了方案未退出当前仍在规划状态，且 plans/PLAN.md 存在模型认为方案需要人审阅，等待你确认读取 plan 文件，确认后调用 exitPlanMode(ctx)
只叙述不行动当前仍在规划状态，且没有 plans/PLAN.md模型写了长篇解释但没有落成方案，也没有请求执行在下一轮明确要求「把方案写入 plan 文件」，或直接 exitPlanMode(ctx) 放行
第三与第四种终态不可混用同一套处理逻辑

「写了方案未退出」意味着成果已经在 plans/PLAN.md 里，你只需要审阅；「只叙述不行动」意味着没有任何可审阅的成果，你如果直接放行，模型会在缺少方案的情况下执行，这正是 Plan Mode 本来要避免的情况。因此判定顺序必须是：先看是否仍在规划状态，再看 plan 文件是否存在。

12.3动手：四个示例

本章场景的实现分为四步。示例一是完整流程，示例二与三解决交互控制，示例四把终态判定做成可复用的方法。

启用并观察

用 enablePlanMode() 构建 Agent，通过事件流观察三个工具的调用。

程序化控制

用 enterPlanMode / exitPlanMode 在代码里切换状态，并在执行阶段临时提权。

任务清单

订阅 todo_write 的结果事件，实时更新界面上的进度。

终态判定

把四种终态判定写成一个方法，附带处理建议。

示例一：完整流程与事件观察

先用提示词约定规划行为。由于规划阶段模型仍然可以读取 AGENTS.md，把「什么时候需要先规划」写进人格文件比写在每次提示词里更有效。

workspace/AGENTS.mdmarkdown
## 规划规则

- 任务涉及批量文件改动、跨模块引用更新、数据迁移时，
  必须先进入规划状态，产出方案并请求确认。
- 方案写入 `plans/PLAN.md`，至少包含：目标、影响范围、
  逐步操作、验证方式、回滚方案。
- 单个文件的查询与回答不需要规划。

下面是完整的配置与一次完整流程。事件流用于确认三个工具各在什么时机被调用：

PlanModeBasic.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.event.AgentEventType;
import io.agentscope.core.event.ToolResultEndEvent;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;

import java.nio.file.Paths;

public class PlanModeBasic {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get(".agentscope/workspace"))

                // 注册 plan_enter / plan_write / plan_exit 三个工具
                .enablePlanMode()
                // plan 文件根目录，缺省为 "plans"，此处显式写出便于理解
                .planFileDirectory("plans")
                // 规划阶段的任务清单以 reminder 形式呈现
                .enableTaskList()
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan").sessionId("plan-001").build();

        // 第一轮：提出长任务，观察模型是否先进入规划状态
        agent.streamEvents(new UserMessage(
                "把 knowledge/payment/ 下的文档迁移到 knowledge/payment-v2/，"
                + "并更新所有引用。先给我方案，不要直接改文件。"))
                .doOnNext((AgentEvent e) -> {
                    if (e.getType() != AgentEventType.TOOL_RESULT_END) {
                        return;
                    }
                    ToolResultEndEvent end = (ToolResultEndEvent) e;
                    String name = end.getToolCallName();
                    if ("plan_enter".equals(name)
                            || "plan_write".equals(name)
                            || "plan_exit".equals(name)) {
                        System.out.println("[plan] 调用了 " + name);
                    }
                })
                .blockLast();

        System.out.println("当前仍在规划状态： "
                + agent.isPlanModeActive(ctx));

        // 第二轮：确认方案后进入执行阶段
        Msg reply = agent.call(new UserMessage(
                "方案没问题，按方案执行。"), ctx).block();
        System.out.println(reply.getTextContent());
    }
}

第一轮结束时你会看到大致如下的输出顺序：plan_enter 先出现，plan_write 紧随其后，而 plan_exit 出现在人工确认之后。如果输出里缺少 plan_exit，那么 Agent 停在的就是「写了方案未退出」这一终态。

为了观察方便，也可以把计划正文写成一段提示词常量。下面这段代码展示 Java 文本块的写法，它要求模型至少覆盖目标、影响范围、验证方式三项。

PlanPrompt.javajava
public final class PlanPrompt {

    /** 要求模型在规划阶段至少说明三件事。 */
    public static final String PLAN_REQUIREMENT =
            """
            // 方案至少要覆盖以下三项，缺一不可：
            //   1. 目标：本次变更要达到什么结果
            //   2. 影响范围：会改动哪些文件、哪些模块会受影响
            //   3. 验证方式：完成后如何确认变更正确
            //
            // 请把方案写入 plans/PLAN.md，
            // 写完之后调用 plan_exit 请求确认，不要直接开始执行。
            """;

    /** 人工确认后放行执行。 */
    public static final String APPROVE =
            "方案已确认，请按 plans/PLAN.md 中的步骤执行。";
}

示例二：程序化控制与权限模式切换

模型自主调用 plan_enter 与 plan_exit 适合对话式场景。但在服务端场景中，你往往希望由应用程序决定何时进入规划、何时放行执行。这时使用运行时方法。

运行时方法作用与工具调用的关系
setPermissionMode(ctx, mode)设置当前会话的权限模式无对应工具，由应用程序直接控制
getPermissionMode(userId, sessionId)读取当前权限模式用于确认设置是否生效
enterPlanMode(ctx)进入 Plan Mode等价于模型调用 plan_enter
exitPlanMode(ctx)退出 Plan Mode 进入执行阶段等价于 plan_exit；程序化调用不会触发人工确认
isPlanModeActive(ctx)判断是否处于规划状态用于分支逻辑与终态判定
getAgentState(userId, sessionId)读取完整状态可取出 PlanModeContext、任务清单、权限规则

PermissionMode 位于 io.agentscope.core.permission，共五档：DEFAULT、ACCEPT_EDITS、EXPLORE、BYPASS、DONT_ASK，完整说明见第 06 章。本章只用到其中的 BYPASS、DEFAULT 与 DONT_ASK。

需要注意的是，Plan Mode 与权限模式是两套独立的机制：前者限制「能不能写文件」，后者决定「需要写文件时是否要问」。因此两者可以组合使用，例如在 plan 阶段保持 DEFAULT 模式，退出后再切换为 BYPASS 以减少提示次数。

PermissionMode含义适用场景
BYPASS允许全部操作，不提示计划已确认后的执行阶段，或可信的自动化流程
DEFAULT按规则强制校验，需要确认时询问缺省值，日常使用
DONT_ASK拒绝需要确认的操作，不询问无人值守的拒绝优先场景
PlanModeRuntime.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.permission.PermissionMode;
import io.agentscope.harness.agent.HarnessAgent;

import java.nio.file.Paths;

public class PlanModeRuntime {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get(".agentscope/workspace"))
                .enablePlanMode()
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan").sessionId("my-session").build();

        // 1. 由应用程序主动进入规划状态，不等模型自己决定
        agent.enterPlanMode(ctx);
        System.out.println("规划状态： " + agent.isPlanModeActive(ctx));

        // 2. 规划阶段可以正常对话，模型只能读文件并写 plan
        agent.call(new UserMessage(
                "看一下 knowledge/payment/ 有多少个文件，然后写出迁移方案。"),
                ctx).block();

        // 3. 人工审阅 plans/PLAN.md 之后，由应用程序放行。
        //    注意：程序化调用 exitPlanMode 不会触发人工确认，
        //    因此「确认」这一步必须由你的应用负责。
        agent.exitPlanMode(ctx);
        System.out.println("规划状态： " + agent.isPlanModeActive(ctx));

        // 4. 执行阶段需要完整权限，临时提权。
        //    若不设置，批量改动会逐项请求确认。
        agent.setPermissionMode(ctx, PermissionMode.BYPASS);
        Msg result = agent.call(new UserMessage(
                "按 plans/PLAN.md 中的步骤执行迁移。"), ctx).block();

        // 5. 执行完成后恢复正常强制校验，不要把提权状态留在会话里
        agent.setPermissionMode(ctx, PermissionMode.DEFAULT);

        PermissionMode current =
                agent.getPermissionMode("zhangsan", "my-session");
        System.out.println("执行结果： " + result.getTextContent());
        System.out.println("当前权限模式： " + current);
    }
}
临时提权之后一定要恢复

PermissionMode.BYPASS 是会话级设置，它会持续到会话结束或被显式改回。如果忘记恢复，后续所有需要确认的操作都会被静默放行，这在生产环境中是一个难以发现的安全缺口。因此建议把恢复语句写成 try 的 finally 块。

try-finally 写法java
// 推荐：提权与恢复成对出现
agent.setPermissionMode(ctx, PermissionMode.BYPASS);
try {
    agent.call(new UserMessage("按 plans/PLAN.md 执行迁移。"), ctx).block();
} finally {
    agent.setPermissionMode(ctx, PermissionMode.DEFAULT);
}

示例三：任务清单与进度流式观察

执行阶段的工作通常分解为若干步骤。todo_write 工具负责维护这份清单，而框架不提供独立的任务表，因此读取进度的方式是从 AgentState 中取。

任务对象的状态有三种：PENDING、IN_PROGRESS、COMPLETED。清单存放于 AgentState.getTasksContext().getTasks()。

Task 类的全限定名

官方文档未给出 Task 类的完整包名，不同版本可能存在差异。下面示例统一使用 var 声明局部变量，这样无论包名如何变化都可以编译。查阅具体方法时请以你所安装版本的 API 参考为准。

TaskProgress.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEventType;
import io.agentscope.core.event.ToolResultEndEvent;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;

import java.nio.file.Paths;

public class TaskProgress {

    private static final String USER = "zhangsan";
    private static final String SESSION = "plan-task-001";

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get(".agentscope/workspace"))
                .enablePlanMode()
                .enableTaskList()
                .build();

        // 应用程序放行，进入执行阶段
        RuntimeContext ctx = RuntimeContext.builder()
                .userId(USER).sessionId(SESSION).build();
        agent.exitPlanMode(ctx);

        agent.streamEvents(new UserMessage(
                "按 plans/PLAN.md 执行文档迁移，每完成一个步骤就更新任务清单。"))
                .filter(e -> e.getType() == AgentEventType.TOOL_RESULT_END)
                .filter(e -> "todo_write".equals(
                        ((ToolResultEndEvent) e).getToolCallName()))
                .doOnNext(e -> {
                    // 清单内容由框架保存，这里重新读取最新状态
                    var tasks = agent.getAgentState(USER, SESSION)
                            .getTasksContext()
                            .getTasks();
                    updateUI(tasks);
                })
                .subscribe();

        // 主线程可以继续做别的事，事件在回调线程到达
    }

    /** 把任务清单渲染到界面上。 */
    private static void updateUI(Iterable<?> tasks) {
        StringBuilder sb = new StringBuilder("任务进度\n");
        for (Object t : tasks) {
            // Task 的具体类型请按所用版本核对，
            // 这里通过反射之外的方式：调用 toString 展示内容
            sb.append("  ").append(t).append('\n');
        }
        System.out.println(sb);
    }
}

为什么用 todo_write 事件作为刷新触发点

AgentState 的变化本身没有推送机制，因此需要在已知的时机重新读取。todo_write 的结果是清单唯一稳定的变更入口，所以过滤这个事件最为可靠。如果任务粒度很粗、不需要实时进度，也可以在 AgentEventType.AGENT_END 时读取一次，实现会更简单。

示例四：终态判定器

前面说明过，四种终态需要两种信号才能区分：当前是否处于规划状态，以及 是否出现过 plan_enter 与 plan_write。前者可以直接查询框架，后者需要在事件流里记录。把两者组合起来就得到判定器。

PlanOutcome.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.harness.agent.HarnessAgent;

/** 一次调用结束后智能体可能停留的四种状态。 */
public enum PlanOutcome {

    /** 从未进入规划：模型判断任务简单，直接工作。 */
    NEVER_ENTERED("未进入规划", "正常，无需处理"),

    /** 进入后调用了 plan_exit：方案已确认，正在执行。 */
    EXITED("已退出规划，进入执行", "正常，等待执行结果"),

    /** 仍在规划且方案已落盘：等待人工审阅。 */
    PLAN_WRITTEN("已写出方案，等待确认",
            "读取 plans/PLAN.md，审阅后调用 exitPlanMode(ctx) 放行"),

    /** 仍在规划但没有方案文件：只叙述不行动。 */
    NARRATION_ONLY("只叙述未行动",
            "下一轮明确要求写入方案，或直接 exitPlanMode(ctx) 放行");

    private final String title;
    private final String advice;

    PlanOutcome(String title, String advice) {
        this.title = title;
        this.advice = advice;
    }

    public String getTitle() {
        return title;
    }

    public String getAdvice() {
        return advice;
    }
}
PlanOutcomeClassifier.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEventType;
import io.agentscope.core.event.ToolResultEndEvent;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public class PlanOutcomeClassifier {

    /** 会话级观察记录：是否出现过 plan_enter。 */
    private static final Map<String, Boolean> ENTERED = new ConcurrentHashMap<>();

    /** 会话级观察记录：是否出现过 plan_write。 */
    private static final Map<String, Boolean> PLAN_WRITTEN = new ConcurrentHashMap<>();

    private static String key(String userId, String sessionId) {
        return userId + "/" + sessionId;
    }

    /**
     * 在事件流中记录规划工具的调用。
     * 这个方法是判定器的数据来源。
     */
    public static void observe(String userId, String sessionId, String toolCallName) {
        if ("plan_enter".equals(toolCallName)) {
            ENTERED.put(key(userId, sessionId), Boolean.TRUE);
        } else if ("plan_write".equals(toolCallName)) {
            PLAN_WRITTEN.put(key(userId, sessionId), Boolean.TRUE);
        }
    }

    /**
     * 判定当前处于哪一种终态，并输出处理建议。
     */
    public static PlanOutcome classify(HarnessAgent agent,
                                       String userId,
                                       String sessionId) {
        String k = key(userId, sessionId);

        // 信号一：框架报告的规划状态
        RuntimeContext ctx = RuntimeContext.builder()
                .userId(userId).sessionId(sessionId).build();
        boolean active = agent.isPlanModeActive(ctx);

        // 信号二：本进程观察到的规划工具调用
        boolean everEntered = ENTERED.containsKey(k);
        boolean planWritten = PLAN_WRITTEN.containsKey(k);

        if (!active) {
            // 已退出与从未进入，在框架层面都是「不在规划状态」。
            // 因此必须用是否出现过 plan_enter 把它们区分开。
            return everEntered ? PlanOutcome.EXITED : PlanOutcome.NEVER_ENTERED;
        }
        return planWritten ? PlanOutcome.PLAN_WRITTEN : PlanOutcome.NARRATION_ONLY;
    }

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .enablePlanMode()
                .build();

        String user = "zhangsan";
        String session = "plan-classify-001";

        RuntimeContext ctx = RuntimeContext.builder()
                .userId(user).sessionId(session).build();

        // 第一轮：提出长任务
        agent.streamEvents(new UserMessage(
                "把 knowledge/payment/ 的文档迁移到 knowledge/payment-v2/。"))
                .filter(e -> e.getType() == AgentEventType.TOOL_RESULT_END)
                .doOnNext(e -> {
                    String name = ((ToolResultEndEvent) e).getToolCallName();
                    observe(user, session, name);
                })
                .blockLast();

        PlanOutcome outcome = classify(agent, user, session);
        System.out.println("终态：" + outcome.getTitle());
        System.out.println("建议：" + outcome.getAdvice());

        switch (outcome) {
            case PLAN_WRITTEN:
                // 人工审阅 plans/PLAN.md 之后放行
                agent.exitPlanMode(ctx);
                break;
            case NARRATION_ONLY:
                // 没有可审阅的方案，不要直接放行，
                // 先要求模型把方案写入 plan 文件
                agent.call(new UserMessage(
                        "请把方案写入 plans/PLAN.md，不要只在对话中描述。"),
                        ctx).block();
                break;
            case EXITED:
            case NEVER_ENTERED:
            default:
                break;
        }
    }
}
判定器的两个前提

其一，ENTERED 与 PLAN_WRITTEN 是进程内状态，进程重启后会丢失。此时如果 Agent 仍处于规划状态，判定器会退化到「只叙述不行动」。生产环境应当改为持久化这两项标记，或者读取 plans/ 下是否存在 plan 文件来代替。

其二，如果人工直接删除了 plan 文件，「已写出方案」这一信号也会消失。因此判定结果应当作为提示而不是依据，重要操作前仍应确认 plan 文件的实际存在。

如果你的服务需要跨进程恢复，更稳妥的做法是把「本会话是否已产出方案」这一信息写进你自己的会话记录，而不是依赖进程内存。判定器的骨架不变，只替换数据来源。

12.4适用场景与边界

什么任务该用 Plan Mode

任务特征是否需要 Plan Mode原因
单个文件的查询与回答不需要意图明确，规划的开销大于收益
批量文件改动、跨模块引用更新需要影响范围广，方案需要人工确认
数据迁移与格式转换需要不可逆操作，事先审阅方案是唯一防线
线上环境操作强烈建议把影响范围写成计划再执行，是基本的变更管理流程
需求本身不清晰需要先让模型写出对需求的理解，人工纠正后再执行
高频重复的机械任务不需要每次都规划会显著增加 token 消耗与延迟

值得注意的是，规划本身也消耗 token 与时间。因此它不是默认应该开启的能力，而是按任务类型选择性开启的机制。一个常见做法是始终启用 enablePlanMode()，然后在 AGENTS.md 中明确规定哪些场景必须调用 plan_enter，哪些场景直接执行。模型的判断力足够区分这两类任务。

子智能体的继承问题

这里有一个必须说明的缺口：Plan Mode 期间通过 agent_spawn 生成的子智能体不会自动继承只读限制。也就是说，主智能体处于规划状态时，如果它派发子任务，子智能体仍然可以写入文件。这是只读约束上的一个缺口，因为 Plan Mode 的白名单只作用于主 Toolkit。

与此同时，官方 Release Notes 的 RC2 条目中出现了 Enforce Plan Mode for subagents (#2377)，表明该行为已被修正。两处信息存在版本差异：文档正文与该条目覆盖的版本范围不完全一致。因此请以你所使用版本的实际行为为准，不要依据本节文字假定约束一定生效。

如何自行验证

做一个最小验证：在规划状态下向模型提出一个明确会写文件的请求，观察它是否被拒绝。如果 write_file 返回 [Tool denied — plan mode is active]，说明该版本的主 Toolkit 约束生效；再让模型派发一个写文件的子智能体，观察子智能体的行为。两次结果结合起来，才是你所处版本的真实约束范围。

如果你的场景对只读约束要求严格，在验证清楚之前不要让模型在规划阶段派发写文件的子任务。

管理 HTTP API

使用 agentscope-admin-spring-boot-starter 模块时，管理端提供了直接操作 Plan Mode 的接口。它们适合用于人工干预与运维排查，因为程序化调用不会触发人工确认。

方法与路径作用
POST /v1/admin/sessions/{id}:enter-plan-mode让指定会话进入 Plan Mode
POST /v1/admin/sessions/{id}:exit-plan-mode让指定会话退出 Plan Mode，进入执行阶段
GET /v1/admin/sessions/{id}/plan读取该会话当前的 plan 文件内容
GET /v1/admin/sessions/{sessionId}/tasks读取任务清单，含各任务的 blocks 与 blockedBy 依赖关系

任务清单里的 blockedBy 表示任务之间的先后约束。迁移这类任务通常可以表达为：「迁移文档」阻塞「更新引用」，「更新引用」阻塞「验证结果」。读取这份依赖关系有助于判断任务是否卡在某一步。

任务依赖关系的用途text
[1] COMPLETED     盘点 knowledge/payment/ 下的文档清单
[2] PENDING       迁移到 knowledge/payment-v2/        blockedBy: [1]
[3] PENDING       更新引用该目录的其他文档              blockedBy: [2]
[4] PENDING       校验无残留旧路径引用                  blockedBy: [3]

读到这份清单即可知道：若 [2] 长时间 PENDING，问题在迁移本身；
若 [4] 长期等待，问题多半是引用更新未完成。

plan 文件目录

缺省 plan 文件是 plans/PLAN.md。如果一个工作区里有多套智能体共用 Plan Mode，可以通过 planFileDirectory 给每套智能体一个独立目录，避免计划文件互相覆盖。

为不同用途划分 plan 目录java
// 知识助手：缺省的 plans/
HarnessAgent kbAgent = HarnessAgent.builder()
        .name("kb-assistant")
        .model(model)
        .workspace(workspace)
        .enablePlanMode()
        .planFileDirectory("plans")
        .build();

// 运维助手：独立目录，两者的计划文件互不覆盖
HarnessAgent opsAgent = HarnessAgent.builder()
        .name("ops-assistant")
        .model(model)
        .workspace(workspace)
        .enablePlanMode()
        .planFileDirectory("ops-plans")
        .build();

于是工作区中的目录结构为：

工作区中的 plan 目录text
workspace/
├── plans/                  ← kb-assistant 的计划
│   └── PLAN.md
└── ops-plans/              ← ops-assistant 的计划
    └── PLAN.md

注意 planFileDirectory 接受的是工作区相对路径，不是文件系统路径。写成 "/data/plans" 这类绝对路径不符合它的语义。另外这两个目录里的 Markdown 文件都属于 Workspace 的内容，因此可以被 read_file 读取，也可以纳入版本管理。这与上一节提到的 PlanModeContext 不同，后者在 AgentState 中，不出现在工作区里。

12.5本章小结

  • Plan Mode 是针对长任务的只读规划状态，它的价值在于把「意图」与「行动」解耦，让方案先于文件改动出现。
  • 机制由三个工具构成：plan_enter 进入规划、plan_write 写出方案、plan_exit 触发人工确认并进入执行。三者由 enablePlanMode() 一并注册。
  • 规划阶段只有只读工具与plan_write、todo_write 可用，写文件类工具会被拒绝，提示文本为 [Tool denied — plan mode is active]。
  • 计划正文存在工作区的 plans/PLAN.md，而规划状态存在 AgentState 的 PlanModeContext 中。两者位置不同是有意设计，并且压缩都不会影响它们。
  • 运行时方法 enterPlanMode / exitPlanMode 让应用程序接管状态切换，但是程序化退出不会触发人工确认，因此确认责任落在你的应用上。
  • 一次调用结束后有四种终态：从未进入、已退出、写了方案未退出、只叙述不行动。后两种需要区分处理，因为前者有可审阅的成果而后者没有。
  • Plan Mode 期间派发的子智能体是否受只读约束，文档正文与 Release Notes 存在版本差异，请以所用版本的实际行为为准，并按本章给出的方法自行验证。
练习
  1. 按示例一配置一个启用 Plan Mode 的知识助手，用事件流打印三个规划工具的调用时机，并记录一轮调用后 Agent 停在哪一种终态。
  2. 分别构造四种终态：让模型直接回答（从未进入）、让它规划后确认放行（已退出）、只让它写方案不确认（已写出方案）、只问不做（只叙述不行动）。验证判定器给出的结论与实际一致，并说明为什么后两种不能共用一套处理逻辑。
  3. 在规划阶段向模型提出一个明确的写文件请求，记录拒绝提示的完整文本；然后开启 allowShellInPlanMode() 再试一次，对比两次的差异，并说明这个开关没有做什么。在规划阶段派发一个会写文件的子智能体，记录它的行为，并说明这对只读约束意味着什么。
  4. 为知识助手与运维助手配置不同的 planFileDirectory，验证两个 plan 文件互不覆盖；并说明这两个目录里的文件为什么可以纳入版本管理，而 PlanModeContext 不可以。用 setPermissionMode 临时提权执行一段迁移，故意注释掉恢复语句，观察后续操作是否仍然弹确认，由此说明为什么恢复语句必须写在 finally 中。
  5. 设计题：为团队设计一份 AGENTS.md 中的规划规则，要求区分必须规划、建议规划与无需规划三类任务。请写出每类的判定条件与对应的工具调用，并说明为什么始终启用 enablePlanMode() 而不在代码里分类路由。
