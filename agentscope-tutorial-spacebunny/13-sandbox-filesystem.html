让执行发生在正确的位置

一个具体的风险

知识助手现在有一个新需求：「把用户上传的运维脚本放到我们的环境里执行一遍，把输出整理成报告。」这个需求看起来合理，但是它让智能体第一次接触到了不受信任的代码。

如果文件与命令仍然在宿主上执行，那么这段脚本可以：

  • 读取 /etc/passwd、~/.ssh/id_rsa、~/.agentscope/state/ 中的凭据
  • 用绝对路径或 .. 改写工作区以外的文件
  • 发起对外请求，把数据发送到任意外部地址
  • 耗尽内存与磁盘，导致同一台机器上的其他服务不可用

在 AGENTS.md 里写「不要做危险操作」并不能解决这些问题。提示词是建议，不是边界；真正的边界必须由执行环境提供。因此本章讨论的核心不是提示词怎么写，而是让命令与文件操作在一个受控的环境里发生。

场景

本章场景

延续第八章的团队知识助手，为它增加受控的执行环境：

  • 它处理用户上传的文档与用户提供的脚本，这些内容一律视为不受信任
  • 它的文件操作与命令执行在隔离的沙箱容器内完成，宿主环境不受影响
  • 它可以运行不受信任的脚本，容器有内存、CPU 与网络限制
  • 环境状态可以跨调用恢复：这一轮装好的依赖，下一轮仍然可用
  • 不同用户的工作目录互相隔离，张三看不到李四的临时文件

13.1先讲理论：Workspace 抽象

第八章我们已经使用 .workspace(Paths.get(...)) 指定工作区。这个参数只回答了一个问题：逻辑路径的根在哪里。本章要讲的是另一个问题：这些文件操作真正落到哪个执行环境。

AgentScope Java 把这两件事分开处理。工作区是一套逻辑路径，框架保证 AGENTS.md、MEMORY.md、knowledge/ 这些相对路径在三种模式下含义完全相同；而文件系统实现决定这些路径背后的物理落点与执行边界。

因此可以把整个模型概括为一句话：智能体的行为代码不变，切换文件系统实现即切换执行环境。开发时用本地模式，改一行配置就能迁到 Docker 沙箱，再改一行就能迁到 Kubernetes 集群。

逻辑层与物理层的分离 智能体代码 ──→ 逻辑路径 ──→ 物理落点 read_file("knowledge/payment/service.md") │ │ 三种实现之一 ├─→ LocalFilesystemSpec 宿主磁盘 + 宿主 sh ├─→ DockerFilesystemSpec 容器内文件 + 容器内 sh └─→ RemoteFilesystemSpec 远程 KV（无 shell） 上层不感知下层的存在，这是可插拔的前提。
shell 是文件系统实现的能力，不是智能体的能力

只有能执行命令的实现才提供 shell 工具。远程 KV 模式没有 shell，因此模型只能读写文件，不能运行 grep、tar 这类命令。这个差异会影响到工具集，理解它才能理解为什么三种模式的配置项差别很大。

三种文件系统模式

AgentScope Java 提供三种模式，配置方式与适用场景差别很大。

模式配置方式shell何时使用
1 · 共享存储filesystem(new RemoteFilesystemSpec(store))无多副本共享 MEMORY.md、会话日志、子任务记录（KV 存储）
2 · 沙箱filesystem(new DockerFilesystemSpec()...)，或 K8s / Daytona / E2B / AgentRun有（容器内）隔离执行、跨调用恢复、可选快照
3 · 本地 + shell
（缺省）		省略 .filesystem(...)有（宿主 sh -c）单进程、本地开发、可信环境

模式 3 是缺省行为。省略 .filesystem(...) 时，框架使用本地文件系统，并且启用 shell 工具。因此一个刚刚构建好的 HarnessAgent 已经可以执行命令，这一点与很多框架的默认行为不同，需要留意。

本地模式不提供沙箱隔离

官方 FAQ 明确说明：本地工作区（LocalWorkspace）运行在宿主进程上，不提供沙箱隔离。它的工作是把路径限制在允许的目录内，但这与「进程被关在一个容器里」是两种不同性质的保护：前者是路径检查，后者是资源与权限的边界。

因此：生产环境中，只要智能体有可能运行用户提供的代码，就必须使用沙箱模式。本地模式适用于开发调试、内部可信工具、以及明确没有不受信任输入的场景。把不受信任的代码交给本地模式执行，等于把宿主权限交给了模型。

还有一个必须知道的约束：filesystem(...) 与 abstractFilesystem(...) 是互斥的。前者接收框架提供的实现，后者接收你自己实现的 AbstractFilesystem。同时设置会导致构建失败。

13.2IsolationScope：隔离到哪一层

隔离维度决定「谁的目录和谁的目录分开」。这个选择看起来只是命名，但是它直接影响会话日志、长期记忆、临时文件是否互相可见，因此需要在设计阶段确定。

取值命名空间 key典型用途
SESSIONagents/<agentId>/sessions/<sessionId>/...多用户 SaaS，每个会话完全隔离
USER（缺省）agents/<agentId>/users/<userId>/...同一用户的多个会话共享长期记忆
AGENTagents/<agentId>/shared/...公共知识库型智能体
GLOBALglobal/...整个 store 实例共用一个位置，谨慎使用

缺省值是 USER，也就是说同一用户在不同会话之间共享工作区。这符合大多数产品的预期：一个用户的长期记忆不应该因为换了一个会话 ID 就消失。

缺省标识的回退规则

不是每次调用都带 userId 和 sessionId。框架为缺失的情况定义了明确的回退行为：

情况行为
USER 作用域下缺少 userId回退到 SESSION 作用域
SESSION 作用域下缺少 sessionId跳过状态查找，并新建一个环境（不尝试恢复）
AGENT 作用域使用 agent name 作为 key，build() 时固定
匿名调用方需要显式指定

如果你的服务允许未认证访问（例如公开的试用接口），请用 anonymousUserId("anonymous") 指定一个缺省标识。否则这些调用会退到 SESSION 作用域，每个新会话都变成一个全新沙箱，跨调用恢复与长期记忆都失效。

13.3运行时镜像契约

沙箱模式把智能体的文件工具与命令执行放进一个容器。框架的工具实现依赖容器里的一组系统程序，这些程序必须存在且行为符合预期。官方文档把这组要求称为运行时镜像契约。

换句话说：image("ubuntu:24.04") 不是随便写一个镜像名就可以，这个镜像里必须装齐下表中的程序。

类别要求被谁使用
ShellPOSIX 兼容 sh：支持 [ ]、&&、管道、重定向、heredoc每个 file 工具、execute
核心工具mkdir dirname rm mv test printf sort单文件操作
文本检索sed、grep（需支持 -rHnF、--include）、findread_file 分页、grep_files、glob_files
元数据GNU 风格 stat -c（不是 BSD 的 stat -f）list_files、glob_files
归档编码tar、base64（需支持 -d）快照持久化与回填、文件上传下载
解释器python3edit_file（精确字符串替换）
文件系统可写的工作区根目录（缺省 /workspace）全部工具

合规性检查命令

在把某个镜像投入生产之前，用下面这条命令验证它是否满足契约。这条命令依次检查 shell、python3、tar、base64、stat -c 与 grep 的参数支持情况。

check-runtime-image.shsh
# 在候选镜像内执行；任何一条失败都说明该镜像不满足契约
docker run --rm -it ubuntu:24.04 sh -c '
  echo ok &&
  python3 --version &&
  tar --version &&
  printf x | base64 | base64 -d &&
  stat -c %Y /tmp &&
  grep -rHnF --include="*.txt" x /tmp
'
等价的一次性判断（脚本形式）sh
sh -c 'echo ok' && python3 --version && tar --version \
  && printf x | base64 | base64 -d && stat -c %Y /tmp && grep -rHnF --include='*.txt' x /tmp; true
alpine 与 distroless 不满足契约

ubuntu:24.04 与 debian 系列开箱可用，但是 alpine 与 distroless 镜像不满足要求。原因是这两类镜像使用 busybox 提供的工具，而 busybox 的 grep 不支持 --include，grep 的输出格式也不含 -H 提供的文件名，stat 同样不是 GNU 语义。这些差异会让 grep_files、glob_files、list_files、edit_file 在运行期以难以定位的方式失败，而不是在构建期给出明确错误。

如果你的团队出于镜像体积的考虑倾向 alpine，需要自行安装 GNU 工具链（grep、sed、findutils、coreutils、tar、python3）并重新执行上面的检查命令。这一条是本章最容易出问题的地方，因此单独强调。

13.4快照与跨调用恢复

沙箱的容器是短命的：一次调用结束，容器就停止并释放。如果每次调用都从空目录开始，那么 npm install 这类耗时且有累积效果的操作每次都要重做。快照机制就是为这个问题设计的。

它的原理分三步：

恢复环境

下一次调用开始时，框架从快照存储中读取上一次的目录内容，在新的容器里重新构造出同样的工作区。

正常运行

Agent 在这个环境里读写文件、运行命令，整个过程与普通沙箱调用没有区别。

保存快照

调用结束时，框架把工作区打包成 archive，上传到配置的快照存储，下次调用使用。

可选的快照实现有五种，缺省是 NoopSnapshotSpec，即不做快照。

Snapshot 实现存储位置适用场景
NoopSnapshotSpec不做快照每次调用都是干净环境；或不需要跨调用恢复
LocalSnapshotSpec本地目录单机部署；开发与验证快照行为
OssSnapshotSpec对象存储（S3 兼容）多副本部署，跨节点共享同一份快照
RedisSnapshotSpecRedis已经引入 Redis，希望状态与快照同源
JdbcSnapshotSpecMySQL JDBC BLOB已经引入 MySQL，且不想新增存储组件
配置快照java
HarnessAgent agent = HarnessAgent.builder()
        .name("kb-assistant")
        .model(model)
        .workspace(workspace)
        .filesystem(new DockerFilesystemSpec()
                .image("ubuntu:24.04")
                .snapshotSpec(new OssSnapshotSpec(
                        ossClient,          // S3 兼容客户端
                        "my-bucket",        // 桶名
                        "agentscope/")))    // key 前缀
        .build();
没有快照就没有跨调用保留

沙箱模式的文件与进程状态默认不跨调用保留。一个常见的误解是「沙箱会自动记住上一次的文件」，实际上默认配置是 NoopSnapshotSpec，容器停止后工作区内容随之消失。因此如果你的任务需要累积（例如安装依赖、生成多份报告的中间产物），必须显式配置快照。

13.5构建期校验规则

有些配置错误在运行期才会暴露，但框架在 build() 阶段就能识别一部分。了解这些规则可以在部署前发现问题。

配置组合结果原因
配置了 filesystem(RemoteFilesystemSpec)，但没有 stateStore(...) 或 distributedStore(...)build() 抛 IllegalStateException共享存储模式依赖状态存储提供命名空间，缺少它无法定位路径
配置了 filesystem(沙箱实现)，但使用了本地 AgentStateStorebuild() 打 warning本地状态存储在多副本下不可靠，沙箱状态无法与调用对应
同时设置 filesystem(...) 与 abstractFilesystem(...)构建失败两者互斥，同时设置无法确定使用哪个实现

这里的第一条值得特别注意：共享存储模式不会隐式创建状态存储。你必须显式提供 stateStore(...) 或 distributedStore(...)，这与本地模式下可以省略配置的习惯不同。

13.6动手：五种配置

本章场景的实现分五个示例。示例一先建立沙箱模式的基础配置，示例二演示跨调用恢复，示例三转向共享存储，示例四回到本地模式并说明路径策略，示例五处理 Kubernetes 部署。

示例一：Docker 沙箱的完整配置

SandboxAgent.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.IsolationScope;
// 请按版本核对：DockerFilesystemSpec 的包路径
import io.agentscope.harness.agent.sandbox.impl.docker.DockerFilesystemSpec;
// 请按版本核对：快照实现的包路径
// import io.agentscope.harness.agent.sandbox.snapshot.LocalSnapshotSpec;

import java.nio.file.Path;
import java.nio.file.Paths;
import java.util.Map;

public class SandboxAgent {

    public static void main(String[] args) {
        Path workspace = Paths.get("/opt/agent/workspace");

        HarnessAgent agent = HarnessAgent.builder()
                .name("sandbox-agent")
                .model("dashscope:qwen-plus")
                .workspace(workspace)
                .filesystem(new DockerFilesystemSpec()
                        // 镜像必须满足运行时镜像契约，不要用 alpine
                        .image("ubuntu:24.04")
                        // 每个会话一个独立容器
                        .isolationScope(IsolationScope.SESSION)
                        // 资源限制：防止不受信任脚本耗尽宿主资源
                        .memorySizeBytes(512L * 1024L * 1024L)
                        .cpuCount(2L)
                        // 网络策略；不需要外网时应显式限制
                        .network("none")
                        // 需要被容器外访问的端口
                        .exposedPorts(8080, 3000)
                        // 容器内环境变量
                        .environment(Map.of("NODE_ENV", "development"))
                        // 快照：跨调用保留工作区
                        .snapshotSpec(new LocalSnapshotSpec("/data/snapshots")))
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan")
                .sessionId("doc-review-1")
                .build();

        Msg reply = agent.call(
                Msg.user("列出 knowledge/ 下的所有文档，并统计总字数"), ctx).block();

        System.out.println(reply.getTextContent());
    }
}

DockerFilesystemSpec 的完整配置项如下。这些选项中的大部分用于收紧边界，因此建议逐项评估而不是全部使用缺省值。

方法说明缺省
image(String)Docker 镜像必填
isolationScope(IsolationScope)隔离维度SESSION
memorySizeBytes(Long)容器内存限制Docker 默认
cpuCount(Long)CPU 限制Docker 默认
network(String)Docker 网络Docker 默认
exposedPorts(int...)暴露端口无
environment(Map)容器环境变量无
workspaceRoot(String)容器内工作区挂载点/workspace
additionalRunArgs(String...)额外的 docker run 参数无
snapshotSpec(SandboxSnapshotSpec)快照策略NoopSnapshotSpec
workspaceSpec(WorkspaceSpec)工作区挂载规则默认
executionGuard(SandboxExecutionGuard)AGENT / GLOBAL 作用域的并发守卫无
workspaceProjectionEnabled(boolean)宿主到沙箱的静态资源投影true
workspaceProjectionRoots(List)参与投影的根路径AGENTS.md、skills、subagents、knowledge、.skills-cache
关于 SandboxFilesystemSpec 与 DockerFilesystemSpec 两个名称

官方文档在不同段落同时使用了 SandboxFilesystemSpec 与 DockerFilesystemSpec 两个名称。诚实地说明这一点：SandboxFilesystemSpec 是沙箱类型的抽象，DockerFilesystemSpec 是其中基于 Docker 的具体实现，与 Kubernetes、E2B、Daytona、AgentRun 等实现并列。配置时使用具体实现类名；当你看到文档写 filesystem(SandboxFilesystemSpec) 时，它表达的是「配置一个沙箱类型的文件系统」这个意图。本章统一使用具体类名，以免你在检索 API 时对不上号。

网络策略的选择

network(String) 这一项值得单独说明。沙箱内执行不受信任代码时，默认的网络配置通常是不够的：容器可能访问内网服务、云元数据接口、甚至外部地址。

取值效果适用场景
"none"无网络纯本地计算；处理不可信文档内容
"bridge"Docker 默认桥接网络，可访问外网需要下载依赖
"host"共享宿主网络命名空间需要访问宿主上的服务，隔离性下降

一个实用的分法是：安装依赖阶段与运行阶段使用不同网络策略。前者需要 bridge，后者可以改为 none。如果不需要恢复累积环境，可以把两阶段合并成一次调用，统一使用 bridge 并在 AGENTS.md 中限制网络访问范围。

示例二：跨调用恢复

这个示例解决一个具体问题：第一轮装好依赖，第二轮构建时依赖仍然存在。它的实现方式是把 IsolationScope 设为 USER 并启用快照，两次调用使用相同的 userId 与 sessionId。

ResumeAcrossCalls.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.IsolationScope;
import io.agentscope.harness.agent.sandbox.impl.docker.DockerFilesystemSpec;
// 请按版本核对：快照实现的包路径
// import io.agentscope.harness.agent.sandbox.snapshot.LocalSnapshotSpec;

import java.nio.file.Paths;

public class ResumeAcrossCalls {

    public static void main(String[] args) {
        HarnessAgent codingAgent = HarnessAgent.builder()
                .name("coder")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get(".agentscope/workspace"))
                .filesystem(new DockerFilesystemSpec()
                        .image("node:20-slim")
                        // 同一用户的多个会话共享同一个沙箱环境
                        .isolationScope(IsolationScope.USER)
                        .memorySizeBytes(1024L * 1024L * 1024L)
                        .snapshotSpec(new LocalSnapshotSpec("/data/sandbox-snapshots")))
                .build();

        // alice 的第一次调用：在沙箱内执行安装与测试，结束后保存快照
        RuntimeContext rc = RuntimeContext.builder()
                .userId("alice")
                .sessionId("dev-session-1")
                .build();
        codingAgent.call(Msg.user("npm install && npm test"), rc).block();

        // alice 的第二次调用：从快照恢复，node_modules 仍然存在
        codingAgent.call(Msg.user("npm run build"), rc).block();
    }
}

这一段里有几处需要说明：

  • IsolationScope.USER 而不是 SESSION。如果设为 SESSION，两次调用虽然 sessionId 相同，但快照 key 会与隔离维度绑定；明确用 USER 表达「这个人的开发环境要保留」更清晰。
  • image("node:20-slim") 属于 Debian 系列，满足镜像契约；如果你要用 node:20-alpine，必须先确认它满足契约（默认情况下不满足）。
  • 示例中的变量名统一为 codingAgent。官方文档这一段示例存在一个不一致：变量定义为 codingAgent，后续调用却写成 agent.call(...)。照抄这段代码会得到编译错误，因此这里使用一致的变量名。
恢复是有条件的

跨调用恢复依赖三件事同时成立：配置了快照、隔离维度与期望一致、状态存储可用。如果第二次调用读不到 node_modules，按这个顺序逐项确认：是否配置了非 Noop 的 snapshotSpec；两次调用的 userId 是否一致；状态存储是否指向同一个位置。

示例三：共享存储模式

沙箱解决了隔离问题，但是多副本部署还有另一个问题：四个副本上的同一个用户，如果各自有一个本地工作区，那么请求被负载均衡到不同副本时，MEMORY.md 和会话日志就会呈现不一致的内容。共享存储模式为这类数据提供一个所有副本共同访问的位置。

SharedStorageAgent.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.harness.agent.DistributedStore;
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.IsolationScope;
// 请按版本核对：RemoteFilesystemSpec 的包路径
// import io.agentscope.harness.agent.sandbox.remote.RemoteFilesystemSpec;
import io.agentscope.extensions.redis.RedisDistributedStore;

import redis.clients.jedis.JedisPooled;

import java.nio.file.Paths;

public class SharedStorageAgent {

    public static void main(String[] args) {
        // 一个连接池供 stateStore / baseStore / executionGuard 复用
        JedisPooled jedis = new JedisPooled("redis://shared-redis:6379");

        // distributedStore 一次配置即提供 stateStore 与 baseStore
        DistributedStore store = RedisDistributedStore.fromJedis(jedis);

        HarnessAgent agent = HarnessAgent.builder()
                .name("customer-service")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get("/opt/agent/workspace"))
                .distributedStore(store)
                .filesystem(new RemoteFilesystemSpec()
                        // 每个 userId 一个命名空间
                        .isolationScope(IsolationScope.USER)
                        // 未认证调用方的缺省标识
                        .anonymousUserId("anonymous"))
                .build();

        // 无论请求落到哪个副本，都会读写同一份 MEMORY.md
        RuntimeContext ctx = RuntimeContext.builder()
                .userId("alice")
                .sessionId("chat-1")
                .build();
        Msg reply = agent.call(Msg.user("我习惯用中文回答，称呼我为张工"), ctx).block();

        System.out.println(reply.getTextContent());
    }
}

RemoteFilesystemSpec 的路由规则

共享存储模式不是「所有文件都放 KV」。框架对不同路径做了区分：需要长期保存、需要跨副本一致的文件进 KV，其余文件留在本地。

路径KV 命名空间段

agents/<agentId>/sessions/sessions

不在表中的路径会落到本地

示例四：本地模式与路径策略

本地模式是缺省行为，也是开发阶段最常用的模式。它提供 shell，命令通过宿主 sh -c 执行。因此它的路径策略直接决定了智能体能够访问宿主上的哪些目录。

LocalModeAgent.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.harness.agent.HarnessAgent;
// 请按版本核对：LocalFilesystemSpec 与 LocalFsMode 的包路径
// import io.agentscope.harness.agent.sandbox.local.LocalFilesystemSpec;
// import io.agentscope.harness.agent.sandbox.local.LocalFsMode;

import java.nio.file.Path;
import java.nio.file.Paths;
import java.util.List;

public class LocalModeAgent {

    public static void main(String[] args) {
        Path project = Paths.get("/srv/knowledge-repo");

        HarnessAgent agent = HarnessAgent.builder()
                .name("local-agent")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get(".agentscope/workspace"))
                .filesystem(new LocalFilesystemSpec()
                        // 限制命令执行时间
                        .executeTimeoutSeconds(60)
                        // 限制单条命令的输出捕获量
                        .maxOutputBytes(200_000)
                        // 显式添加环境变量，不继承父进程全部环境
                        .env("TZ", "Asia/Shanghai")
                        .inheritEnv(false)
                        // 缺省 ROOTED
                        .mode(LocalFsMode.ROOTED)
                        // 项目根目录
                        .project(project)
                        // 额外允许访问的宿主目录
                        .addRoot(Paths.get("/srv/shared-docs"))
                        .additionalRoots(List.of(Paths.get("/srv/reports")))
                        // 关闭「非工作区写入路由到项目目录」
                        .projectWritable(false))
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("zhangsan").sessionId("local-1").build();

        Msg reply = agent.call(
                Msg.user("统计 /srv/knowledge-repo 下所有 markdown 文件的标题"), ctx).block();

        System.out.println(reply.getTextContent());
    }
}

这里显式配置了 LocalFilesystemSpec。如果只是想限制命令超时与输出量，也可以完全省略 .filesystem(...)，本地模式会以同样的缺省值生效。两者写法的差别只在于可配置的粒度。

LocalFsMode 三档行为

LocalFsMode 决定路径如何被解析与校验。这是本地模式下最关键的安全开关。

模式绝对路径.. 穿越适用场景
ROOTED（缺省）仅允许 workspace + project + additionalRoots 之下的路径拒绝本地开发、可信环境
SANDBOXED全部锚定到 workspaceRoot，拒绝绝对路径拒绝只应访问工作区内容的场景
UNRESTRICTED原样透传允许仅用于测试与完全可信环境

三档的区别可以用一个具体请求来看。假设智能体要读取 /etc/passwd，并访问 ../../../../etc/shadow：

请求ROOTEDSANDBOXEDUNRESTRICTED
绝对路径 /etc/passwd拒绝拒绝允许
相对路径 ../../etc/passwd拒绝拒绝允许
工作区内相对路径 knowledge/a.md允许允许允许
额外根 /srv/shared-docs/x.md允许拒绝允许
UNRESTRICTED 不提供任何保护

UNRESTRICTED 会把路径原样传给宿主 shell，此时唯一的屏障是操作系统权限。如果运行 Agent 的进程是 root 或者一个权限很宽的账号，那么智能体实际上拥有了整台机器的读写能力。因此这个模式只用于自动化测试，不要出现在任何对外服务的配置里。

LocalFilesystemSpec 完整方法

方法说明缺省
executeTimeoutSeconds(int)shell 超时（秒）120
maxOutputBytes(int)单条命令最大捕获输出字节100000
env(String, String)添加 shell 环境变量无
inheritEnv(boolean)继承父进程环境false

关于 inheritEnv：缺省是 false，也就是不继承宿主全部环境变量。这个默认值是合理的，因为宿主环境里往往包含数据库口令、云服务密钥等敏感变量，继承之后它们就出现在智能体的 shell 上下文里。需要某个变量时用 env(...) 显式添加，这样取值范围是可控的。

关于 projectWritable：开启后，落在工作区之外的写入会被重定向到项目目录，而不是被拒绝。这在「智能体需要写一个编译产物到项目里」的场景下很方便，但是它把「拒绝」变成了「改道」，因此在处理不可信输入时应保持关闭，让越权写入直接失败而不是被静默改写。

示例五：Kubernetes 沙箱

Kubernetes 模式把沙箱从容器换成了 Pod。它的额外收益是预热池：可以预先准备一批空闲 Pod，在需要时立即分配，因此适用于强化学习训练这类需要大量并行沙箱的场景。

KubernetesSandbox.javajava
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.IsolationScope;
// 请按版本核对：KubernetesFilesystemSpec 的包路径
// import io.agentscope.harness.agent.sandbox.impl.k8s.KubernetesFilesystemSpec;

import java.nio.file.Paths;

public class KubernetesSandbox {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("k8s-sandbox-agent")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get("/opt/agent/workspace"))
                .filesystem(new KubernetesFilesystemSpec()
                        // 命名空间，缺省 default
                        .namespace("agents")
                        // 必填：预热池名称
                        .warmPoolName("agent-sandbox-pool")
                        // 容器内工作区挂载点，缺省 /workspace
                        .workspaceRoot("/workspace")
                        // 必须与 workspaceRoot 保持一致
                        .fileApiBaseDir("/workspace")
                        // 通过网关暴露 file-API
                        .gatewayName("sandbox-gateway")
                        .gatewayNamespace("agents")
                        .gatewayScheme("http")
                        .serverPort(8888)

                        // .apiUrl("http://sandbox-gateway.agents.svc:8888")

                        .snapshotSpec(new OssSnapshotSpec(ossClient, "my-bucket", "agentscope/")))
                .build();

}

KubernetesFilesystemSpec 中有两个字段必须与集群资源对齐，否则沙箱无法初始化：

  • workspaceRoot 必须对应 SandboxTemplate 中声明的 PVC 挂载点，缺省为 /workspace。
  • fileApiBaseDir 必须与 workspaceRoot 一致，缺省同为 /workspace。框架的文件上传下载 API 以这个目录为基准。
  • warmPoolName 是必填项，它指向一个 SandboxWarmPool 资源。

沙箱 Pod 的形状由 SandboxTemplate 声明。下面这份模板声明了运行容器、file-API 端口与可写工作区卷：

运行时 HTTP API 契约

image 里那个容器需要自己实现四个 HTTP 端点，框架通过它们操作沙箱内的文件系统。这一点与 Docker 模式有本质区别：Docker 模式由框架直接执行 docker run 与 docker exec，而 Kubernetes 模式只与 HTTP 接口对话。

Endpoint语义
POST /execute
body: {"command": "..."}		必须按 POSIX shell 语义解析命令，返回 {"stdout", "stderr", "exit_code"}
POST /upload
multipart，filename 为相对路径		在 file-API base dir 下写入文件
GET /download/{path}按相对路径下载字节
GET /list/{path}目录列举
GET /exists/{path}存在性检查
自建运行时有三个容易出错的点

第一，/execute 必须真正按 shell 语义解析，不能把参数直接交给 exec()，否则管道、&&、重定向、heredoc 全部失效。

第二，stat 类元数据要返回 GNU 风格字段，与 stat -c 的输出一致。

第三，路径参数必须做规范化与越界检查，不能允许 .. 逃出 base dir。这三点在本地开发时容易被忽略，因为框架自带的镜像已经处理好了。

示例六：执行守卫与并发租约

前五节的所有配置都假设「同一个沙箱同一时刻只有一个副本在用」。在多副本部署下，如果 IsolationScope 是 AGENT 或 GLOBAL，那么四个副本可能同时尝试使用同一个沙箱，而容器的状态是一次性的。执行守卫就是为这个场景设计的：它保证同一沙箱同一时刻只有一个使用者。

WithExecutionGuard.javajava
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.IsolationScope;
import io.agentscope.harness.agent.sandbox.impl.docker.DockerFilesystemSpec;
// 请按版本核对：执行守卫实现类的包路径
// import io.agentscope.harness.agent.sandbox.guard.RedisSandboxExecutionGuard;

import redis.clients.jedis.JedisPooled;

import java.time.Duration;

public class WithExecutionGuard {

    public static void main(String[] args) {
        JedisPooled jedis = new JedisPooled("redis://shared-redis:6379");

        HarnessAgent agent = HarnessAgent.builder()
                .name("shared-sandbox-agent")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get("/opt/agent/workspace"))
                .filesystem(new DockerFilesystemSpec()
                        .image("ubuntu:24.04")
                        .isolationScope(IsolationScope.USER)
                        .executionGuard(RedisSandboxExecutionGuard.builder(jedis)
                                // 租约时长要大于单次调用的预期耗时，
                                // 否则会在调用执行中被判定为超时
                                .leaseTtl(Duration.ofMinutes(30))
                                .build()))
                .build();
    }
}
实现底层机制依赖
RedisSandboxExecutionGuardRedis SET key val NX PX ttlagentscope-extensions-redis
JdbcSandboxExecutionGuardMySQL GET_LOCK()agentscope-extensions-mysql

租约时长的设置需要注意：它必须大于单次调用的预期耗时。如果一次调用（包含模型推理与命令执行）可能运行 40 分钟，而租约只有 30 分钟，那么在第 31 分钟时另一个副本会获得租约，此时两个副本同时认为自己在使用同一个沙箱，容器状态会被破坏。因此宁可设得宽松一些——租约过期的代价是两个副本互相干扰，而租约过长只会让故障恢复变慢。

示例七：自定义文件系统实现

前面六节使用的都是框架提供的实现。如果你的文件落点既不是本地磁盘、也不是容器或远程 KV——例如一套内部对象存储、或者一个自研的虚拟工作区——可以实现 AbstractFilesystem 并用 abstractFilesystem(...) 注册。

CustomFiles.javajava
import io.agentscope.harness.agent.HarnessAgent;

public class CustomFiles {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("custom-fs-agent")
                .model("dashscope:qwen-plus")
                .workspace(Paths.get("/opt/agent/workspace"))
                // 与 filesystem(...) 互斥，只能二选一
                .abstractFilesystem(new MyFilesystem(
                        new InternalObjectStore("oss://agent-workspace")))
                .build();
    }
}

实现 AbstractFilesystem 需要覆盖两组能力，具体抽象方法列表请以你所安装版本的 API 参考为准：

  • 文件操作：读、写、列举、删除、存在性判断、移动与重命名。这一组是必需项。
  • 命令执行：接受一段命令字符串并返回 stdout、stderr、退出码。如果不提供这一组，Agent 就不会注册 execute 工具，模型只能读写文件。
  • 可选能力：快照槽位、并发租约。不实现则对应功能不可用，但不影响基本读写。
先确认内置实现是否已经够用

实现自定义文件系统之前，先用内置的七种实现对照一遍。多数看起来很特殊的需求，可以用 RemoteFilesystemSpec 加上自定义的存储实现满足，而不需要从头实现 AbstractFilesystem。后者的维护成本明显更高：路径安全、并发、快照一致性问题都要自己处理。如果你只是需要一个新的落点，实现 BaseStore 的成本远低于实现 AbstractFilesystem。

13.7静态资源投影

沙箱模式下有一个看起来矛盾的问题：AGENTS.md、skills/、knowledge/ 这些静态资产在宿主工作区里，而命令在容器内执行。模型要读到这些文件，就必须让它们出现在容器内。

框架的处理方式是启动时投影：

打包

启动时把工作区的静态资产打成一个 archive，参与投影的根路径由 workspaceProjectionRoots 决定，缺省为 AGENTS.md、skills、subagents、knowledge、.skills-cache。

增量比较

框架用内容 hash 比较变化。未变化的文件跳过，变化的文件用 SHA-256 增量重写。因此反复调用不会重复传输全部内容。

注入

archive 在容器内 hydrate 到 /workspace，此后模型的读取行为与本地模式一致。

MEMORY.md 与会话日志不在沙箱内

MEMORY.md、memory/、agents/<id>/ 位于沙箱内部，不参与投影。原因很直接：这些是运行时状态，每次调用都不同，投影它们没有意义，而正确的持久化方式是快照。因此你在设计任务时，不要指望「在沙箱里写 MEMORY.md，沙箱重建后还在」——它靠的是快照，不是投影。

13.8后端选型对照表

七种实现的差异集中在三点：是否提供隔离、是否提供 shell、适合什么场景。下表用于快速对照。

实现隔离能力shell适用场景
LocalFilesystemSpec无（路径检查，非进程隔离）有（宿主 sh -c）开发调试、内部可信工具
DockerFilesystemSpec容器隔离，可设内存 / CPU / 网络有（容器内）生产主力方案；单副本或共享存储配合
KubernetesFilesystemSpecPod 隔离有（通过运行时 HTTP API）K8s 集群部署；需要预热池与大规模并行

DaytonaFilesystemSpec托管沙箱有同上；以 CPU / 内存 / 磁盘规格配置

托管沙箱（E2B / Daytona / AgentRun）的共同点是把容器运维交给第三方，代价是需要额外的凭据、网络往返与外部服务可用性依赖。如果你的环境里已经有容器编排能力，自建 Docker 或 K8s 沙箱的可控性更好。

13.9接管外部沙箱

有一种情况沙箱的生命周期不由框架管理：你已经在别处创建并启动了一个沙箱，希望框架在本次调用中使用它。这时通过 SandboxContext 把外部沙箱传入。关键差异在调用结束时的行为：框架只调用 stop()，不会调用 shutdown()。

ExternalSandbox.javajava
// 请按版本核对：Sandbox / SandboxContext / SandboxState 的包路径
// import io.agentscope.harness.agent.sandbox.Sandbox;
// import io.agentscope.harness.agent.sandbox.SandboxContext;
// import io.agentscope.harness.agent.sandbox.SandboxState;

Sandbox mySandbox = dockerClient.create(workspaceSpec, snapshotSpec, options);
mySandbox.start();

SandboxContext callCtx = SandboxContext.builder()
        .client(dockerClient)
        .externalSandbox(mySandbox)     // 框架在调用结束时只 stop()
        .build();

agent.call(msgs, RuntimeContext.builder()
        .sessionId("my-session")
        .put(SandboxContext.class, callCtx)   // 通过上下文传入
        .build()).block();

// 关闭时机由你决定
mySandbox.shutdown();

如果希望在本次调用结束后立刻销毁沙箱，而不等外部流程，可以改为传入一个已保存的状态：框架从这个状态恢复沙箱，并且拥有它的完整生命周期。

从保存的状态恢复java
SandboxState savedState = dockerClient.deserializeState(savedStateJson);

SandboxContext callCtx = SandboxContext.builder()
        .client(dockerClient)
        .externalSandboxState(savedState)   // 框架拥有生命周期
        .build();
参数调用结束时的行为适用场景
externalSandbox(Sandbox)只 stop()，不 shutdown()沙箱由外部流程管理，需要在多次调用之间保持存活
externalSandboxState(SandboxState)由框架完整管理希望立刻获得一个干净沙箱，用完即销毁

13.10上线前的安全清单

沙箱配置的错误大多在运行期才显现，而且症状往往不直观。因此下面这份清单建议逐项确认。

#检查项要求不满足时的表现
1运行时镜像是否满足契约执行合规性检查命令全部通过；不使用 alpine、distrolessgrep_files、glob_files、list_files、edit_file 以非预期方式失败
2资源限制是否设置memorySizeBytes 与 cpuCount 已显式配置不受信任脚本耗尽宿主资源，同机服务不可用
3网络策略是否收紧不需要外网时使用 network("none")容器可访问内网服务与云元数据接口
4是否需要快照任务需要累积效果时配置非 Noop 的 snapshotSpec每次调用都是干净环境，依赖与中间产物丢失
5快照存储是否与状态存储一致多副本时快照存储在所有副本可达的位置副本之间环境不一致
6隔离维度是否符合业务语义IsolationScope 显式配置，缺省 USER 已确认会话之间互相可见文件，或反过来频繁丢失环境
7匿名调用方是否指定允许未认证访问时配置 anonymousUserId(...)退到 SESSION 作用域，跨调用恢复失效
8执行守卫是否需要AGENT / GLOBAL 作用域的多副本必须配置多个副本同时使用同一沙箱，容器状态被破坏
9租约时长是否大于单次调用耗时leaseTtl 留有余量调用尚未结束租约已过期，出现并发冲突
10projectWritable 是否关闭处理不可信输入时保持 false越权写入被静默改道而不是拒绝，问题被隐藏
11inheritEnv 是否关闭保持 false，敏感变量用 env(...) 显式添加宿主凭据进入智能体的 shell 上下文
12UNRESTRICTED 是否出现在生产配置中不出现智能体拥有宿主全部可访问路径
最容易忽略的三项

根据实际项目的故障分布，下面三项被遗漏的概率最高：

第 1 项。镜像问题在开发阶段经常被绕过（因为本地模式用的是宿主环境），切换到沙箱后才第一次暴露。

第 6 项。缺省值是 USER，很多场景（例如需要每会话干净环境的批处理任务）并不合适，但不显式配置就会沿用缺省。

第 8 项。单副本测试时并发守卫完全没有必要，因此它往往在扩容到多副本时才被加上，而此时线上已经出现过并发冲突的记录。

13.11本章小结

  • Workspace 抽象把逻辑路径与物理落点分开。智能体代码不变，切换文件系统实现即切换执行环境。
  • 三种模式：共享存储（无 shell）、沙箱（容器内 shell）、本地 + shell（缺省）。filesystem(...) 与 abstractFilesystem(...) 互斥。
  • 本地模式不提供沙箱隔离。生产环境中只要存在运行不受信任代码的可能，就必须使用沙箱模式。
  • IsolationScope 缺省为 USER，四档分别是 SESSION、USER、AGENT、GLOBAL；缺 userId 时回退到 SESSION。公开接口应配置 anonymousUserId(...)。
  • 沙箱镜像必须满足运行时镜像契约：POSIX sh、mkdir/rm/mv/test/printf/sort、sed/grep(-rHnF/--include)/find、GNU stat -c、tar、base64 -d、python3、可写 /workspace。alpine 与 distroless 不满足。
  • 跨调用保留依赖三件事：非 Noop 的快照、一致的隔离维度、可用的状态存储。缺省配置不做快照，容器停止后工作区随之消失。
  • 构建期会校验配置：共享存储缺少状态存储会抛 IllegalStateException；沙箱配本地状态存储会打 warning。
  • AGENT / GLOBAL 作用域在多副本下必须配置执行守卫，且租约时长要大于单次调用耗时。
  • 共享存储模式下，不在路由表中的路径落到本地且无 shell，因此 execute 不可用——这与沙箱模式的取舍正好相反，需要按需求选择。
练习
  1. 把本章示例一改为 IsolationScope.USER，配置 network("none")，并验证 Agent 仍然可以正常读写工作区中的文档。
  2. 用沙箱模式执行一段会删除文件的脚本（例如 rm -rf /workspace/tmp），确认宿主工作区不受影响。然后把同一段脚本交给本地模式执行，对比两者的差别。
