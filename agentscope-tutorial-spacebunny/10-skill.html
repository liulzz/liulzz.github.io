为什么需要技能

第九章我们让助手能够检索文档、写入记忆。但是有一些工作它做得并不稳定：让它「审校一篇文档」，它每次关注的字段不一样；让它「按规范输出引用」，它有时用角标，有时用方括号。问题的根源是：这些流程你只写在系统提示词的一句描述里，而系统提示词每轮都会被重新组织，模型能记住的比例并不稳定。

技能提供的是另一种做法：把流程写成独立文件，并且在提示词中只放入一条简短的索引（名称加说明）。模型判断当前任务需要这个流程时，再主动读取完整内容。因此技能的常驻上下文成本很低，但是流程描述可以写得非常详细。

场景

本章场景

为团队知识助手增加可沉淀的工作方法。它需要能够：

  • 按团队规范审校文档（字段完整性、术语一致性、引用格式）
  • 输出符合规范的引用，而不是每次重新发明格式
  • 把团队反复使用的检查流程写成技能，团队成员可以直接新增
  • 在助手的使用过程中自动学习新技能，并交由人工审核后生效

本章结束时，助手的行为不再随回答而变；而且当团队成员反复问同一类问题时， 助手可以起草一份新技能，经审核后正式生效。

10.1技能与工具的区别

第三章我们详细讨论过工具。当时有一个说法容易造成误解：工具决定能力边界。这个说法本身没错，但是它容易让人以为「所有事情都要做成工具」。技能与工具解决的是完全不同类型的问题。

维度工具（Tool）技能（Skill）
承载内容一段可执行的代码能力一份给模型看的 Markdown 指令
执行主体Java 代码，在模型返回参数后执行模型自己读取后按指令改变行为
是否需要写代码需要不需要，编辑 Markdown 即可
上下文占用JSON Schema 常驻，占用固定额度只有名称与说明常驻，正文按需读取
触发方式模型看到 Schema 后决定是否调用模型看到索引后决定是否读取全文
典型例子search_docs、delete_doc文档审校流程、引用格式规范、迁移前检查清单

换句话说：工具是能力，技能是指令。「怎么检索文档」是能力，必须用代码实现；「审校时先看标题层级再看术语」是指令，写清楚就行。如果把指令硬做成工具，你会得到一个只能被调用、无法被模型内化的黑盒；如果把能力写成技能，模型会尝试用自然语言描述检索过程，然后失败。

一个任务的处理路径 用户请求 │ ├──> 需要新的执行能力？ ── 是 ──> 写成工具（Java 代码） │ └──> 已有能力，但流程不规范？ ── 是 ──> 写成技能（Markdown） │ ↓ 提示词里只保留 名称 + 说明 │ 模型判断需要时读取正文 ──> 按指令改变后续行为
第三章提到的 load_skill_through_path

第三章讲元工具时出现过 load_skill_through_path 这个名字，当时只说它会在存在额外工具组或技能时自动注册。本章会把它作为技能机制的核心一环展开说明。

10.2四层技能来源

技能可以从四个地方进入一个 Agent。这四层在构建时按优先级从低到高合并，因此高层的同名技能会覆盖低层。

优先级来源配置方式典型用途
1（最低）项目全局目录projectGlobalSkillsDir(Path)个人通用技能，例如 ~/.agentscope/skills/，跨项目复用
2技能市场（Marketplace）skillRepository(...)，可多次调用团队共享或第三方分发的技能包；后注册者胜出
3Workspace 共享目录workspace/skills/，自动纳入项目专用技能，可随仓库一起版本控制
4（最高）按用户隔离目录<userId>/skills/在同一部署下为特定用户叠加或替换技能

这个设计的意义在于：团队可以统一发布，个人可以临时覆盖。市场层提供官方维护的通用技能，Workspace 层提供本项目特有的流程约定，而用户层让某个测试同学可以放入自己正在试验的提示词，不影响其他人。

同名覆盖是一把双刃剑

因为用户层优先级最高，它同时也是最难排查的故障来源： 用户看到的行为与仓库里写的不一致，而仓库里确实没有错误。

建议在排查技能问题时按优先级从低到高依次确认，" "不要一上来就修改 Workspace 里的文件。

技能文件在运行环境中的位置

技能被激活后，模型的指令里会带一个 files-root，这是技能目录在当前文件系统中的实际路径。它的取值取决于运行模式，因此不要在脚本里硬编码这个路径，应该从指令给出的路径读取。

文件系统模式Workspace 技能市场技能
Sandbox/workspace/skills/<name>/workspace/.skills-cache/<source>/<name>
Local 且启用 shell<wsRoot>/skills/<name><wsRoot>/.skills-cache/<source>/<name>
Local 无 shell / Composite不渲染不渲染

第三行的「不渲染」值得注意：当运行环境既没有沙箱也没有 shell 能力时，框架不会在提示词中给出文件路径，因为模型无法通过任何工具访问这些文件。因此如果你打算在技能里放脚本，就不能使用 Local 无 shell 模式。沙箱模式的默认投影根目录包含 AGENTS.md、skills/、subagents/、knowledge/ 与 .skills-cache/，这个列表可以用 workspaceProjectionRoots(List) 调整，也可以用 workspaceProjectionEnabled(false) 完全关闭。

10.3SKILL.md 的结构

一个技能就是一个目录，其中 SKILL.md 是必需项：

code-reviewer/ ├── SKILL.md # 必需：front matter + 给 agent 的指令 ├── references/ # 可选：按需阅读的长文档 │ └── style-guide.md └── scripts/ # 可选：agent 可通过 shell 调用的脚本 └── run-checks.sh

这三个位置有明确分工：SKILL.md 承载流程本身，references/ 放详细规范这类长内容，scripts/ 放确定性检查。把长文档放进 references 的原因是上下文成本 —— SKILL.md 每次激活都会占用额度，而 references 里的文件只在流程真正走到那一步时才读取。

front matter 规范

字段必需说明
name是技能名称。通常与目录名一致，是模型识别该技能的主要标识
description是一句话说明触发条件。它是模型决定是否读取全文的唯一依据，写得好坏直接决定技能会不会被用上
skills/doc-auditor/SKILL.mdmarkdown
---
name: doc-auditor
description: Use when the user asks to review, audit, or proofread a document for completeness, terminology consistency, or citation format.
---

# Document Auditor

Follow this order. Do not skip step 2 even when the document looks short.

1. Read the target document with `read_file`.
2. Read `references/audit-rules.md` and check every rule it lists.
3. Run `scripts/check-citations.sh <target-path>` and summarize the output.
4. Report findings grouped by severity. State explicitly when no issue was found
   for a rule, so that the user can tell checked items from skipped ones.
description 写「用途」而不是「主题」

对比下面两种写法：
description: Document auditing rules —— 模型在用户说「帮我看看这份规范有没有问题」时很可能不会激活它。
description: Use when the user asks to review, audit, or proofread a document... —— 写法中包含了用户可能的说法，命中概率明显更高。

换句话说，description 是写给模型的触发条件，因此应当使用用户会说的话，而不是功能名称。

skills/citation-format/SKILL.mdmarkdown
---
name: citation-format
description: Use whenever the answer quotes or paraphrases team documentation, including summaries and comparison tables.
---

# Citation Format

Every claim taken from team documentation must carry a source marker.

- Format: `[来源: <文档路径>]`
- Place it at the end of the sentence that contains the claim.
- Multiple sources: `[来源: a.md, b.md]`
- If no source supports the claim, write the claim without a marker and add
  a note that it is not covered by team documentation.

Never invent a document path. If `search_docs` returned nothing relevant,
say so instead of fabricating a path.

第二个例子展示了技能的一个实际价值：「引用必须带来源」是一条规则，而模型在没有明确指令时倾向于给出确定的语气。把它写成技能之后，只要回答涉及团队文档就会被激活，因此规则不再依赖「记得一直遵守」。

10.4索引注入与按需读取

技能系统最关键的设计是提示词里只放索引，不放正文。每轮推理前，中间件会重新合并所有可用技能，并且只把名称与说明写进系统提示词。

系统提示词中的技能索引片段xml
<available_skills>
<skill>
  <name>doc-auditor</name>
  <description>Use when the user asks to review, audit, or proofread a document for completeness, terminology consistency, or citation format.</description>
  <skill-id>doc-auditor_workspace-namespaced</skill-id>
  <files-root>/workspace/skills/doc-auditor</files-root>
</skill>
<skill>
  <name>citation-format</name>
  <description>Use whenever the answer quotes or paraphrases team documentation, including summaries and comparison tables.</description>
  <skill-id>citation-format_user-alice</skill-id>
  <files-root>/workspace/.skills-cache/team-skills/citation-format</files-root>
</skill>
</available_skills>

请注意 skill-id 的构成规则：它由技能名与来源命名空间拼接而成，因此不同来源的同名技能有不同的 id，这正是覆盖能够生效的技术前提。另外 files-root 在索引里已经给出，所以模型不需要先「找到文件在哪」就可以读取。

索引注入

每轮推理前，DynamicSkillMiddleware 重新合并四层技能，把名称与说明写入系统提示词。正文一律不注入。

模型判断

模型根据 description 判断当前任务是否需要某个技能。这是唯一的选择时机，因此 description 的质量直接决定技能的使用率。

读取正文

模型调用 load_skill_through_path(skillId, path="SKILL.md")，框架按提示词中给出的 files-root 定位文件并返回全文。

按需读取附属文件

如果 SKILL.md 中提到 references/ 或 scripts/ 下的文件，模型用同一个工具继续读取，路径相对于该技能的 files-root。

行为改变

正文进入上下文后，模型按其中的指令执行。因为索引仍在提示词中，后续轮次不需要再次判断就能继续使用。

与技能相关的工具名如下：

工具名作用备注
load_skill_through_path按 skillId 与相对路径读取技能文件读取正文的唯一入口
read_skill读取已注册技能的元信息与正文供框架与工具实现使用
propose_skill起草一份新技能，进入 skills/_drafts/开启自我学习后可用
skill_manage技能管理操作入口与晋升门禁配合使用
execute_shell_command执行 shell 命令，例如运行技能自带的检查脚本需要在 Local 启用 shell 或沙箱模式下可用
按需加载的三级 fallback

技能文件的读取有一条明确的降级链：先查内存命中，未命中则读文件系统，仍然失败则报错，并且在错误信息中列出所有可用路径。因此当技能读取失败时，错误消息本身就能告诉你有哪些候选目录可以检查。

10.5自我学习闭环

前面四节讲的都是「人先写好技能，模型再使用」。AgentScope Java 还提供了相反的方向：让助手从自己反复成功的做法中起草新技能。这个能力由 enableSkillManageTool(...) 开启。

从有效工作模式起草

模型在完成任务后调用 propose_skill，把刚刚验证有效的工作方式写成技能草稿。

进入草稿目录

草稿写入 skills/_drafts/。此时它对用户不可用，只有团队成员能看到。

审核决定是否晋升

晋升门禁（Promotion Gate）决定草稿能否成为正式技能。门禁可以要求人工批准，也可以按环境与灰度比例过滤。

清理器标记长期未使用的技能

后台清理器（Curator）定期检查使用计数，把长期无人使用的技能标记为过期（stale）。

归档

超过归档阈值的技能被移入 skills/.archive/，不再出现在索引中，但文件保留，可随时恢复。

默认阈值如下：

配置项默认值含义
staleAfterDays30 天超过这个天数未被使用则标记为 stale
archiveAfterDays90 天超过这个天数则归档到 skills/.archive/
intervalHours—清理器运行间隔；文档示例中设为 7 * 24，即每周一次

使用计数记录在 skills/.usage.json 中。因此清理器判断「是否被使用」依据的是这个文件，而不是模型自己的记忆。需要注意的是，清理器的合并动作默认是 dry-run：它会给出建议但不会真的改动文件，需要你在确认之后显式执行。

10.6动手：建立第一个技能

我们先手工建立一份技能，验证读取路径是否正确，然后在下一节引入自动起草。本章场景需要两条流程：文档审校与引用规范。

先创建目录与主文件：

创建技能目录bash
workspace/
└── skills/
    ├── doc-auditor/
    │   ├── SKILL.md
    │   ├── references/
    │   │   └── audit-rules.md
    │   └── scripts/
    │       └── check-citations.sh
    └── citation-format/
        └── SKILL.md
workspace/skills/doc-auditor/SKILL.mdmarkdown
---
name: doc-auditor
description: Use when the user asks to review, audit, or proofread a document for completeness, terminology consistency, or citation format.
---

# Document Auditor

Work through the three groups in order.

## 1. Structure

- Read the document with `read_file`.
- Confirm that there is exactly one top-level heading, and that heading levels
  never skip a level.

## 2. Terminology

- Read `references/audit-rules.md` section "Terminology".
- Report every place where a deprecated term appears, with line numbers.

## 3. Citation format

- Run `scripts/check-citations.sh <absolute-path>` and summarize its output.
- Do not fix anything. This skill only reports.
workspace/skills/doc-auditor/references/audit-rules.mdmarkdown
# Audit Rules

## Terminology

| Deprecated | Use instead |
|---|---|
| 服务间调用 | RPC |
| 消息队列 | MQ |
| 配置文件 | 配置项 |

## Structure

- A document must declare exactly one `#` heading.
- Headings must not skip levels (`#` -> `##` -> `###`).

## Citation

- Every factual claim about the system needs a `[来源: path]` marker.
- A claim without a supporting document must be marked as
  "未在团队文档中记载".
workspace/skills/doc-auditor/scripts/check-citations.shbash
#!/usr/bin/env bash
# 统计缺少来源标记的句子数量。退出码 0 表示通过。
set -euo pipefail

target="${1:?usage: check-citations.sh <document-path>}"
missing=0

while IFS= read -r line; do
  # 跳过标题、代码块与表格行
  case "$line" in
    '#'*|'|'*|'>'*|'```'*) continue ;;
  esac
  if [[ -n "$line" && "$line" != *"[来源:"* ]]; then
    missing=$((missing + 1))
    printf '缺少来源标记: %s\n' "$line"
  fi
done < "$target"

printf '共 %d 行缺少来源标记\n' "$missing"
[[ "$missing" -eq 0 ]]

接下来把技能目录纳入 Workspace，并在程序中启用技能机制。下面这份配置使用 HarnessAgent，并且把用户主目录下的全局技能目录也加入进来。

SkillAgentDemo.javajava
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;

import java.nio.file.Path;
import java.util.List;

/**
 * 知识助手 + 技能系统。
 *
 * 说明：
 * 1. workspace/skills/ 下的技能会被自动纳入，不需要逐个注册。
 * 2. projectGlobalSkillsDir 指向个人通用技能目录（例如 ~/.agentscope/skills/），
 *    它的优先级低于 Workspace，因此仓库内的版本会覆盖同名的个人版本。
 * 3. 如果所安装版本的 projectGlobalSkillsDir 不在 HarnessAgent 构建器上，
 *    请以该版本的 API 参考为准核对归属类。
 */
public class SkillAgentDemo {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .sysPrompt(jt(24,
                        "你是一个团队知识助手。",
                        "回答涉及团队文档内容时，必须遵守 citation-format 技能。",
                        "被要求审校文档时，先加载 doc-auditor 技能再开始。"))
                .model("dashscope:qwen-plus")
                .workspace(Path.of("./workspace"))
                // 项目全局技能目录：跨项目复用的个人技能，优先级最低
                .projectGlobalSkillsDir(Path.of(
                        System.getProperty("user.home"), ".agentscope", "skills"))
                // 开启元工具后，load_skill_through_path 会自动注册
                .enableMetaTool(true)
                .build();

        Msg answer = agent.call(List.of(
                        new UserMessage(
                                "审校 docs/onboarding.md，重点看术语与引用标记。")),
                        null)
                .block();

        System.out.println(answer.getTextContent());
    }
}

为什么脚本放在技能目录里

审校中的「引用是否规范」是确定性判断，" "适合用脚本实现；而「术语是否一致」需要语义理解，适合写在指令里。" "把两者放在同一个技能下，模型按需选择合适的手段，" "既减少了模型推理负担，也让检查结果稳定可复现。

10.7动手：四种技能来源

技能可以从多个仓库同时进入一个 Agent。下面先看四种实现的对照，再给一份可运行的配置。

实现类构造方式适用场景Maven 坐标
ClasspathSkillRepositorynew ClasspathSkillRepository("skills")随应用打包的只读技能，随 JAR 一起发布核心依赖
GitSkillRepositorynew GitSkillRepository(String url)团队共享的技能仓库，独立演进agentscope-extensions-skill-git-repository
NacosSkillRepositorynew NacosSkillRepository(aiService, "namespace")已有 Nacos 配置中心的团队，可复用其推送能力agentscope-extensions-nacos-skill
MysqlSkillRepositoryMysqlSkillRepository.builder(dataSource)...build()需要通过数据库管理技能，支持在线编辑核心依赖（io.agentscope.core.skill.repository.mysql）

接口名是 SkillRepository，因此你可以自己实现数据源而不必受限于上述四种。另外需要注意包名差异：MysqlSkillRepository 的全限定名在官方文档中明确给出，而其余三个在文档中只出现了简单类名，实际使用时请以你所安装版本的包名为准。

SkillRepositoryDemo.javajava
import io.agentscope.core.skill.SkillRepository;
import io.agentscope.core.skill.repository.mysql.MysqlSkillRepository;
// 以下三个类的包名请按你所安装版本核对
// import io.agentscope.core.skill.repository.classpath.ClasspathSkillRepository;
// import io.agentscope.core.skill.repository.git.GitSkillRepository;
// import io.agentscope.core.skill.repository.nacos.NacosSkillRepository;
import io.agentscope.harness.agent.HarnessAgent;

import java.nio.file.Path;

public class SkillRepositoryDemo {

    public static void main(String[] args) {
        // 1) 随包发布的只读技能
        SkillRepository bundled = new ClasspathSkillRepository("skills");

        // 2) 团队 Git 仓库。后注册者胜出，因此这个技能会覆盖 bundled 中的同名项
        SkillRepository team = new GitSkillRepository(
                "https://git.example.com/team/agentscope-skills.git");

        // 3) 数据库仓库，需要一个 DataSource。
        //    HikariCP 需要自行加入依赖。
        //    表不存在时自动创建，允许写入（技能自我学习需要写权限）
        SkillRepository editable = MysqlSkillRepository.builder(dataSource)
                .databaseName("agentscope")
                .skillsTableName("skills")
                .createIfNotExist(true)
                .writeable(true)
                .build();

        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(Path.of("./workspace"))

                // skillRepository 可多次调用，形成来源链
                .skillRepository(bundled)
                .skillRepository(team)
                .skillRepository(editable)

                // 也可以一次性传入列表
                // .skillRepositories(List.of(bundled, team, editable))

                // 仓库层也可以手动驱动
                // team.sync();                  // 主动同步远端变更
                // System.out.println(team.getSource());  // 来源名，用于冲突后缀

                .build();
    }

    // 仅为示例保留的占位，实际使用时由连接池提供
    static javax.sql.DataSource dataSource = null;
}

Git 仓库的两个默认行为

行为默认策略如何改变
同步时机每次读取时做一次轻量远端检查，只有 HEAD 变化才真正拉取使用 new GitSkillRepository(url, false) 改为完全手动
技能根目录仓库含 skills/ 子目录时以它为根，否则以仓库根为根按仓库结构调整目录结构
名称冲突时框架会自动加后缀

当多个市场来源提供了同名技能，materialize 阶段会逐文件计算 SHA-256 去重；若内容不同但名字相同，框架会自动追加来源后缀，形如 <source>_2，避免互相覆盖。因此在日志里看到带数字后缀的技能名是正常的，但它也提示你可能需要检查来源配置是否重复。

10.8动手：自我学习与晋升门禁

开启 enableSkillManageTool(...) 之后，模型可以在完成一段有效工作后起草新技能。草稿不会立即生效，它必须通过晋升门禁。

门禁由两部分组成：

组件类型职责
审批器LocalApprovalGate决定「谁来批准」。默认实现是 reject-all，即不配置批准人时所有晋升都会被拒绝
过滤器链CompositeFilter决定「什么条件下允许」。链上任意一项不通过即拒绝

过滤器链包含两个常用过滤器：

过滤器行为
EnvironmentFilter("prod", store)环境过滤。与当前 environment 一致时才允许晋升
CanaryFilter(0.10, store)灰度过滤。以 10% 的比例允许晋升，其余继续留在草稿
SkillLearningDemo.javajava
import io.agentscope.core.skill.gate.CanaryFilter;
import io.agentscope.core.skill.gate.CompositeFilter;
import io.agentscope.core.skill.gate.EnvironmentFilter;
import io.agentscope.core.skill.gate.LocalApprovalGate;
import io.agentscope.core.skill.SkillManageConfig;
import io.agentscope.harness.agent.HarnessAgent;

import java.nio.file.Path;
import java.util.List;

// SkillUsageStore 与 SkillCuratorConfig 的包名请按你所安装版本核对
// import io.agentscope.core.skill.SkillUsageStore;
// import io.agentscope.core.skill.SkillCuratorConfig;

public class SkillLearningDemo {

    public static void main(String[] args) {
        // 使用计数仓库：清理器与灰度过滤器都需要它
        SkillUsageStore usageStore = SkillUsageStore.create(workspacePath());

        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(workspacePath())

                // 开启技能管理工具：模型可以调用 propose_skill 起草草稿
                .enableSkillManageTool(SkillManageConfig.defaults())
                // 也可以简写为 .enableSkillManageTool(true)

                // 环境标识，供 EnvironmentFilter 比对
                .environment("prod")

                // 晋升门禁：先过人工审批，再过环境与灰度过滤
                .enableSkillPromotionGate(
                        new LocalApprovalGate(LocalApprovalGate.defaultPrompter()),
                        new CompositeFilter(List.of(
                                new EnvironmentFilter("prod", usageStore),
                                new CanaryFilter(0.10, usageStore))))

                .build();
    }

    private static Path workspacePath() {
        return Path.of("./workspace");
    }
}
默认配置下晋升一定失败

LocalApprovalGate 的默认行为是 reject-all。这意味着如果你只写了 enableSkillPromotionGate(gate, filter) 而没有配置批准人，所有草稿都会停在 skills/_drafts/。这不是故障，而是刻意设计的默认值 —— 新技能不应该在没有人类确认的情况下自动生效。调试时看到「草稿不晋升」，先检查批准人配置。

草稿到正式技能的完整流转路径如下：

模型完成一次有效工作 │ ├──> propose_skill 起草 │ ↓ │ skills/_drafts/<name>/SKILL.md │ │ │ ├── LocalApprovalGate（人工批准） │ ├── EnvironmentFilter（环境匹配） │ └── CanaryFilter（灰度比例） │ ↓ │ skills/<name>/ # 晋升成功，进入索引 │ └──> Curator 定期检查 ├── 30 天未使用 ──> 标记 stale └── 90 天未使用 ──> skills/.archive/<name>/

10.9动手：清理器与运维接口

清理器负责把长期无人使用的技能标记并归档。它的运行间隔与阈值都可以配置，默认阈值是 30 天与 90 天。

SkillCuratorDemo.javajava
import io.agentscope.core.skill.SkillCuratorConfig;
import io.agentscope.core.skill.SkillAuditLog;
import io.agentscope.harness.agent.HarnessAgent;

import java.time.LocalDate;
import java.util.List;

public class SkillCuratorDemo {

    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(workspacePath())
                .enableSkillManageTool(true)
                .enableSkillCurator(SkillCuratorConfig.builder()
                        .intervalHours(7 * 24)   // 每周一次
                        .staleAfterDays(30)       // 30 天未使用标记为 stale
                        .archiveAfterDays(90)     // 90 天后归档
                        .build())
                .build();

        // ---- 运维接口：三项都可以在运行期观察技能状态 ----

        // 1) 查询某一天的技能审计条目，第二个参数是过滤器
        List<SkillAuditLog.Entry> entries = agent.queryAudit(
                LocalDate.now(), e -> true);
        entries.forEach(e -> System.out.printf(
                "%s  %s  %s%n", e.getTimestamp(), e.getAction(), e.getDetail()));

        // 2) 手动执行一次清理器，返回报告
        agent.runCuratorOnce()
                .doOnNext(report -> System.out.println(report))
                .subscribe();

        // 3) 人工晋升指定技能，第二个参数是操作人
        agent.promoteSkill("notes-taker", "alice")
                .doOnNext(result -> System.out.println(result))
                .subscribe();
    }
}

这三项接口的用途与差异：

接口输入输出典型使用时机
queryAudit(date, filter)日期 + 谓词List<SkillAuditLog.Entry>排查「这个技能什么时候被启用的」
runCuratorOnce()无清理报告灰度期间先手动执行一次观察结果再交给定时任务
promoteSkill(name, operator)技能名 + 操作人晋升结果人工审核通过后立刻生效，不必等模型再次起草

仓库层还有两个方法可用于自定义同步策略：

  • repo.sync()：主动触发一次同步，适合在 CI 中显式调用。
  • repo.getSource()：返回来源名。名称冲突时框架用这个名字生成后缀，因此它也是排查重复来源的依据。

10.10技能设计清单

并不是所有经验都值得写成技能。下面这张表给出判断依据：

情形建议原因
同一类请求出现三次以上，每次都要纠正模型写成技能流程稳定且模型无法自行发现
团队有明文规范，但模型经常不遵守写成技能规范本身就是指令
需要引用外部文档才能说清做法写成技能，正文放 references正文短，细节按需读取
需要执行命令或访问文件系统才能判断写成技能并附带 scripts确定性判断交给脚本
一次性的做法、临时调试步骤不要写成技能会占用索引额度且几乎不会被再次命中
需要多步确定性计算（求和、格式转换）写成工具这是能力而不是指令
需要访问外部系统并产生副作用写成工具技能不具备执行能力

description 的写法对照

写法问题改进方向
Team document auditing rules只有主题，没有触发条件补上「Use when the user asks to ...」句式
文档审校中文短描述，与用户实际表述的匹配概率低使用用户会说的说法，如 review / proofread / 检查
Use when the user mentions quality触发条件过宽，几乎每轮都被激活，挤占上下文并增加误触发把条件收紧到具体动作与具体对象

另外三点需要注意：

  • 一个技能只做一件事。把审校与引用规范写成两个技能，模型才能在只需要其中一个时不去读另一个。
  • 正文里不要重复 description。description 已经说明触发条件，正文应当直接给步骤。
  • 写明不要做什么。本节示例中的「Do not fix anything. This skill only reports.」这一句能显著减少模型顺手修改文件的情况。

10.11本章小结

  • 工具是能力，技能是指令。需要执行能力时写工具，需要规范做法时写技能。
  • 技能来源有四层：项目全局目录、技能市场、Workspace 共享目录、按用户目录，优先级从低到高，高层的同名技能覆盖低层。
  • SKILL.md 是必需项，需要 name 与 description 两个 front matter 字段；references/ 存放长文档，scripts/ 存放确定性检查脚本。
  • 每轮推理只把名称与说明注入系统提示词，模型判断需要时用 load_skill_through_path 读取正文。因此 description 决定技能会不会被使用。
  • 自我学习闭环包含五步：起草、进入草稿目录、晋升门禁审核、清理器标记过期、归档。默认阈值是 30 天标记过期、90 天归档。
  • LocalApprovalGate 默认拒绝全部晋升，因此新技能在没有人类确认时不会生效，这是设计意图而不是配置错误。
练习
  1. 为知识助手写一份 citation-format 技能，要求包含 description、引用格式约定，以及「找不到来源时不要编造路径」这条明确指令。然后故意问一个文档里没有的问题，观察模型是否遵守。
  2. 把第 10.6 节中的技能从 workspace/skills/ 复制到「按用户目录」下并修改内容，观察 skill-id 与 files-root 的变化，确认同名技能确实被覆盖了。
  3. 分别用 ClasspathSkillRepository、GitSkillRepository 与 MysqlSkillRepository 配置同一个技能，验证「后注册者胜出」以及同名冲突时的 <source>_2 后缀。
  4. 开启 enableSkillManageTool(true) 后让助手完成一次文档审校，查看 skills/_drafts/ 中是否产生草稿；在不配置批准人的情况下调用 promoteSkill，确认它被拒绝，然后配置批准人再试一次。
  5. 设计题：为一个有 200 篇文档的知识库设计技能体系。需要覆盖文档审校、术语规范、引用格式、迁移前检查四类流程。请说明每类流程应该做成几个技能、分别放在哪一层（Workspace、市场还是用户层）、description 如何措辞，以及清理器的 staleAfterDays 该设多少天，并解释理由。
