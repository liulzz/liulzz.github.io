一个具体的约束

假设知识助手已经开始被团队使用，然后你接到两个要求：第一，服务不能因为单台机器重启而中断；第二，用户数增长到原来的二十倍时，扩容不能靠换更大的机器。

这两个要求看起来是运维问题，但根因在代码里。默认的状态存储是 JsonFileAgentStateStore，它把状态写在本机磁盘的 ~/.agentscope/state/<agentId>/ 目录下。于是：

  • 请求被负载均衡分发到副本 B，但用户 张三 的会话在副本 A 上，副本 B 读不到
  • 副本 A 重启，磁盘上的状态文件如果没有落盘或已过期，这一副本上的所有会话都不存在了
  • 沙箱快照、任务记录、记忆文件同样落在本机，换副本之后无法恢复

AgentScope Java 2.0 对此的答案是 DistributedStore：把四类需要跨副本共享的能力抽象成接口，并提供 Redis、OSS、MySQL 三套实现。一行配置即可替换，业务代码不变。

场景

本章场景

把知识助手部署为一个多副本、水平扩展的 Web 服务，要求：

  • 任意副本可处理任意用户的请求，会话不落在某一台机器上

  • 沙箱状态跨副本可恢复：用户换一台副本继续对话，环境不变
  • 多租户数据隔离：不同租户的状态在键空间上可区分
  • 具备可观测性：调用链可以导出到 OpenTelemetry

14.1先讲理论：单机方案的四个限制

在引入分布式存储之前，先把问题界定清楚。默认配置的局限可以归结为四条，每一条都对应生产环境中的真实故障。

限制现象在生产中的后果
单点故障状态文件只存在于一台机器的磁盘上该机器故障或被调度系统重新调度后，这一副本上的全部会话不可恢复；如果它是唯一副本，服务整体不可用
容量上限会话日志、记忆文件、工具大结果都写在本地磁盘磁盘容量成为并发会话数的硬约束；会话日志只追加不压缩，容量消耗随时间单调增长
滚动重启丢状态进程收到终止信号后立即退出，在途调用尚未写入状态滚动发布期间用户会看到「助手忘记了刚才说过什么」，越是发布频繁，问题越频繁
无法跨可用区本地磁盘不参与跨机房复制无法满足数据同城或异地冗余要求；单可用区故障时没有可切换的副本
关键判断：这些问题不能靠加机器解决

增加副本数量只会放大前两个问题：副本越多，用户会话被分散到越多台机器上，「请求到达没有该状态的副本」的概率越高；同时所有副本的磁盘消耗线性增长。因此必须先把状态从本机磁盘移出去，扩容才有意义。这就是本章的核心动机。

DistributedStore 的四类能力

AgentScope Java 2.0 没有提供一个大而全的「分布式存储」实现，而是把需求拆成四个正交的接口，再用一个 DistributedStore 把它们组合起来。理解这四类能力，就理解了生产部署的全部可配置项。

DistributedStore 组合的四类能力 DistributedStore │ ├── agentStateStore ──────── AgentStateStore（接口） │ 运行时状态：会话上下文、计划模式状态、任务清单、权限规则 │ → 决定「同一 (userId, sessionId) 能否跨副本、跨请求恢复」 │ ├── baseStore ────────────── BaseStore（接口） 键值型基础存储：技能仓库、后台任务仓库、消息总线等插件的落点 │ → 决定「插件数据是否共享」，并发写策略由此确定 │ ├── sandboxSnapshotSpec ─── SandboxSnapshotSpec（接口） │ 沙箱快照的存放位置与恢复来源 │ → 决定「换一副本后能否恢复沙箱环境」 │ └── sandboxExecutionGuard ── SandboxExecutionGuard（接口） 沙箱执行的互斥保护（锁语义） → 决定「同一用户是否可能被两个副本同时写入同一沙箱」 这四个接口彼此独立，可以来自不同的后端。 最常见的组合是「状态与锁放 Redis，快照放对象存储」， 因为这两类数据的访问特征差别很大。

这个拆分带来的直接好处是：一行配置即可完成替换。第 08 章的最小配置只需增加一个调用。

一行配置java
DistributedStore store = RedisDistributedStore.fromJedis(jedis);
// 或 MysqlDistributedStore.create(dataSource);
// 或 OssDistributedStore.create(ossClient, bucket, prefix);

HarnessAgent.builder()
    .distributedStore(store)   // 自动配置 stateStore + snapshotSpec + executionGuard
    .filesystem(...)            // 选择你的工作区模式
    .build();

AgentStateStore 实现对照

AgentStateStore 是四类能力里最关键的一个：它决定会话能否跨副本恢复。接口的全限定名是 io.agentscope.core.state.AgentStateStore，实现分散在 core 与三个扩展模块中。

实现模块何时使用
InMemoryAgentStateStoreagentscope-core单元测试。不做任何持久化，进程退出即丢失
JsonFileAgentStateStoreagentscope-core单机开发；HarnessAgent 的缺省实现。root 位于 ~/.agentscope/state/<agentId>/。仅单机可用
RedisAgentStateStoreagentscope-extensions-redis多副本生产的缺省选择。支持 Jedis / Lettuce / Redisson 三种客户端，可对接 Standalone、Cluster、Sentinel 部署形态
OssAgentStateStoreagentscope-extensions-oss已有对象存储基础设施，希望状态与快照共用一套存储与权限体系
MysqlAgentStateStoreagentscope-extensions-mysql状态必须落在关系库：需要对状态做 SQL 审计、报表，或与业务表 join

RedisAgentStateStore 的全限定名是 io.agentscope.extensions.redis.state.RedisAgentStateStore。它的构建器支持三种客户端连接方式，按你的既有技术栈选择：

RedisAgentStateStore 构建器java
AgentStateStore stateStore = RedisAgentStateStore.builder()
        .jedisClient(new JedisPooled("redis://localhost:6379"))
        .keyPrefix("myapp:session:")
        .build();

// Lettuce Cluster（更适合写密集场景）
// .lettuceClusterClient(RedisClusterClient.create(...))

// Redisson（项目其他位置已经在用 Redisson 时优先选它）
// .redissonClient(redisson)

keyPrefix 是多环境共用的关键：同一套 Redis 实例上，预发环境与生产环境使用不同的前缀，两者互不干扰。这一点与后面讨论的多租户键设计是同一个思路，只是一个用于环境隔离，一个用于租户隔离。

选择依据可以整理为以下几步：

先问：是否需要跨副本

否（单机开发、单元测试）→ JsonFileAgentStateStore 或 InMemoryAgentStateStore，不需要引入任何外部依赖。

再问：是否需要 SQL 能力

是（要对状态做审计、报表，或与业务表 join）→ MysqlAgentStateStore。这是唯一能直接查询状态内容的方式。

再问：是否已有对象存储体系

是（希望状态与快照统一权限与生命周期）→ OssAgentStateStore。需要注意 OSS 方案在写并发场景下不如 Redis。

其余情况

选 RedisAgentStateStore。它延迟低、生态成熟、客户端选择多，是多副本生产环境的默认答案。

三个后端的能力矩阵

三类后端对四类能力的支持并不相同。这张矩阵是选型时最常查的一张表，因为它直接决定了自定义组合的可行范围。

能力Redis
agentscope-extensions-redis		OSS
agentscope-extensions-oss		MySQL
agentscope-extensions-mysql
AgentStateStoreRedisAgentStateStoreOssAgentStateStoreMysqlAgentStateStore
BaseStoreRedisStoreOssBaseStoreJdbcStore
SandboxSnapshotSpecRedisSnapshotSpecOssSnapshotSpecJdbcSnapshotSpec
SandboxExecutionGuardRedisSandboxExecutionGuard—
对象存储无法实现锁语义		JdbcSandboxExecutionGuard
OSS 一行是刻意留空的

这不是功能缺失，而是技术约束：SandboxExecutionGuard 需要原子性的互斥操作，而对象存储的 PUT 语义不提供条件写与分布式锁。因此 OSS 方案下这一项没有对应实现。如果你的沙箱需要执行守卫，就必须为这一项选用 Redis 或 MySQL，这正是「自定义组合」存在的意义。

Release Notes 中还出现过另外两类实现：PostgresDistributedStore（PostgreSQL 方向），以及腾讯云 COS 方向的 CosDistributedStore、CosAgentStateStore、CosBaseStore。这说明后端是可扩展的：JdbcStore 自动识别 MySQL / PostgreSQL / SQLite / H2 方言，因此新增一种关系库通常不需要新模块。

BaseStore 的并发安全

技能仓库、后台任务仓库、消息总线这些插件都通过 BaseStore 落数据。多副本环境下，如果两个副本同时写同一个键，必须有一致的策略，否则后写会静默覆盖先写。

BaseStore 提供了一套版本化 CAS（compare-and-swap）API：getVersioned 读取值与版本号，saveIfVersion 与 putIfVersion 只在版本号未变化时写入。

BaseStore 实现并发控制方式说明
RedisStoreCAS用 Lua 脚本实现原子的 putIfVersion；前缀搜索使用 ZRANGEBYLEX 按字典序扫描
JdbcStoreCAS单条 UPDATE 语句完成版本比对与写入；自动识别 MySQL / PostgreSQL / SQLite / H2 方言
InMemoryStoreCAS进程内实现，带版本号比较
OssBaseStoreLWW对象存储无原子条件写语义，采用后写覆盖

其余实现为 LWW（last-write-wins，后写覆盖）。如果你需要「冲突时失败」而不是「静默覆盖」，可以把策略显式设为 ConflictPolicy.FAIL，并配合 SessionTurnGate 使用——后者用于确保同一个会话的同一轮不会被两个副本同时处理。

键路径的组织方式如下，注意分隔符与层级：

BaseStore 键路径text
agentscope:store:item:agents\0X\0users\0alice\0memory\0memory/2026-06-02.md
              └─ 命名空间   └─ 类型  └─ 层级路径用 \0 分隔   └─ 逻辑相对路径

从上面的示例可以看出，键由三段组成：前缀（这里是 agentscope:store:item:）、以 \0 分隔的层级路径、以及末尾的逻辑相对路径。层级分隔符选择 \0（零字节）而不是斜杠或冒号，是为了避免与路径中的正常字符冲突。

多租户键设计

状态存储的键最终由 RuntimeContext 中的 userId 与 sessionId 决定。因此多租户隔离的关键是在这两个字段里体现租户边界。

把租户标识编入键java
agent.call(msg, RuntimeContext.builder()
        .userId(tenantId + ":" + userId)
        .sessionId(agentId + ":" + sessionId)
        .build()).block();

这样做的好处是无需框架提供额外的隔离开关，而且租户边界在键上直接可见——排查问题时可以一眼确认数据归属。代价是你需要自己保证前缀拼接的一致性，因此建议在应用层封装一次，不要在多处重复拼接。

注意 IsolationScope 与此的关系：前者决定「工作区与文件系统如何分区」（第 08、13 章），后者由 userId / sessionId 的取值决定。把租户标识编入 userId，同时也让 IsolationScope.USER 的分区粒度变成「租户内的用户」。

构建期校验规则回顾

第 13 章讨论过沙箱镜像必须满足的契约，这里再明确一次，因为它在生产环境里是构建期就会失败的规则，而不是运行时问题。

校验项规则失败时机
沙箱镜像契约使用 .filesystem(new DockerFilesystemSpec()...) 时，镜像必须满足 Harness 约定的工具可用性要求build() 阶段抛出异常
压缩提示词替换标记compaction(...).summaryPrompt(...) 必须包含 {messages} 替换标记build() 阶段抛出异常
记忆合并替换标记memory(...).consolidationPrompt(...) 必须恰好包含两个 %d 替换标记build() 阶段抛出异常
隔离级别合法性IsolationScope 与文件系统模式组合需自洽，例如 GLOBAL 与远程存储的组合有额外约束build() 阶段抛出异常
为什么这些规则放在构建期

因为它们都是配置错误而不是运行时故障。放在构建期校验，意味着应用启动即失败、健康检查不会通过、流量不会进入该副本，而不是等到第一个用户请求到来才暴露。在滚动发布中这一点尤其重要：配置错误的副本会在启动阶段被直接拒绝，不会替换掉正在服务的旧副本。

14.2动手：从最小配置到完整配置

本章的五个示例按复杂度递增排列。示例一是可以立即运行的最小改动；示例二是可直接使用的生产模板；示例三展示自定义组合；示例四解决滚动重启；示例五把这些配置组织成一个 HTTP 服务。

示例一：最小生产配置

如果你已经有一个能工作的单机构建，把它变成多副本只需要两处改动：引入 DistributedStore，以及把工作区换成共享位置。

MinimalProduction.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.memory.compaction.CompactionConfig;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.extensions.redis.RedisDistributedStore;
import io.agentscope.harness.agent.DistributedStore;
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.IsolationScope;
import io.agentscope.harness.agent.sandbox.impl.docker.DockerFilesystemSpec;

import java.nio.file.Path;
import java.nio.file.Paths;

import redis.clients.jedis.JedisPooled;

public class MinimalProduction {

    public static void main(String[] args) {
        // 依赖：启动时创建一次，全进程共享
        Path workspace = Paths.get("/var/agentscope/workspace");
        JedisPooled jedis = new JedisPooled(
                System.getenv().getOrDefault("REDIS_URI", "redis://localhost:6379"));
        DistributedStore store = RedisDistributedStore.fromJedis(jedis);

        // 单例 Agent：启动时创建一次，不要按请求创建
        HarnessAgent agent = HarnessAgent.builder()
                .name("kb-assistant")
                .model("dashscope:qwen-plus")
                .workspace(workspace)
                // 一行配置替换状态存储、沙箱快照与执行守卫
                .distributedStore(store)
                .filesystem(new DockerFilesystemSpec()
                        .image("python:3.12-slim")
                        .isolationScope(IsolationScope.USER))
                .compaction(CompactionConfig.builder()
                        .triggerMessages(50)
                        .keepMessages(20)
                        .build())
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("tenant-a:zhangsan")
                .sessionId("kb-assistant:s-1001")
                .build();

        Msg reply = agent.call(new UserMessage(
                "支付服务的读超时是多少？"), ctx).block();

        System.out.println(reply.getTextContent());
    }
}

这个示例相对第 08 章的改动集中在三处：工作区从相对路径改为绝对路径（容器内路径在所有副本上一致）；增加 .distributedStore(store)；文件系统从本地改为 DockerFilesystemSpec。其余业务代码完全不变。

Agent 实例必须是单例

HarnessAgent 的构建包含中间件链装配、工具注册、技能合并等一次性工作，它是线程安全的，设计上就是单例使用的。按请求创建会导致每次请求都重新装配，同时把 RuntimeContext 之外的状态混在一起。正确做法是在启动时构建一次，之后只传 RuntimeContext。

示例二：完整生产配置

这是一个可以直接作为起点的生产模板。它包含状态存储、沙箱、上下文治理、大结果落盘、技能仓库与链路追踪六部分。

                .filesystem(new DockerFilesystemSpec()
                        .image("python:3.12-slim")
                        .isolationScope(IsolationScope.USER))
                .compaction(CompactionConfig.builder()
                        .triggerMessages(50)
                        .keepMessages(20)
                        .build())
                .toolResultEviction(ToolResultEvictionConfig.defaults())
                .skillRepository(MysqlSkillRepository.builder(skillsDs)
                        .databaseName("agentscope")
                        .skillsTableName("skills")
                        .createIfNotExist(false)   // 表结构由迁移脚本管理，不在运行期创建
                        .writeable(false)          // 只读分发，生产环境推荐
                        .build())
                .middlewares(List.of(new OtelTracingMiddleware()))
                .build();
    }

    public static void main(String[] args) {
        HarnessAgent agent = create(skillsDataSource());

        String reply = agent.call(
                new io.agentscope.core.message.UserMessage("列出仓库中的构建脚本。"),
                RuntimeContext.builder()
                        .userId(System.getenv("TENANT_ID") + ":u-2048")
                        .sessionId("coding-assistant:s-7")
                        .build())
                .block()
                .getTextContent();

        System.out.println(reply);
    }
}

逐项说明这些配置的意图：

配置意图不这样配置会怎样
.distributedStore(store)状态、快照、执行守卫三项一次到位多副本下会话互相不可见
IsolationScope.USER同一用户的所有会话共享沙箱环境，换副本后环境不变每次调用都是全新沙箱，pip install 之类的结果全部丢失
triggerMessages(50) / keepMessages(20)上下文深度受控；保留 20 条近期消息避免丢失任务目标长会话超出模型上下文窗口
toolResultEviction(...)超过 80K 字符的工具结果落盘，上下文只留预览与指针一次 grep 结果就可能占满上下文
createIfNotExist(false)表结构交给数据库迁移脚本管理运行账号需要 DDL 权限；多副本同时建表可能冲突
writeable(false)技能仓库只读，Agent 无法在运行期修改技能定义模型可能误写技能定义，且无法审计变更来源
OtelTracingMiddleware调用链导出到 OpenTelemetry，可按 trace 还原一次完整交互线上出现超时或异常时无法定位是哪一环慢
技能仓库还可以用 Git

示例三：自定义组合

回到 DistributedStore 的四类能力拆分。当你希望不同能力落在不同后端时，用 builder() 显式组合。最实用的组合是状态放 Redis、快照放对象存储：状态访问频繁、对延迟敏感；快照体积大、访问稀疏。

CustomCompositeStore.javajava
import io.agentscope.extensions.oss.OssDistributedStore;
import io.agentscope.extensions.redis.RedisDistributedStore;
import io.agentscope.harness.agent.DistributedStore;
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.IsolationScope;
import io.agentscope.harness.agent.sandbox.impl.docker.DockerFilesystemSpec;

// ...

DistributedStore redisStore = RedisDistributedStore.fromJedis(jedis);
DistributedStore ossStore = OssDistributedStore.create(
        ossClient,
        "agentscope-sandbox-snapshots",
        "prod/");                         // 环境隔离的 key 前缀

DistributedStore store = DistributedStore.builder()
        .agentStateStore(redisStore.agentStateStore())
        .baseStore(redisStore.baseStore())
        .sandboxSnapshotSpec(ossStore.sandboxSnapshotSpec())
        // 执行守卫必须有锁语义，因此留在 Redis，不从 OSS 取
        .sandboxExecutionGuard(redisStore.sandboxExecutionGuard())
        .build();

HarnessAgent agent = HarnessAgent.builder()
        .name("coding-agent")
        .model(model)
        .workspace(workspace)
        .distributedStore(store)
        .filesystem(new DockerFilesystemSpec()
                .image("python:3.12-slim")
                .isolationScope(IsolationScope.USER))
        .build();

这个组合的取舍是清楚的：沙箱快照可能有 GB 级，放进 Redis 既不经济也不合适；而执行守卫需要原子锁，只能留在 Redis 或 MySQL。OssDistributedStore 的第三个参数是 key 前缀，这里用 prod/ 做环境隔离，预发环境改为 staging/ 即可复用同一个 bucket。

如果你已经在使用框架提供的控制面存储抽象，还可以用 ControlPlaneStores.fromEnv() 从环境变量读取配置，避免把连接信息写在代码里：

ControlPlaneStoresjava
ControlPlaneStores cp = ControlPlaneStores.fromEnv();

HarnessAgent.builder()
        .distributedStore(cp.withAgentStateStore(redis.agentStateStore()))
        .filesystem(new RemoteFilesystemSpec().isolationScope(IsolationScope.USER))
        .build();

远端文件系统与 WorkspaceIndex

当工作区落在远程存储上时，ls、glob、grep 这三类操作会频繁访问远端，延迟直接影响模型响应速度。WorkspaceIndex 为此提供了一份本地索引：

WorkspaceIndex 加速java
HarnessAgent.builder()
        .distributedStore(store)
        .filesystem(new RemoteFilesystemSpec(store)
                .workspaceIndex(WorkspaceIndex.open(workspace)))   // 加速 ls / glob / grep
        .build();

索引本身也需要持久化才能跨副本生效，因此它依赖 DistributedStore 提供的 BaseStore。换句话说，索引加速也属于分布式部署才能获得的收益。

示例四：优雅启停与滚动发布

状态移出本机磁盘解决的是「重启后能读回来」，但没有解决「退出时正在进行的调用怎么办」。如果副本收到终止信号后立即退出，此刻正在写入的状态会丢失，用户侧表现为「助手在回答到一半时失去了会话」。GracefulShutdownManager（io.agentscope.harness.agent）解决这个问题：它在进程退出前等待在途调用完成。

GracefulShutdownAgent.javajava
import io.agentscope.harness.agent.GracefulShutdownManager;
import io.agentscope.harness.agent.HarnessAgent;
import jakarta.annotation.PreDestroy;

public class GracefulShutdownAgent {

    private final HarnessAgent agent;
    private final GracefulShutdownManager shutdownManager;

    public GracefulShutdownAgent(HarnessAgent agent,
                                 GracefulShutdownManager shutdownManager) {
        this.agent = agent;
        this.shutdownManager = shutdownManager;
    }

    /**
     * 在 Spring 容器销毁 bean 时调用。
     * 容器会先让此回调完成，再结束进程。
     */
    @PreDestroy
    public void shutdown() {
        // 1. 健康检查端点先返回「不接流量」，让负载均衡把新请求转到其他副本
        readinessFlag.markNotReady();

        // 2. 等待在途调用完成，并把最终状态写入状态存储
        shutdownManager.awaitQuiescence(java.time.Duration.ofSeconds(30));

        // 3. 释放连接池等资源
        agent.close();
    }
}

完整的滚动发布流程需要四步配合，缺一不可：

下线前标记

副本收到 SIGTERM 后，先把就绪探针置为失败，让负载均衡停止分发新请求。

等待在途调用

GracefulShutdownManager 等待正在执行的 call() 完成。这一步的等待时间应大于典型调用的耗时上限。

写入最终状态

调用完成后，AgentState 由分布式状态存储负责持久化。因为写入的是共享存储，新副本可以立即读到。

超时强制退出

等待超过上限时强制结束进程，避免副本永远无法下线。此时未完成的调用会丢失，因此上限不应设置得过大。

与之对应的容器配置示例：

Kubernetes 优雅终止yaml
spec:
  terminationGracePeriodSeconds: 45      # 应大于 awaitQuiescence 的等待上限
  containers:
    - name: kb-assistant
      readinessProbe:
        httpGet:
          path: /actuator/health/readiness
        periodSeconds: 3
      lifecycle:
        preStop:
          exec:
            # 留出摘流量的时间，避免「标记不健康」到「停止发请求」之间的空窗
            command: ["sh", "-c", "sleep 5"]
为什么 preStop 的等待是必要的

负载均衡感知到探针失败并真正停止分发请求，需要经过探测间隔与后端更新周期，通常有几秒延迟。如果探针一失败就立即退出，这几秒内到达的请求会落到正在退出的副本上。preStop 的短暂等待就是覆盖这个空窗。terminationGracePeriodSeconds 必须大于等待上限，否则 awaitQuiescence 还没返回进程就被强杀了。

示例五：多租户 HTTP 服务骨架

最后把上述配置组织成一个可用的服务骨架。要点是：Agent 是单例，请求级信息全部通过 RuntimeContext 传入。

KnowledgeAssistantService.javajava
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;

import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestHeader;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class KnowledgeAssistantService {

    private final HarnessAgent agent;

    public KnowledgeAssistantService(HarnessAgent agent) {
        this.agent = agent;   // 单例，启动时构建一次
    }

    @PostMapping("/chat")
    public ChatResponse chat(@RequestHeader("X-Tenant-Id") String tenantId,
                             @RequestHeader("X-Session-Id") String sessionId,
                             @RequestBody ChatRequest request) {

        RuntimeContext ctx = RuntimeContext.builder()
                // 租户标识编入 userId，隔离在键路径上直接可见
                .userId(tenantId + ":" + request.userId())
                .sessionId("kb-assistant:" + sessionId)
                .build();

        Msg reply = agent.call(new UserMessage(request.message()), ctx).block();

        return new ChatResponse(reply.getTextContent());
    }
}

这个骨架里有三个容易出错的点：

  • 不要按请求创建 Agent。构建过程包含中间件装配与技能合并，开销显著；而且 HarnessAgent 内部维护了状态，每次新建等于每次都是空的工作区上下文。
  • 租户标识必须来自可信来源。如果 X-Tenant-Id 由客户端自行填写而服务端不校验，等于没有隔离。生产环境应从已验证的令牌或网关注入的请求头中获取。
  • 租户前缀拼接要集中。示例中直接拼接是为了清晰，实际项目中应封装成一个 TenantKeys 工具方法，否则格式不一致会导致同一用户的会话被分散到两个键空间上。

另外，.block() 会把响应式流阻塞成同步结果。在 Web 请求线程中这通常可以接受，但如果引入 WebFlux 或虚拟线程，建议改为响应式返回，避免占用线程。

14.4选型决策指南

本章涉及的配置项不少，但决策顺序是固定的。按下面三步走，可以在十分钟内确定方案。

第一步：确定是否需要跨副本

只需要单机（本地开发、内部工具、单人使用）→ 保持缺省的 JsonFileAgentStateStore，不引入任何外部依赖。分布式配置此时是纯粹的负担：多一个依赖，多一个故障点。

第二步：确定状态与沙箱各自的访问特征

状态与会话日志是访问频繁、体积可控的；沙箱快照是体积大、访问稀疏的。如果两者规模相当，用同一个后端（最简单）；如果沙箱快照明显更大，用自定义组合分开存放。

第三步：确定是否需要额外能力

需要 SQL 审计 → MySQL；需要跨可用区冗余 → 确认所选后端本身是否支持多可用区部署；需要链路追踪 → 增加 OtelTracingMiddleware；需要多环境共用一套 Redis → 设置 keyPrefix。

不同规模下的推荐组合：

规模状态存储文件系统技能仓库其他
本地开发JsonFileAgentStateStore
（缺省）		本地磁盘工作区目录不需要任何外部依赖
单机内测JsonFileAgentStateStore
（可换 Redis 以便日后平滑迁移）		DockerFilesystemSpec工作区目录GracefulShutdownManager 便于停机时保存状态

不要一次性做完所有配置。更稳妥的顺序是：先在单机上把业务功能与工作区内容确定下来，然后只替换状态存储为 Redis 并验证多副本行为，接着再引入沙箱，最后处理技能仓库与可观测性。每一步都可以独立验证，出问题时容易定位。一次性改五处，出问题时会难以判断是哪一处引起的。

#检查项确认方式不满足的后果

14.6本章小结

  • 默认的 JsonFileAgentStateStore 仅单机可用。多副本部署必须把状态移出本机磁盘，否则增加副本数量反而会放大故障面。
  • DistributedStore 组合四类正交能力：AgentStateStore、BaseStore、SandboxSnapshotSpec、SandboxExecutionGuard。一行配置即可整体替换。
  • 官方文档中并存两套 API 名称：DistributedStore 与 DistributedBackend。语义一致，升级版本时以该版本的 API 参考为准。
  • 状态存储的选型：多副本生产缺省 RedisAgentStateStore；需要 SQL 审计时用 MysqlAgentStateStore；已有对象存储体系时用 OssAgentStateStore。
  • 能力矩阵中 SandboxExecutionGuard 在 OSS 一列刻意留空，因为对象存储无法实现锁语义。需要守卫时必须用 Redis 或 MySQL。
  • BaseStore 提供版本化 CAS API（getVersioned / saveIfVersion / putIfVersion）；Redis 与 JDBC 实现支持 CAS，OSS 为 LWW。需要冲突失败时用 ConflictPolicy.FAIL。
  • 多租户隔离的简单有效做法是把租户标识编入 userId，使隔离边界在键路径上直接可见。
  • 状态存储解决「重启后读回来」，GracefulShutdownManager 解决「退出时不丢在途状态」。两者缺一不可，并且 terminationGracePeriodSeconds 必须大于等待上限。
  • 官方文档在本章这部分没有提供 YAML / properties 配置示例，只用环境变量、CLI 选项与 URI。这与第 04 章的模型 YAML 配置不同，需要注意区分。
练习
  1. 把本章的示例一运行验证：用一个本地 Redis 实例，以 JedisPooled 连接，验证 .distributedStore(store) 生效之后状态不再写入 ~/.agentscope/state/。
  2. 验证缺省行为作为对照：去掉 .distributedStore(...)，重启进程后再提问，观察状态是否从本地 JSON 文件恢复。由此说明为什么这个方案不能用于多副本。
  3. 用 DistributedStore.builder() 组合出「状态用 Redis、快照用 OSS」的方案，确认执行守卫仍来自 Redis。再尝试把执行守卫也改成 OSS，观察框架如何处理这个不支持的能力。
  4. 为 RedisAgentStateStore 设置 keyPrefix，在同一个 Redis 上模拟两个环境，验证两套状态互不干扰。
  5. 实现 GracefulShutdownManager 的 @PreDestroy 回调，在等待期间发起一次调用，验证该调用完成后状态已写入共享存储，并且新副本可以读到。
  6. 设计题：一个日活百万的智能体服务，每天需要保存约 2000 万次对话、沙箱快照平均 80MB 且每周至少恢复一次。请给出存储与沙箱方案设计，需要回答：(1) 四类能力各选什么后端，为什么；(2) 快照与会话日志如何避免互相影响；(3) 同一用户被分配到两个副本时，如何保证沙箱不会同时被写入；(4) 容量估算与保留期；(5) 你如何验证方案在故障切换时的一致性。
  7. 对照本章的上线检查清单，检查你目前的服务，列出尚未满足的条目并按严重程度排序，说明每一项的风险来源。
