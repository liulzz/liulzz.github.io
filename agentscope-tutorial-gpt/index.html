01 · AgentScope 2.0 到底解决什么问题？

不要先把 AgentScope 理解成“调用大模型的 Java SDK”。2.0 的重点是把 Agent 从一次性推理程序扩展为可以长期运行、持续保存状态、受控执行工具的工程系统。

两层 Agent 架构

ReActAgent 是推理核心：输入消息 → 模型推理 → 工具调用 → 工具结果 → 再推理 → 最终回复。HarnessAgent 基于同一推理核心增加 Workspace、持久化、Memory、Compaction、Skill、Subagent、Sandbox、Plan 等工程能力。

学习顺序建议：先用 ReActAgent 学原理，再用 HarnessAgent 学长期运行与生产部署。

一次 call 与一段长期运行

一次 call() 只是执行入口；2.0 会把运行状态落到 AgentStateStore，并根据 (userId, sessionId) 找到对应会话。因此同一个 Agent 实例可以服务不同用户和不同 session。

关键认知：Agent 实例不应该承载某一个用户的“当前会话变量”，会话状态应由框架按上下文维度管理。

02 · 场景：做一个能回答问题的 Java 助手

目标：创建最小 Agent，理解 Maven 依赖、模型配置、UserMessage、call。

工程初始化

推荐环境为 JDK 17+，Maven 3.9+。2.0 将模型提供商拆成独立 extension，因此只依赖 harness/core 还不够。

<dependency>
  <groupId>io.agentscope</groupId>
  <artifactId>agentscope-harness</artifactId>
  <version>2.0.3</version>
</dependency>

<dependency>
  <groupId>io.agentscope</groupId>
  <artifactId>agentscope-extensions-model-dashscope</artifactId>
  <version>2.0.3</version>
</dependency>

最小可运行代码

import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;

public class FirstAgent {
  public static void main(String[] args) {
    var agent = HarnessAgent.builder()
        .name("assistant")
        .sysPrompt("你是一个有帮助的 Java 技术助手。")
        .model("dashscope:qwen-plus")
        .build();

    var result = agent.call(
        new UserMessage("解释一下 Java 中的 CompletableFuture"))
        .block();

    System.out.println(result.getTextContent());
  }
}

03 · 场景：同一个 Agent 切换不同模型

目标：理解 Credential、Chat Model、Formatter、ModelRegistry，以及模型失败重试和备用模型。

Model 层分工

  • Credential：API Key、Base URL 等鉴权信息。
  • Chat Model：具体 provider + model 的推理实现。
  • Formatter：在内部消息结构与 provider message 格式之间转换。
  • ModelRegistry：允许使用 provider:model 字符串解析模型。

容错

var agent = ReActAgent.builder()
    .name("resilient")
    .sysPrompt("...")
    .model("dashscope:qwen-plus")
    .maxRetries(3)
    .fallbackModel("dashscope:qwen-max")
    .build();

2.0.3 的官方模型层也覆盖 Anthropic prompt caching 等能力；实际可用 provider 请以对应 extension 与 Release Notes 为准。

04 · 场景：让 Agent 同时处理文本、图片和工具结果

目标：不要把 Message 当成一个字符串。2.0 用 Msg + ContentBlock 组织完整对话状态。

核心结构

Msg 表示一个完整对话轮次；内容由有序的 ContentBlock 组成。常见块包括 TextBlock、DataBlock、ThinkingBlock、ToolUseBlock、ToolResultBlock、HintBlock。

2.0 中 DataBlock 用于统一多媒体数据，可以使用 base64 或 URL。这样模型、工具结果、多 Agent 通信都可以共享同一套消息模型。

为什么事件不是 Msg？

Msg 是完整状态；AgentEvent 是执行过程中的增量进度。一个 call() 最终对应一条 assistant Msg，但过程中可以产生多个事件，用于前端流式渲染、工具进度展示和人工介入。

学习重点：后面做 Web SSE 时，你主要消费的是 Event；做持久化与会话恢复时，你要理解 Msg 和 AgentState。

05 · 场景：做一个“查询订单”工具

目标：让模型不只是生成文字，而是可以调用 Java 业务能力。理解 @Tool、ToolBase、Toolkit、Tool Group。

最小工具

import io.agentscope.core.tool.Tool;

public class OrderTools {
  @Tool(
      name = "query_order",
      description = "根据订单号查询订单状态")
  public String queryOrder(String orderNo) {
    return "订单 " + orderNo + " 状态：已支付";
  }
}

注册到 Toolkit

var toolkit = new Toolkit();
toolkit.registerTool(new OrderTools());

ReActAgent agent = ReActAgent.builder()
    .name("order-agent")
    .sysPrompt("你是订单查询助手")
    .model("dashscope:qwen-plus")
    .toolkit(toolkit)
    .build();
生产项目中建议把工具按领域拆分到不同的 Tool Group，并结合 Permission 控制工具的可用范围。
工具元数据
模型看到的是工具名称、描述和 JSON Schema。
Tool Group
可以将一组工具/MCP/Skill 一起启用或停用。
只读属性
isReadOnly() 等信息会参与权限与执行治理。

06 · 场景：把“自然语言回答”变成 Java 对象

目标：做数据抽取、分类、表单填写时，不要继续解析模型文本，而应使用 Structured Output。

public record RiskResult(
    String level,
    String reason,
    int score) {}

Msg result = agent.call(
    List.of(new UserMessage("评估这笔交易的风险")),
    RiskResult.class).block();

RiskResult data = result.getStructuredData(RiskResult.class);
System.out.println(data.level());

2.0 会根据模型能力选择原生 JSON Schema 路径或降级路径；调用方保持同一套代码。Structured Output 也可以和工具调用组合：Agent 先调用工具获取数据，再输出符合 Java schema 的最终结果。

07 · 场景：做一个浏览器式流式 UI

目标：理解 streamEvents()，并知道为什么 2.0 的事件系统是重要升级。

代码

agent.streamEvents(
    List.of(new UserMessage("分析这个接口的错误")))
  .doOnNext(event -> {
    System.out.println(event.getClass().getSimpleName());
  })
  .blockLast();

事件生命周期

2.0 使用类型化事件，例如 AgentStartEvent、ModelCallStartEvent、TextBlockStartEvent、TextBlockDeltaEvent、ToolCallStart/Delta/End、ToolResult...、RequireUserConfirmEvent、AgentResultEvent、AgentEndEvent，以及可扩展的 CustomEvent。

事件带有 replyId / blockId / toolCallId 等关联信息，因此前端不需要自己维护“这一段增量属于哪个块”。

08 · 场景：同一个用户第二次提问，Agent 记得第一次会话

目标：理解 RuntimeContext、AgentState、AgentStateStore、Session 与并发隔离。

RuntimeContext

var ctx = RuntimeContext.builder()
    .userId("alice")
    .sessionId("order-session-001")
    .put("request_id", "req-001")
    .build();

agent.call(
    List.of(new UserMessage("我刚才查询的订单是什么状态？")),
    ctx).block();

RuntimeContext 是本次调用的瞬态上下文；AgentState 才是可持久化的运行状态。两者要严格区分。

并发模型

不同 (userId, sessionId) 可以并行；相同二元组的调用会按顺序串行化，以保护对话一致性。这样同一个 Agent 实例可以服务多个会话。

生产系统通常应显式设置 userId + sessionId，并将租户等维度编码进你的会话标识体系，避免跨用户串读。

09 · 场景：给 Agent 一个“项目目录”，而不是一条 Prompt

目标：学习 Workspace。它保存 Agent 的工程化上下文，包括人格、知识、技能、子 Agent、工具配置与持久化文件。

推荐理解方式：文件即配置与资产

.agentscope/workspace/
├── AGENTS.md                 # agent 人格、项目规则
├── MEMORY.md                 # 长期记忆摘要
├── memory/                   # 每日事实记录
├── knowledge/                # 项目知识
├── skills/                   # 项目技能
├── subagents/                # 子 Agent 声明
├── tools.json                # MCP / 工具白名单等配置
└── agents/<agentId>/
    ├── sessions/             # 不压缩的会话日志
    └── tasks/                # 任务记录

这里有一个很重要的边界：AgentState 不等于 Workspace 文件。AgentState 保存运行期上下文、权限规则、Plan 状态、tool state 等；Workspace 更偏向可持久化的工程资产与日志。

10 · 场景：用户上周说过的偏好，今天仍然有效

目标：理解两层长期记忆、三类 LLM 辅助调用、上下文压缩和大工具结果卸载。

两层记忆

memory/YYYY-MM-DD.md 保存每天新增事实；后台 consolidation 将其整理为 MEMORY.md，后者在每轮推理时作为长期记忆的一部分进入 system prompt。

.memory(MemoryConfig.builder()
    .flushTrigger(
        MemoryConfig.FlushTrigger.throttled(
            Duration.ofMinutes(10)))
    .build())

Context Compaction

当上下文接近阈值时，对话前缀会生成摘要并保留最近消息；模型真正返回 context_length_exceeded 时，如果配置了 compaction，框架还可做兜底压缩后重试。

.compaction(CompactionConfig.builder()
    .triggerMessages(30)
    .keepMessages(10)
    .build())
大工具结果卸载也属于上下文治理：默认超过约 80K 字符的工具结果可以落盘，上下文只保留首尾预览与文件路径。Agent 需要时可再次读取。

11 · 场景：把“代码评审规范”沉淀成可复用 Skill

目标：理解 Skill 不是单个 Java 方法，而是一套可带参考文档、脚本与资源文件的能力包。

SKILL.md

---
name: code-reviewer
description: 当用户需要代码评审时使用。
---
# Code Reviewer
1. 阅读 references/style-guide.md
2. 使用 scripts/run-checks.sh
3. 按文件和行号给出具体建议

目录结构

code-reviewer/
├── SKILL.md
├── references/
│   └── style-guide.md
└── scripts/
    └── run-checks.sh

技能来源支持项目 Workspace，也支持 Git、Nacos、MySQL、classpath、自定义 repository。2.0 的技能体系还支持 skill filter、skill tool group 与自学习/审核闭环。

12 · 场景：主 Agent 把“代码审查”交给独立子 Agent

目标：理解多 Agent，不是简单实例化几个 Agent，而是要处理任务边界、上下文隔离、同步/后台执行与事件转发。

声明式 Subagent

workspace/subagents/reviewer.md
---
description: 代码审查专家
---
请检查 PR 改动、指出具体文件和行号问题。

主 Agent 可以使用 agent_spawn 委派独立任务。框架内置 general-purpose 子 Agent，也支持 workspace Markdown spec 和编程式声明。

同步与后台

短任务可以同步委派；长任务可以后台运行。2.0 支持事件实时转发，并通过 source 路径区分 main agent 与 subagent 事件来源。

适合场景：研究、代码审查、测试、文档生成、独立的数据整理任务。

13 · 场景：修改 Java 项目前，先生成 Plan

目标：让 Agent 先分析和写入计划，再在人工确认后进入执行阶段。

开启 Plan Mode

var agent = HarnessAgent.builder()
    .name("planner")
    .model("dashscope:qwen-plus")
    .workspace(Path.of("workspace"))
    .enablePlanMode()
    .planFileDirectory("plans")
    .build();

Plan 阶段可做什么

Plan 阶段以只读为核心，允许 plan_enter、plan_write、plan_exit、todo_write、agent_spawn、agent_send、agent_list、task_output、task_list 等配套工具；其它写操作会被拒绝。

退出 Plan Mode 会复用 Permission 的 ASK 流程，让用户确认是否进入执行阶段。

14 · 场景：删除文件前必须经过用户确认

目标：理解 PermissionMode、PermissionRule、Built-in Checks 与 HITL 的关系。

五种权限模式

模式含义
DEFAULT默认安全策略，需要规则或用户确认
ACCEPT_EDITS自动放行工作目录中的文件编辑
EXPLORE只读探索
BYPASS放行规则之外的一般调用，但 deny / ask 与危险路径检查仍有效
DONT_ASK无人值守，ASK 转 DENY

权限判断不是简单 if

框架综合 Rules、Mode、Tool 自身的运行时检查。某些危险路径检查即使在 BYPASS 下也不能被绕过。对于 ASK，Agent 会发出 RequireUserConfirmEvent 并暂停，用户提供 ConfirmResult 后继续。

PermissionContextState permCtx =
    PermissionContextState.builder()
        .mode(PermissionMode.DEFAULT)
        .build();

15 · 场景：让 Agent 在 Docker 里编译并测试 Java 项目

目标：理解 Filesystem 抽象与 Sandbox。沙箱解决的是不可信命令、跨调用恢复、多用户隔离等问题。

三类 Filesystem

本机 + shell：开发机直接执行；Remote/shared：多个副本共享 Workspace；Sandbox：文件与命令在隔离环境中执行。

IsolationScope 可以按 SESSION、USER、AGENT、GLOBAL 决定文件/沙箱的共享范围。

Docker 示例

.filesystem(new DockerFilesystemSpec()
    .image("ubuntu:24.04")
    .isolationScope(IsolationScope.USER))

2.0 还支持 Kubernetes、Daytona、E2B、AgentRun 等沙箱实现。生产环境可以结合 snapshot 保存沙箱工作目录与可执行环境状态。

安全原则：不要让生产 Agent 在宿主机无保护地执行模型生成的 shell / Python / npm 等命令。需要执行不可信命令时，应优先设计 Permission + Sandbox 的组合。

16 · 场景：给所有 Agent 调用加审计和追踪

目标：理解 Middleware。不修改 Agent 或 Model 的实现，也可以在生命周期关键节点加入统一逻辑。

Hook适合做什么
onAgent一次完整 reply 流程：统一审计、总耗时
onReasoning一轮 ReAct：推理前后、上下文治理
onActing工具执行：工具耗时、成功率
onModelCall底层模型 API：模型耗时、错误、token
onSystemPrompt每次组装 system prompt 时做变换
onAgentStateReadyAgentState 就绪后、进入流水线前处理状态

2.0.1 引入 Middleware 执行优先级；因此在复杂系统里可以明确外层与内层 middleware 的顺序。2.0.3 还新增了 FinalAnswerFilterMiddleware 这类对 ReAct stream 的能力。

17 · 场景：让 Agent 使用一个外部 MCP 服务

目标：理解 MCP 和 Java Tool 的关系：两者最终都进入 Toolkit，并以工具 schema 形式提供给模型。

编程式接入

McpClientWrapper amap =
    McpClientBuilder.create("amap")
        .streamableHttpTransport(
            "https://mcp.amap.com/mcp?key="
            + System.getenv("AMAP_API_KEY"))
        .buildAsync()
        .block();

toolkit.registerMcpClient(amap).block();

声明式治理

Workspace 的 tools.json 可以用于声明 MCP server 与工具白名单。再结合 Permission，可以做到“哪些工具存在、哪些可以使用、哪些调用要先确认”。

MCP 不是替代 Java Tool，而是一种外部工具生态接入方式。AgentScope 最终仍通过 Toolkit 管理能力。

18 · 场景：把 Agent 接到企业微信 / HTTP / Web UI

目标：理解 Channel 与 Gateway。它们负责把外部消息平台映射到 Agent 的会话模型，并统一流式事件回传。

Channel 的职责

解析消息来源 → 确定 userId / session → 路由目标 Agent → 传递消息 → 把结果或事件投递回消息平台。官方 2.0 新闻与文档覆盖 Chat UI，以及钉钉、飞书、企业微信等场景。

协议层

AgentScope Java 2.0 的生态还包含 AG-UI、A2A 等协议适配，用于与外部 Agent/UI 系统集成。这里要区分“框架能力”和“协议集成”：协议模块是 extension，不等于 ReAct 核心。

19 · 场景：从单机 Demo 部署到 Kubernetes 多副本

目标：理解为什么 AgentScope 2.0 强调“distributed, long-running”。真正生产化需要同时考虑 State、Workspace、Sandbox Snapshot、执行锁、Skill 治理和 Observability。

单机 → 分布式

DistributedStore store =
    RedisDistributedStore.fromJedis(jedis);

HarnessAgent agent = HarnessAgent.builder()
    .name("prod-agent")
    .model("dashscope:qwen-plus")
    .distributedStore(store)
    .filesystem(new RemoteFilesystemSpec()
        .isolationScope(IsolationScope.USER))
    .build();

DistributedStore 可以统一配置 AgentStateStore、BaseStore、SandboxSnapshotSpec、SandboxExecutionGuard 等分布式能力。

生产选型要点

  • AgentStateStore：Redis / MySQL / PostgreSQL / OSS 等；多副本需要共享状态。
  • Workspace：RemoteFilesystemSpec + BaseStore，或 Sandbox 模式。
  • Sandbox：快照与跨节点执行锁不能遗漏。
  • Observability：OpenTelemetry / 事件流 / 审计日志。
  • Concurrency：Session Turn Gate、状态版本化与 CAS 用于防止重复推进与并发覆盖。
2.0.3 引入 AgentState 版本化与乐观并发原语，因此生产部署时可以进一步关注“状态读写冲突”问题，而不只是“Redis 能不能存下来”。

从 1.x 升级到 2.0，应该怎么学？

如果你已经有 AgentScope 1.x 项目，先不要一次性重写。先区分“必须迁移”的 API 变化和“推荐迁移”的弃用 API。

核心迁移认知

2.0 重点变化包括：新的 Agent 抽象、类型化 Event、Permission、Middleware 栈、Workspace 抽象、RuntimeContext 与 AgentState 解耦，以及模型 provider extension 模块化。

推荐路线

  1. 先把模型与 Tool 迁移到 2.0。
  2. 再切换到新的 call / streamEvents。
  3. 最后再增加 Harness、Workspace、State、Memory、Sandbox。
不要把 2.0 的 Harness 能力一次性全部启用。建议先做最小运行闭环，再根据场景逐步打开能力。

建议按顺序完成。浏览器会把完成状态保存在本地，因此可以分多次学习。
