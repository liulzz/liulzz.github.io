源码深度拆解AgentScope Harness：设计思想与实现原理

基准：agentscope-java 主分支源码（2026-10-05 浅克隆）与官方文档 v2.0.3 ｜ 全部结论均给出源码锚点（文件:行号）

0 · 引言：为什么需要 Harness

设想一个已经通过单元测试的 ReActAgent 被部署为在线服务，同时服务多名用户。此时问题清单立刻出现：第二轮对话如何恢复上一轮的上下文？上下文逼近模型窗口上限时如何收缩？用户 A 的文件与记忆如何对用户 B 隔离？危险的 shell 命令由谁审查？团队积累的领域经验如何沉淀并被复用？

裸的 ReActAgent 只解决"一次请求 → 推理 → 工具 → 回复"这个单循环。官方架构文档对 Harness 的定位因此非常明确：

HarnessAgent is a thin wrapper around ReActAgent that packages the engineering capabilities long-running agents need — workspace-driven persona, long-term memory, subagent orchestration, sandbox isolation, skill composition, plan mode, channel routing — into a single builder.

— docs/v2/en/docs/harness/architecture.md（仓库内 Mintlify 文档原稿）

换句话说，Harness 不重新发明推理循环，它回答循环之外的所有工程问题：跨调用续接、上下文有界、多租户隔离、危险动作审查、能力沉淀。本文以源码为唯一事实源，逐层拆解它是如何做到的。

1 · 全景：模块版图与定位

仓库根目录的 AGENTS.md 给出官方模块边界规则：

  • 可复用的 agent 行为 → agentscope-core（ReAct 循环、消息/事件、工具、中间件、状态、权限）；
  • 高层能力 → agentscope-harness（HarnessAgent、workspace、记忆、子代理、技能、通道、沙箱、文件系统）；
  • 模型/服务提供方专属代码 → agentscope-extensions；
  • 应用装配 → examples 或 agentscope-service。

类关系的核心是一条委托链：HarnessAgent 实现 Agent 接口，内部持有一个由 ReActAgent.Builder 构建的 ReActAgent delegate，getDelegate() 将其暴露（HarnessAgent.java L492）。构建完成时输出一条日志，概括了它装配出的三要素：

"HarnessAgent '{}' built [workspace={}, filesystem={}, subagents={}]"
HarnessAgent.java L2952（build 末尾日志）
线程安全契约HarnessAgent 在两次 call() 之间无状态，单实例即可服务多用户多会话；状态按 (userId, sessionId) 隔离，同一会话自动串行，跨会话并行（L164–167 Javadoc；串行机制见第 4 节 call gate）。

2 · 设计思想三原则

通读 harness 模块后可以提炼出三条贯穿性的设计原则。它们同时出现在官方架构文档与源码结构中，因此可以作为理解全部子系统的骨架。

原则一：能力注册在循环的钩子上，不修改循环本体

core 的 MiddlewareBase（242 行）定义了全部 6 个扩展点，分为三种模式：

扩展点模式签名要点介入时机
onAgent洋葱型（next 委托）Flux<AgentEvent> onAgent(next, agent, ctx, msgs)整次调用的最外层
onReasoning洋葱型同上，作用于推理阶段每次推理前后
onActing洋葱型同上，作用于工具执行工具调用前后
onModelCall洋葱型同上，作用于模型 API 调用请求发出前后（流式增量可改写）
onSystemPrompt管道型Mono<String> onSystemPrompt(agent, ctx, currentPrompt)系统提示重建时，链式变换
onAgentStateReady通知型void onAgentStateReady(agent, ctx, state, inputMessages)AgentState 绑定后、进入流水线前（单次通知）

default Flux<AgentEvent> onAgent(Agent agent, RuntimeContext ctx,
        List<Msg> msgs, NextFluxListener next) { return next.onAgent(agent, ctx, msgs); }

MiddlewareBase.java（签名摘录，注释见 L229–241）

两个控制维度同样定义在此：activePoints() 声明中间件参与哪些钩子（构造时定型，运行期不再判断），order() 决定层级——数值越大越靠外层，默认 1。

这一协议的收益在 harness 模块里体现得非常直观：压缩、记忆冲刷、会话记录、子代理、技能、计划模式、沙箱生命周期、消息收件箱……十七项能力全部实现为中间件，通过 build() 顺序注册到内部 ReActAgent 上（清单见第 3 节）。引擎侧没有任何 if (harness) 式的条件分支；新增能力等价于新增一个中间件类。

原则二：能力互不依赖，共享三个对象

官方架构文档指出，各能力之间不相互引用，而是共享三个对象：

  • RuntimeContext —— 谁在说话（userId、sessionId、attributes）；
  • workspace —— 谁读写哪些文件（工作区根目录与文件系统后端）；
  • AgentStateStore —— 状态如何跨调用恢复。

源码印证相当一致：文件系统接口的每一个方法都以 RuntimeContext 作为首参（见 5.3 节），身份随每次 I/O 流动；WorkspaceContextMiddleware 只持有 WorkspaceManager；CompactionMiddleware 只持有 ConversationCompactor 与 MemoryFlushManager；build() 装配出的各中间件之间没有字段级引用。因此，disableMemoryTools、disableSubagents、leafSubagent 这类开关可以自由组合而不会产生矩阵式依赖。

原则三：内置能力定序装配，用户中间件始终在外层

builder 的 .middleware(...) 直接写入内部 ReActAgent.Builder（L1613–1624），而全部内置中间件在 build() 阶段才按固定顺序注册（L2533 起）。ReActAgent 侧的 order 语义保证：先注册者在外层，因此用户中间件先于内置中间件看到输入、后于它们看到输出。那么鉴权、审计、限流这类横切逻辑就可以在 harness 内置逻辑之前完成拦截，无需继承或改造任何内置类。

约束通知型钩子 onAgentStateReady 在同会话重入时会在 call gate 上死锁。MiddlewareBase 的 Javadoc 明确要求该钩子非阻塞、快速失败（L229–241）。这是三模式中唯一带有死锁警示的扩展点，也说明通知型钩子的执行时机位于会话串行窗口之内。

4 · 一次 call() 的状态流转

官方架构文档将状态划分为三层，源码结构与之一一对应：

层级内容载体
单次调用内AgentState + RuntimeContextcore ReActAgent 循环内的活动状态
跨调用会话快照、全量日志、子任务记录、沙箱元数据AgentStateStore（默认 ~/.agentscope/state/<agentId>/，按 (userId, sessionId) 寻址）
长期记忆memory/YYYY-MM-DD.md 追加 → 周期性合并进 MEMORY.md → 每步推理注入系统提示workspace 文件系统

三个官方确认的不变量值得单独记录：

  1. 系统提示每步推理都重建——因此修改 AGENTS.md 或 MEMORY.md 后下一轮立即生效，无需重启；
  2. 压缩、记忆蒸馏、后台维护均经过 PeriodicGate 节流——分布式部署用 StoreBackedPeriodicGate 保证跨节点只触发一次，本地用 LocalPeriodicGate；
  3. AgentState 持久化只由 core 的 ReActAgent + AgentStateStore 完成——harness 不追加自己的持久化钩子，状态写入点因此唯一。

会话串行的实现锚点在 core：ReActAgent.slotKey(userId, sessionId)（L408）将每会话状态放入独立槽位，配合 call gate 保证同会话调用排队执行。MiddlewareBase 的死锁警示（第 2 节）正是针对这个门——在通知钩子里同步发起同会话调用会永久等待自身。

5 · 关键子系统拆解

5.1 系统提示装配：每步重建、token 预算、按部署面分支渲染

WorkspaceContextMiddleware 通过管道钩子 onSystemPrompt 把工作区内容注入系统提示：

@Override
public Mono<String> onSystemPrompt(Agent agent, RuntimeContext ctx, String currentPrompt) {
    return Mono.fromCallable(() -> {
        RuntimeContext rc = ctx != null ? ctx : RuntimeContext.empty();
        String base = currentPrompt != null ? currentPrompt : "";
        String section = buildWorkspaceSection(rc);
        String separator = base.isEmpty() || base.endsWith("\n") ? "" : "\n";
        return base + separator + section;
    }).subscribeOn(Schedulers.boundedElastic());
}
WorkspaceContextMiddleware.java L207–217

buildWorkspaceSection 的装配顺序是：会话上下文段 → 指引段（记忆召回/持久化说明）→ 工作区说明段 → 已加载内容段（AGENTS.md、MEMORY.md、KNOWLEDGE.md、附加上下文）。其中有一个精细的预算控制：

int fixedTokens = estimateTokens(sessionContext) + estimateTokens(agentsContent)
        + estimateTokens(knowledgeBlock) + estimateTokens(additionalBlock);
if (includeMemoryContext) {
    int memoryTokens = estimateTokens(memoryContent);
    int available = maxContextTokens - fixedTokens;
    if (available > 0 && memoryTokens > available) {
        memoryContent = truncateToTokenBudget(memoryContent, available);  // MEMORY.md 优先级最低
    }
}
WorkspaceContextMiddleware.java L236–247

另一处值得注意的细节：工作区说明段按文件系统类型分支渲染（本地 overlay / 沙箱 / 远端 composite / 其他四种），让模型看到的自我描述与真实部署面一致（L314–345 的 Javadoc 与实现）。沙箱分支会明确告知"文件无法离开沙箱"，或者提示使用 deliver_artifact 工具（若已配置）。

5.2 上下文压缩：非 LLM 修剪在前，LLM 摘要在后，逐级降级

压缩由 CompactionMiddleware 在 onReasoning 钩子触发（L84），核心算法在 ConversationCompactor.compactIfNeeded：

// 第 1 步：非 LLM 修剪（轻量、零成本）
List<Msg> messages = pruneToolResults(
        truncateArgs(conversationMessages, config.getTruncateArgsConfig()),
        config.getPruneConfig());

int totalTokens = TokenCounterUtil.calculateToken(messages);
if (!shouldCompact(messages, totalTokens, config)) { return Mono.just(Optional.empty()); }

int cutoff = determineCutoffIndex(messages, totalTokens, config);
if (cutoff <= 0) { return Mono.just(Optional.empty()); }   // 安全截断点为 0：跳过

List<Msg> summaryInput = new ArrayList<>(messages.subList(0, cutoff));
List<Msg> flushInput   = filterSummaryMessages(summaryInput);  // 旧摘要不再重复冲刷
List<Msg> tail         = new ArrayList<>(messages.subList(cutoff, messages.size()));

// 第 2/3 步：记忆冲刷（best-effort）+ 原始消息卸载 JSONL（失败降级为无文件引用）
// 第 4 步：LLM 汇总（summaryInput 包含既往摘要 ⇒ 滚动摘要）
return flushStep.then(offloadStep).flatMap(offloadPath ->
        summarizePrefix(summaryInput, config).map(summary -> {
            Msg summaryMsg = buildSummaryMessage(summary, filePath);
            List<Msg> compacted = new ArrayList<>();
            compacted.add(summaryMsg);
            compacted.addAll(tail);          // 结果 = [摘要] + 保留尾部
            ...
        }));
ConversationCompactor.java L92–205（结构摘录，注释为原文）

关键参数（CompactionConfig Builder 默认值）：triggerMessages = 50、keepMessages = 20；模型未上报上下文窗口时启用 token 回退阈值；-1 表示动态尾部保留模式。设计上有两处明显意图：

  • 成本分级——参数截断与工具结果修剪不需要 LLM，先执行；只有确实超过阈值才进入摘要调用；
  • 优雅降级——记忆冲刷失败仅记 warn（best-effort），消息卸载失败退化为无文件引用的普通摘要，cutoff 为 0 则整体跳过。压缩是增益路径而非正确性依赖。

配套的 ToolResultEvictionMiddleware 处理单条超大结果：默认超过 80_000 字符即写盘到 large_tool_results/，原位置保留 2_000 字符预览（ToolResultEvictionConfig L46–52），并维护默认排除工具集。

5.3 文件系统抽象：一张接口承载全部 I/O

AbstractFilesystem 是 harness 的底座接口。工作区、会话记录、消息总线、异步工具注册表、技能缓存、任务存储——全部经由它存取：

public interface AbstractFilesystem {
    LsResult        ls(RuntimeContext runtimeContext, String path);
    ReadResult      read(RuntimeContext runtimeContext, String filePath, int offset, int limit);
    WriteResult     write(RuntimeContext runtimeContext, String filePath, String content);
    EditResult      edit(...);
    GrepResult      grep(RuntimeContext runtimeContext, String pattern, String path, String glob);
    GlobResult      glob(RuntimeContext runtimeContext, String pattern, String path);
    List<FileUploadResponse>   uploadFiles(...);
    List<FileDownloadResponse> downloadFiles(RuntimeContext runtimeContext, List<String> paths);
    WriteResult     delete(RuntimeContext runtimeContext, String path);
    WriteResult     move(RuntimeContext runtimeContext, String fromPath, String toPath);
    boolean         exists(RuntimeContext runtimeContext, String path);
    static void     validatePath(String path) { ... }
}
AbstractFilesystem.java L53–178（签名摘录）

三个实现分支对应三种部署形态：本地 LocalFilesystem（及其带 shell 的 LocalFilesystemWithShell overlay 变体）、沙箱 BaseSandboxFilesystem 系（Docker 等）、远端 RemoteFilesystem（对象存储-backed）与组合式 CompositeFilesystem（按路径前缀路由）。接口方法全部以 RuntimeContext 为首参——身份与租户信息随每次 I/O 流动，而不是在文件系统对象里保存当前用户。这是多租户正确性的关键取舍。

部署形态由三种 Spec 声明（SandboxFilesystemSpec / RemoteFilesystemSpec / LocalFilesystemSpec，互斥），也可以直接传入 AbstractFilesystem 实例作为逃生舱。builder 负责把 Spec 翻译成运行时组件（图 2 第 04 步）。

5.4 沙箱：生命周期中间件 + 快照恢复 + 执行守护

沙箱子系统由四个协作件组成：SandboxManager（容器管理，含 Docker 实现 DockerSandbox，775 行）、SessionSandboxStateStore（跨调用快照与恢复）、SandboxExecutionGuard（执行前守护，默认 no-op，可插拔策略）以及注册在栈首的 SandboxLifecycleMiddleware。技能市场的数据库技能由 MarketplaceStager 预物化到工作区 .skills-cache，物化动作通过 sandboxLifecycleMw.setBeforeStartCallback(...) 在沙箱启动前执行。

一个安全上的默认值得强调：ShellExecuteTool 只在文件系统为 AbstractSandboxFilesystem 时注册。也就是说，默认本地文件系统下模型没有 shell 工具；要给模型 shell 能力，必须显式声明沙箱。默认面收窄，危险面才可控。

5.5 子代理编排：同步/后台语义与"不静默升级"

AgentSpawnTool（1795 行）实现 spawn 工具。其超时语义在 Javadoc 中写得很明确：

If the sync wait exceeds the timeout, the subagent is interrupted and the tool returns status: timeout — it is not promoted to an async background task.

— AgentSpawnTool.java L169–171
  • timeout_seconds = 0 ⇒ 纯后台模式；
  • 同步等待超时 ⇒ 子代理被中断、返回 timeout 状态，不升级为后台任务——禁止在调用方无感知的情况下改变执行模式；
  • 调用方可通过 RuntimeContext 覆盖：CTX_FORCE_SYNC = "agentscope.subagent.force_sync" 与 CTX_FORCE_SYNC_TIMEOUT_SECONDS（L185–204）；
  • 后台任务用 wait_async_results(task_ids=...) 或 wait_all=true 统一等待。

结构上，每个子代理拥有独立会话，条目通过 id/parentId 构成会话树（SessionTree）。另有一个克制的设计：被 spawn 出的叶子代理不再安装 SubagentsMiddleware（build() 条件 !leafSubagent，L2646），即子代理默认不能再 spawn 子代理，递归扩散被构造期关断。

5.6 技能体系与自学习：默认拒绝晋升的人工闸门

技能以 SKILL.md（YAML frontmatter + 指令正文，可选 references/ 与 scripts/）为单位，仓库支持四层叠加：ClasspathSkillRepository、GitSkillRepository、NacosSkillRepository、MysqlSkillRepository，经 composeSkillRepositories 合成统一视图。运行期由 HarnessSkillMiddleware 加载（frozen 或 dynamic 两种模式）。

自学习回路由四个组件构成：SkillUsageStore（使用记录）→ SkillAuditLog（审计）→ SkillCurator（后台策展，PeriodicGate 节流，runCuratorOnce() 可手动触发）→ SkillPromoter（把 propose_skill 产生的草案晋升为正式技能）。其中晋升闸门默认是 RejectAllGate——新技能默认不会被自动晋升，必须显式配置晋升策略或人工审批。模型可以提议，但不能自证合格；这个默认值体现了对"模型自主修改自身能力面"的谨慎。

外围还有两组能力：计划模式（PlanModeManager + plan_enter/plan_write/plan_exit 三工具，PlanModeMiddleware 用 isReadOnly() 收紧工具白名单，allowShellInPlanMode 可为沙箱加例外）与通道路由（channel(T) 注册、gateway() 懒建并复用 volatile 内部网关，DistributedStore 支撑跨节点 SubagentRegistry 恢复）。

对 Java 工程师而言，这套代码的迁移价值不止于 agent 领域本身：

  1. 钩子协议优先于特性开关——扩展点固定且语义单一，新能力以新实现加入，而不是在主流程上增加分支；
  2. 文件系统作通用底座——把状态、消息、任务全部收敛到一张 I/O 接口上，本地/沙箱/远端三态切换便只剩装配差异；
  3. 构造期失败优于运行期异常——互斥校验与一致性红线都在 build() 完成；
  4. 禁止静默模式切换——同步超时就返回超时，绝不悄悄变成后台任务；
  5. 有损与无损分离——上下文可以压缩（有损），审计日志永不压缩（无损）；
  6. 高危自动化默认关闭——模型可以提议新技能，但晋升默认被全部拒绝。
