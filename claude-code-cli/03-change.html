第 3 章

改代码的完整闭环

让 Claude 改代码不难，难的是改完能证明它是对的。这一章用一条完整的链路：先计划，再改，再验证。

场景

订单系统有一个金额 bug：优惠券叠加满减时，应付金额比预期少 10 元。你能稳定复现，但不确定计算顺序应该改哪一层。改动会涉及公共方法，不能让它顺手重构整个模块。

3.1 先开分支

无论 Claude 多可靠，改动前先隔离：

bash
git switch -c fix/coupon-stacking
git status

工作区有未提交的改动时，先提交或 stash。否则 /rewind 和 git diff 都会混在一起，很难判断哪些是 Claude 改的。

3.2 用计划模式开始

计划模式下，Claude 可以读文件、跑只读命令，但不能改源码。两种进入方式：

bash
claude --permission-mode plan

或者进入会话后按 Shift+Tab 循环权限模式，切到 plan。模式会显示在输入框附近。

3.3 把需求写成四段

不要只说「修一下优惠券 bug」。给它现象、复现、边界、验收：

Claude Code 会话（plan 模式）
> 现象：订单同时使用满减和优惠券时，应付金额少 10 元。
> 复现：订单 300 元，满 300 减 50，优惠券 9 折，期望 225，实际 215。
> 范围：只改 packages/domain/coupon 和调用它的金额计算，不要重构其他模块，不要改数据库结构。
> 验收：补一个覆盖「满减 + 折扣券叠加」的单测；`pnpm test -- --run coupon` 通过；给出修改前后的计算顺序对比。
> 先给方案，不要改代码。

这段提示做了四件事：给出可复现输入、限定修改范围、定义验收标准、明确当前只要方案。

3.4 审计划

计划通常包含：涉及的文件、修改点、测试方案、风险。逐条检查：

  • 文件列表是否只覆盖该覆盖的地方？出现无关模块就要求删掉。
  • 是否说明了计算顺序？金额问题多数错在顺序，而不是公式。
  • 测试是否包含边界：无券、单券、叠加、退款？
  • 有没有「顺便重命名」「顺便升级依赖」这类范围外动作？

计划不对就继续讨论，不要急着批准。计划模式下的来回修改不产生代码 diff，成本最低。

3.5 批准并切到可编辑模式

计划确认后，Claude 会请求退出计划模式。选择接受后，按 Shift+Tab 切到 acceptEdits，文件编辑不再逐次询问，但执行命令仍会请求确认。

模式行为适合
default / manual每个工具首次使用时询问第一次在某仓库工作
plan只读探索，不改源码需求不清楚、改动范围大
acceptEdits自动接受工作目录内的文件编辑计划已确认，进入执行
auto常规操作不询问，由分类器判断风险信任度较高的日常开发
bypassPermissions跳过权限提示只在容器或虚拟机里用
不要默认开 bypassPermissions

它会跳过包括 .git、.claude 在内的写入提示。这个模式适合一次性、可丢弃的环境，不适合你的主工作区。

3.6 让它自己验证

改完后，把验证动作写进同一轮对话，而不是自己再猜：

Claude Code 会话
> 运行 `pnpm test -- --run coupon`，失败就继续修，直到通过。
> 然后运行 `pnpm typecheck`，把结果贴出来。

测试通过后，再让它解释改动：

Claude Code 会话
> 用三句话说明：改了什么、为什么这样改、哪些场景没有覆盖

最后一句很关键。它主动说出的未覆盖场景，往往就是你上线后遇到的第一个问题。

3.7 自己看 diff

bash
git diff
git diff --stat

重点看三处：公共方法的签名有没有变、错误处理有没有被吞掉、测试是不是只改了断言而没有真正覆盖新逻辑。

3.8 改坏了怎么退

Claude Code 每次你发起一轮对话时都会记录检查点。改坏了有两个选择：

  • /rewind，或连按两次 Esc：选择恢复到某一轮之前的代码与对话；
  • git checkout -- <file>：只丢弃某个文件，前提是你之前已经提交过。

检查点只跟踪 Claude 通过编辑工具改过的文件。只用 Bash 命令改的文件不在其中，这类改动仍然要靠 Git。

3.9 提交

Claude Code 会话
> 根据 diff 写一条提交信息，说明根因和修复方式，不要写「fix bug」

提交信息让它生成，提交动作你自己执行，或者明确批准它执行 git commit。

3.10 验收

  • 计划阶段就限定了文件范围，diff 里没有无关改动
  • 新增测试能在修复前失败、修复后通过
  • pnpm test 与 pnpm typecheck 都通过
  • 能用自己的话解释根因，而不是只复述 diff

3.11 常见坑

坑后果改法
需求只写「修一下」它按自己的理解大改给现象、复现、范围、验收
跳过计划直接改方案错了，diff 已经很大复杂改动先 plan
只看「测试通过」测试可能被改弱检查测试是否覆盖新逻辑，是否删了断言
在工作区有未提交改动时开工回滚和 diff 混在一起先提交或 stash，再开分支
