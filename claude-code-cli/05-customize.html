第 5 章

命令、技能与子代理

同一段流程解释到第三遍，就该把它写下来。这一章把「你重复说的话」变成命令，把「会污染主对话的任务」交给子代理。

场景

每次发版前，你都要重复同一套检查：跑测试、看迁移、确认版本号、生成变更说明。另外，代码审查会让主对话塞满大段 diff，之后的修改开始丢上下文。

5.1 技能就是带说明的命令

在项目里新建一个目录和文件：

bash
mkdir -p .claude/skills/release-check
.claude/skills/release-check/SKILL.md
---
name: release-check
description: 发版前检查。用于准备发布、生成变更说明、确认版本号与迁移状态时。
---

# 发版前检查

按顺序执行，任何一步失败就停下来报告，不要继续后面的步骤。

1. 运行 `pnpm test -- --run`，记录失败用例。
2. 运行 `pnpm typecheck`。
3. 检查 `packages/db/migrations/` 是否有未提交的新迁移。
4. 对比 `package.json` 的版本号与最新 Git tag，确认是否已递增。
5. 汇总最近一次 tag 到 HEAD 的提交，按 feat / fix / chore 分类生成变更说明。
6. 输出一份检查结果表：项目、结果、证据（命令输出或文件路径）。

保存后，Claude Code 会自动发现这个技能。两种调用方式：

Claude Code 会话
> /release-check

或者直接说「准备发版，帮我检查一下」，它根据 description 判断是否加载。

SKILL.md 的两个部分

description 决定「什么时候用」，正文决定「怎么做」。描述里写清楚触发场景，正文写可执行的步骤和验收标准。名字会成为命令名。

5.2 老格式：.claude/commands

已有 .claude/commands/deploy.md 的项目不需要迁移，它仍然生成 /deploy。新写的流程建议放 .claude/skills/，因为技能支持附带脚本、模板等辅助文件。

位置作用范围适合
.claude/skills/<name>/SKILL.md当前仓库，随代码共享团队流程、发版检查、项目规范
~/.claude/skills/<name>/SKILL.md你的所有项目个人习惯，例如提交信息风格
.claude/commands/<name>.md当前仓库旧格式，简单一次性命令

5.3 子代理：独立上下文干一件事

子代理有自己的上下文窗口，只把结论带回主对话。适合「读很多文件、只回一个结论」的任务，例如代码审查、日志排查、依赖升级评估。

.claude/agents/reviewer.md
---
name: reviewer
description: 审查当前分支相对 main 的改动，只报告真实缺陷。用于提交前检查、PR 自查。
tools: Read, Grep, Glob, Bash
model: sonnet
---

你是代码审查者。只审查 `git diff main...HEAD` 的改动。

关注顺序：
1. 逻辑错误与边界条件
2. 安全与权限问题
3. 数据一致性与事务边界
4. 缺失或变弱的测试

不报告纯风格问题。每条发现给出文件路径、行号、复现条件、建议修改。
超过 10 条时，按严重程度排序，只保留前 10 条。

使用时不需要记名字，直接描述任务：

Claude Code 会话
> 用 reviewer 子代理审查当前分支，重点看金额计算和权限判断

5.4 技能和子代理怎么选

技能（Skill）子代理（Subagent）
上下文在主对话里执行独立上下文，只回摘要
适合流程、规范、检查清单大量阅读、独立调查、并行任务
调用/name 或自动匹配描述任务，主代理委派
典型例子发版检查、提交信息规范代码审查、日志分析、迁移评估

5.5 验证

Claude Code 会话
> /skills
> 列出当前可用的子代理

再实际跑一次 /release-check，看它是否按顺序执行、失败时是否停下、最后是否输出了结果表。技能写得对不对，跑一次就知道。

5.6 常见坑

坑后果改法
技能名和内置命令重名技能不加载，或命令被覆盖用项目特有的前缀，例如 acme-release
description 写成功能介绍该用的时候不触发写「用于……时」的触发条件
子代理给太多工具审查者也能改代码，风险变大只给 Read, Grep, Glob 等必要工具
把临时任务写成技能技能目录越来越乱只固化重复三次以上的流程
