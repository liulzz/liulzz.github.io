第 2 章：架构与核心概念

2.1 三个角色：Host、Client、Server

MCP 定义了三个角色，每个角色有明确的职责边界：

角色职责典型实例
Host 面向最终用户的应用程序。它持有 LLM 上下文，决定何时调用工具，以及如何把工具结果反馈给模型。 Claude Desktop、Cursor、自定义 AI 应用
Client Host 内部的 MCP 协议实现模块。每个 Client 对应一个 Server 连接，负责完成握手、发送请求、接收响应。一个 Host 可以同时持有多个 Client 实例。 Host 内置的 MCP Client 库
Server 独立进程，暴露 Tools、Resources、Prompts 等能力。Server 不知道 Host 是什么，只通过 MCP 协议与 Client 通信。 文件系统 Server、SQLite Server、GitHub Server

三者的关系用文字描述：Host 通过内部的 Client 组件与外部的 Server 建立会话；一个 Host 可以同时维护多个 Server 连接，每个连接是一个独立的 Client-Server 对。

┌─────────────────────────────────────┐
│  Host（AI 应用）                     │
│  ┌──────────┐    ┌──────────┐        │
│  │ Client A │    │ Client B │  ...   │
│  └────┬─────┘    └────┬─────┘        │
└───────│───────────────│──────────────┘
        │ MCP协议        │ MCP协议
        ▼                ▼
  ┌──────────┐    ┌──────────┐
  │ Server A │    │ Server B │
  │ 文件系统  │    │ SQLite   │
  └──────────┘    └──────────┘

2.2 JSON-RPC 2.0 基础

MCP 的所有消息都使用 JSON-RPC 2.0 格式编码。JSON-RPC 是一个轻量级的远程过程调用协议，只有三种消息类型。

请求（Request）

Client 向 Server 发起调用，带有唯一的 id：

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "read_file",
    "arguments": { "path": "/tmp/data.txt" }
  }
}

响应（Response）

Server 返回结果，id 与请求匹配：

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [{ "type": "text", "text": "hello world" }],
    "isError": false
  }
}

通知（Notification）

通知没有 id，不需要响应，用于进度更新、日志、资源变更推送等单向消息：

{
  "jsonrpc": "2.0",
  "method": "notifications/progress",
  "params": {
    "progressToken": "abc",
    "progress": 50,
    "total": 100
  }
}
关于错误响应

当 Server 无法处理请求时，返回的是错误响应而不是正常响应：

{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32602,
    "message": "Invalid params",
    "data": { "detail": "path is required" }
  }
}

标准错误码：-32700 解析错误，-32600 无效请求，-32601 方法不存在，-32602 参数无效，-32603 内部错误。

2.3 三大原语

MCP Server 可以向 Client 暴露三类能力，称为「原语」（Primitives）：

原语控制方语义典型场景
Tools模型决定何时调用可执行的动作，有副作用查询数据库、发送邮件、执行命令
ResourcesHost / 用户决定加载只读数据，用于扩充上下文文件内容、数据库视图、实时日志
Prompts用户触发预设的提示模板工作流代码审查流程、报告生成模板

三者的关键区别在于「谁来决定使用它」：Tools 由模型根据对话上下文自主决定调用；Resources 由 Host 应用程序（或用户）主动拉取后注入上下文；Prompts 由用户在界面上显式选择触发。

2.4 能力协商

MCP 连接建立时，Client 和 Server 通过 initialize 握手交换各自支持的能力集合。因此，一个 Server 不需要实现所有原语，也不需要支持所有可选特性。

Client 在 initialize 请求中声明自己支持的特性：

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-03-26",
    "clientInfo": { "name": "MyApp", "version": "1.0.0" },
    "capabilities": {
      "roots": { "listChanged": true },
      "sampling": {}
    }
  }
}

Server 在响应中声明自己支持的特性：

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-03-26",
    "serverInfo": { "name": "SQLiteServer", "version": "0.3.0" },
    "capabilities": {
      "tools": { "listChanged": true },
      "resources": { "subscribe": true, "listChanged": true },
      "prompts": {}
    }
  }
}

握手完成后，双方都知道对方支持什么，因此不会发送对方无法处理的请求。

2.5 完整消息流示意

以「用户要求模型查询数据库」为例，完整的消息流如下：

用户          Host(AI应用)      Client        Server(SQLite)
 │               │               │                │
 │  "查询订单表"  │               │                │
 │─────────────▶│               │                │
 │              │ 组装上下文+     │                │
 │              │ tools列表给LLM  │                │
 │              │◀─ LLM决定调用   │                │
 │              │   query_db()   │                │
 │              │ tools/call ──▶ │                │
 │              │               │ tools/call ──▶ │
 │              │               │                │ 执行 SQL
 │              │               │ ◀── result ─── │
 │              │ ◀── result ── │                │
 │              │ 结果附加上下文  │                │
 │              │ 再次请求LLM生成 │                │
 │ ◀── 回复 ────│               │                │
