第 8 章：JSON-RPC 与连接生命周期

8.1 initialize 握手时序

连接建立后，双方必须完成三个步骤才能开始正常通信。

Client                                    Server
  │                                          │
  │ ── 1. initialize（含协议版本、能力）──────▶ │
  │                                          │
  │ ◀── 2. initialize 响应（协议版本、能力）── │
  │                                          │
  │ ── 3. notifications/initialized ────────▶ │
  │                                          │
  │ ── 正式通信（tools/list 等）─────────────▶ │

第 1 步，Client 发送 initialize：

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-03-26",
    "clientInfo": { "name": "ClaudeDesktop", "version": "1.0.0" },
    "capabilities": {
      "roots": { "listChanged": true },
      "sampling": {},
      "elicitation": {}
    }
  }
}

第 2 步，Server 响应，同时声明自己的能力和协议版本。如果 Server 不支持 Client 请求的协议版本，应在响应中返回自己支持的版本，由 Client 决定是否继续。

第 3 步，Client 发送 notifications/initialized 通知。这条通知告诉 Server：握手已完成，可以开始处理正常请求。

⚠ 常见错误

在收到 notifications/initialized 之前，Server 不应接受 tools/call 等业务请求。部分自定义 Server 会因为忽略这个约定而在某些 Client 上报错。

8.2 核心方法一览

方法方向说明
initializeClient → Server握手，交换能力
notifications/initializedClient → Server握手完成通知
tools/listClient → Server列出所有 Tool
tools/callClient → Server调用指定 Tool
resources/listClient → Server列出静态资源
resources/templates/listClient → Server列出 URI 模板
resources/readClient → Server读取资源内容
resources/subscribeClient → Server订阅资源变更
prompts/listClient → Server列出所有 Prompt
prompts/getClient → Server获取渲染后的 Prompt
sampling/createMessageServer → ClientServer 反向请求 LLM 补全
roots/listServer → ClientServer 询问可访问的根目录
notifications/progress双向进度通知
notifications/cancelled双向取消通知
ping双向保活探测

8.3 进度通知

对于耗时操作，请求方可以在 params._meta.progressToken 中传入一个令牌。接收方在处理过程中通过 notifications/progress 上报进度，令牌用于匹配是哪一个请求的进度。

// 请求中携带 progressToken
{ "jsonrpc": "2.0", "id": 10, "method": "tools/call",
  "params": {
    "name": "process_files",
    "arguments": { "count": 100 },
    "_meta": { "progressToken": "task-001" }
  } }

// Server 上报进度
{ "jsonrpc": "2.0", "method": "notifications/progress",
  "params": { "progressToken": "task-001", "progress": 50, "total": 100 } }

8.4 取消机制

任何一方都可以取消正在处理的请求，方式是发送 notifications/cancelled，携带原请求的 requestId 和可选原因。

{ "jsonrpc": "2.0", "method": "notifications/cancelled",
  "params": { "requestId": 10, "reason": "用户取消了操作" } }
取消是尽力而为的

接收方收到取消通知后，应立即停止处理并返回 -32800（请求已取消）错误。但是，如果操作已经执行完毕或不可中断，接收方也可以正常返回结果。因此，发送方不应假设取消一定生效。

8.6 保活与关闭

ping 方法用于探测对端是否存活。任何一方都可以发送 ping，对方只需返回空结果。

// 请求
{ "jsonrpc": "2.0", "id": 99, "method": "ping" }
// 响应
{ "jsonrpc": "2.0", "id": 99, "result": {} }

关闭连接时，标准的做法是关闭底层传输通道：stdio 模式下关闭子进程，HTTP 模式下删除会话（发送带 Mcp-Session-Id 的 DELETE 请求）。

✓ 本章小结

MCP 连接的生命周期分握手、通信、关闭三个阶段。握手通过 initialize + notifications/initialized 完成能力协商。通信阶段使用 JSON-RPC 2.0 的请求/响应/通知三种消息，并支持进度上报与取消。下一章介绍 Sampling、Elicitation、Roots 等进阶特性。
