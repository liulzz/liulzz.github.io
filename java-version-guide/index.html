先建立整体认知

Java 8 之后的升级，并不只是语法糖增加，更重要的是并发、运行时、封装与交付方式的演进。

01 / LANGUAGE

代码表达更简洁

var、文本块、records、sealed classes、模式匹配，以及更轻量的源文件启动方式，逐步减少样板代码。

02 / CONCURRENCY

并发模型升级

JDK 21 的虚拟线程是关键节点；Structured Concurrency、Scoped Values 等方向持续演进，但仍需关注预览状态。

03 / JVM & GC

性能与启动优化

G1、ZGC、分代 ZGC、紧凑对象头、AOT 缓存和类加载优化，面向吞吐、延迟、启动速度与内存占用。

04 / SECURITY

封装与安全边界更严格

JDK 内部 API 强封装、Security Manager 退场、动态加载 Agent 告警等变化，可能影响老项目和诊断工具。

重点版本怎么理解？

以企业后端开发的视角，快速把特性与真实收益对应起来。

Java 8 → 11

现代 Java 的第一步

  • HTTP Client、TLS 1.3、JFR 等能力补齐。
  • 新增 var（JDK 10），代码表达更简洁。
  • 需要处理模块化之后的 JDK 内部 API、Java EE / CORBA 模块变更。
  • 适合作为老系统现代化的初始评估目标，但必须确认应用框架和依赖支持。

Java 17 → 21

并发与语言模型的显著升级

  • records、sealed classes、instanceof / switch 模式匹配让领域模型和分支处理更清晰。
  • JDK 21 虚拟线程正式可用，适合大量阻塞式 I/O 请求，但不代表 CPU 密集型任务会自动变快。
  • Sequenced Collections 补齐有序集合接口；分代 ZGC 改善低延迟场景。
  • 迁移时重点验证反射、Agent、序列化、TLS 和容器资源配置。

Java 21 → 25

面向后续维护的 LTS 升级

  • Java 25 是最新 LTS，新增更轻量的源文件 / main 方法入口、模块导入声明等最终特性。
  • 紧凑对象头、AOT 缓存与启动优化值得在高内存密度、冷启动场景压测。
  • 部分结构化并发、惰性常量、密码 API 等仍是 Preview，不宜直接当稳定接口设计。
  • 建立“编译—测试—灰度—观测—回滚”升级闭环，避免只做 JDK 替换。

从 Java 8 升级的排查清单

版本升级往往卡在兼容性与运行参数，而不是新语法本身。

1. 盘点依赖与框架

核实 Spring / Spring Boot、ORM、JSON、日志、APM、数据库驱动、构建插件与代码生成器的目标 JDK 支持范围；先升级依赖，再切换运行时通常更容易定位问题。

2. 检查 JDK 内部 API 与反射

Java 9 起模块化和后续强封装逐步收紧。检查对 sun.*、com.sun.*、深反射和旧版字节码工具的依赖；不要把 --add-opens 当永久方案。

3. 核查已删除或变化的组件

重点检查 Java EE / CORBA 模块、Nashorn、Pack200、Applet API、旧 GC 参数和废弃启动参数；同时确认默认字符集、TLS、安全算法与证书链行为。

4. 按实际负载做性能验证

记录升级前后的启动耗时、吞吐、P95 / P99 延迟、堆与 RSS、GC pause、线程数和容器 CPU / 内存。虚拟线程、ZGC、AOT 等收益必须基于业务负载测量。

5. 处理 Agent 与诊断工具

核实 Arthas、APM Agent、覆盖率和字节码增强工具；JDK 21 起动态加载 Agent 会有告警趋势，后续版本可能继续收紧。优先评估启动时加载和工具版本升级。

6. 明确 Preview / Incubator 边界

预览功能需要显式启用，后续版本可能调整或移除。生产公共 API、持久化格式和跨服务协议尽量不要依赖预览特性，除非团队能承担迁移成本。

建议策略：先选定受支持的目标 LTS（例如 21 或 25），再按官方迁移指南逐步验证；如果从 Java 8 跨多个大版本升级，最好先在中间版本做依赖扫描与兼容性定位，不必把每个非 LTS 版本都作为生产中转站。
