4.1 本章场景：多用户待办助理

🎬场景任务

假设你要把第 2 章的助理升级为团队服务：alice 与 bob 同时使用同一个服务实例，各自维护独立的待办对话；服务重启后对话不丢失；用户关闭页面时，正在生成的回答要能够被安全中止。因此，本章要讲清四件事：ReActAgent 的完整接口、AgentState 持久化、多用户多会话并发、中断（interrupt）。

4.2 理论：推理-行动循环与无状态实例

ReActAgent（接口 io.agentscope.core.agent.Agent）是框架的核心抽象：一个推理-行动循环引擎。每次调用时，它反复执行“模型推理 → 发起工具调用 → 获得工具结果 → 继续推理”，直到给出最终回答，或者因权限确认、外部执行而暂停。

有一个设计要点必须先建立认知：Agent 实例本身对会话无状态。同一个实例可以同时服务所有用户；每次调用通过 RuntimeContext 携带的 (userId, sessionId) 定位该次调用使用哪份对话状态。因此，生产环境中应当把 Agent 做成单例，而不是每个请求新建实例。

4.3 核心接口

方法说明
call(List<Msg>) / call(List<Msg>, RuntimeContext)运行推理-行动循环，返回 Mono<Msg>；内部消费全部事件，在完成或暂停时返回最终消息
streamEvents(List<Msg>) / streamEvents(Msg)同样驱动循环，但是逐一产出 AgentEvent，适合构建实时界面
observe(Msg) / observe(List<Msg>)把消息写入上下文但不触发推理；适用于一个智能体观察另一个智能体输出的场景
interrupt(...)中止指定会话正在进行的调用（见 4.6）
getAgentState(userId, sessionId)读取指定会话的状态快照
call(msgs, Xxx.class, ctx)结构化输出重载（第 3 章已实践）

4.4 实践：多用户与状态持久化

配置 stateStore 后，每次调用结束时 AgentState（对话上下文、压缩摘要、权限规则、工具状态）自动写回存储；下次以相同 (userId, sessionId) 调用时自动恢复：

单实例服务多用户import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.state.JsonFileAgentStateStore;
import java.nio.file.Paths;
import java.util.List;

// 应用启动时创建一个实例（单例）
ReActAgent agent = ReActAgent.builder()
        .name("todo-assistant")
        .sysPrompt("你是团队待办助理，帮助用户记录与整理待办事项。")
        .model("dashscope:qwen-plus")
        .stateStore(new JsonFileAgentStateStore(
                Paths.get(System.getProperty("user.home"), ".agentscope/sessions")))
        .build();

// HTTP handler 中：不同请求携带不同身份，状态完全隔离
agent.call(List.of(new UserMessage("user", "我今天要提交周报")),
        RuntimeContext.builder().userId("alice").sessionId("session-1").build()).block();

agent.call(List.of(new UserMessage("user", "Hello")),
        RuntimeContext.builder().userId("bob").sessionId("session-2").build()).block();

内置的状态存储实现有四种，按部署形态选择：

实现模块适用
InMemoryAgentStateStoreagentscope-core单元测试、单进程演示
JsonFileAgentStateStoreagentscope-core单机开发，按 (userId, sessionId) 分目录存 JSON
RedisAgentStateStoreagentscope-extensions-redis多副本生产，跨进程跨机器共享
MysqlAgentStateStoreagentscope-extensions-mysql需要审计与报表的关系型库场景

并发行为也要记住：同一 (userId, sessionId) 的调用按到达顺序串行执行，第二个请求等待第一个完成，因此不会出现并发写坏同一份状态的问题；但是不同 session 之间完全并行。

4.5 实践：RuntimeContext 的三层槽位

RuntimeContext（io.agentscope.core.agent.RuntimeContext）是“每次调用”的元数据容器，分三层：

构造并传入RuntimeContext ctx =
        RuntimeContext.builder()
                .userId("alice")                            // 可选；null 表示匿名
                .sessionId("session-001")                   // 选择状态槽位
                .put("request_id", "req-abc-123")           // 字符串属性层
                .put(UserContext.class, new UserContext("alice", "zh"))  // 类型化属性层
                .build();

Msg result = agent.call(List.of(new UserMessage("user", "Hi.")), ctx).block();

三层槽位的可见范围不同：

  • 会话字段：驱动状态持久化的寻址；
  • 字符串属性：通常用于内部协调，例如中间件之间传递值；
  • 类型化属性：为工具准备——@Tool 方法里声明同类型参数，框架会自动注入（第 5 章实践）。

注意区分：RuntimeContext 不持久化，它承载“本次调用”的瞬态数据（租户、请求 ID、数据库连接等）；AgentState 才是可恢复状态。不传 context 时框架使用 RuntimeContext.empty()，并回退到 builder 上的 defaultSessionId。

4.6 实践：中断执行

用户关闭页面、请求超时、服务优雅停机——这些时刻需要从外部中止一个正在运行的调用。interrupt 按会话生效，不会波及其他会话：

中断指定会话// 构造标识目标会话的 RuntimeContext
RuntimeContext target = RuntimeContext.builder()
        .userId("alice")
        .sessionId("session-001")
        .build();

// 方式一：直接中断
agent.interrupt(target);

// 方式二：带消息中断——中断消息会被模型在恢复时看到
agent.interrupt(target, new UserMessage("user", "用户已取消操作"));

// 也可以直接用字符串：
agent.interrupt("alice", "session-001");

中断后的行为：当前推理或工具执行在下一个检查点（推理开始、行动开始、流式输出每个分片）被拦截；调用方得到一个带 GenerateReason.INTERRUPTED 标记的 Msg；AgentState 自动保存，因此下次调用会从中断点恢复。

4.7 更多 builder 能力

ReActAgent 的 builder 还有几组常用参数，此处先混个面熟，后续章节各自展开：

参数说明
maxIters / reactConfig主循环最大迭代次数（默认 10）与拒绝处理方式
maxRetries / fallbackModel / failoverListener模型容错：失败重试次数、备用模型、切换监听器
permissionContext工具执行权限规则（第 6 章）
middlewares中间件列表（第 7 章）
enableMetaTool(true)注册 list_tools / activate_group 元工具，让模型自主发现并切换工具组
enableTaskList()注册任务列表工具，让模型把复杂任务拆解为步骤并逐步完成

4.8 本章小结

ReActAgent 是无状态的单例引擎，状态保存在 AgentState 中并由 AgentStateStore 持久化；RuntimeContext 决定每次调用使用哪个状态槽位，并且携带瞬态元数据。此时你已经能构建可靠的多用户服务了，但是智能体还只能“说”不能“做”——下一章引入工具。
