12.1 本章场景：能动手的编码智能体

🎬场景任务

产品终于要给智能体“配电脑”了：它要在代码仓库里查缺陷、改文件、执行测试。但是问题随之而来——智能体在你身边执行任意 shell 命令，等于把生产密钥和数据库交给一个“不确定会不会失误的实习生”。因此，本章解决两件事：文件系统放哪里（本机 / 共享存储 / 远端沙箱），命令在哪里执行（隔离与守护）。

12.2 理论：文件系统的三种部署模式

AgentScope 把智能体的文件操作抽象为文件系统接口，官方给出三种模式，由轻到重：

模式适用场景特点
本机 + shell本地开发、单机部署直接读写本地目录，命令在本机执行，配置最简单
共享存储多副本部署、需要持久化文件 API 指向 NFS / 对象存储等远端，多个实例看到同一份文件
沙箱不可信代码执行、多租户 SaaS文件与命令都在隔离环境中，宿主机零暴露

无论哪种模式，智能体的 Workspace 逻辑路径保持不变，因此业务代码不需要修改——改变的只是底层实现。

12.3 实践：沙箱执行环境

当智能体需要执行不可信代码（例如“帮我运行这段用户上传的脚本”），必须使用沙箱。文件系统通过构建器上的 .filesystem(...) 配置，后端按基础设施选择：自托管环境用 DockerFilesystemSpec（单机容器，开发首选）或 KubernetesFilesystemSpec（集群化生产）；托管环境可选 Daytona、E2B 或阿里云 AgentRun，框架将它们与 Docker / K8s 后端等价对待。以 Docker 为例：

Docker 沙箱配置HarnessAgent agent = HarnessAgent.builder()
    .name("code-agent")
    .model(model)
    .workspace(workspace)
    .filesystem(new DockerFilesystemSpec()
        .image("ubuntu:24.04")                       // 沙箱镜像
        .isolationScope(IsolationScope.SESSION))     // 每个会话一个独立沙箱
    .build();

沙箱不只是“换个地方执行”，它还带来两块生产级能力：

  • 快照（Snapshot）：把沙箱内的文件状态保存为快照（本地或 OSS），下次会话恢复现场——就像给虚拟机存档：
OSS 快照.filesystem(new DockerFilesystemSpec()
    .image("ubuntu:24.04")
    .snapshotSpec(new OssSnapshotSpec(ossClient, "my-bucket", "agentscope/")))
  • 执行守护（Execution Guard）：对命令做前置校验与拦截（框架提供 RedisSandboxExecutionGuard、JdbcSandboxExecutionGuard 等实现），配合第 6 章的权限系统形成双重防线。

一个容易忽略的对齐细节：沙箱挂载路径必须与工作区一致。例如 K8s 部署时，把卷挂载到 /workspace，那么 workspaceRoot 与 fileApiBaseDir 也要指向同一位置，否则文件 API 与 shell 看到的内容会不一致。

12.4 内置文件与 shell 工具

框架内置一组文件操作工具（读文件、写文件、搜索文件、执行 shell），注册后模型即可操作文件系统。它们与沙箱天然配合：工具发出的调用会被路由到沙箱内执行。因此，实现本章场景只需要三步：

  1. 选择沙箱后端并配置（开发阶段用 Docker 即可）；
  2. 把内置文件工具注册进 Toolkit；
  3. 为高危命令配置权限规则（第 6 章），例如“禁止 rm -rf /”。
✍️动手练习 12
  1. 用 DockerFilesystemSpec 构建一个能执行 Python 的编码智能体，让它写一段脚本并运行，观察文件都落在沙箱内部；
  2. 尝试让智能体执行 curl 外网地址，验证执行守护或权限规则能否拦截；
  3. 制作一个快照，重启沙箱后恢复，验证“上次修改的文件还在”。

12.5 本章小结

文件系统决定“智能体的手放在哪里”，沙箱决定“这双手能不能闯祸”。三种文件模式 + 多种沙箱后端 + 快照与守护，构成完整的执行安全体系。下一章我们把智能体真正搬到用户面前——Channel 与 Gateway。
