第 9 章记忆与上下文压缩

9.1 本章场景：长期项目助理

🎬场景任务

一个项目助理要服务整个项目周期（以月计）：它要记住“项目代号、关键干系人、已定决策”，而不是每次会话结束就失忆；同时，随着对话越来越长，模型上下文不能无限膨胀，否则又慢又贵。因此本章解决两个互补的问题：长期记忆（Memory）负责跨会话积累，上下文压缩（Compaction）负责单会话瘦身。

9.2 理论：记忆系统的三层结构

HarnessAgent 的记忆分布在三处，各司其职：

位置内容写入者
memory/YYYY-MM-DD.md每日事实流水账智能体在对话结束后自动抽取（flush）
MEMORY.md整理后的长期事实（策划层）后台整合任务把流水账合并进此文件
memory_search 等工具运行时按需检索历史会话框架内置记忆工具（可关闭）

与上下文（第 4 章的 AgentState）不同，记忆是面向“值得记住的事实”的：状态回答“我们聊到哪了”，记忆回答“这个用户是谁、项目有什么约定”。

9.3 实践：配置记忆写入节奏

记忆 flush 默认在对话结束后触发抽取。节流模式适合高频短对话的生产环境：

MemoryConfigHarnessAgent agent = HarnessAgent.builder()
    .name("project-assistant")
    .model(model)
    .workspace(workspace)
    .memory(MemoryConfig.builder()
        .flushTrigger(MemoryConfig.FlushTrigger.throttled(Duration.ofMinutes(10)))
        .build())
    .build();

// 完全关闭自动写入（例如只读演示环境）：
.memory(MemoryConfig.builder()
    .flushTrigger(MemoryConfig.FlushTrigger.never())
    .build())

9.4 实践：自定义抽取与整合提示词

抽取什么、保留什么，都可以用提示词定制。下面的例子让 flush 过程遵守合规要求：

flush 提示词追加规则.memory(MemoryConfig.builder()
    .flushPrompt(MemoryFlushManager.DEFAULT_FLUSH_PROMPT + """

        Additional project rules:
        - Never record customer PII (names, emails, phone numbers).
        - Always use Chinese for project-internal vocabulary.
        """)
    .build())
整合（consolidation）定制.memory(MemoryConfig.builder()
    .consolidationPrompt("""
        You are merging daily memory ledgers into MEMORY.md.
        Keep within %d tokens (~%d chars). Output the complete file in markdown.
        ... your custom rules ...
        """)
    .consolidationMinGap(Duration.ofHours(2))   // 整合至少间隔 2 小时
    .dailyFileRetentionDays(30)                 // 30 天后归档流水账
    .sessionRetentionDays(60)                   // 60 天后清理 session JSONL
    .consolidationMaxTokens(8_000)              // MEMORY.md 上限放宽到 8K tokens
    .build())

9.5 实践：记忆与压缩的专用小模型

记忆抽取、整合与压缩摘要都是内部任务，不必消耗主力模型。因此常见做法是“主模型管推理，小模型管家务”：

分级模型配置HarnessAgent.builder()
    .model("openai:o3")                    // 主推理模型
    .memory(MemoryConfig.builder()
        .model("openai:gpt-4.1-mini")      // 记忆操作用小模型
        .build())
    .compaction(CompactionConfig.builder()
        .model("openai:gpt-4.1-mini")      // 压缩摘要也用小模型
        .build())
    .build();

9.6 实践：上下文压缩（Compaction）

压缩解决“单次会话过长”的问题：消息条数达到阈值时，框架把较早的对话压缩为摘要，只保留最近若干条原文。原始日志仍完整保存在 sessions/ 中，因此压缩只影响进入模型上下文的内容，不影响审计。

CompactionConfigHarnessAgent agent = HarnessAgent.builder()
    .name("project-assistant")
    .model(model)
    .workspace(workspace)
    .compaction(CompactionConfig.builder()
        .triggerMessages(30)     // 消息条数到 30 触发
        .keepMessages(10)        // 压缩后保留最近 10 条
        .build())
    .build();

工具调用密集的会话还有两个瘦身手段。其一，截断超长工具参数：

参数截断CompactionConfig.builder()
    .triggerMessages(80)
    .truncateArgs(CompactionConfig.TruncateArgsConfig.builder()
        .maxArgLength(2000)
        .truncationText("... [truncated] ...")
        .build())
    .build();

其二，淘汰陈旧工具结果：

工具结果淘汰HarnessAgent.builder()
    ...
    .toolResultEviction(ToolResultEvictionConfig.defaults())
    .build();

9.7 关闭记忆的两种粒度

粒度控制HarnessAgent.builder()
    ...
    .disableMemoryHooks()   // 关掉 flush + 后台维护（并去掉「对话结束自动抽取」引导）
    .disableMemoryTools()   // 不注册 memory_search / memory_get / memory_save / session_search
    .build();
✍️动手练习 9
  1. 与助理进行两段对话（间隔开不同 session），第二段追问第一段提到的事实，验证跨会话记忆；然后打开 memory/ 目录阅读自动生成的流水账；
  2. 把 triggerMessages 调到 8、keepMessages 调到 3，人为制造一次压缩，观察回答质量变化；
  3. 用 9.4 的方式在 flush 提示词中加入“只记录与工作相关的决定”，对比流水账内容差异。

9.8 本章小结

记忆系统是“流水账 → 策划”的双层写入，压缩是“摘要 + 保留窗口”的单层瘦身，两者共用小模型即可显著降本。现在智能体已经能长期服务了；但是复杂任务往往超出单智能体能力圈，因此下一章引入子智能体与计划模式。
