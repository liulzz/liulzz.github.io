第 8 章HarnessAgent 与工作区

8.1 本章场景：团队知识助理

🎬场景任务

平台组要部署一个团队助理：它的“职责说明书”由运维人员以 Markdown 文件维护，而不是硬编码在代码里；每个成员还能拥有自己的个性化配置（例如 alice 偏好中文回答）。因此，本章进入 HarnessAgent 的核心概念——工作区（Workspace），并且理解 Harness 架构为什么这样设计。

8.2 理论：Harness 架构是什么

“Harness”的原意是马具与测试支架，在智能体语境中指围绕模型的一整套长期运行基础设施。ReActAgent 解决“一次调用”，HarnessAgent 则在它外围整合了工作区、记忆、技能、子智能体、计划、沙箱与渠道，构成可持续服务的产品形态。一句话概括分工：

  • ReActAgent：无状态引擎，适合嵌入你自己的应用；
  • HarnessAgent：完整产品底座，自己负责状态、文件与运维约定。

官方文档把 Harness 的能力拆为九个模块，本教程分别在第 8~13 章覆盖：工作区（本章）、记忆与压缩（第 9 章）、子智能体与计划（第 10 章）、技能（第 11 章）、文件系统与沙箱（第 12 章）、渠道（第 13 章）。

8.3 工作区目录布局

工作区是 HarnessAgent 的“家目录”，约定优于配置——目录名固定，框架自动识别：

完整目录结构.agentscope/workspace/
├── AGENTS.md                    # 静态：人格 + 行为约定
├── MEMORY.md                    # 长期记忆：整理后的长期事实
├── tools.json                   # 静态：MCP server + 工具白名单（可选）
├── memory/                      # 长期记忆：每天追加的事实流水账
│   └── YYYY-MM-DD.md
├── knowledge/                   # 静态：领域知识入口 + 任意参考文件
│   ├── KNOWLEDGE.md
│   └── ...
├── skills/                      # 静态：技能目录，每个子目录一份 SKILL.md
│   └── <skill-name>/SKILL.md
├── subagents/                   # 静态：子 agent 声明（文件名即 agent_id）
│   └── <agent-id>.md
├── plans/                       # 运行时：Plan Mode 写下的计划文件
└── agents/<agentId>/            # 运行时：每个 agent 自己的运行时根
    └── sessions/                # 会话索引 + 永不压缩对话日志

8.4 实践：AGENTS.md 人格文件

把第 2 章 sysPrompt 里的长提示词迁移到工作区：AGENTS.md 会在会话开始时全文注入 system prompt，因此它适合放“身份 + 行为约定”这类稳定内容：

.agentscope/workspace/AGENTS.md# 团队助理

你是平台组的内部助理，遵循以下行为约定。

## 行为
- 回答使用中文；术语首次出现时给出英文对照
- 涉及线上变更时，先给出影响面分析再给方案
- 不知道的信息明确说不知道，禁止编造
构建时指向工作区HarnessAgent agent = HarnessAgent.builder()
    .name("MyAgent")
    .model(model)
    .workspace(Paths.get(".agentscope/workspace"))  // 不传则按默认解析顺序
    .build();

8.5 实践：附加上下文与注入预算

除 AGENTS.md 外，还可以声明任意多个附加上下文文件（全文注入），并且通过 maxContextTokens 控制 MEMORY 的注入预算：

多文件注入HarnessAgent agent = HarnessAgent.builder()
    .name("MyAgent")
    .model(model)
    .workspace(Paths.get(".agentscope/workspace"))
    .additionalContextFile("STYLE.md")         // 任意 workspace 相对路径
    .additionalContextFile("PREFS.md")
    .maxContextTokens(8000)                    // MEMORY 注入预算
    .build();

部署到容器时，用环境变量 AGENTSCOPE_WORKSPACE 指定工作区位置，代码同样无需改动：

Dockerfile / k8senv:
  - name: AGENTSCOPE_WORKSPACE
    value: /data/agent-workspace

8.6 实践：用户级覆盖

这是工作区设计中最巧妙的部分。文件读取按两级解析：先查当前用户的覆盖层，再查共享工作区：

两级解析// 1. 问当前配置的 AbstractFilesystem：有没有这个 relative path？
//    有 → 返回该内容（"覆盖"层）
//    没有 → 2. 读本地磁盘 workspace.resolve(relativePath)
目录示例：alice 定制自己的评审技能workspace/
├── skills/code-reviewer/SKILL.md     # 共用版（所有人可见）
└── alice/
    └── skills/
        └── code-reviewer/
            └── SKILL.md              # 只对 alice 生效，覆盖共用版

因此，团队统一维护一份基础配置，个人差异用覆盖层表达，互不干扰。

8.7 知识目录 KNOWLEDGE.md

knowledge/ 目录存放领域知识入口 KNOWLEDGE.md 与任意参考文件。与记忆不同，知识是静态维护的——由人（或 CI 流程）写入，智能体按需读取；而记忆（第 9 章）由智能体自己积累。

✍️动手练习 8
  1. 为你的助理编写一份 AGENTS.md，把第 2 章 sysPrompt 中的指令迁移进去，验证行为一致；
  2. 创建 PREFS.md（内容写“回答控制在 200 字以内”），通过 additionalContextFile 注入并验证生效；
  3. 为 alice 创建用户级 AGENTS.md 覆盖层（要求英文回答），验证只有 alice 的会话受影响。

8.8 本章小结

工作区用“目录即配置”的方式管理智能体的身份、知识、技能与记忆；两级解析带来用户级覆盖能力；环境变量让部署位置与代码解耦。那么，工作区里的 MEMORY.md 与 memory/ 究竟如何自动生长？下一章展开记忆与上下文压缩。
